# P0 验证执行器

把《移动端 Agent 约束分析与迭代优化方案》§4.1 里那五项 P0 事项，
做成**能在电脑上跑、能留档、能被复核**的东西。

> **P0 的五项全部是「验证」而非「开发」。**
> 在三个决定性实验都没做的情况下写更多代码，是在给可能不存在的地基做装修。

这个工具的目的，就是让"做验证"这件事的成本低到不会有人跳过它。

---

## 为什么需要它

P0 的实验都是"上机操作 + 看一个数字 + 判断"，听起来不需要工具。但实际情况是：

| 问题 | 后果 |
|---|---|
| 命令要现查 | 每次实验前花 20 分钟翻文档，翻到一半去干别的了 |
| 结论要现记 | 记在聊天记录/便签里，一周后找不到，只好重做 |
| 判定靠印象 | "好像没被拦"——而受限设置被拦的表现恰恰是**开关是灰的但没报错** |
| 状态不留痕 | 不知道这次和上次的设备配置一不一样，两次结论没法比 |

工具要解决的是这四条。它不替你做实验，它让实验**做得完、记得住、比得了**。

---

## 快速开始

```bash
# 0. 先看连上设备没有
python tools/p0/run_p0.py probe

# 1. P0-1 需要在手机上手动跑一次（Node 在 Termux 里）
python tools/p0/run_p0.py node-command      # 打印要执行的命令

# 2. 跑全部实验，报告写到文件
python tools/p0/run_p0.py all --out p0-report.md
```

退出码：

| 码 | 含义 | 该做什么 |
|---|---|---|
| 0 | 全部通过 | 继续下一阶段 |
| 1 | 有实验**不通过** | 拿到了反面证据，做设计决策 |
| 2 | 有实验**未测到或被阻塞** | 还没拿到证据，去解决障碍或重跑 |

> ⚠️ 退出码 2 **不是错误**。它表示"还需要人做点什么"。
> 把它当成失败会让 CI 或脚本做出错误判断。

## 五项实验

### P0-1 · Node 20+ 在 K60 上跑起来

**为什么是 P0**：路线 C（dsh 移植）的唯一前置关卡。这一项不过，整套 dsh 方案作废。

**步骤**

```bash
python tools/p0/run_p0.py node-command    # 会打印下面这些
```

1. 装 Termux —— **必须从 F-Droid 装**，Play 商店那份已废弃
2. `pkg update && pkg install nodejs-lts`
   - 是 `nodejs-lts` 不是 `nodejs`。前者当前是 **24.18.0**
   - 从 24.13.0 起 npm 已从 lts 包里拆出，需要就再 `pkg install npm`
3. 执行工具打印的那段脚本，把输出复制成一个文件
4. `python tools/p0/run_p0.py run P0-1 --node-report node-report.txt`

**判定标准**

| 检查 | 标准 | 依据 |
|---|---|---|
| Node 版本 | ≥ 20 | dsh 核心包用了 `toReversed()`，Node 20 才稳定 |
| `toReversed()` | 实际能调用 | 防"版本号够但方法不存在"的裁剪版构建 |
| dsh | `dsh --profile headless "1+1"` 有正常输出 | Node 只是载体，dsh 才是要跑的东西 |

**失败预案**：路线 C 作废，退回路线 B。
**注意**：Node 通过 ≠ 路线 C 可行。**两个检查分开看**，工具也会分开报。

> ⚠️ 这里测的是 **Termux 里的 Node**，不是我们 APK 里的 Node。
> Termux 的包按 `/data/data/com.termux/files/usr` 前缀构建，
> **不能直接塞进别的应用**。所以这一步回答的是"Node 能不能在这台机器上跑"，
> 而不是"我们的方案能不能用"。后者需要照 Termux 的配方自行交叉编译。
> 但如果这一步都过不了，交叉编译就更不用谈。

### P0-2 · EX-13 侧载应用的受限设置

**为什么是 P0**：决定产品形态是否成立。若侧载拿不到无障碍，
整个「社区分发 + 无障碍读屏」方案在 Android 13+ 上不成立。

**步骤**

```bash
# 先装 APK
adb install -r android/app/build/outputs/apk/debug/app-debug.apk

# 读状态（不改设备）
python tools/p0/run_p0.py run P0-2
```

如果读到 `deny`，去手机上走一遍解除流程：

```
设置 → 应用管理 → PocketAgent → 右上角 ⋮ → 允许受限设置 → 验证指纹
设置 → 更多设置 → 无障碍 → 已下载的应用 → PocketAgent 屏幕操作 → 打开
```

然后重跑，看模式是否变成 `allow`、服务是否启用。

**四种模式的含义**

| 模式 | 无障碍开关能开吗 | 说明 |
|---|---|---|
| `deny` | ❌ 灰的 | 系统主动拦截，需走"允许受限设置" |
| `ignore` | ❌ 仍是灰的 | 用户**看过弹窗但没授权**。⚠️ 不是"没操作"，是"操作了一半" |
| `allow` | ✅ | 放行，等同商店安装 |
| `default` | ✅ | 该 appop 从未被设置，通常意味着这个版本没实施该限制 |

> ⚠️ **`ignore` 不算通过。** 这是最容易写错的地方 —— 把它当允许，
> 报告会说"已经可以了"，用户去开开关发现开不了，然后怀疑自己操作错了。

**可选的覆盖安装实验**

```bash
python tools/p0/run_p0.py run P0-2 --reinstall-apk path/to/app-debug.apk
```

比较重装前后的模式。若被重置，说明**每次更新版本用户都要重走一遍流程** ——
对一个靠自内更新分发的应用，这是留存杀手，必须在更新流程里加显式引导。

> ⚠️ 这是本工具唯一会改动设备且**不能完全回滚**的操作（appop 由安装流程设置）。
> 所以必须显式加参数才执行。

### P0-3 · EX-16 虚拟屏可行性

**为什么是 P0**：决定「不影响用户使用」这个核心卖点是否成立。

**步骤**

```bash
python tools/p0/run_p0.py run P0-3 \
    --allow-display-changes \
    --vd-target com.android.settings/.Settings \
    --vd-target com.tencent.mm/.ui.LauncherUI
```

工具会：创建副屏 → 把目标 App 启上去 → 截图 → 试一次输入注入 → **恢复原设置**。

**判定标准**

| 检查 | 标准 |
|---|---|
| 创建副屏 | 出现 `uniqueId="overlay:N"` 的新显示设备 |
| 启动 App | 至少 3 个**主流** App 能启上去 |
| 截图 | `screencap -d <id>` 成功 |
| 输入注入 | `input -d <id> tap` 成功 |

> ⚠️ **判据认的是 `overlay` 类型，不是"有没有多出 displayId"。**
> `dumpsys display` 里还有 `virtual:` 设备（投屏、录屏），
> 只看"多了个 id"的话，一次投屏就能让这个实验**假通过**。

**要覆盖的 App 类型**（设计文档要求）
- 声明了 `resizeableActivity="true"` 的（大多数现代 App）
- 未声明的（老 App、部分工具类）
- 明确拒绝多显示的（金融类、安全类）
- 游戏类

**失败预案**：虚拟屏需求不成立，产品降级为"小窗为主 + 全屏接管兜底"。

> ⚠️ **这一步用的是 adb，不是 Shizuku。** 两者都以 shell 身份运行，
> 所以 adb 的结果是**必要但不充分**的：它证明了"机制在本机型可用"，
> 没有证明"我们的 App 通过 Shizuku 能用"。
> 后者要等 Shizuku 通道落地后再测一次。

### P0-4 · 内存预算实测

**为什么是 P0**：设计文档估算常驻 150–230MB，而豆包的 aikernel 是 160MB。

```bash
python tools/p0/run_p0.py run P0-4 --mem-samples 10 --mem-interval 3
```

**判定标准**：峰值 PSS ≤ 230MB。

> ⚠️ **这测的是空闲的 App。** 真正要测的是"一次完整 agent 任务期间"的峰值 ——
> 那时才有截图缓冲、无障碍节点树、模型请求体同时在内存里。
> 任务跑起来之前，这个数字只能当**下界**。

### P0-5 · 能耗基线实测

**为什么是 P0**：设计文档 §2.4 的能耗**全是估算**（8 轮约 0.07% 电量）。
"轮次优化省三个数量级"这个核心论点需要实测支撑。

```bash
python tools/p0/run_p0.py run P0-5 --reset-batterystats
```

**方法**：跑 10 次同样的 8 轮任务，取平均。

> ⚠️ **不要用库仑计测单次任务。**
> `Charge counter` 的量化误差约 ±1%，5000mAh 电池上是 ±50mAh，
> 而单次 8 轮任务预计只耗几十 mAh —— 差值会被误差淹没。
> 工具会检测库仑计是否可用并说明这一点。

> ⚠️ `dumpsys batterystats` 给的是**系统的估算值**，不是测量值。
> 它的模型对"屏幕亮着"权重很高、对"短时 CPU 峰值"权重偏低，
> 而 agent 任务恰好是后者。**只能当数量级参考。**

## 安全约定

| 约定 | 说明 |
|---|---|
| **默认不动设备** | P0-3 改显示设置、P0-2 重装、P0-5 清电池统计，都必须显式加参数 |
| **改动必恢复** | P0-3 的恢复写在 `finally` 里，中途抛异常也会还原；失败会记进报告的 errors 段 |
| **证据必留原始输出** | 每条判定都附命令的原始输出，报告里可折叠查看，供人工复核 |
| **取不到就说取不到** | 解析不出来返回 `None`，不返回默认值。见下 |

> ⚠️ **为什么"取不到就返回 None"值得单列一条。**
> 如果内存解析失败时返回 0，报告会显示"内存占用 0 KB，远低于预算"。
> 那不是解析失败，那是一个**会让项目做出错误决策的假数据**。
> `None` 会逼着人去查，`0` 不会。

## 结构

```
tools/p0/
├── run_p0.py              命令行入口
├── p0kit/
│   ├── adb.py             只负责把命令送到设备、拿回文本
│   ├── parse.py           只负责把文本变成结构（纯函数，零 I/O）
│   ├── experiments.py     只负责判定
│   └── model.py           结果模型与报告渲染
├── tests/                 离线单测（65 个用例）
└── fixtures/              样本，来源见 fixtures/README.md
```

**分层不是洁癖**：真机只有一个，每次实验都要手动操作几分钟。
如果解析逻辑只能在真机上验证，那么每改一行代码就要占用一次真机时间，
最后一定会变成"跑一次能出数就算通过"。把解析拆成纯函数之后，
全部边界情况可以在 **9 毫秒**内跑完。

```bash
cd tools/p0 && python -m unittest discover -s tests -v
```

## 扩展

新增一项检查时：

1. 解析逻辑加进 `parse.py`，**必须是纯函数**，并写清"这条防的是什么 bug"
2. 判定逻辑加进 `experiments.py`，写清 `consequence`（对项目意味着什么）
   和 `next_step`（下一步做什么）
3. 在 `tests/` 加用例 —— 尤其是**边界情况**（空输出、格式变体、未知值）
4. 加一个 fixture，并在 `fixtures/README.md` 的表格里登记

**判定用四态，不要退回布尔**：

| 状态 | 含义 | 处置 |
|---|---|---|
| `PASS` | 拿到证据，支持假设 | 继续 |
| `FAIL` | 拿到证据，推翻假设 | 改设计 |
| `BLOCKED` | 想测但被挡住 | 解决具体障碍 |
| `UNKNOWN` | 没拿到证据 | 重跑或改解析 |

把 `BLOCKED` 和 `UNKNOWN` 混进"不通过"，会让项目在**明明没拿到证据**的时候
以为已经拿到了反面证据。对 P0 这种"结论决定产品形态"的实验，这个区别是致命的。
