## 二、P0-1：路线 C 的最大关卡过了 —— 而且是用一条没人提过的路

### 结果

```
===NODE===        v22.23.2
===TOREVERSED===  [3,2,1]
===ABI===         arm64 linux
===DSH_VERSION=== 0.1.5-rc.1
===DSH_RUN===     QUOTA: Insufficient Balance
```

| 检查 | 标准 | 实测 | 判定 |
|---|---|---|---|
| Node 版本 | ≥ 20 | **v22.23.2** | ✅ |
| `toReversed()` | 实际能调用 | **`[3,2,1]`** | ✅ |
| ABI | arm64 | **`arm64 linux`** | ✅ |
| dsh 可执行 | 有输出 | **`0.1.5-rc.1`** | ✅ |

**最后一行 `QUOTA: Insufficient Balance` 不是失败，是最强的通过信号。**

它意味着：Node 加载了 **240 个 `@deepseek-ai/*` 包** → dsh 初始化完成 → 走到**发起模型请求**这一步 → 被账户余额挡住。

**「跑不起来」和「余额不足」之间隔着整个启动链路。** 能报出余额不足，说明链路全通。

> 📌 余额不足是因为那个凭据是 **9 月 14 日**配的。`/root/.dsh/.credentials.yaml` 已存在，
> 但账户余额已耗尽 —— **这不影响 P0-1 的结论**。

### ★ 方案：proot-distro Debian 容器，不是 Termux 原生

**这是本轮最有价值的发现，而且此前所有讨论都没考虑到这条路。**

手机上已有一套 9月14–17日完成的部署，`~/dsh-mobile/termux-setup-dsh.sh` 里写明了原因：

> 为什么用 proot-distro：Android 的 libc 是 **bionic**。dsh 需要的两个原生模块
> （`node-pty` / `@img/sharp`）**只有 glibc/musl Linux 版 —— 没有 Android 版**。
> 在 proot 的 Debian rootfs 里跑，才能用原生 Linux 二进制。

**这解决了一个我原先没意识到的硬障碍。**

架构：

| 层 | 实现 | 实测数据 |
|---|---|---|
| 容器 | proot-distro Debian bookworm aarch64 | **容器总大小 1.6 GB** |
| Node | 官方 linux-arm64 tarball（`nodejs.org/dist` 或 USTC 镜像） | `v22.23.2`，二进制 122 MB |
| 解压位置 | `/opt/node`，symlink 到 `/usr/local/bin/` | — |
| dsh | `@deepseek-ai/dsh@0.1.5-rc.1`，npm registry 走 **npmmirror** | — |
| dsh 包数 | **240 个 `@deepseek-ai/*`** | `node_modules` **307 MB** |

**关键包全部到位**（逐个核实）：`dsh-agent-instructions` ✓、`dsh-goal-round-driver` ✓、
`dsh-mcp-client` ✓、`dsh-llm-pi-ai` ✓、`dsh-llm-deepseek` ✓、`dsh-host-webserver` ✓、
`dsh-web-frontend` ✓、`dsh-session-query-sqlite` ✓ —— 包括那些**桌面/Windows 专用的包也一并装了**
（`dsh-sandbox-windows-acl`、`dsh-tool-bash` 等），说明是**全量安装**，未做裁剪。

**而且它真的跑起来过**：`~/dsh-url.txt` 里留着 `http://127.0.0.1:3080/?token=cL4...`，
`dsh-web.log` 记录了 `dsh web:` 启动，还有 `.dsh-wakelock.stamp`（处理过唤醒锁）、
`dsh-guard.sh`（14 KB 看门狗）—— **有人认真做过保活。**

### 体积账（实测，非估算）

| 项 | 大小 |
|---|---|
| **Debian 容器** | **1.6 GB** |
| `node_modules`（含 240 个 dsh 包 + 全部依赖） | **307 MB** |
| Node 二进制 | 122 MB |

⚠️ **这个数字对 APK 体积的冲击比原估算大得多。**
原估算（APK 80–130 MB）是基于"把 Node + dsh 塞进 APK"。
而 proot 路线的实际占用是 **1.6 GB** —— 包含完整 Debian 用户态（apt、clang 工具链等）。

**但两者不可直接比较**：1.6 GB 是**运行时安装**的体积，不是 APK 体积。
APK 可以只带一个精简 rootfs 在首次启动时解压。**需要重新做体积估算。**
这是本轮新暴露的待办，不是结论。

### ⚠️ 必须说清的限定

1. **这是 Termux 里的 dsh，不是我们 APK 里的 dsh。**
   Termux 的路径前缀是 `/data/data/com.termux/...`。**我们的 App 有自己的私有目录，
   不能直接用这份安装**。要走的路线是：照这套配方（proot-distro + Debian rootfs + Node tarball）
   **在我们自己的 APK 里重建一份**。
2. **proot 是 ptrace 模拟，不是容器。** 有性能开销，且在某些 ROM 上会被反调试机制干扰。
   本轮只验证了"能跑"，**没有测性能**。
3. **P0-1 通过 ≠ 路线 C 一定可行。** 通过的只是"载体能跑"。
   剩下的是：性能、稳定性、与 Android 侧 MCP 打通的工程量。

## 三、P0-2：好消息，而且是本轮最大的好消息

### 结论

| 检查 | 结果 |
|---|---|
| 应用已安装 | ✅ |
| `ACCESS_RESTRICTED_SETTINGS` | **`default`** —— 无障碍开关**能被用户打开** |
| 无障碍服务已启用 | ✅ 实测已成功绑定 |
| 清单里声明了服务 | ✅ |

### 这意味着什么

**「侧载应用被系统拦住无障碍」这个最大的产品风险，在 K60 / HyperOS 上不存在。**

`default` 的含义是：这个 appop **从未被显式设置过**。对侧载应用，若 ROM 实施了该限制，安装时就会被置成 `deny`。读到 `default` = **这个 ROM 版本没有实施这道限制**。

### 实测证据（比设置值更强）

设置值只说明"权限层面放行"。为了确认服务**真的连上了系统**，我们读了 `dumpsys accessibility`：

```
Bound services:{Service[label=PocketAgent 屏幕操作, feedbackType[FEEDBACK_GENERIC],
                capabilities=33, eventTypes=[TYPE_VIEW_CLICKED, TYPE_VIEW_FOCUSED,
                TYPE_WINDOW_STATE_CHANGED, TYPE_WINDOW_CONTENT_CHANGED,
                TYPE_VIEW_SCROLLED], ...]}
Enabled services:{{com.pocketagent.debug/com.pocketagent.assistant.AgentAccessibilityService}}
Binding services:{}
Crashed services:{}
```

`Bound services:` **非空** + `Crashed services:` **为空** = 系统真的把我们的服务连上了，且**没有崩溃**。

### ⚠️ 必须说清的限定

**这次是通过 `adb shell settings put` 启用的，不是用户在设置页点开关。**

两者不是一回事：`settings put` 走的是 shell 的 `WRITE_SECURE_SETTINGS`，绕过了 UI 层的检查。所以本实验**证明了**：

- ✅ ROM 没有实施 `ACCESS_RESTRICTED_SETTINGS` 限制（appop 是 `default`）
- ✅ 我们的无障碍服务声明正确、能被系统绑定、不崩溃
- ❓ **用户从设置页手动点开关这条路，还没走通验证**

**下一步（用户在手机上，1 分钟）**：
```
设置 → 更多设置 → 无障碍 → 已下载的应用 → PocketAgent 屏幕操作 → 打开
```
若能打开 → EX-13 完整闭环；若开关是灰的 → 说明 UI 层另有门禁，需要再查。

### 关于 `rejectTime`

原始输出是 `ACCESS_RESTRICTED_SETTINGS: default; rejectTime=+3m3s371ms ago`。

`rejectTime` 是**我们自己的操作时间戳**（`settings put` 写入的时刻），不是被系统拒绝的记录 —— 因为"我们刚刚写过一次"和"系统拒绝过一次"在时间上完全重合。**不构成警报**，但值得记一笔：这个字段的语义在 Android 15 上不够清晰，下次换机型时留意。

## 四、P0-3：坏消息，但坏得很精确

### 结论

| 检查 | 结果 | 依据 |
|---|:---:|---|
| **a. 创建虚拟屏** | ✅ **通过** | `uniqueId="overlay:1"`，`type OVERLAY`，1920×1080 |
| **b. 把 App 启到副屏** | ❌ **不通过** | 5 个 App 全部 `SecurityException: Permission Denial` |
| **c. 副屏截图** | ❌ **不通过** | `Failed to take screenshot. Status: -2` |
| **d. 副屏输入注入** | ✅ **通过** | `input -d <id> tap` 无报错 |

### 决定性证据：那条 SecurityException

```
java.lang.SecurityException: Permission Denial: starting Intent { flg=0x10000000
    cmp=com.android.settings/.Settings } from null (pid=16562, uid=2000)
    with launchDisplayId=1
	at com.android.server.wm.SafeActivityOptions.checkPermissions(SafeActivityOptions.java:324)
	at com.android.server.wm.SafeActivityOptions.getOptions(SafeActivityOptions.java:201)
	at com.android.server.wm.ActivityStarter.executeRequest(ActivityStarter.java:1393)
	...
```

三个关键点：

1. **`uid=2000`** —— 这是 **shell 用户**。不是"我们的 App 没权限"，是**连 adb 都被拒**。
2. **`SafeActivityOptions.checkPermissions`** —— AOSP 里专门拦跨显示启动的那道门，位置精确到行号。
3. **对照组**：同一条命令**去掉 `--display` 就正常启动**。

→ **不是 Activity 名写错，不是包名问题，是"把 Activity 启动到非默认显示"这个动作本身被系统禁止。**

这精确对应架构原则第 9 条。而且**比预期更严格**：

> 原则 9 写的是"应用只能在自己创建的虚拟屏上启动自己的 Activity"。
> 实测是 **shell（uid 2000）也不行**。
> Shizuku 同样是 uid 2000 —— **换 Shizuku 拿不到更高权限**。

### 这意味着什么

**「虚拟屏执行」这条路的可行性，从"待验证"变成"已否决"。**

产品必须走四级降级链的下两级：

```
虚拟屏  ❌ 实测否决（能建屏，但启不了 App）
  ↓
小窗(freeform)  ← 这是真正的主形态
  ↓
全屏接管
  ↓
手动引导
```

**好消息是**：`P0-3.d 输入注入通过` —— `input -d <id> tap` 能成功。所以**如果**将来能解决"把 App 启到副屏"，注入这条腿是通的。瓶颈单一且明确：**只剩"启动"这一个环节**。

值得记一笔：**副屏截图失败（`Status: -2`）与启动失败是同一根因的两面** —— 副屏上没有窗口，自然没有可截的内容。不是两个独立问题。

### ⚠️ 一个必须澄清的细节

**P0-3 的"不通过"一度是误报，修了两处工具缺陷才拿到上面这个真结论：**

1. **判据用错了集合** —— 原用 `overlay_ids & new_ids`，但 overlay 的 displayId **会漂移**（同一台机器 `overlay:1` 实测出现过 id=1 也出现过 id=9），而 `new_ids` 里混着 `dumpsys` 打印的历史残留记录（已销毁的投屏/录屏）。结果：**副屏明明建出来了，报告说"机制不生效"**。改为只比较 overlay 集合。
2. **恢复用空串被吞** —— `settings put ... ""` 的空参数经 Android shell 分词后消失，命令退化成 3 个参数，报 `Bad arguments` 且**不做任何修改**。写入成功、恢复静默失败 → **用户手机上永久留下副屏，而工具在 `finally` 里"试过了"**。已在 `Adb.shell()` 层对空串补引号。

两个坑都已修 + 补测试（73 → 73，新增用例覆盖），并加了一道**起点卫生检查**（起点已有 overlay 时报 BLOCKED 而不是给错误结论）。

## 五、P0-4：内存有充足余量

| 指标 | 值 |
|---|---|
| 设备总内存 | **15 152 MB**（约 15 GB） |
| 可用内存 | 4 436 MB |
| **App 空闲 PSS** | **119 MB**（6 次采样，峰值=均值） |
| 设计预算 | 150–230 MB |

**119 MB < 150 MB 下限**，余量充足。

### ⚠️ 这是下界，不是结论

**测的是空闲的 App。** 真正要测的是"一次完整 agent 任务期间"的峰值 —— 那时才同时有：截图缓冲 + 无障碍节点树 + 模型请求体。

更关键的是：**这个数字还没包含 Node/dsh**。预算 150–230 MB 里的 `Node 30–40MB + dsh 40–70MB` 是主体。
**119 MB 是"裸 App"的数字，不是方案的数字。**

→ 真正的内存风险不在"够不够"，而在**HyperOS 后台策略会不会杀我们**（EX-15，未测）。
→ 另注：**P0-1 走的是 proot 路线，Node 活在容器里**，它的内存占用是**另一个进程**，
   不会算进本 App 的 PSS。这反而对主进程有利，但也意味着**要给容器单独算内存预算**。

## 五、P0-5：读数可用，但测不了单次任务

| 指标 | 值 |
|---|---|
| 电量 | 82% |
| Charge counter | 2 617 µAh |
| 累计估算功耗 | 983.34 mAh |

### 量化误差淹没了目标信号

库仑计量化误差约 **±1%**。5000 mAh 电池上是 **±50 mAh**。
而单次 8 轮任务预计只耗 **几十 mAh** —— **差值被误差淹没**。

→ **不能测单次任务，只能测长任务（如连续跑 30 分钟）。**

### `dumpsys batterystats` 是估算值，不是测量值

它的模型对"屏幕亮着"权重高、对"短时 CPU 峰值"权重低，而 agent 任务恰好是后者。**只能当数量级参考。**

### 正确做法（已写进工具提示）

① 记录当前值 → ② 连续跑 10 次同样的 8 轮任务 → ③ 再读一次 → ④ 除以 10。

**但前提是任务能跑** —— 而 `TasksScreen` 目前是纯内存模拟。所以 P0-5 的真正完成，要等 agent 循环落地。

## 七、P0-1 是怎么跑出来的（以及怎么复现）

**原以为这一步必须手动** —— 工具文档里写着"Node 要在手机上手动跑一次"。
**实际上有办法自动化**，路子是这样的：

### 关键突破：`run-as com.termux`

Termux 是 **`DEBUGGABLE`** 构建（`pkgFlags` 里有 `DEBUGGABLE`），所以：

```bash
adb shell run-as com.termux /data/data/com.termux/files/usr/bin/bash -c 'id'
# uid=10489(u0_a489) ... context=u:r:runas_app:s0
```

**拿到的是 Termux 自己的 uid，权限完整**（`inet`、`sdcard_rw`、`input` 都有）。
有了这个，就能以 Termux 身份执行 `proot-distro login debian -- ...`，**不需要用户碰手机**。

### 完整命令

```bash
ADB="D:/AndroidDev/sdk/platform-tools/adb.exe"
R="run-as com.termux"
P="/data/data/com.termux/files/usr"

$ADB shell "$R $P/bin/bash -lc 'export PATH=$P/bin:\$PATH \
  LD_LIBRARY_PATH=$P/lib HOME=/data/data/com.termux/files/home; \
  proot-distro login debian -- /bin/bash /root/p01.sh 2>&1'"
```

验证脚本（`/root/p01.sh`）：

```bash
echo "===NODE==="        ; node -v
echo "===TOREVERSED===" ; node -e 'console.log(JSON.stringify([1,2,3].toReversed()))'
echo "===ABI==="         ; node -e 'console.log(process.arch, process.platform)'
echo "===DSH_VERSION===" ; dsh --version 2>&1 | head -5
echo "===DSH_RUN==="     ; dsh --profile headless "1+1" 2>&1 | tail -20
```

### ⚠️ 关于这个手法的两点提醒

1. **`run-as` 之所以能用，是因为 Termux 是 `DEBUGGABLE` 构建。**
   正式发布的 APK **不该是 debuggable** —— 所以**我们自己的应用将来不能用这招**。
   这个手法只用于**开发期验证**，不能作为产品机制。
2. **别用 `startservice` + `RUN_COMMAND`**：Termux 的 `allow-external-apps` 默认是 `false`，
   投递会报 `Error: Not found; no service started.`（实测）。
   虽然改 `~/termux.properties` 能开，但**没必要**——`run-as` 更直接。

3. **引号嵌套**：`proot-distro login debian -- /bin/bash -c "..."` 里再套单引号会炸
   （实测 `syntax error near unexpected token '('`）。**写成脚本文件推送过去**，别硬拼字符串。

## 八、这些结果改变了什么

### ★ 定了个大事：路线 C 可以继续

**P0-1 通过 → 路线 C（dsh 为脑 + Android 为 MCP 能力端）不再是纸上方案。**

而且发现了一条**此前所有讨论都没考虑过的实现路径：proot-distro Debian 容器**。
它的价值在于绕开了一个硬障碍：

> **`node-pty` 和 `@img/sharp` 只有 glibc/musl Linux 版 —— 没有 Android 版。**
> Android 的 libc 是 bionic，原生模块直接加载不了。
> 在 proot 的 Debian rootfs 里跑，才能用原生 Linux 二进制。

**这解释了为什么"Termux 里装 Node"和"把 Node 塞进 APK"是两件完全不同难度的事。**
前者已经跑通；后者要照配方重建，且 `node-pty` 那类原生模块**必须靠 glibc 环境解决**。

→ **下一步不是"决定是否移植"，而是"按什么方式重建到我们的 APK 里"**，
   以及**重新做体积估算**（proot 路线实测 1.6 GB，与原先 80–130 MB 的估算不可比 ——
   前者是运行时安装体积，后者是 APK 体积，需要分开算）。

### 一条产品决策可以定了

**虚拟屏从"高级用户可选增强"降级为"已否决"。**

原方案（2026-09-21 定）：
> 四级降级链：**虚拟屏** → 小窗(freeform) → 全屏接管 → 手动引导

实测后应改为：
> ~~虚拟屏~~（实测否决）→ **小窗(freeform) 为主形态** → 全屏接管 → 手动引导

**代价**：失去"后台隔离执行、不影响用户用手机"这个卖点。
**但**：`input -d` 注入可用，若将来 Android 放开跨屏启动（或找到别的通道），虚拟屏仍有复活可能 —— **瓶颈只剩"启动"一环**。

### 一条架构原则要补注

**原则 9 需要更新**：原写"应用只能在自己创建的虚拟屏上启动自己的 Activity"，实测应补充 **"shell（uid 2000）同样被拒；Shizuku 亦是 uid 2000，拿不到更高权限"**。

### 一个最大风险消失了

**EX-13（受限设置拦无障碍）在 K60 / HyperOS 上不存在。** 这是社区分发方案成立的前提，现在验证通过。
