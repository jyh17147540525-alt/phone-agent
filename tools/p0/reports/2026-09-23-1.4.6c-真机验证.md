> 日期：2026-09-23 · 设备：Redmi K60（`mondrian` / Android 15 / API 35 / HyperOS）
> 结论：**✅ 端到端通过** —— dsh 经我们生成的配置把请求发到本地地址，并渲染出回答。
> 复现脚本：`tools/p0/probe-146c-stage{1,2,3,4}.sh`

## 1. 为什么需要这次验证

1.4.6c 的产出是"把本地网关接进 dsh 的配置"。这件事此前只有**纸面依据**：

- 研讨文档 `docs/BYOK模型接入与dsh代理设计-v1.0.md` §2.5 设想写 `cordis.patch.yml`
- 设计假设 dsh 的 `baseURL` 可覆盖、`apiKeyEnv` 能解析

但这些都**没有在真机上确认过**。而配置类错误的后果全是静默的：
写对了没生效、写错了不报错、报错了指向错误方向。所以必须真机验证。

## 2. 真机上读到的结构（全部实读，非推测）

配置根：`$R/root/.dsh/`，其中
`$R = /data/data/com.termux/files/usr/var/lib/proot-distro/containers/debian/rootfs`

| 文件 | 作用 | 要点 |
|---|---|---|
| `settings.yaml` | 用户设置层 | `agent-default-model: {provider: deepseek-official, model: deepseek-flash}` |
| `.credentials.yaml` | 凭据存储 | `version: 1` + `refs:`（环境变量名 → 明文值）+ `records:` |
| `profiles/<name>/package.json` | bundle 列表 | `dsh.profile.bundles: [dsh-base, dsh-headless]` |
| `profiles/<name>/cordis.yml` | profile 根 | **永远是空数组 `[]`**（注释明说改 patch 文件） |
| `profiles/<name>/cordis.patch.yml` | 用户补丁层 | `web` 有 10 条 `disabled: false`；`headless` 只有 `[]` |

**版本**：dsh `0.1.5-rc.1`。

### 关键依据（源码注释原文）

`dsh-llm-deepseek/lib/index.d.ts`：

> the plugin layers its `cordis.yml` entry config under the optional
> **`llm-deepseek` user-settings section (`ctx.settings`)** … so a changed
> **base URL, catalog, or key reaches the very next request without restarting anything**.

`lib/index.js` 里的字面量：

```js
const name = "llm-deepseek";
const NS = "llm-deepseek";
const PROVIDER = "deepseek-official";
const DEFAULT_API_KEY_ENV = "DEEPSEEK_API_KEY";
```

→ **`settings.yaml` 里的段名必须逐字是 `llm-deepseek`**。写错会静默失效。

`dsh-credentials-local/README.md`：

> Credential lookup follows a fixed precedence: **the launch environment wins**,
> followed by **the stored file**, the project's `.env`, and the harness-home `.env`.
>
> Only your OS user can read the file, but **agent tool processes run as that same user,
> so this store cannot isolate secrets from the agent**.

→ 第二条**正是我们安全模型的依据**：dsh 自己承认无法把凭据与 agent 隔离，
所以**绝不能把真 Key 交给它**，只能给本地一次性 token。

### 为什么改 settings 层而不是 cordis.patch.yml

1. settings 层**热重载**（见上引原文），patch 层要 `patchReload: "startup"` → 改完要重启
2. settings 层是官方给**用户配置**用的；patch 层是"改 bundle 组合"用的
3. **不用碰 profile 目录** —— 那目录由 pnpm 管理，手改会被 dsh 自我修复覆盖

## 3. 验证设计

### 手法：桩服务

在容器内起一个桩 HTTP 服务（`node`），把 dsh 的 `baseURL` 指过去。
若桩收到请求 → 说明 `baseURL` 生效；若 dsh 渲染出桩的回答 → 说明**全链路通**。

桩分两版：

- **阶段 2**：返回**非流式** JSON
- **阶段 3**：返回**真正的 SSE 流**，线格式**刻意模仿我们的 `SseResponseWriter`**
  （`data: {...}\n\n` 帧 + 结尾 `data: [DONE]\n\n`）

### 安全边界

- **绝不把真 Key 写进任何产出**：`DshConfigPatch` 的构造器上就没有"真 Key"这个位置
- 阶段 2 的 token 走**启动环境**层（`export POCKETAGENT_LOCAL_TOKEN=...`）
- 阶段 3 的 token 走 **`.credentials.yaml` 的 `refs`**（即我们产品实际会写的路径）
- 每次改动前**备份**，结束前**恢复并核对**

## 4. 结果

### 4.1 `--dump-config` 不含 settings（一个反直觉的发现）

`dsh --profile headless --dump-config` 输出 348 行，是 **loader 树**（插件清单）：

```
- id: llm-deepseek
  name: '@deepseek-ai/dsh-llm-deepseek'
```

证明插件**确实被加载**，但 **settings.yaml 的内容不在 dump 里**（它是运行时另一层）。

> ⚠️ **"配置有没有生效"不能靠 dump 判断**，只能靠实际请求。这一点如果没验证就下结论，
> 会得出"配置没生效"的错误结论，然后去改本来正确的东西。

### 4.2 不带 token → dsh **念出了我们的变量名**（证明 settings 段被采纳）

```
dsh: MISSING_CREDENTIAL: llm-deepseek: no API key for provider route "deepseek-official";
store POCKETAGENT_LOCAL_TOKEN through the credentials service (the web Models page writes it),
or export POCKETAGENT_LOCAL_TOKEN in the launching environment
```

它把 `apiKeyEnv` 里的变量名**逐字念了出来** —— settings 段被采纳，无歧义。
这句话还同时指明了**两条凭据来源**：credentials service（写文件）与启动环境。

### 4.3 带 token → 桩收到请求（证明 baseURL 生效 + 协议形状正确）

```
REQ POST /v1/chat/completions auth=Bearer pa-local-test-token-123
    body={"model":"deepseek-flash","messages":[{"role":"system","content":"You are an AI agent..."}]}
```

- 方法/路径 = `POST /v1/chat/completions` —— 与 `HttpGatewayServer` 的实现**完全一致**
- 鉴权 = `Authorization: Bearer <token>` —— 与 `GatewayTokenProvider.extract` 一致

### 4.4 阶段 3：**dsh 渲染出了桩的回答**（完整闭环）

token 只放在 `.credentials.yaml` 的 `refs` 里，并用 `env -u` 清掉环境变量：

```
--- 不带任何环境变量发请求 ---
PA-STUB-ANSWER-42

--- 桩收到了什么 ---
REQ POST /v1/chat/completions auth=Bearer pa-file-token-456 stream=true
REQ POST /v1/chat/completions auth=Bearer pa-file-token-456 stream=true
```

**dsh 把桩生成的回答原样打印出来了。** 完整闭环：

1. 我们生成的 `settings.yaml` 段 → `baseURL` 生效 ✅
2. 我们生成的 `.credentials.yaml` 的 `refs` 条目 → `apiKeyEnv` **从文件**解析成功 ✅
   （无环境变量 → **证明我们产品的写入路径有效**）
3. `POST /v1/chat/completions` + `Bearer` + `stream=true` ✅
4. SSE 流被 dsh 正确消费并**渲染出答案** ✅

> **结论：把桩换成我们真正的 `HttpGatewayServer`，dsh 就能工作。**
> `DshConfigPatch` 的产出格式与 `HttpGatewayServer` 的线协议**都被真机证实**。

### 4.5 dsh 默认请求**流式**，且**要求 `[DONE]` 收尾**

阶段 2 的桩返回非流式 JSON 时：

```
dsh: STREAM_CLOSED: SSE stream ended without [DONE]
```

> ⚠️ **这不是失败，是重要信息**。它印证了 `HttpGatewayServer` 里
> "`[DONE]` 无条件发一次"那个刻意决定 —— 写成 `if (!sawDone)` 是**恰好错的**
> （`chunkToSse` 把 `ChatChunk.Done` 翻成收尾分片、从不产 `[DONE]` 文本）。
> **我们的实现天然满足 dsh 的要求。**

### 4.6 dsh 会发**多个**请求，不只一次

桩收到两条：一条是任务本身，另一条是**会话标题生成**：

```
"Create a concise title for an AI coding-assistant session from the supplied human messages."
```

> **对预算的影响**：`Consumer.Dsh` 名下的用量会**含辅助调用**，
> `AgentBudget` 的轮次估算必须把它算进去，否则预算会比预期提前耗尽。

### 4.7 dsh 传的 `model` 是它自己的名字

`"model":"deepseek-flash"` —— 不是我们声明的 `pocketagent-auto`。

> 印证 `GatewayContext` 的注释：**客户端给的 model 字段必须忽略**
> （`GatewayCore` 已覆盖为路由结果）。
> 也印证 `models` 清单只是"给界面看的"（`.d.ts` 原文 "requests remain unrestricted"）。
>
> **→ 所以 1.4.6c 不需要改 `agent-default-model`**，只加 `llm-deepseek:` 段 + 一条凭据即可。

## 5. 对实现的三个直接影响

1. **`credentialRef` 必须用我们自己的名字**（`POCKETAGENT_LOCAL_TOKEN`），
   不能复用 `DEEPSEEK_API_KEY` —— 后者在真机上存着用户的真 Key，覆盖它等于毁掉
   用户"绕过网关直连"的能力。
2. **凭据文件只插一行**，其余内容一个字节不动（实测行数 9 → 10，
   `records` 块与 `DEEPSEEK_API_KEY` 均完好）。
3. **`models` 清单必须非空** —— 不放的话 dsh 会回落到内置真实模型名，
   用户在 dsh 界面上看到一堆用不了的模型。

## 6. 未覆盖的部分（诚实清单）

- **本报告验证的是"配置格式与线协议正确"，不是"我们的 App 真的这样做了"。**
  把桩换成 `HttpGatewayServer` 需要 App 侧完成装配（Hilt 接线 + 启动网关），
  这属于后续工作。
- **投递方式未定**：我们的进程**写不进** Termux 私有目录（跨 UID + SELinux），
  当前实现只写应用私有目录 + 提示用户手工粘贴。
  "经 Shizuku 写"与"经 Termux 脚本拉取"两条路**尚未验证**。
- **`--dump-config` 不含 settings** 这一点只在本版本（`0.1.5-rc.1`）确认过；
  dsh 是 RC 版本，升级后需重验。
