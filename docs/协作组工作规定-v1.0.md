# 协作组产出规定 v1.0

> **面向**：负责产出代码 / 文档的一方
> **目的**：让产出**一次通过审核**，减少往返。不是挑刺，是省钱省时间
> **依据**：2026-09-30 对 `f7a5565`（v4.0 P1+P2）的完整审核 ——
> 34 个文件 / 5292 行，找出 9 处问题，**全部可归入下面 6 条**

---

## 先声明：这份规定的前提不是"你不合格"

那次产出的**设计水平高于本项目平均线**，以下几条是实打实的，不需要改：

- **隐私红线的类型隔离是真的**：`OffloadPayload` 私有构造 + `internal cleared`，
  全项目唯一调用点（grep 确认只有 `ContextOffloader:77`），且在任何写入之前。
  「不过关卡直接写」在模块外**编译不过** —— 约定做进了类型，不是写在注释里。
- 拒绝走**异常**而非返回结果值 ⇒「拒绝了但流程继续」这个状态**写不出来**
- `ToneAxes` 用具名字段而非 `Map` ⇒「缺一根轴」**构造不出来**
- `expectRejection` 强制校验 reason 码 ⇒ 防住「骨骼被拒」与「未知字段被拒」混为一谈
- `AtomExtractor` 的「丢弃必须可观测」；`AtomEntry` 全字段默认值是为了
  「把判断权交给显式校验」而非兜底

**9 处问题的共同形状只有一个**：

> **设计意图写得很清楚（注释里全有），实现只覆盖了主路径，边界落在没覆盖的那一侧；
> 而测试要么没写，要么写了但断言跳过了关键那一步。**

所以下面 6 条规则**全部是「如何验证自己真的做到了」，不是「如何设计得更好」**。
设计能力不是问题，**收尾时的自我校验**才是。

---

## 规则 1 · 注释里的每个承诺，必须有断言接住

**要求**：`src/main/` 里每一句「绝不 / 必须 / 永远 / 一律 / 不可」，
在 `src/test/` 里必须有一条**会因它失效而变红**的断言。做不到，就删掉那句话。

**自查（30 秒）**：

```bash
grep -rn "绝不\|必须\|永远\|一律\|不可" android/<你的模块>/src/main/ --include=*.kt
```

逐条读，问一句：**「我把实现改坏，哪条测试会红？」** 答不出来 → 补测试，或删掉承诺。

**本次实例**：`ToneAxes.coerce` 的注释写着

> 历史数据越界只可能来自早期版本的校验更松……抛异常会让整个助理起不来 ——
> 那才是真正的「安静地做不了任何事」。所以回放路径钳制并继续。

而调用点是 `PersonaSpec.kt:83`：

```kotlin
ToneAxes.coerce(delta.newValue.toInt())
```

`coerce` 只管**越界**（数字但超范围）；`toInt()` 在**非数字**时抛 `NumberFormatException`。
注释承诺的「不抛」没有任何测试覆盖 —— 所以它一直是假的。
一条 `TONE_WARMTH / "abc"` 的账本条目（早期版本 / 手工编辑 / 序列化损坏）
会让 `currentSpec()` 直接崩，**助理起不来**。作者说要避免的结果，从他要防的那条路上来了。

## 规则 2 · 测试名就是断言清单 —— 名字里的每个名词都要有断言

**要求**：写完测试，把**测试名里的名词逐个圈出来**，每个名词都要找到对应断言。
找不到的 → 要么补断言，要么承认那个名词不该出现在名字里。

**本次实例**：测试名 `相同内容重复卸载落到同一个文件且引用 id 相同`

| 名字里的名词 | 对应断言 | 结论 |
|---|---|---|
| 相同**内容** | — | ❌ **漏了** |
| **重复**卸载 | `store.files.size == 1` ✓ | ✓ |
| 同一个**文件** | `relativePath` 相同 ✓ | ✓ |
| 引用 **id** 相同 | `id` 相同 ✓ | ✓ |

**漏掉的那一项，恰好是唯一会坏的**：

- `OffloadRef.id` 由 `(kind, taskId, body)` 派生，**刻意不含时间**（为了重试幂等）
- 但 `sha256 = OffloadCodec.sha256(encoded)`，而 `encoded` **含 `at = now`**
- ⇒ 两次不同时刻卸载同一内容：`id` 相同、文件**被覆盖**、
  而第一次返回的 ref 的指纹指向**已被覆盖的旧内容**
- ⇒ 之后 `recall(旧ref)` → 指纹不符 → 报 `Corrupted`

ref 是要持久化进 `:memory`(Room) 的。用户重试一次任务，
上一轮存下的引用**集体变成「内容损坏」**。

**这条规则为什么最值钱**：写测试的人**相信自己测了**。
「相同内容重复卸载」这个测试名让他安心的，正是他没测的那一项。

## 规则 3 · 恒真断言是装饰，不是测试

**要求**：一条断言如果**在当前实现下永远为真**，它不构成验证。

**自查**：问自己 —— **「我要怎么改代码，才能让它变红？」** 答不出来，就是恒真。

**本次实例**：

```kotlin
assertTrue("骨骼必须完好", tuner.currentSpec().bones.isIntact())
```

而 `PersonaSpec.derive` 里是 `bones = SafetyBones()` —— **硬编码**，所以永远 `true`。
`isIntact()` 在生产代码里**零调用点**，只在 2 个测试里出现。
（注释还承诺它用于「透明度报告」—— 那个用途不存在。）

**升级方式**：改成「**试图改它 → 断言抛异常**」：

```kotlin
expectRejection(PersonaRejectionReason.PROTECTED_BONES) { tuner.tune(...) }
```

这类断言本次**是有的，而且有效** ✓ —— 要保留的是**这种**，删掉恒真的那种。

## 规则 4 · 不变量要么做全，要么注明为什么只做一半

**本次实例**：`Offload.kt` 写下了一条完全正确的原则 ——

> **时间属于引用的元数据，不属于它的身份。**

然后只落实了一半：`id` 确实不含时间 ✓，
但 `sha256` 依赖的 `encoded` **含** `at`。
⇒ 同一个「身份」下出现两个指纹，「身份稳定」与「内容可比对」互相拆台。

**要求**：一个原则若只在**部分字段 / 部分路径**上落实，
**必须在注释里写明另一半为什么不做**。
不写 ⇒ 下一个读代码的人会以为它做全了，然后按错误的假设继续改。

## 规则 5 · 映射表要双向覆盖，且能生成的不许手写

**本次实例（两条，同一个根因）**：

**① 拦截表有中文，放行表没有。**
骨骼表收了「支付 / 付款 / 解锁 / 隐私 / 诚实 / 安全」，
白名单表**只有英文**（`PersonaField.name` + 英文别名）。
⇒ 模型输出「温度」→ 落 `Unknown` → **一条完全合法的微调被拒**。
讽刺的是 `PersonaField.label` 和 `ToneAxis.label` **本来就是「温度」** ——
数据在枚举里躺着，却手写了一份英文别名表。

**② 骨骼表自己漏了关键项，且与它自己的声明矛盾。**
注释写「**宁可多收**：多收的代价几乎为零，少收的代价是静默放行」，
而 `refuseUnlock` 的注释自己写着「锁屏密码 / 支付密码 / 生物识别」——
表里**没有**「密码 / 指纹 / 人脸 / 转账 / 红包 / 撒谎 / 上传」。
⇒ 用户说「以后密码你自己填」→ 落 `Unknown` → 错误码是 `NOT_WHITELISTED`
而不是 `PROTECTED_BONES` ⇒ 用户看到「我没听懂要改哪个方面」，
而不是「这是我的底线」—— **正是作者写三态枚举时要避免的那件事**。

**要求**：

1. 拦截表与放行表**必须同时有中英文**，不允许只做一侧
2. 能从一个已有数据源（如 `label`）生成的，**不许手写第二份**（手写的那份必然漂移）
3. **自查（一行）**：

```kotlin
PersonaField.entries.forEach {
    assertTrue(PersonaFieldRefs.resolve(it.label) is PersonaFieldRef.Whitelisted)
}
```

**★ 这条的通用形态**：本次两条都是「**防御侧做了，使用侧没做**」。
⇒ **凡是加一条拦截规则，同时问一遍：这条规则会不会误伤正常输入？**

## 规则 6 · 给调用方的能力，要么自己防误用，要么把前提写进签名

**本次实例**：`CandidateGate.combine(confidences)` 用概率或合并，
注释说明成立前提是「证据**互相独立**」，但**函数本身不检查**。

⇒ `["INTERRUPT", "INTERRUPT", "INTERRUPT"]` → `1 − 0.55³ = 0.834 ≥ 0.7` → **升级**。

而作者自己写着「**「被一句话改坏」是需求②最要命的**」——
这就是它的实现路径。同一句话被记 3 次 = 用户下令改人格。

**要求**：纯函数的正确性若依赖调用方满足某前提，**三选一**：

| | 做法 |
|---|---|
| ① | 函数内校验（推荐） |
| ② | 用类型保证（如收 `Set` 而非 `List`） |
| ③ | 签名或 KDoc 里**显式**写出前提，**并写清违反后果** |

**不允许**「注释里提一句、代码里不管」。

## 规则 7（元规则）· 注释写得越自信，越要自查

前 6 条能全部命中，靠的是一个很土的方法：**拿注释当验收清单**。

| 注释说 | 核之后 |
|---|---|
| 「回放路径钳制并继续（不抛异常）」 | **抛**（`toInt()`） |
| 「宁可多收」 | **没收**（缺密码 / 指纹 / 转账…） |
| 「向前兼容读取」（`ignoreUnknownKeys = true`） | **不兼容** —— `recall` 的往返闭合检查会把这种兼容判成 `Corrupted` |

**原因**：写承诺时写的是**意图**，写实现时写的是**当时想到的路径**。
两者的差额，就是 bug 的所在。

⇒ **把「核注释」提前到自己这边做。**
提交前用规则 1 那条 `grep` 扫一遍，比等审核方扫出来再返工便宜得多。
