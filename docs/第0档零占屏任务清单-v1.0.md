# 第 0 档零占屏任务清单 v1.0

> 2026-09-23 · 全部命令均在真机 K60（`mondrian` / Android 15 / API 35 / HyperOS `OS3.0.8.0.VMNCNXM`）
> 上实测取得，标注 ✅ 的表示**现场验证过**，标注 ⚠️ 的表示**仅推断、待实测**。

---

## 0. 为什么要有这份清单

前面几轮已经依次否掉三条路：

| 方向 | 结论 | 死因 |
|---|---|---|
| 虚拟屏 | ❌ 已否决 | P0-3：`isCallerAllowedToLaunchOnDisplay()` 架构封死，第三方无法把别人的 App 启到非默认屏 |
| freeform 小窗 | ❌ 本机不可用 | 无 `freeform_window_management` feature + `setprop` 被 SELinux 拒 + `--windowingMode 5` 静默降级 |
| 系统分身 | ❌ 已否决 | 全机只有一块 INTERNAL display，分身与主空间是**切换式**关系 |

⇒ **「不占屏地操作别人的 App」这条路，第三方应用走不通。**

第 0 档换一个问法：**不操作界面，能不能把事办了？**

答案是可以，而且能办的事比预想的多 —— 前提是**目标 App 提供了无界面的入口**。

## 1. 定义与判据

### 1.0 ★★ 先说清楚：不占屏是**约束**，不是**目的**

这一条是 2026-09-23 补上的，因为**最初的实现把约束当成了目的**。

按三条判据机械地筛，能筛出一大把东西：改亮度、切深色、调音量、开关 Wi-Fi、收通知栏……
第一版第 0 档页收了 **14 条**这样的设备开关，全部满足判据。

**但它们里没有一个能帮用户完成一件事。** 用户点进去，看到的是一串"能做的动作"，
而不是"能办的事"。这就是把约束当目的的典型症状：**判据成了唯一的筛选器，
于是筛选器能过什么，产品就是什么。**

正确的问题不是「不占屏能做什么」，而是：

> **在不占屏的前提下，什么能力对用户最有价值？**

答案是**文件与数据办公** —— 读文件、写文件、创建和管理文件。
理由有三条：

1. **它是"电脑端办公"能力的真子集**，而不是"手机操作的替代品"。
   手机上做文档工作之所以难受，正是因为要占屏、要来回切应用。
2. **它是唯一不需要任何特权的通道**（T0-D，SAF）：用户点一次目录就完事，
   不需要电脑、不需要 Shizuku、不需要任何系统权限。
3. **它天然不占屏**：读写文件本来就不需要界面。

⇒ **判据本身一个字没改**（三条判据仍然全满足），改的是**产品范围**。

落地方式是把"技术判据"与"产品范围"分成两个正交的东西：

| | 判据 | 谁回答 |
|---|---|---|
| 技术上算不算零占屏 | 三条判据 | `Capability.isZeroScreen` 的**推导依据** |
| 产品上放不放进第 0 档 | 是不是"用户要办的事" | `CapabilityGroup.isZeroScreen` |

那 14 条设备控制类**全部仍然满足判据**（它们确实不占屏），只是**不再属于第 0 档**。
代码保留（`CapabilityGroup.DEVICE`），从第 0 档页移出。

⚠️ **`CapabilityCatalog.zeroScreen` 用 `group.isZeroScreen`，不写死 `group != DEVICE`** ——
否则下次再挪一条能力，又要改一处判断，而"改漏一处"的表现是**某个能力悄悄出现在它不该出现的页面上**。

---

> **第 0 档 = 任务执行全程，屏幕上不出现任何「因 agent 而起」的界面变化。**

三条判据（必须全满足）：

1. 不调用 `startActivity`
2. 不读无障碍节点树、不截图
3. 不注入触摸/按键事件（**媒体键除外** —— 它不改变画面）

### 1.1 一个必要的细分

| 档位 | 含义 | 例子 |
|---|---|---|
| **第 0 档（严格）** | 全程零界面变化 | 「把 Wi-Fi 关了」「给张三发条短信」 |
| **第 0 档+（终点跳转）** | 全程零界面变化，**只在最后跳一次到结果页** | 「打开淘宝的订单页」 |

⚠️ **关键区分**：

- 「agent **为了自己操作**而把界面拉起来」→ **占屏**
- 「任务**的结果本身就是**给用户看的页面」→ **不算占屏**

这条区分决定了 `startActivity` 不是绝对禁止 —— 但它只能出现在**终点**，且**只能出现一次**。
一旦出现第二次（翻页、返回、重进），任务就掉出第 0 档。

## 2. 六条零占屏通道

| 通道 | 机制 | 需要什么 | 本机状态 |
|---|---|---|---|
| **T0-A** 系统设置 | `Settings.Global/System/Secure` 读写 | `WRITE_SECURE_SETTINGS` | ✅ 该权限 `prot=signature\|privileged\|development\|installer\|role` → **可变更**（实测）；⚠️ **必须先在 manifest 声明** |
| **T0-B** Shizuku shell | 以 uid 2000 执行 `cmd *` / `pm` / `settings` / `svc` | 用户装 Shizuku 并授权 | ✅ Shizuku 已安装（当前未运行）；`cmd -l` 列出 **354** 个服务 |
| **T0-C** 通知 | 读（`NotificationListenerService`）/ 写（`cmd notification post`）/ 回复（`RemoteInput`） | 通知使用权 / Shizuku | ✅ `cmd notification` 支持 `post`/`set_dnd`/`list`/`get`/`snooze`；⚠️ 当前通知使用权被小米自带服务占用 |
| **T0-D** 数据接口 | `ContentProvider` / 网络 API / SAF 文件 | 运行时权限 / SAF 授权 | 部分就绪（`:filelogic` 判定层已完成，Android 侧通道待做） |
| **T0-E** 音频与媒体 | TTS 播报 / `cmd media_session dispatch` / 音量 | 无（媒体控制需 Shizuku） | ✅ `dispatch play\|pause\|next\|previous` 可用；本机有活跃会话 `cn.longniu.pages` |
| **T0-F** 广播与服务 | `am broadcast` / `am start-foreground-service` | Shizuku；目标 App 需导出对应组件 | ✅ 可用（导出组件需逐 App 调研） |

### 2.1 T0-A 的实测细节（重要）

`WRITE_SECURE_SETTINGS` 是本清单里**唯一能让 App 直接写系统设置**的路径。实测结论：

```bash
# ① 该权限本身是可变更的 —— 对照组能反证
$ pm grant <pkg> android.permission.WRITE_SECURE_SETTINGS        # → 无异常
$ pm grant <pkg> android.permission.BIND_NOTIFICATION_LISTENER_SERVICE
  SecurityException: ... is not a changeable permission type      # ← 纯 signature 的报这个

# ② 但「没在 manifest 里声明」时，pm grant 是【静默无效】的
$ pm grant <pkg> android.permission.WRITE_SECURE_SETTINGS        # → 不报错
$ dumpsys package <pkg> | grep WRITE_SECURE_SETTINGS             # → 空，没生效
```

⇒ **正确流程：先在 `AndroidManifest.xml` 里声明，再由用户 `adb shell pm grant` 授予。**
跳过声明那一步不会报错，只会安静地不生效 —— 属于本项目反复踩的那类 bug。

✅ **已实测通过（2026-09-23，K60 / Android 15）**：声明放进 `:capability` 的 manifest、
构建安装后：

```bash
$ dumpsys package com.pocketagent.debug | sed -n '/requested permissions:/,/install permissions:/p'
      android.permission.WRITE_SETTINGS
      android.permission.WRITE_SECURE_SETTINGS                    # ← 声明进了 APK
$ pm grant com.pocketagent.debug android.permission.WRITE_SECURE_SETTINGS   # → 退出码 0
$ dumpsys package com.pocketagent.debug | grep "WRITE_SECURE_SETTINGS:"
      android.permission.WRITE_SECURE_SETTINGS: granted=true      # ← 真的生效了
```

⚠️ **但声明要进 APK，`:app` 必须真的依赖 `:capability`** —— manifest 合并只在
有人依赖那个模块时才生效。少那一行的话模块代码照样编译通过、权限却不在 APK 里，
`pm grant` 静默无效。又一次"不报错、只是安静地少做一件事"。

#### ★★ 三个命名空间用的是**两类**权限（真机 `dumpsys package android` 实测）

| 命名空间 | 权限 | 保护级别（原样） | `pm grant` |
|---|---|---|---|
| `GLOBAL` / `SECURE` | `WRITE_SECURE_SETTINGS` | `signature\|privileged\|`**`development`**`\|installer\|role` | ✅ 能授 |
| `SYSTEM` | `WRITE_SETTINGS` | `signature\|`**`appop`**`\|pre23\|preinstalled\|role` | ❌ 报错 |

差别就在那一位上：`development` 位让 `pm grant` 生效；`appop` 型的不走包管理器。

`WRITE_SETTINGS` 的三条实测（声明进 manifest 之后）：

- `pm grant … WRITE_SETTINGS` → `SecurityException: Permission … is managed by role`，退出码 **255**
- `cmd appops get <pkg> WRITE_SETTINGS` → 声明前 `No operations / Default mode: default`，声明后 `ignore`
- `cmd appops set <pkg> WRITE_SETTINGS allow` → 复查为 **`allow`** ✅ 可行

⚠️ **把两者混成一个"没有写设置权限"，用户拿到的指引会有一半是错的** ——
而错的指引比没有指引更坏：他会照着 `pm grant` 做一遍、撞上一个
`is managed by role` 的报错（那句话里没有一个字提到"你该改用 appops"），
然后认定"这个功能坏了"。

⇒ 两条指引已固化在 `SettingsPermissionPolicy.guidanceFor()`，**逐字命令有测试钉住**。

### 2.2 T0-B 的边界

Shizuku 给的是 **uid 2000（shell）**，不是 root。它能做 `cmd`/`pm`/`settings`/`svc`/`am`，
**不能**改 SELinux 策略、不能 `setprop` 受限属性（P0-3 里 `enable_freeform_support` 就是被这条挡住的）。

#### ⚠️⚠️ `Shizuku#newProcess` 已经不存在了（2026-09-23 核实）

对 `dev.rikka.shizuku:api:13.1.5` 的 `classes.jar` 直接 `javap`：

- `rikka.shizuku.Shizuku` 里**没有** `newProcess`。它只有 `pingBinder` /
  `checkSelfPermission` / `requestPermission` / `getBinder` / `bindUserService` /
  `unbindUserService` / `transactRemote` 等
- `rikka.shizuku.ShizukuRemoteProcess` 还在，但构造器收的是
  `moe.shizuku.server.IRemoteProcess`，而且是**包内可见**的 —— 外部构造不了
- 官方 Changelog 13.1.1：「Prepare to remove `Shizuku#newProcess`, developers
  should have to use `UserService` instead」

⇒ **T0-B 的实现路径是 `UserService`**：应用自带一个 `.aidl` 接口 + 一个 service 类，
由 Shizuku 在 shell/root 身份的进程里拉起，应用再通过 `bindUserService` 拿它的 binder。
代价是要开 AIDL 代码生成（`buildFeatures { aidl = true }`）。

⚠️ **为什么要把这段写下来**：社区里仍在流传 `Shizuku.newProcess` 的写法，而它们
**看起来能跑**。实测过的一个开源终端 App 就是用**反射**去调它 ——
反射失败后回落到无权限的 `Runtime.exec`，界面上照常显示「Shizuku 模式」，
命令却一点特权都没有；而它的 README 还写着"可访问 `/data`、`pm grant`、`dumpsys`"。
⇒ 那正是本项目最忌讳的形态：**不报错、不崩溃，只是安静地少做一件事。**

⚠️ 因此 `:capability` 刻意**不**依赖 shizuku —— 设置通道走 `Settings.*` 的 API，
不需要 shell 身份。这是第 0 档能在 Shizuku 服务没跑起来时仍然可用的原因。

#### 4.4.1 文件能力落地实况（2026-09-23）

**真机已目击**：授权 `PocketAgentTest` 目录 → 第 0 档页显示
`你的目录（1）` / `PocketAgentTest` / **`/storage/emulated/0/PocketAgentTest`**（路径由 SAF tree URI
正确推导）/ `撤销`；`file.list` 与 `file.read` 都**真的执行成功**。

**第 0 档页现在一共 6 条**：SAFE 3（`file.list` / `file.read` / `notification.post`）+
GUARDED 3（`file.write` / `file.delete` / `file.move`）。那 14 条设备控制类全部消失。

实现里三个**不显然但必须这样**的决定：

| 决定 | 不这样的后果 |
|---|---|
| **不用 `DocumentFile`**，直接用 `DocumentsContract` 读 `COLUMN_SIZE` | `DocumentFile.length()` 拿不到大小时返回 **0**，与 `EntryStat.sizeBytes` 的「null ≠ 0」契约冲突。写 `length().takeIf { it > 0 }` 会把**真正 0 字节的空文件**报成"大小未知" —— 为修一个假话制造另一个假话 |
| 授权真相来源是 `ContentResolver.persistedUriPermissions`，**不自建列表** | 自建列表会与系统漂移（系统设置里撤销 / 数据从备份恢复 —— URI 授权**不进备份**），漂移方向永远是「我们以为能读，其实读不到」 |
| `derivePath` 认不出的 provider **返回 null，不编路径** | 编一个路径不是"展示难看"：`ScopeRoot.path` 的用途是**与请求路径做字符串匹配**，编出来的会让**另一条**路径被判定为"在范围内" |

**两个闸必须分开**（这是文件能力最容易做错的地方）：

| | 问的是什么 | 多久问一次 | 谁产出 |
|---|---|---|---|
| `CapabilityVerdict.RequireConfirmation` | 你允许 agent 做**这类事**吗 | 一次（放行后长期有效） | `CapabilityGuard` |
| `ChannelResult.NeedsConfirmation` | 这一次要动的**那个文件**，你确定吗 | **每次** | `:filelogic` 的 `FileAccessDecider` |

⚠️ `CapabilityGuard.decide()` **不是 suspend**（这是它能进离线跑器的前提），而文件裁决需要 `stat`
（suspend + IO）→ 所以 `CapabilityGuard` 里那个 `is PlannedExecution.FileIntent -> Unit` 分支
**刻意是空的**，不是漏了。

⚠️ **真机上发现的缺口（未修）**：这两个闸**共用一个 `confirmedByUser` 标志**，于是"第一次使用
某个 GUARDED 能力"时，第一个闸的确认会**顺带把第二个闸也答掉** —— 真机上用户看到的是

> 要执行「把一段文字写进文件……」。这一次具体是：写入 /storage/emulated/0/PocketAgentTest/hello.txt（14 字）。

用户确实知道**要写哪个文件**，但**不知道那个文件已存在、原内容会被替换掉**。
⇒ 待办：要么让放行确认框带上覆盖警告，要么给两个闸各自一个标志。

**两处契约债务（已记录，未收敛）**：

1. **`FileChannel.write` 的「必须走 `AtomicTextFile`」在 SAF 上做不到。**
   `AtomicTextFile` 的签名是 `write(target: java.io.File, ...)`，靠**同一文件系统内 `rename(2)` 是原子的**；
   而 SAF 里文档由 `Uri` 标识、可能在云盘上，**没有 `java.io.File`**。
   ⇒ 退到同一策略的 SAF 版本（临时文档 + `renameDocument`，不支持则"先删旧再改名"）。
   **保证「不会丢内容」，不保证「不会出现临时名字」** —— 失败信息里明确写出那个临时名字。

   > **★★ 真机实证（2026-09-23，已修）—— 比上面那条推断严重得多**
   >
   > 覆盖一个已存在的文件时，`DocumentsContract.renameDocument(temp, "hello.txt")` 在
   > 目标名已存在时**既不报错、也不替换** —— 它**静默地把临时文档改名成 `hello (1).txt`**
   > 并返回一个非 null 的 Uri。原代码只看"返回了非 null"就报告成功，于是：
   >
   > | | 实际发生的 |
   > |---|---|
   > | 用户以为 | `hello.txt` 被覆盖了 |
   > | 实际上 | 旧文件完好，新内容在 `hello (1).txt` 里 —— **目录里凭空多出一个副本** |
   >
   > ⚠️ 这比"改名失败"糟得多：失败是可见的，而这个是**报告成功**。用户要等到下一次
   > `file.list` 才会发现两个文件，而那时他已经不记得哪一份是新的。
   >
   > ⇒ 判据必须是**改完之后它叫什么**（`renamedTo()` 查 displayName），而不是"这一步有没有报错"。
   > ⚠️ **不能用比较 documentId 代替**：外部存储用路径式 id（改名后 id 会变），而云盘类提供者
   > 可能用不透明 id（**改名后 id 不变**）—— 在后一种上比较 id 会把"静默改名"误判成"替换成功"。
   >
   > **⚠️⚠️ 第一次修法本身又出事了（同一天、同一台机器）**
   >
   > 以为"名字不对就把那个副本删掉，再走『先删旧再改名』的退路"就行。但**改名是"消耗性"的**：
   > `renameDocument` 之后那个 `tempUri` **就失效了**（文档已经改叫别的名字），退路拿着它去改名
   > 会抛 `IllegalArgumentException: Missing file for ...` —— **而旧文件已经在上一步被删了**。
   >
   > ⇒ 真机上 `hello.txt` **真的消失了**：旧内容没了，新内容也没落盘。
   > （logcat 证据：`Missing file for .../hello.txt.tmp-df1657fe.txt`，栈顶就是 `replaceExistingFile`）
   >
   > ⇒ 最终改成**每一步都能回滚**的顺序：**把旧文件改名挪开**（不是删掉！）→ 在新名字上新建
   > → 成功则删掉那个备份、失败则把备份**改回原名**。代价是中间有一瞬 `name` 不存在
   > （用户那一刻看目录会发现它"不见了"），但**内容一秒都没丢过**。
   >
   > ⚠️ 这条教训比 bug 本身重要：**「改名」不是「复制」—— 它消耗源对象。**
   > 任何"改名失败就退回去再改一次"的写法都是错的。
   >
   > `move` 的同类问题：同目录改名**已加校验**（只报错、不删文件）；
   > **跨目录的 `createDocument` 也会静默改名**（目标名已存在时），目前**只记录未修** ——
   > 它不丢数据（源文件在复制成功之后才删），表现为"移动到了 `b (1).txt`"。

2. **`FileChannel.delete` 没法在类型上报告"删掉了什么"**（签名是 `ChannelResult<Unit>`）。
   目前只能靠调用方自己知道删的是哪个路径。

**一个已知不足（失败方向是安全的）**：`/sdcard` 是 `/storage/emulated/0` 的符号链接，而
`PathNormalizer` 只做字符串运算 → 用户写 `/sdcard/Documents/a.txt` 时**匹配不上**授权目录，
被拒为"不在授权范围内"。这是**拒绝而非放行**，所以可以接受；界面上给的是
`/storage/emulated/0/...` 形式的路径。

## 7. 与既有架构的衔接

- **感知阶梯的第 0 档就是本清单**：不感知 → 直接走能力通道，跳过树/截图
- ✅ **纯逻辑层已实现：`:capabilitylogic`**（纯 Kotlin、零 Android 依赖，见 §9.1）
  - `Capability` 声明 + `CapabilityCatalog`（**15 条**内置能力）+ `CapabilityParams` 参数校验
  - `CapabilityGuard` **七步裁决**：目录 → 硬拒绝 → 来源 → 参数 → 规划 → 规划后硬校验 → 放行 → 确认
  - `CommandPlanner` 展开成 `PlannedExecution`；`ShellArgv` 用**数组**，注入在结构上不可能
  - `CapabilityAuditLog` 审计：只记包名与设置键，**绝不记参数原值**
- ✅ **通道层也已就位**（纯模块内）：`SettingsAccess` / `ShellRunner` 两个端口 +
  `ChannelResult` 结果模型 + `CapabilityRunner` 派发器 + `CapabilityRuntime` 编排
  - ⚠️ 端口声明在纯模块、实现在 Android 侧，与 `filelogic` 的 `FileChannel` 同构 ——
    好处是**派发逻辑能离线钉死**（argv 过边界、先读后写、端口缺失走哪个分支）
  - ⚠️ **编排层（`CapabilityRuntime`）也在纯模块里**，而不是 Android 侧：它一行
    Android 代码都没有，三个依赖全是本模块定义的纯对象。而「裁决 → 执行 → 记账」
    的**顺序**恰恰最该被钉住 —— 单看每个组件都对，连错顺序也不会让任何一条
    "正向测试"变红（记账提前 = 日志说执行了而实际没执行）
  - ⚠️ `ShellRunner.run` 收的是 `List<String>`。**把它改成 `String`（或实现方自己
    `joinToString(" ")` 再交给 shell）会让「注入在结构上不可能」这条论证整个作废** ——
    而后果不会立刻显现，要等某条能力的某个参数恰好含 `;` 才发作
  - ⚠️ **两种「不可用」必须分开**：`Unavailable`（去配置：权限没给 / Shizuku 没跑 /
    端口没接）与 `Failed`（试过了，没成）。混成一个 `Boolean` 之后界面上就只剩
    「操作失败」一句 —— 而那句话对这两种情况**都是错的指引**
  - ⚠️ 设置写入**先读原值再写**。顺序反了不报错，只会让撤销把设置「恢复」成
    它刚变成的那个样子（SAFE 的判据之一是「可逆」）
  - ⚠️ **连续同因的通道失败只记第一条**（不同能力不合并 —— 它们的 `targetDigest` 不同）。
    不合并的后果是 500 格环形缓冲被同一句话填满，而那份日志是用户判断
    「这个插件想干什么」的唯一线索
- ✅ **Android 侧薄适配器已落地：`:capability`**（2026-09-23，`compileDebugKotlin` 通过）
  - `AndroidSettingsAccess`：`Settings.Global / System / Secure` 的读写
    - ⚠️ 走 **API 而不是 `settings put` 命令** —— 两者权限要求相同，但只有 API 路径
      有返回值，能区分「权限被拒」与「写成功了」
    - ⚠️ 权限判据与界面**必须同源**（`isGranted()` 就是 `write()` 用的那一个），
      否则会出现"页面显示已授权、点下去却报没权限"，而用户无从判断该信哪一个
  - ⚠️ 权限声明放在 `:capability` 自己的 manifest 里（遵循「随功能落地逐项启用」），
    但 **`:app` 必须真的依赖 `:capability`** —— 见 §2.1
  - ⏳ **shell 通道（T0-B）尚未实现**：上游已移除 `Shizuku#newProcess`，正解是
    `UserService`（要开 AIDL 代码生成）。**不要照旧文档写 `newProcess`** —— 见 §2.2
- ✅ **用户入口已落地**（2026-09-23）—— 这一页是「用户真的能用一次」的那一步：
  - **能力页**（设置 → 第 0 档能力）：按风险分组列出 15 条内置能力，填参数 → 执行，
    结果与审计都显示在同一页
  - **权限页新增两项**：「修改系统安全设置」与「修改系统设置」。⚠️ 它们**必须是两项** ——
    前者在系统设置里**没有开关**（签名级权限），后者有（特殊应用权限）。
    合并成一项会让一半的用户被指引到一个找不到开关的地方
  - ⚠️ **「手机上做不到」是第四种状态**（`GrantState.NeedsComputer`），
    不能并进 `Denied`：后者的下一步是「去设置点一下」，前者的下一步是
    「去电脑上跑一条命令」。判据不同 → 界面上的按钮与文案必须不同
  - ⚠️ **判定结果 → 用户那句话的映射也在纯模块**（`CapabilityMessages`）：
    「还差一步配置」与「试过了，没成」合成一句「操作失败」的后果是
    用户反复重试 —— 而前者要的是一条 adb 命令，重试一百次也不会变
  - ⚠️ **「还没实现」不等于「端口没接上」**：shell 通道传 `PendingShellRunner`
    而不是 `null`。传 null 会让判定层说「没有接上通道」（指向一个用户找不到的开关），
    而事实是「我们还没写」（指向一个更新）
  - ⏳ 放行记录**只在本次运行内有效**（界面上明说）。持久化那一步还没做 ——
    但不假装：不说的话，用户放行过一次、第二天发现要重新放行，而**没有任何东西解释为什么**
- ⏳ **`ActionExecutor` 需要新增一条 T0 通道**：无手势、无节点树，只有 `PlannedExecution`
- **SafetyGuard 必须覆盖 T0** —— `settings put` / `pm disable` / `cmd *` 的破坏力不比点击小
  - ✅ **已按「能力白名单」落地**（不是命令白名单）：能力必须先在目录里声明才能被调用
  - ✅ 危险项由 `CapabilityDenyRules` **固定拒绝**，不参与任何覆盖逻辑：
    10 类能力 id 前缀（`setting.write.*` / `locksettings.*` / `credential.*` / `role.*` /
    `package.install` / `package.uninstall` / `package.grant` / `package.revoke` /
    `process.kill` / `debug.*`）+ **28 条设置键** + **13 个系统包**
  - ⚠️ 最重要的一条是 `secure/enabled_accessibility_services`：它可写 = agent 能
    **给自己授予无障碍权限**（读全屏、点全屏、看得到支付页），
    而整个安全模型建立在"特殊权限只能由用户亲手授予"这个前提上
- `AgentBudget`：T0 任务几乎不耗 token（多数是本地命令）→ 预算压力最小
- ⚠️ **T0 是唯一能「息屏 + 后台」执行的档位** → 与 `PowerGovernor` 天然契合，
  也让「悬浮球只作待命信号」这个设计更有意义

### 9.1 落地时确立的硬约束（**改动需评审**）

| 约束 | 为什么 |
|---|---|
| **一条能力 = 一个具体动作**；禁止 `shell.exec(argv…)` / `setting.write(ns,key,val)` 这类通用能力 | 通用能力一旦存在，风险分级 / 参数校验 / 确认流程都只是在给一个后门镶边 |
| **`ShellArgv` 必须是数组**，实现方不得拼成字符串再交给 shell | `Shizuku.newProcess(String[])` → `Runtime.exec(String[])` **不经过 shell**，分号 / 竖线 / 反引号 / `$()` 全是普通字符 |
| **配方里不支持拼接**（不许出现 `--set={index}` 这种半拼接 token） | 拼接是注入的温床。代价是少数能力暂时进不来，这个取舍划算 |
| **设置键是配方字面量**，不能由参数决定 | 否则一条能力就能写任意设置键，`CapabilityDenyRules` 的键白名单立刻失效 |
| **`confirmedByUser` 只在最后一步被消费** | 提前消费 = 把"用户点过确认"变成绕过一切的后门 |
| **规划后的产物要再校验一次** | 防"安全的能力 + 危险的参数"：`app.set_enabled` 本身正当，而 `com.android.systemui` 是**格式合法**的包名，参数校验拦不住 |
| **审计只记包名与设置键，绝不记参数原值** | 通知正文是用户内容；而"昨晚停用了哪个 App"是必须能回答的 —— 单条规则（只有像包名的值才记）让这个取舍不随能力数量漂移 |
| **`CapabilityRisk` 只有 SAFE / GUARDED 两级**，不设 `FORBIDDEN` | "永不放行"的东西要做成**能力不存在**，而不是"出现在目录里但标着禁止" —— 后者迟早会有人写一行 `if (risk != FORBIDDEN)` 放它过去 |
| **通道层必须区分 `Unavailable` 与 `Failed`** | 前者是「去配置」，后者是「试过了，没成」。而「用户放行这条能力」与「系统给了这个权限」是**两套独立授权**（前者在本体数据库、后者在系统包管理）—— 混起来用户就不知道该去点授权还是去跑 adb |
| **端口签名 `ShellRunner.run(List<String>)` 不得改成 `String`** | 这是 argv 过边界的**最后一道**。后果不会立刻显现，要等某条能力的某个参数恰好含 `;` 才发作 |
| **设置写入必须先读原值、再写** | 顺序反了不报错，只会让撤销把设置「恢复」成它刚变成的那个样子。SAFE 的判据之一是「可逆」，而不知道原值就改不回去 |
| **`Succeeded.previousValue` 不进审计日志，且 `toString()` 必须覆写隐去它** | `data class` 自动生成的 `toString()` 会原样打出来 —— 一句 `Log.d(TAG, result.toString())` 就把它写进日志。**自动生成的东西没人会去审，所以它是最安全的泄漏路径** |
| **不要用 `internal` 构造器去「加固」`PlannedExecution`** | 试过，白费力气：`data class` 的 `copy()` 绕得过任何非公开构造器（编译器会警告 `non-public primary constructor is exposed via the generated copy()`）。更根本的是，可见性**挡不住真正危险的那件事** ——「跳过裁决器直接调 runner」。⇒ 真正的边界是**接口形状**：runner 要的那个对象只能来自 `Allowed.execution`。**可见性挡不住「绕过去」，只有「没有别的入口」才挡得住** |
| **`GLOBAL`/`SECURE` 与 `SYSTEM` 是两类授权，指引**绝不**能合并** | `WRITE_SECURE_SETTINGS` 有 `development` 位（`pm grant` 能授）；`WRITE_SETTINGS` 是 `appop` 型（`pm grant` 报 `is managed by role`，只能 `appops set … allow`）。合并成一个"没有写设置权限"= 一半指引是错的，而**错的指引比没有指引更坏**：用户照做一遍、撞上一个看不懂的报错，然后认定功能坏了 |
| **权限声明所在模块必须被 `:app` 真正依赖** | manifest 合并只在有人依赖时生效。少那一行的话模块代码照样编译通过、权限却不在 APK 里，`pm grant` 静默无效。**声明写在哪不重要，"有没有人依赖它"才决定它进不进 APK** |
| **`CapabilityRuntime`（编排）留在纯模块**，不下沉到 Android 侧 | 它一行 Android 代码都没有。而「裁决 → 执行 → 记账」的**顺序**必须能离线钉住 —— 记账提前的后果是"日志说执行了、实际没执行"，而它不会让任何正向测试变红 |
| **连续同因的通道失败只记第一条**（不同能力不合并） | 权限没配时每一次调用都产生一条 `Unavailable`，500 格环形缓冲会被同一句话填满。而那份日志是用户判断「这个插件想干什么」的**唯一线索** —— 被填满的日志看起来和"什么都没发生"一样。不同能力即使原因相同也不合并：它们的 `targetDigest` 不同，而"想动哪个目标"正是那份日志的主要用途 |
| **界面的权限判据必须与执行判据同源** | `AndroidSettingsAccess.isGranted()` 就是 `write()` 用的那一个。界面自己写一套会出现"页面显示已授权、点下去却报没权限"，而用户**完全无从判断该信哪一个** |
| **`:app` 用到的纯逻辑类型必须显式声明 `implementation(project(":xxx"))`** | **离线跑器看不出来**：它把所有模块塞进同一次 kotlinc 调用，跨模块引用会顺便解析成功；只有 Gradle 会挂。而 `:capability` 对 `:capabilitylogic` 是 `implementation` 依赖，**不会传递**到 `:app` 的编译类路径上。⇒ 这个缺口靠 `check_module_deps.py` 兜住 —— 它正是为此存在的（本轮真的拦下了一次） |
| **「手机上做不到」必须是**独立的**状态**（`GrantState.NeedsComputer`），不能并进 `Denied`** | 两者的下一步完全不同：前者要上电脑跑命令，后者去设置点一下。合并的后果是用户把「应用 → 特殊应用权限」逐页翻一遍找一个**从来不在那里**的开关，然后以为是机型差异 |
| **判定结果 → 用户那句话的映射放在纯模块**（`CapabilityMessages`） | 把 `Unavailable`（去配置）与 `Failed`（试过了没成）合成一句「操作失败」，或者把 `NOT_GRANTED`（还没放行）标成红色失败 —— 这些错法在界面上都**看起来正常**，只会让用户做出错误的下一步动作。所以它必须能被离线测试钉住 |
| **「还没实现」≠「端口没接上」**（shell 通道传 `PendingShellRunner` 而非 `null`） | 传 `null` 让判定层说「没有接上通道」—— 那句话把原因指向**配置**，用户会去翻设置找一个开关；而事实是**我们还没写**，他只能等一个更新。把「还没做」说成「没接上」，正是「不报错、只是安静地少做一件事」的一种形态 |
| **T0-B 的实现路径是 Shizuku `UserService`，不是 `newProcess`** | `Shizuku#newProcess` 在 13.1.1 起已被移除（`javap` 核实 13.1.5 的 `Shizuku` 类里没有它）。照旧文档写 `newProcess` 会**静默降级**成无特权的 `Runtime.exec` —— 有开源项目就是这么做的，界面显示"Shizuku 模式"而命令一点特权都没有。**不要照旧文档写实现** |
