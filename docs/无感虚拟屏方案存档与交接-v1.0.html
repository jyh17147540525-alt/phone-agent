无感虚拟屏方案存档与交接 · v1.0

状态：本文档 + 仓库内代码资产 = 可交接。 归档日期：2026-09-25 归档人：主项目 agent 适用设备：红米 K60（mondrian）/ Android 15 / API 35 / HyperOS OS3.0.8.0.VMNCNXM / arm64-v8a / 1440×3200

⚠️ 本文档的目的不是「宣传成果」，而是「让接手人不踩我们踩过的坑」。 因此未解问题与错误结论的修正所占篇幅，大于已验证的能力。

0. 一页速览（TL;DR）

问题 结论
虚拟屏能不能建起来？ 能，三条路线都能。
哪条路线可用？ 只有 VDM 路线（createVirtualDisplay 直建 + 自带 ImageReader 消费面）。
能不能做到「主屏零干扰」？ 部分能 —— 主屏无悬浮层、可注入输入、可读像素；但跨应用跳转会切走主屏。
能不能「独立 display group」？ 能（flags 里的 OWN_DISPLAY_GROUP 位），但需要满足一组 flag 约束。
无障碍能不能读这块屏？ 取决于 FLAG_PRIVATE，与 display group 无关（⚠️ 我们曾误判，见 §2.4）。
现在能不能上产品？ 不能。 三个前置未满足，见 §4。

一句话：机制上打得穿，但「读屏」与「不打扰用户」在 Android 15 上难以同时拿满，且存在隐私红线。

1. 三代路线的最终判定

代 路线 建屏 树 像素 注入 主屏干扰 判定
1 settings put global overlay_display_devices ✅ ❌ ✅ ⚠️ 投到主屏 ❌ 主屏出现「叠加视图 #1」 否决
2 MediaProjection / freeform / 系统分身 ⚠️ — — — — 否决（能力不足）
3 createVirtualDisplay 直建 + 自有消费面 ✅ ✅ ✅ ✅ ✅ 零悬浮层 唯一走通

1.1 第一代（overlay）为什么被否决

settings put global overlay_display_devices "1280x720/240" 真的生效（uniqueId="overlay:1"、 type OVERLAY，MIUI 还会起 SecondaryDisplayLauncher + ImageWallpaper），且带 FLAG_TRUSTED。

但两条致命伤： - 无障碍读不到（dumpsys accessibility 仍 1 valid display: 0）； - overlay 会投到主屏 —— 主屏左上角出现「叠加视图 #1」，直接违反「尽量少影响用户」的最高优先级。

⚠️ 写入后要等 ~3-4 秒再 dump，否则会误判「没生效」。（我们曾因此得出「P0-3 连 shell 都拒」的错误结论。）

1.2 第三代（VDM）为什么能成

关键差异是它不是 overlay 类型：

// app_process + shell 特权
Context ctx = sysCtx.createPackageContext("com.android.shell", 0);
ImageReader ir = ImageReader.newInstance(1080, 2340, PixelFormat.RGBA_8888, 3);
VirtualDisplay vd = dm.createVirtualDisplay("vd-xxx", 1080, 2340, 240, ir.getSurface(), flags);
  • 自带 ImageReader 消费面 → 虚拟屏内容渲染进我们自己的 Surface，可读像素
  • 不是 overlay 类型 → 无障碍的 isValidDisplay() 不因 TYPE_OVERLAY 直接拒绝（但仍卡 FLAG_PRIVATE，见 §2.4）
  • 主屏零悬浮层 → 不像 overlay 那样叠加

2. VDM 路线技术细节

2.1 VIRTUAL_DISPLAY_FLAG_* 逐位表

来源：AOSP android15-release frameworks/base/core/java/android/hardware/display/DisplayManager.java

位 名称 值 语义要点
0 PUBLIC 1 非 PUBLIC ⇒ 强制 FLAG_PRIVATE
1 PRESENTATION 2 可用于演示
2 SECURE 4 内容不可截屏
3 OWN_CONTENT_ONLY 8 只显示自有内容（非 AUTO_MIRROR 时被强制加上）
4 AUTO_MIRROR 16 镜像默认屏内容
5 CAN_SHOW_WITH_INSECURE_KEYGUARD 32 ⚠️ 与 PUBLIC 互斥
6 SUPPORTS_TOUCH 64 ⚠️ 实测可能多余，见 §2.5
7 ROTATES_WITH_CONTENT 128
8 DESTROY_CONTENT_ON_REMOVAL 256
9 SHOULD_SHOW_SYSTEM_DECORATIONS 512
10 TRUSTED 1024 需 ADD_TRUSTED_DISPLAY（shell 持有）
11 OWN_DISPLAY_GROUP 2048 独立 DisplayGroup；只在非 AUTO_MIRROR 分支生效
12 ALWAYS_UNLOCKED 4096 需 OWN_DISPLAY_GROUP 或 DEVICE_DISPLAY_GROUP
13 TOUCH_FEEDBACK_DISABLED 8192
14 OWN_FOCUS 16384 维持自有焦点与触摸模式；需 TRUSTED
15 DEVICE_DISPLAY_GROUP 32768
16 STEAL_TOP_FOCUS_DISABLED 65536 不抢别屏 top focus；需 TRUSTED + OWN_FOCUS

2.2 三层约束（最容易踩的地方）

源码：VirtualDisplayAdapter.java:477-489

if ((mFlags & VIRTUAL_DISPLAY_FLAG_PUBLIC) == 0) {
    mInfo.flags |= FLAG_PRIVATE | FLAG_NEVER_BLANK;      // ① 非 PUBLIC ⇒ 强制 PRIVATE
}
if ((mFlags & VIRTUAL_DISPLAY_FLAG_AUTO_MIRROR) != 0) {
    mInfo.flags &= ~FLAG_NEVER_BLANK;
} else {
    mInfo.flags |= FLAG_OWN_CONTENT_ONLY;                 // ② 非 AUTO_MIRROR ⇒ 强制 OWN_CONTENT_ONLY
    if ((mFlags & VIRTUAL_DISPLAY_FLAG_OWN_DISPLAY_GROUP) != 0) {
        mInfo.flags |= FLAG_OWN_DISPLAY_GROUP;            // ③ 独立 group 只在这个分支生效
    }
}

推导出的约束链：

想要 必须 代价
无障碍可见 不能有 FLAG_PRIVATE ⇒ 必须带 PUBLIC
OWN_DISPLAY_GROUP 生效 不能有 AUTO_MIRROR ⇒ 被强制加 OWN_CONTENT_ONLY（这个本身无害）
带 PUBLIC — ⇒ 不能再带 CAN_SHOW_WITH_INSECURE_KEYGUARD（抛异常）

⚠️ 实测：PUBLIC | CAN_SHOW_WITH_INSECURE_KEYGUARD 直接抛 IllegalArgumentException: Public display must not be marked as SHOW_WHEN_LOCKED_INSECURE。 这是 framework 的真约束，不是调用方的 bug。

⚠️ 实测：想「去掉 OWN_CONTENT_ONLY」是无效的 —— 传 89122（已清 bit 3）， dumpsys 里 FLAG_OWN_CONTENT_ONLY 依然在，因为是系统按 ② 补上的。

2.3 ★★★ 实测矩阵（本文档最硬的一张表）

同一台设备，同一操作（建屏 → 启动设置 → 注入点击），只改 flags：

表内 + 表示 flag 按位或组合（即源码里的 |）。之所以不用 |，是因为它在 Markdown 表格里 必须写成 \| 转义，而多数渲染器（含本仓库的 docs/build_html.py）在 code span 内不会把它还原 —— 会显示成 PUBLIC\|PRESENTATION。用 + 可以做到任何渲染器下都正确。

flags 十进制 FLAG_PRIVATE 无障碍收录 跨应用跳转落点
PUBLIC + PRESENTATION 3 无 ✅ 2 valid displays: 0, 33 ❌ 切走主屏
PRESENTATION + OWN_CONTENT_ONLY + TRUSTED + OWN_FOCUS + … 87162 有 ❌ 1 valid display: 0 ✅ 留屏
同上 + OWN_DISPLAY_GROUP + ALWAYS_UNLOCKED 89130 有 ❌ 1 valid display: 0 —
同上去掉 OWN_CONTENT_ONLY 89122 有 ❌ 1 valid display: 0 —
PUBLIC + PRESENTATION + OWN_CONTENT_ONLY + TRUSTED + OWN_DISPLAY_GROUP + OWN_FOCUS + STEAL_TOP_FOCUS_DISABLED 85003 无 ✅ 2 valid displays: 0, 36 ✅ 留屏

flags=85003 是目前的「最优解」 —— 它是唯一同时满足「无障碍可见 + 独立 group + 自有焦点」的组合。

2.4 ★★★ 无障碍的真判据是 FLAG_PRIVATE，不是 display group

源码：AccessibilityManagerService.java:5477（AccessibilityDisplayListener.isValidDisplay()）

private boolean isValidDisplay(@Nullable Display display) {
    if (display == null || display.getType() == Display.TYPE_OVERLAY) {
        return false;                                    // overlay 屏直接排除
    }
    if (display.getType() == Display.TYPE_VIRTUAL
            && (display.getFlags() & Display.FLAG_PRIVATE) != 0
            && display.getOwnerUid() != mSystemUiUid) {
        return false;                                    // ★ 私有虚拟屏、owner 非 SystemUI ⇒ 跳过
    }
    return true;
}

⚠️ 这是本项目踩过的一个大坑，必须记住： 我们曾一度把「无障碍读不到」归因为 OWN_DISPLAY_GROUP，并据此写下「树与无感二选一」的结论。 那个归因是错的 —— 真正的开关是 FLAG_PRIVATE。 教训：判断「某块屏能不能被无障碍读」的唯一有效判据是 dumpsys accessibility 的 valid display 列表， 且必须回到源码看 isValidDisplay 的判定条件，不要从 flag 名字猜因果。

⚠️ uiautomator dump 不是有效的无障碍判据：它没有 --display 参数，永远只读 display 0。 用它测虚拟屏 = 测了个寂寞。

2.5 其他实测结论（易错）

  • TOUCH 标志可能是多余的：设备报 touch NONE，但 input -d <id> tap 真实生效 ⇒ 输入走的是窗口自己的 input channel，不是 display 的 touch 属性。
  • --display 陷阱：目标 App 在主屏已是 top-most 时，am start --display N 会被忽略 （Warning: intent has been delivered to currently running top-most instance） ⇒ 先让主屏前台是别的 App 再启。
  • 坐标非线性：HyperOS 会给虚拟屏 App 加 Embedded{Miui Caption} + scale（1.43~3.0） ⇒ 按「帧坐标 + 窗口偏移」点击会偏（实测点蓝牙 → 跳到小米账号）。1:1 只在首次冷启动时成立。
  • 帧产出节奏：内容变化时才出帧，页面静止时 NO_FRAME yet 属正常。 AUTO_MIRROR 型（镜像）会跟着主屏 vsync 持续刷帧 —— 不要用它判断「渲染是否正常」。
  • dumpsys display 的 displayGroupId 字段不反映 OWN_DISPLAY_GROUP（两种屏都显示 0） ⇒ 判 group 只能靠行为（无障碍收录数 / 跳转落点）。

4. 未解问题（交接人必读）

4.1 ⚠️ isVisible=false —— 本轮唯一未闭环项

flags=85003 的屏上，设置窗口报：

mViewVisibility=0x8  mObscured=true  isVisible=false
mCurrentFocus    = Window{... com.android.systemui}
mObscuringWindow = Window{... com.android.systemui}     ← systemui 盖住整块屏

怀疑：实验当时主屏处于安全锁（deviceLocked=1，上滑解不开）→ systemui 把锁屏层也铺到了虚拟屏。 但未证实。 也可能是「PUBLIC 屏被 systemui 接管」的真问题。

接手人第一件事：在主屏解锁状态下重跑 flags=85003，看 isVisible 是否恢复 true。 这一条不确认，「flags=85003 是最优解」这个结论就不完整。

4.2 ❗ 隐私红线（最高优先级）

像素帧里是用户真实的私人微信聊天列表（联系人名、消息预览、群名）。 叠加协作组已承认的「空屏回退镜像主屏」行为 = 双重风险。

必须在任何读屏代码落地之前就位： 1. PrivacyFilter（提交 6822983）； 2. 帧来源校验（确认目标 App 已绘制，不能只看 display 存在）； 3. 帧内容分级（聊天 / 支付 / 验证码 → 丢弃，不进上下文）。

⚠️ 上传路径的唯一出口就是这里。先装闸，再通水。

4.3 跨应用跳转在 flags=3 下会切走主屏

已实测：mode=3 时在虚拟屏上点击触发跳转 → 主屏被 com.deepseek.chat/.MainActivity 整个占满。 flags=85003 下该现象消失，但 §4.1 的可见性问题未解。

4.4 其他未验证

  • 投递方式（经 Shizuku 写 Termux 私有目录 / 经 Termux 脚本拉取）尚未验证；
  • PowerGovernor 未实现；
  • 长稳（连续运行数小时）未测。

5. 可复现步骤

实验脚本已随本文档入库：tools/p0/vdisplay/

5.1 编译与部署

# 编译（需要 JDK；d8 在 Android SDK build-tools 下）
javac --release 17 -d out/ tools/p0/vdisplay/src/VdOwnGroup.java
d8 --output out/ out/com/pocketagent/verify/*.class
# 打包 + 推送
adb push vd2.jar /data/local/tmp/

5.2 建屏（最优解）

adb shell "cd /data/local/tmp && CLASSPATH=/data/local/tmp/vd2.jar \
  app_process /system/bin VdOwnGroup 85003 > /data/local/tmp/vd_out.txt 2>&1 &"
sleep 5
adb shell "head -3 /data/local/tmp/vd_out.txt"     # 应见 CREATED ... displayId=N

5.3 关键校验（三条都要做）

# ① 无障碍是否收录这块屏（唯一有效判据）
adb shell "dumpsys accessibility | grep 'valid display'"     # 期望：2 valid displays: 0, N

# ② 实际 flag 落地情况（确认 FLAG_PRIVATE 不在）
adb shell "dumpsys display" | grep -o 'DisplayDeviceInfo{"vd-[^}]*}' | grep -o 'FLAG_[A-Z_]*'

# ③ 跨应用跳转落点
adb shell "am start --display N -n com.android.settings/.Settings"
adb shell "input -d N tap <x> <y>"
adb shell "dumpsys window windows | grep -B1 'mDisplayId=N'"

5.4 清理（必做，否则残留）

adb shell "kill -9 \$(pidof VdOwnGroup)"
adb shell "dumpsys display | grep -c vd-"     # 期望 0

⚠️ 应用崩溃/被杀时虚拟屏不会自动清理。产品化时必须实现孤儿屏检测（Application.onCreate 里跑）。

⚠️ :display 模块的过时之处（接手人注意）

  1. settings.gradle.kts 里标注「已否决，勿在此模块投入」—— 这是旧 overlay 路线下的结论， VDM 路线已将其救活，该标注需重新评估；
  2. VirtualDisplayManager.kt 头部写着「无障碍通道无法操作虚拟屏」—— 已被 input -d 实测推翻；
  3. 同文件写着「副屏窗口在主屏上可见」—— VDM 路线零悬浮层，不成立；
  4. 接口基于 overlay_display_devices + screencap -d 设计 —— 与 VDM 路线（createVirtualDisplay + ImageReader）不是同一套机制，实现时不要照抄接口里的命令。

结论：:display 模块当前应视为「历史设计稿」，而非「待实现的规格」。

7. 安全与合规

  • 密钥不落库：API Key 只在设备端 Keystore + AES-GCM + SQLCipher，不进日志 / 崩溃上报 / 备份 / SharedPreferences；
  • 仓库无硬编码密钥：已扫描确认（sk- 的命中全部为测试用假值）；
  • .gitignore 已覆盖：*.jks / *.keystore / keystore.properties / signing.properties / *.token / secrets.properties / .env / .env.*；
  • 推送前检查：tools/verify/check_no_secrets.py（本轮新增）。

8. 下一步建议（按优先级）

  1. 主屏解锁后重跑 flags=85003，确认 isVisible（§4.1）—— 这是唯一的阻塞项；
  2. PrivacyFilter 就位（§4.2）；
  3. 若 §4.1 通过 → 把 VDM 路线产品化：孤儿屏检测、生命周期、降级链；
  4. 若 §4.1 失败 → 回退到 flags=3 + 接受「跳转会切主屏」，或转向分屏 / 手动小窗降级链。
