社区分发版方案 v3.0（身份定位 · 虚拟屏 · 开源治理）

项目：PocketAgent（手机 AI 智能体助手 · BYOK 版） 版本：v3.0 ｜ 日期：2026-09-21 前置文档：v1.0 项目方案 / M0 落地手册 / v2.0 社区分发版方案 本版新增三项关键约束：① 开发者身份为在校学生、全开源、非盈利 ② 需要"虚拟屏幕"运行 Agent ③ 未来提供可推送到指定 GitHub 仓库的密钥

0. 本轮三项约束的实质影响

约束 影响性质 一句话结论
学生 / 开源 / 非盈利 合规大幅简化 备案与许可证压力显著下降，但备案存在结构性死结（见 1.3）
虚拟屏幕运行 Agent 技术路线重排 存在一条 Android 10 起的硬性安全限制，第三方 App 不能把别人的 App 启动到虚拟屏上；唯一出路是 Shizuku 通道
未来提供 GitHub 推送密钥 新增安全红线 绝不能把 token 硬编码进 APK，否则等于把你的仓库公开送人

0.1 最重要的一个发现（先说结论）

Android 10 起，应用只能在自己创建的虚拟屏幕上启动自己的 Activity。 —— AOSP 官方文档《activity 启动政策》

这意味着：普通的第三方应用，无法把微信、美团这类别人的 App 启动到虚拟屏幕上。 虚拟屏上只能跑我们自己的 Activity。

所以"调用虚拟屏幕运行 Agent"这个需求，只有一条路能走通：Shizuku（拿到 shell 权限，用 am start --display 把目标 App 启到副屏上）。

如果 Shizuku 这条路验证失败，虚拟屏方案就不成立，必须降级为小窗模式或全屏接管。这是 M0 的第一优先级实验（EX-16）。

1.3 备案的结构性死结（必须正面承认）

App 备案的流程是：通过接入服务商（云服务商）向省级通信管理局提交，备案信息绑定「域名 + 服务器 + 包名 + 签名」。

矛盾点：

要备案  →  需要接入服务商  →  需要国内服务器与域名
                                          ↑
                            与本项目"无自有服务端"原则直接冲突

三种选择：

方案 做法 代价 建议
A. 不备案，接受风险 保持无服务端架构，小范围社区传播 法律义务未履行；但执法抓手（商店下架、域名拦截）均不适用 ✅ 当前阶段推荐
B. 建最小服务端以完成备案 买一台最低配云服务器 + 域名（约 ¥100-300/年），只放静态页与更新清单 打破"无自有服务端"原则；引入运维负担与成本 ⚠️ 规模扩大后考虑
C. 用 GitHub Pages 替代，不备案 更新源与官网都在 GitHub Pages GitHub 是境外平台，不在境内备案体系内；但因此也无法完成备案 ✅ 与 A 配套

诚实结论：

对于一个学生、开源、非盈利、无服务端、不收集数据、不收费的小范围项目， 备案的实际风险敞口很低，但法律义务在形式上并未消失。

这不构成法律意见。如果项目做大（比如用户数上万），或开始接受捐赠之外的任何收费， 必须重新评估并补办备案。 不要抱着"永远不备案"的侥幸做长期规划。

2. 虚拟屏幕：技术可行性与完整方案

这是本版最重要的章节。结论可能和你的预期不一样，请仔细看。

2.1 平台硬约束：AOSP 的明确规定

AOSP 官方文档《activity 启动政策》原文：

在 Android 10 中，为了防止恶意应用通过从其创建的虚拟屏幕的表面读取用户敏感信息来盗用相关信息， 应用只能在其创建的虚拟屏幕上启动其自己的 Activity。

具体规则表：

调用方 能否在虚拟屏/副屏启动 Activity
普通第三方应用（默认） ❌ 只能在自己创建的虚拟屏上启动自己的 Activity
有 INTERNAL_SYSTEM_WINDOW 权限的系统组件 ✅ 可在任何屏幕启动
有 ACTIVITY_EMBEDDING 权限的调用方 ⚠️ 仅限目标应用声明了 FLAG_ALLOW_EMBEDDED
专有屏幕（proprietary display） ⚠️ 仅屏幕所有者或已在该屏的 Activity

检查 API：ActivityManager#isActivityStartAllowedOnDisplay(context, displayId, intent) 实现位置：ActivityStackSupervisor#isCallerAllowedToLaunchOnDisplay()

2.2 那为什么还有工具能做到？

因为 shell 权限走的是另一条路。

  • am 命令由 shell 执行时，调用身份是 shell UID (2000)，与普通应用不同
  • am start --display <id> 是 ActivityManagerShellCommand 官方支持的参数
  • Shizuku 提供的正是 shell UID 的能力

经验证据：开源项目 SecondaryScreen（副屏模拟器）的文档明确说明—— "可通过 shell 命令提权，使用 am start 命令启动 secondActivity，并通过 --display 参数指定到副屏上"。

⚠️ 但这需要实测确认。不同厂商 ROM 对 shell 的权限授予策略可能不同， 且 Android 大版本可能继续收紧。这是 EX-16 要回答的核心问题。

2.3 方案矩阵：四条路，一条主路

方案 机制 能否跑第三方 App 依赖 用户干扰 评价
A. Overlay Display（副屏） settings put global overlay_display_devices + am start --display ✅ 需 Shizuku WRITE_SECURE_SETTINGS + shell 低（副屏窗可缩放移动） ⭐ 主路
B. Freeform 小窗 enable_freeform_support + am start --windowingMode 5 ✅ 需 Shizuku WRITE_SECURE_SETTINGS + shell 中（小窗占屏） 备选
C. MediaProjection 虚拟屏 MediaProjection.createVirtualDisplay() ❌ 只能镜像，不能跑别人 App MediaProjection 授权 无 仅用于读取
D. 全屏接管 直接在默认显示上操作 ✅ 零依赖 无障碍 高（占满屏幕） 兜底

2.4 方案 A 详解：Overlay Display

创建副屏

# 创建一块 1080x1920、320dpi 的副屏
settings put global overlay_display_devices "1080x1920/320"

# 创建多块（最多 6 块）；带 secure 参数时无法截屏/录屏
settings put global overlay_display_devices "1080x1920/320,secure;1080x1920/320,secure"

# 删除
settings put global overlay_display_devices "null"

权限：WRITE_SECURE_SETTINGS（signature|privileged，但可通过 ADB/Shizuku 授予：pm grant <pkg> android.permission.WRITE_SECURE_SETTINGS）

副屏特征（实测输出）：

DisplayInfo{"叠加视图 #1", displayId 5, FLAG_PRESENTATION, FLAG_TRUSTED,
            real 1920 x 1080, type OVERLAY, layerStack 5}

在副屏上启动目标 App

am start --display 5 -n com.tencent.mm/.ui.LauncherUI

或从代码：

// 方式一：走 Shizuku 执行 shell 命令（推荐，不受 setLaunchDisplayId 限制）
Shizuku.newProcess(arrayOf("am", "start", "--display", "5", "-n", "$pkg/$activity"), null, null)

// 方式二：ActivityOptions（⚠️ 受 Android 10 安全限制，第三方应用大概率被拒）
val opts = ActivityOptions.makeBasic().apply { launchDisplayId = 5 }
startActivity(intent, opts.toBundle())

实现建议：优先用方式一（Shizuku shell），方式二仅作为探测手段。

输入注入到副屏

input -d 5 tap 400 640
input -d 5 swipe 400 800 400 200 300
input -d 5 text "hello"

关键优势：-d <displayId> 让输入只作用于副屏，不干扰用户在主屏的触摸操作。这正是需求的核心。

读取副屏 UI 树

// Android 13+ (API 33)：支持跨显示获取窗口
val nodes = if (Build.VERSION.SDK_INT >= 33) {
    accessibilityService.getWindowsOnAllDisplays()
        .filterKeys { it == targetDisplayId }
        .values.flatten()
        .mapNotNull { it.root }
} else {
    // Android 12 及以下：用 windows 过滤
    accessibilityService.windows
        .filter { it.displayId == targetDisplayId }
        .mapNotNull { it.root }
}

⚠️ 注意：getWindowsOnAllDisplays() 需要 flagRetrieveInteractiveWindows 标志 （已在 v2.0 的无障碍服务配置中声明）。

截取副屏画面

screencap -d 5 -p /sdcard/agent_display5.png

只能走 shell（Shizuku）。MediaProjection 无法截取副屏。

⚠️ 若副屏创建时带了 secure 参数，则无法截屏。所以不要带 secure。

方案 A 的已知限制（必须写进产品）

限制 说明 应对
副屏窗口在主屏上可见 叠加在主屏上，可缩放、可移动，但不可隐藏 ① 缩到最小尺寸并移到屏幕角落 ② 提供"最小化预览"开关 ③ 明确告知用户这是系统行为，非本应用所致
最多 6 块副屏 系统限制 单实例使用即可，无需多块
部分 App 不支持多显示 未声明 resizeableActivity="true" 的 App 可能无法在副屏正常渲染，或黑屏 检测失败后自动降级到方案 B/D
金融类 App 可能拒绝运行 检测到非默认显示可能主动退出 命中即停止并提示用户（与敏感页面策略一致）
依赖 Shizuku 用户需安装 Shizuku 并通过无线调试激活；重启后需重新激活 ① 提供完整的激活引导 ② 检测失效后降级 ③ 主推无障碍通道作为日常，虚拟屏作为增强
副屏音频/通知归属 副屏上 App 的音频仍从设备输出，通知正常 一般无问题，但需实测
强依赖 WRITE_SECURE_SETTINGS 需 Shizuku 授权 同上

2.5 方案 B 详解：Freeform 小窗（备选）

# 开启 freeform 支持
settings put global enable_freeform_support 1
settings put global force_resizable_activities 1

# 以小窗模式启动，并指定边界
am start --windowingMode 5 --bounds 100,200,900,1400 -n com.tencent.mm/.ui.LauncherUI

优点：不需要创建虚拟屏，小窗可移动、可最小化，用户体验比副屏窗口好 缺点：仍占用主屏空间；用户可能误触；部分 App 不支持 freeform

2.6 推荐的降级链（必须实现）

启动 Agent 任务
      ↓
① 虚拟屏模式（方案 A）
   ├─ Shizuku 可用？ ── 否 ──┐
   ├─ 创建副屏成功？ ── 否 ──┤
   ├─ App 启动到副屏成功？ ── 否 ──┤
   └─ 成功 → 在副屏执行，主屏完全不受影响 ✅
                                  ↓
② 小窗模式（方案 B）
   ├─ freeform 可用？ ── 否 ──┐
   └─ 成功 → 小窗执行，主屏可正常使用 ⚠️
                              ↓
③ 全屏接管模式（方案 D）
   └─ 在默认显示上执行，明确告知用户"我正在操作你的屏幕"
      · 提供中止按钮
      · 用户可随时接管
                              ↓
④ 手动引导模式
   └─ 只给出操作步骤，用户自己点

产品要求： - 当前处于哪一档，必须在 UI 上明确显示（如"当前模式：虚拟屏 / 小窗 / 全屏"） - 用户可在设置中强制指定模式（如"永远不要占用我的屏幕"→ 只用虚拟屏或手动引导） - 降级时给出原因说明，而不是默默降级

2.7 关键结论

"调用虚拟屏幕，不影响用户正常使用"这个需求——技术上可达，但有三个前提：

  1. 必须有 Shizuku（无障碍权限做不到，这是 Android 10 起的硬限制）
  2. 副屏窗口在主屏上仍可见（系统行为，可缩放移动但不可隐藏）
  3. 不是所有 App 都能在副屏跑（未声明 resizeableActivity 的会失败）

如果这三条中有任何一条无法接受，那么"虚拟屏"应降级为可选增强， 而非产品的默认形态。建议产品默认走小窗模式，虚拟屏作为"高级用户可选"。

3. 执行层重构：以显示为第一维度

3.1 接口变更（重要）

v2.0 的 ActionExecutor 没有"显示"概念。虚拟屏引入后，所有动作都必须带 displayId。

// 新增：执行目标
sealed interface ExecutionTarget {
    /** 默认显示（物理屏幕）—— 会干扰用户 */
    data object PrimaryDisplay : ExecutionTarget

    /** 虚拟屏 —— 不干扰用户 */
    data class VirtualDisplay(val displayId: Int) : ExecutionTarget

    /** 小窗（freeform） */
    data object FreeformWindow : ExecutionTarget
}

// ActionExecutor 接口变更
interface ActionExecutor {
    val channel: ExecutorChannel

    /**
     * 新增：该通道支持哪些执行目标。
     * 无障碍通道只能操作默认显示；虚拟屏只有 Shizuku 通道支持。
     */
    fun supportedTargets(): Set<Class<out ExecutionTarget>>

    suspend fun perform(action: UiAction, target: ExecutionTarget): ActionResult
}

3.2 通道与执行目标的对应关系（关键矩阵）

执行目标 无障碍 Shizuku IME 悬浮窗引导
默认显示（主屏） ✅ ✅ ✅ ✅
虚拟屏（副屏） ❌ 只能读，不能注入 ✅ 唯一可行 ❌ ❌
小窗（freeform） ✅（在默认显示上） ✅ ✅ ✅

这张表是整个架构的核心约束：

  • 读虚拟屏：无障碍可以（getWindowsOnAllDisplays）
  • 操作虚拟屏：只有 Shizuku
  • 截虚拟屏：只有 Shizuku（screencap -d）

结论：虚拟屏模式是"Shizuku 独占"的能力。没有 Shizuku 就没有虚拟屏。

3.3 新增模块：:display

/**
 * 虚拟显示管理器。
 *
 * 职责：创建/销毁虚拟屏、在虚拟屏上启动 App、判断虚拟屏可用性。
 *
 * ⚠️ 本模块**必须依赖 Shizuku**。无 Shizuku 时所有方法返回 Unavailable，
 *    由上层降级到小窗或全屏模式。
 */
interface VirtualDisplayManager {
    /** 当前是否可用（Shizuku 已激活 + WRITE_SECURE_SETTINGS 已授予） */
    fun availability(): DisplayAvailability

    /** 创建（或复用）虚拟屏，返回 displayId */
    suspend fun ensureDisplay(config: DisplayConfig): DisplayResult

    /** 在虚拟屏上启动目标 App */
    suspend fun launchOnDisplay(packageName: String, displayId: Int): LaunchResult

    /** 检查某 App 能否在虚拟屏运行（预检，避免黑屏） */
    suspend fun canRunOnDisplay(packageName: String): Boolean

    /** 释放虚拟屏并清理副屏上的 App */
    suspend fun release()

    /** 观察虚拟屏上的 App 状态 */
    fun observeRunningApps(displayId: Int): Flow<Set<String>>
}

data class DisplayConfig(
    val width: Int = 1080,
    val height: Int = 1920,
    val densityDpi: Int = 320,
    /** ⚠️ 不要设 true，否则无法截屏 */
    val secure: Boolean = false,
)

sealed interface DisplayResult {
    data class Created(val displayId: Int) : DisplayResult
    data object Unavailable : DisplayResult
    data class Failed(val reason: String) : DisplayResult
}

3.4 坐标映射（虚拟屏预览交互）

如果要在主屏上提供一个可交互的副屏预览窗，需要坐标映射：

/**
 * FIT_CENTER 缩放 + letterbox 偏移。
 * 用户在预览窗上点击 → 换算成副屏坐标 → 通过 input -d 注入。
 */
fun mapToVirtualDisplay(
    touchX: Float, touchY: Float,
    viewWidth: Int, viewHeight: Int,
    virtualWidth: Int, virtualHeight: Int,
): Point? {
    val scale = minOf(viewWidth.toFloat() / virtualWidth, viewHeight.toFloat() / virtualHeight)
    val renderedW = virtualWidth * scale
    val renderedH = virtualHeight * scale
    val offsetX = (viewWidth - renderedW) / 2f
    val offsetY = (viewHeight - renderedH) / 2f

    val contentX = touchX - offsetX
    val contentY = touchY - offsetY
    // 点在黑边上，忽略
    if (contentX < 0 || contentY < 0 || contentX > renderedW || contentY > renderedH) return null

    return Point(
        x = (contentX / renderedW * virtualWidth).toInt().coerceIn(0, virtualWidth - 1),
        y = (contentY / renderedH * virtualHeight).toInt().coerceIn(0, virtualHeight - 1),
    )
}

3.5 生命周期与资源释放（易错点）

必须严格按顺序释放，否则会残留副屏或黑屏：

1. 隐藏副屏预览悬浮窗
2. force-stop 副屏上运行的 App（am force-stop）
3. 释放 VirtualDisplay
4. 关闭 ImageReader
5. 删除 overlay_display_devices 设置

常见坑： - ImageReader 的 maxImages 必须设小（2），且必须及时 acquireLatestImage().close() - 不消费帧会导致 buffer 满，副屏 App 停止渲染（表现为"卡死"） - 应用崩溃/被杀时副屏不会自动清理，下次启动必须做孤儿副屏检测

4. GitHub 仓库推送能力设计

需求："项目达到一定规模后，我会提供一个可推送到指定 GitHub 仓库的密钥。"

4.1 安全红线（最重要的一条）

⚠️ 绝对不要把 GitHub token 硬编码进 APK

APK 是可以被任何人反编译的。一旦 token 内置： - 任何人都能提取它，往你的仓库里灌垃圾、开几百个 issue、甚至删除内容 - GitHub 会自动检测到泄露的 token 并吊销，但你的仓库可能已经被搞了 - 而且你无法追责——因为从 GitHub 的角度看，这就是"你的应用在正常操作"

这是新手最容易犯的致命错误。 见 4.2 的正确做法。

4.2 三种正确做法（按推荐度排序）

方案 1：GitHub OAuth Device Flow ★推荐

用户在 App 内点「连接到 GitHub」
      ↓
App 向 GitHub 请求 device_code + user_code
      ↓
App 展示 8 位码，引导用户打开 github.com/login/device 输入
      ↓
用户在自己账号下授权
      ↓
App 轮询换取 access_token（存在用户设备上）
      ↓
此后以**用户自己的身份**提交内容

优点： - ✅ token 属于用户，不属于你——用户可随时在 GitHub 设置里撤销 - ✅ 不需要 client secret（public client 模式），没有可泄露的长期凭据 - ✅ Client ID 是公开的，硬编码在 APK 里也没关系 - ✅ 责任清晰：用户授权了什么，用户自己知道

实现要点： - 需注册一个 GitHub OAuth App（免费，5 分钟） - 只需 public_repo 或更细粒度的 scope - token 用与 API Key 相同的 Keystore 加密存储（复用 CryptoManager） - 提供"断开连接"按钮，同时引导用户去 GitHub 撤销

方案 2：BYO Token（用户自备令牌）

与 BYOK 理念完全一致，非常适合本项目：

App 引导用户去 GitHub Settings → Developer settings
      → Fine-grained tokens → 生成一个只对指定仓库有 issues:write 权限的 token
      → 粘贴到 App 里

优点： - ✅ 实现最简单（就是一个输入框 + 一次验证） - ✅ 权限可以精确到"只对某一个仓库、只有 issues 写权限" - ✅ 与 BYOK 的产品理念一致，用户容易理解

缺点： - ⚠️ 用户操作门槛略高（要会生成 PAT） - ⚠️ Fine-grained token 有过期时间，需要提醒用户续期

方案 3：不推送，生成内容让用户手动提交

App 生成一份格式化的报告（Markdown）
      ↓
用户点「复制」或「分享」
      ↓
用户自己粘贴到 GitHub Issue 页面

优点：零安全风险、零实现成本 缺点：体验差，转化率低

建议：方案 1 为主，方案 2 为备，方案 3 兜底。

4.3 推送能力的应用场景

场景 推送内容 目标 需要的权限
崩溃/错误报告 脱敏后的堆栈 + 设备信息 + 复现步骤 指定仓库的 Issue issues:write
用户写的规则提交 用户创作的选择器规则（L1 规则包） 官方规则仓库的 PR contents:write + pull_requests:write
插件提交 完整的插件包 + manifest 插件索引仓库的 PR 同上
误报反馈 "我的规则没生效/误触了" + 快照 对应插件的 Issue issues:write
匿名遥测（可选，默认关） 功能使用频次统计 仓库中的 JSON 文件 contents:write
机型适配反馈 "这个 ROM 上权限引导路径不一样" 适配仓库的 Issue issues:write

最有价值的两个场景：用户规则提交（PR） 和 机型适配反馈。 前者直接喂养插件生态，后者解决"没有预算买测试机"的死结——让社区帮你测。

4.4 架构要求

/**
 * GitHub 上报通道。
 *
 * ⚠️ 三条硬性约束：
 * 1. **凭据必须运行时注入**，绝不硬编码。未配置时所有方法直接返回 NotConfigured
 * 2. **默认关闭**。用户必须显式授权后才启用
 * 3. **所有内容必须经用户预览确认后才能发送**
 */
interface GitHubReporter {
    /** 当前连接状态 */
    fun connectionState(): ConnectionState

    /** 通过 Device Flow 发起连接 */
    suspend fun startDeviceFlow(): DeviceFlowSession

    /** 用 BYO token 连接 */
    suspend fun connectWithToken(token: String, repo: String): ConnectionResult

    /** 断开连接（同时提示用户去 GitHub 撤销） */
    suspend fun disconnect()

    /** 提交报告（内容必须先经用户确认） */
    suspend fun submitReport(report: ReportPayload): SubmitResult

    /** 提交规则/插件为 PR */
    suspend fun submitContribution(contribution: ContributionPayload): SubmitResult
}

sealed interface ConnectionState {
    /** 未配置 —— 所有上报功能静默关闭，不打扰用户 */
    data object NotConfigured : ConnectionState
    data class Connected(val login: String, val repo: String) : ConnectionState
    data class Expired(val reason: String) : ConnectionState
    data class Failed(val reason: String) : ConnectionState
}

关键设计： 1. 未配置时完全静默——不弹窗、不提示、不报错。功能就是"不存在" 2. 凭据用 CryptoManager 加密存储（与 API Key 同一套机制，复用现有代码） 3. 提交前必须展示预览——用户看到要发什么，点确认才发 4. 提交内容必须经 LogSanitizer 脱敏——防止把 Key、手机号、截图内容带出去 5. 频次限制——同一类报告每天最多 N 次，防止刷屏和触发 GitHub 限流 6. 失败静默——上报失败不影响主功能，最多记本地日志

4.5 阶段性启用

阶段 状态 说明
M0-M2 不实现 没有 token，也不需要
M3 实现框架 接口、加密存储、Device Flow 打通，但默认关闭
M4+ 正式启用 用户规模起来后，引导用户连接 GitHub
未来 提供仓库 届时把仓库地址配置化（可通过订阅源或本地配置下发，不硬编码）

重要：仓库地址也应该是可配置的，而不是硬编码。 这样将来换仓库（比如从个人仓库迁到组织仓库）不需要发新版。

附：本版核心结论速览

1. 身份变化让合规大幅简化，但备案有个结构性死结：没有服务器就没法备案。 当前阶段建议接受风险，规模扩大后重新评估。

2. 虚拟屏需求技术上可达，但只有 Shizuku 一条路。 Android 10 起，普通应用不能把别人的 App 启动到虚拟屏上——这是 AOSP 的硬规定。 而且副屏窗口在主屏上可见（可缩放移动但不可隐藏），"完全无感"做不到。 建议把虚拟屏定位为"高级用户可选增强"，而非默认形态。

3. GitHub 密钥绝不能硬编码进 APK。 用 OAuth Device Flow，让 token 属于用户而不是你。 这既解决了安全问题，又和 BYOK 的产品理念一脉相承。

4. 两个决定性问题必须在 M0 最先回答：虚拟屏（EX-16）和侧载受限设置（EX-13）。 它们不成立，产品形态就要重写。别先写代码。

文档结束。建议下一步：确认 D21-D27，然后立刻开始 EX-16 与 EX-13 的真机验证。
