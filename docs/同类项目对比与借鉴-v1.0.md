# 同类项目对比与借鉴 v1.0

> 2026-10-14 · workbuddy · 状态：**评估报告，待拍板**
> 触发：内测用户发现 `AAswordman/Operit`，问「我们是不是在重复造轮子，要不要学它的思路」
>
> ★ **先说结论**：是，也不是。功能面重复度很高，但**我们的工程纪律比它好**。
> 真正的问题不是"要不要学它"，而是**"功能数量"这条赛道我们追不上，也不该追**。

---

## §0 一页纸结论

| # | 结论 |
|---|---|
| 1 | **这个赛道已经有 5+ 个成熟项目**，不是"一个 Operit"。智谱官方（Open-AutoGLM）24 小时拿了 1.7k star |
| 2 | **功能面上我们重复度很高**：工具调用、记忆、会话管理、扩展机制、虚拟屏 —— 每一样都有人做了，且做得比我们多 |
| 3 | **但我们的工程纪律是明显的反例优势**：44 模块 + 离线验证器（1924 测试）+ 测试/主源码比 **0.60**。Operit 的 `app/` 是**单体** |
| 4 | ⇒ **不要追功能数量**。我们的定位应该是「**可读、可测、可信**的助理」，不是「最强大的平台」 |
| 5 | **有四件事必须立刻学**（§4）：① 每工具独立权限 ② 按用途分配模型 ③ 会话管理四件套 ④ 本地模型 |
| 6 | **许可证没问题**：他们 LGPL-3.0，我们 GPL-3.0 —— LGPL-3 §2 允许升级为 GPL-3，**可复用代码**（需署名） |

### 2.1 ★ 但注意一件事：他们也在犯我们犯过的病

`Repo_Arch_Basic.md` 原文：

> "`quickjs/` … **当前 README 明确说明该模块尚未接入 `app`**。"

⇒ **"写了没接线"不是我们独有的问题，是这类项目的通病。**
我们的优势不是"不犯这个错"，而是**我们有一整套机制去发现它**
（`check_module_deps.py` 的"零依赖模块"扫描、离线验证器的 `OK (N tests)` 口径、
`grep project(":x")` 复核）。**这套机制值得保留，并且是我们的差异化资产。**

## §3 ★ 我们没重复、且**不该抄**的

这一节同样重要 —— 全盘照抄会把我们唯一的好东西抄掉。

| 他们的做法 | 我们**不抄** | 理由 |
|---|---|---|
| **`app/` 单体** | ❌ | 我们 44 模块 + 离线验证器（1924 测试跑在无 SDK 的机器上）。单体换来迭代速度，代价是**无法离线验证** —— 而我们是"没有 Android SDK 也能跑全部纯逻辑测试"。**这是我们的护城河，不是包袱。** |
| **ObjectBox** | ⚠️ 暂不 | Room + SQLCipher 已有加密链路（Key 永不落明文）。换 ORM 会牵动加密与迁移。**收益（性能）不是我们的瓶颈。** |
| **Root 通道** | ❌ | 我们明写"只负责开发，其余用户自配"；Root 会把目标用户砍到极小，且与"少打扰"冲突 |
| **3D 虚拟形象 / 终端 / 项目工作区** | ❌ | 那是"平台"的活。我们是"助理"。**功能越多，"助理"这个定位越模糊。** |
| **Patreon / 爱发电** | ❌ | 项目明写"不盈利、不设捐款渠道"。这是**价值观差异**，不是能力差异 —— 且是我们**真实的差异化**（对一部分用户，这本身就是选择理由）|
| **统一市场** | ⚠️ 缓 | 需要服务端或至少一个索引托管。我们的"订阅源"走 GitHub Pages 静态 JSON，**方向对，但不必现在就做市场** |

## §4 ★ 必须立刻学的四件事（按优先级）

### 4.1 每个工具**独立**权限：允许 / 每次询问 / 拒绝（默认询问）

**他们原文**：
> "Choose among **Allow automatically, Ask every time, and Deny** for each tool; the default setting asks for permission"

**我们现状**：`SafetyGuard` 是**全局规则引擎**（敏感页一票否决），
但**没有"用户对单个工具授权"这一层**。⇒ 用户要么全信、要么全不信。

**为什么重要**：我们的插件体系（三级）本来就要"默认关进沙箱、逐项放行"，
但那是**插件**的。**本体自己的 10 个工具反而没有这个粒度** —— 这是倒挂。

**改哪里**：`:mcp` 的 `ToolRegistry` 加一层 `ToolPermissionStore`（Room 表 + 每工具三态），
`ToolRegistry` 在派发前查；默认 `ASK`。UI 在工具列表页逐项给三态。

### 4.2 按**用途**分配模型（chat / memory / summarization / UI control 各一个）

**他们原文**：
> "Assign separate models to **chat, memory, summarization, UI control**, and other tasks"

**我们现状**：模型表里已有 `ModelRole`（`SCHEDULER` / `WORKER`）+ 档位（轻量/均衡/重型），
但 **ChatPort 只是 `firstOrNull { enabled }`（最旧优先）** —— 这正是我上一轮记下的债。

★ **他们的做法直接给出了答案**：不是"给聊天选一个模型"，而是**按用途查**。
我们的 `ModelRole` 已经是雏形，**扩成按用途查即可**，不需要新概念。

**改哪里**：`ChatPort` 改成 `modelRepository().forPurpose(Purpose.CHAT)`；
用途枚举先支持 `CHAT` / `MEMORY` / `TITLE`（标题生成）。**这同时解决了选模型债。**

### 4.3 会话管理四件套（我们的侧边栏设计只覆盖了一半）

| 能力 | 我们设计稿 | 他们 |
|---|---|---|
| 列表 / 搜索 / 重命名 / 删除 | ✅ 有 | ✅ |
| **消息分支**（从某条重新开始）| ❌ **没有** | ✅ |
| **自动摘要**（长会话压缩）| ⚠️ 只在 L1 提取里隐含 | ✅ 显式 |
| **上下文上限** | ⚠️ 靠 `AssemblyInput.budgetTokens` | ✅ 显式 |
| 批量迁移 / 备份恢复 | ❌ 没有 | ✅ |
| 导出 | ❌ 没有 | ✅ |

⇒ **设计稿要补「消息分支」与「导出/备份」**。理由：
- 分支是**"试错"的基本单位**（同一个问题换种问法，不该污染原会话）
- 导出/备份是**"数据属于用户"**的兑现 —— 我们没有服务器，用户唯一的保障就是能自己拿走

### 4.4 本地模型（这是"不打扰 + 数据不出设备"的终极形态）

**他们**：MNN / llama.cpp GGUF / Ollama / LM Studio。

**我们**：只支持云端 API（BYOK）。

**为什么值得做**：我们的三条卖点（少打扰、数据不出设备、不盈利）**在本地模型上是同时成立的**：
- 不花用户的钱（没有 API 费用）
- 数据真的不出设备（连 Provider 都不需要）
- 不打扰（可以后台慢慢跑）

⚠️ **但它是大工程**（JNI + 模型分发 + 内存管理）。**不现在做，但要把它写进路线图**，
因为它可能是我们**唯一能拉开差距的方向**（Operit 做了，但那不是他们的主打；
Aries/rikkahub 没做）。

## §5 许可证：可以复用，但要注意方向

| 方向 | 合法性 | 说明 |
|---|---|---|
| Operit(LGPL-3.0) 的代码 → 我们的 GPL-3.0 项目 | ✅ **允许** | LGPL-3.0 §2 明确允许"升级"为 GPL-3.0 |
| 我们的 GPL-3.0 代码 → Operit | ⚠️ 会让那部分变成 GPL | 单向，但技术上可行 |
| 抄**思路**（架构、交互、数据模型） | ✅ 无限制 | 版权不保护思想 |

**纪律（我建议的）**：
- 复用**代码**时：文件头注明来源 + 许可证 + 改动说明
- 复用**思路**时：在文档里注明"参考了 X 的做法"（`docs/` 里已经有这个习惯）
- ⚠️ **不要整段复制他们的 Kotlin**：他们的 `app/` 单体与我们的模块边界不兼容，
  搬进来会同时破坏两边（他们依赖 ObjectBox / 大量内部类）

⇒ **结论：抄思路，不抄代码。** 不是因为法律，是因为**架构不兼容**。

## §6 战略选项（我的倾向）

### 选项 A：继续做，但**放弃功能数量竞赛**
把定位收紧成 **「一个可读、可测、可信的手机助理」**：
- 不追平台化（不碰终端/工作区/3D 形象/市场）
- 把「人格可信 + 记忆可审计 + 少打扰」做深
- 把工程纪律当作产品（可读的代码、可跑的设计文档、离线可验证）

**✅ 我倾向这个。** 理由：我们已有的资产（44 模块、1924 测试、详尽设计文档）
**只在"可读可测"这条线上有价值**；换成"功能数量"那条线，这些资产全是负担。

### 选项 B：参与 Operit（贡献上游）
优点：8,658 星的项目里留名，学到的比自研多。
缺点：我们的大部分代码用不上（架构不同），等于从零学他们的代码库。

### 选项 C：换赛道
承认这个方向已经饱和，把工程能力（模块化 + 离线验证 + 设计文档方法论）用到别处。

### ★ 我的建议：A 为主，B 为辅
- **主线走 A**：把定位写进 README 和项目方案（现在 README 的定位太宽）
- **同时做 B 的一小步**：把「离线验证器 + 模块边界检查」这套工具**开源成独立工具**
  （它对任何 Kotlin 多模块项目都有用，Operit 那种单体项目**恰恰最需要它**）
  ⇒ 这是**低成本、高辨识度**的贡献方式：不搬我们的 App，搬我们的**方法论**
