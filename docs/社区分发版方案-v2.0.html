社区分发版方案 v2.0（增补与修订）

项目：PocketAgent（手机 AI 智能体助手 · BYOK 版） 版本：v2.0 ｜ 日期：2026-09-21 前置文档：《手机AI智能体助手-项目方案-v1.0.md》《M0技术验证与工程落地手册-v1.0.md》 本文档的性质：v1.0 是在"假定上架应用商店"前提下的设计。本版因分发策略转向，对若干核心假设做了实质性修订，不是补丁。

0. 本次转向的实质影响（先读这页）

0.1 三个约束变化带来的连锁反应

变化 解锁了什么 新增了什么麻烦
不上架应用商店 ① 无障碍权限不再受商店审核约束（这是最大的收益）② 不受 Google Play 第三方 AI 集成条款约束 ③ 迭代节奏完全自主，无需等审核 ① 侧载应用的「受限设置」会拦住无障碍权限（Android 13+）② 失去商店的信任背书，用户下载前会犹豫 ③ 无商店更新机制，必须自建 ④ App 备案问题无法靠"已上架"糊过去
主要面向安卓 技术栈可以 100% 聚焦原生能力，不用为 iOS 做任何妥协 无（本来就该这样）
本体 + 插件页架构 ① 功能可无限扩展而不膨胀本体 ② 社区可以贡献适配规则，解决"App 千千万，你适配不过来"的死结 ③ 插件生态本身成为护城河 ① 插件安全模型必须设计好，否则插件就是后门 ② 插件 API 一旦发布就是兼容性负债 ③ 需要额外做插件开发工具链与文档

0.2 一句话总结这次转向

不上商店不是"少了个渠道"，而是把"审核合规"的约束换成了"信任建立"的约束。 v1.0 里最大的技术风险是"Android 17 收紧无障碍"，而转向社区分发后， 新的最大风险变成了 "用户凭什么敢把一个能读屏、能代操作、还能加载第三方插件的 APK 装到自己手机上"。

这个问题必须用产品设计正面回答，而不是靠一句"我们是开源的"。

0.3 修订后的核心策略

分发：   GitHub Releases 为主 + 网盘/群文件为辅，应用内自更新
信任：   开源 + 固定签名 + 哈希公示 + 插件能力白名单 + 快照审查工具
扩展：   三级插件机制（规则包 / JS 脚本 / 原生 APK），L1 规则包为主力
合规：   无自有服务端 + 不收费 + 不收集数据，把备案与许可证问题降到最低敞口
适配：   红米 K60 (HyperOS, 3200×1440) 作为一等公民深度优化

1. 分发与合规现实

这一章是"丑话说在前面"。绕过商店不等于绕过监管，只是把监管的抓手换了一批。

1.1 侧载应用的权限拦路虎：受限设置（Restricted Settings）

这是转向社区分发后第一个必须解决的技术问题。

Android 13 起引入「受限设置」机制：通过侧载（非商店渠道）安装的应用，默认无法被授予无障碍服务、通知监听等敏感权限。Android 14 进一步收紧。

具体表现： - 用户在「设置 → 无障碍」里找不到你的应用，或开关是灰色的 - 点击时提示"出于安全考虑，此设置当前不可用"

解除方式（必须做进引导流程）：

设置 → 应用 → 应用管理 → 找到本应用 → 右上角菜单（或"应用信息"页内）
  → 「允许受限设置」/「允许使用受限设置」 → 允许
  → 然后才能到「设置 → 更多设置 → 无障碍」中开启本应用

⚠️ 关键细节：每次通过侧载方式覆盖安装（更新）后，受限设置可能被重置， 用户需要重新授权一次。这意味着应用内自更新会导致无障碍权限失效， 必须在更新后检测并引导用户重新授权，否则用户会以为"更新完就坏了"。

产品化处理： 1. 首次启动的权限引导中，把"允许受限设置"作为独立一屏，附截图级的分步指引 2. 提供「权限自检」按钮：一键检测无障碍服务是否可用，不可用时给出当前机型的具体解除路径 3. 应用内更新完成后，主动检测无障碍服务状态，失效则弹窗引导，而不是等用户发现功能坏了 4. 更新包优先引导用户用「系统安装器」而非应用内直接安装，减少受限设置重置的概率

1.2 Android 14/15+ 侧载的其他限制

限制 影响 应对
安装来源 App 每次安装都需用户确认 更新流程变长 更新说明中提前告知，减少用户困惑
目标 SDK < 23 的 APK 无法安装 无（我们的 targetSdk 是 36） —
Android 15：Play Protect 实时行为监控 系统会扫描"屏幕读取和按键记录"类行为，本产品的核心能力正好命中这些特征，可能触发警告 ① 不申请无关权限，降低行为特征 ② 在官网/README 提供 VirusTotal 报告 ③ 明确告知用户"如果 Play Protect 提示，这是误报，原因是本应用需要读屏" ④ 考虑提供"关闭 Play Protect"的说明（但这会降低安全性，需谨慎措辞）
Android 15：静默安装被全面封杀 不能用 ADB/脚本自动装更新 更新必须用户手动确认，接受这个流程
Android 15+：安装来源 App 需来自可信来源 用户用第三方文件管理器可能装不上 引导用户用系统自带的文件管理器

⚠️ Play Protect 这一条要高度重视。本产品的行为特征（读屏 + 模拟点击 + 后台常驻） 与银行木马高度相似。国内 ROM 的"安全中心"也可能拦截。建议： 主动去各家安全中心做误报申诉，并在社区维护一份"误报处理指南"。

1.3 App 备案：绕不开但敞口可控

法律现实（工信部《关于开展移动互联网应用程序备案工作的通知》，2023-07）：

  • 在境内从事互联网信息服务的 App 主办者，须向省级通信管理局履行备案手续
  • 2024-07 起转入常态化执法，对未备案 App 采取"先通报、后下架、再处罚"的处置链条
  • 备案号格式：京ICP备2023111111号-1A（App 后缀是 -1A，网站是 -1）
  • 备案绑定的是「应用名称 + 包名 + 签名」

执法抓手在哪（这决定了实际风险敞口）：

抓手 对本项目是否适用
应用市场下架 ❌ 不适用（不上架）
接入服务商拦截域名 ❌ 不适用（无自有服务端、无域名）
智能终端厂商配合治理 ⚠️ 部分适用（国内 ROM 的安全中心可能配合）
分发平台配合 ⚠️ 部分适用（网盘、论坛可能被要求配合清理）
传播渠道（群组、论坛） ⚠️ 适用（平台方可能被要求处理）

结论与建议：

  1. 架构上继续坚持"无自有服务端"，这不仅是成本与合规优势，也直接消除了最主要的执法抓手（域名拦截）
  2. 不做经营性收费（无会员、无内购、无广告变现），避免触发 ICP/EDI 许可证要求
  3. 不收集用户数据（不建账号体系、不做云端同步），降低个人信息保护合规压力
  4. 但必须承认：法律上备案义务仍然存在，只是执法概率与强度较低。 这是需要用户自行决策并咨询律师的风险点，本文档不构成法律意见
  5. 准备一条"随时可合规"的路径：如果项目规模扩大或开始收费，能立刻补办备案 （需准备：主体资质、包名与签名固定、服务信息说明）

诚实提示：如果你的目标只是小范围社区传播、不收费、无自有服务器，备案的实际风险敞口不大。 但一旦要"做大"，备案就是必须补的第一课。别抱着"永远不备案"的侥幸做产品规划。

2.3 新增功能详细定义

F-01 插件页（独立页面）

App 内的独立一级入口，承担插件的全生命周期管理。详见第 3、4 章。

F-02 权限引导与自检向导

因为要面对侧载 + 受限设置 + HyperOS 的三重门槛，这套引导必须是产品级的：

  • 分机型定制路径：检测到小米/HyperOS 就走小米的指引，华为走华为的
  • 截图级步骤：每一步都配真实截图（不能只有文字）
  • 逐步校验：每完成一步自动检测是否生效，不生效就停在那一步
  • 一键跳转：能通过 Intent 直达的设置页就直接跳，减少用户找路径的成本
  • 失败兜底：提供"手动排查"清单

F-03 快照审查工具

让用户能看懂屏幕的节点树，从而写出自己的规则：

  • 悬浮窗触发 → 冻结当前界面 → 展示节点树（含 vid、text、层级、clickable）
  • 点击节点可高亮其在屏幕上的位置
  • 一键生成规则片段（复制到剪贴板）
  • 导出快照为 JSON（用于提交 issue 或分享）

这个工具是插件生态的入口。没有它，用户写不出规则，插件机制就是空中楼阁。 GKD 的规则生态之所以能起来，快照审查工具是关键基础设施。

F-04 应用内自更新

无商店环境下的更新方案（不依赖自有服务端）：

启动/定时
   ↓
请求 GitHub Releases API（或订阅源中的版本清单）
   ↓
比对 versionCode
   ↓
有新版本 → 展示更新说明 + 下载链接 + 文件哈希
   ↓
用户下载 APK → 校验哈希 → 调用系统安装器
   ↓
安装完成 → 检测无障碍服务状态 → 失效则引导重新授权

关键设计： - 支持多渠道更新源（GitHub / 自建静态 JSON / 网盘直链），任一可用即可 - 必须校验哈希，并在 UI 上展示，让用户能自己核对 - 提供"跳过此版本"选项，避免打扰 - 更新前提示："更新后可能需要重新授予无障碍权限"

F-05 配置与规则的分享

社区传播的天然载体：

  • 导出单个规则包为 .pagent 文件（本质是签名过的 JSON）
  • 生成分享链接（如果规则托管在 GitHub 上）
  • 导入时校验签名与来源
  • 分享内容是规则，不是 Key（Key 永不出设备）

3. 本体与插件页的职责边界

这是 v2.0 最重要的架构设计。边界划错了，后期会陷入"插件能做什么、本体该不该做"的无尽争论。

3.1 一句话原则

本体提供「能力」，插件提供「意图」。 本体负责"能看见、能操作、能调用模型、能保证安全"； 插件负责"在什么场景下、按什么条件、做什么"。

3.2 职责划分表

能力 本体 插件 说明
API Key 管理与加解密 ✅ ❌ 安全红线，插件永不接触 Key 明文
模型调用（LLM） ✅ 通过能力代理 插件只能请求"用模型做某事"，不能直接拿 Key
屏幕感知（节点树/截图/OCR） ✅ 通过能力代理 插件拿到的是归一化后的数据，不是原始 AccessibilityNodeInfo
动作执行（四通道） ✅ 通过能力代理 插件不能直接调用 AccessibilityService
敏感页面拦截 ✅ ❌ 本体强制，插件无法绕过
任务编排（Agent 多步规划） ✅ 可调用 插件可请求本体执行一个子任务
记忆存储 ✅ 通过能力代理 插件有独立沙箱存储
插件加载与生命周期 ✅ ❌
插件权限校验 ✅ ❌
插件 UI 渲染 ✅ 提供 schema 插件声明 UI，本体渲染（避免动态代码加载 UI）
具体场景的规则/逻辑 ❌ ✅ 这是插件的核心价值
第三方 App 的适配 ❌ ✅ 千千万万个 App，本体不可能都适配
插件自身的配置界面 渲染 定义
数据加工/格式转换 ❌ ✅
自定义工作流 ❌ ✅

3.3 硬性边界（不可逾越）

边界 理由
❌ 插件永远无法读取 API Key 明文 Key 泄漏是产品死线。插件只能通过本体代理发起模型调用
❌ 插件无法绕过 SafetyGuard 敏感页面规则本体强制执行，插件的动作请求也要过一遍
❌ 插件无法修改本体行为 只能通过公开的 API 调用，不能 hook / 反射本体
❌ 插件不能访问其他插件的数据 每个插件独立沙箱存储
❌ 插件不能申请 payment.* 类能力 该能力类别不开放
❌ 插件不能常驻后台（L1/L2） 插件由本体按需加载，生命周期由本体管理
⚠️ L3 原生插件可以有自己的后台组件，但必须显式声明并被用户批准

3.4 插件页的界面结构

插件页（一级入口）

4. 插件拓展机制

4.1 三级插件体系

参考 GKD 的成功经验：规则包（声明式）是主力，脚本是进阶，原生是长尾。 不要把"插件"设计成只有一种形态，那样要么太弱（不够用）要么太危险（不敢用）。

级别 形态 能力边界 安全模型 开发门槛 预期占比
L1 规则包 JSON/YAML 声明式 页面匹配 + 条件判断 + 动作序列 纯声明，无代码执行 低（会用快照工具即可） 80%
L2 脚本插件 JavaScript（QuickJS 沙箱） L1 能力 + 逻辑运算 + 循环 + 数据加工 + 调用本体 API 沙箱 + 能力白名单 + 执行超时 + 内存上限 中（需会 JS） 18%
L3 原生插件 独立 APK 完整 Android 能力 + 自定义 UI + 后台组件 签名白名单 + 用户逐项授权 + 权限清单审查 高（需 Android 开发） 2%

为什么主力是 L1？

因为社区贡献的门槛决定了生态的规模。GKD 的规则生态之所以能起来，就是因为写一条规则不需要会编程——用快照工具看一眼节点树，写几行 JSON 就行。L2/L3 是给开发者的，L1 是给所有人的。

4.3 L2 脚本插件规范

运行时选型：QuickJS（推荐，体积小、启动快、可设内存与超时限制）或 Rhino（GKD 的选择，生态成熟）。

沙箱约束：

// 插件可用的全局 API（其余一律不可见）
declare const agent: {
  // 感知
  getSnapshot(): Snapshot;
  findNodes(selector: string): Node[];

  // 动作
  click(selector: string | {x: number, y: number}): Promise<void>;
  inputText(text: string): Promise<void>;
  scroll(direction: string, distance?: number): Promise<void>;

  // 模型（经本体代理，插件拿不到 Key）
  llm(prompt: string, opts?: {model?: string}): Promise<string>;

  // 存储（插件独立沙箱）
  store: {
    get(key: string): string | null;
    set(key: string, value: string): void;
  };

  // 工具
  log(msg: string): void;
  sleep(ms: number): Promise<void>;
};

// ❌ 不可用：require / import / fetch / XMLHttpRequest /
//    Java / Packages / 文件系统 / 其他插件的数据

4.4 L3 原生插件规范

发现机制：通过 PackageManager 查询声明了特定 action 的 APK：

<intent-filter>
    <action android:name="com.pocketagent.plugin.BIND" />
</intent-filter>
<meta-data android:name="pocketagent.plugin.api" android:value="1" />

通信方式：AIDL 接口（跨进程），插件在自己的进程中运行。

安全要求： 1. 签名白名单：本体维护一份可信签名指纹列表，未签名的插件不加载 2. 能力清单审查：安装前展示插件声明的所有能力，用户逐项批准 3. 权限隔离：插件无法访问本体的 Key 存储与数据库 4. 可撤销：用户随时可撤销已授予的能力

⚠️ L3 是双刃剑。它给了插件完整能力，也给了恶意插件完整的攻击面。 建议：M1-M3 阶段先不做 L3，只做 L1 + L2。等社区信任建立、有真实的 L3 需求时再开放。

能力 说明 风险级 需二次确认
screen.read 读取当前界面的节点树 高 ✅
screen.capture 截取屏幕 极高 ✅
action.click 点击元素 高 ✅
action.input 输入文本 高 ✅
action.gesture 滑动/长按等手势 中 ✅
app.launch 打开指定应用 低
notification.post 发送通知 低
notification.read 读取通知 高 ✅
clipboard.read 读剪贴板 高 ✅

设计要点： - 能力用用户能看懂的话展示，而不是技术名词 - ❌ "请求 screen.capture 能力" - ✅ "这个插件可以截取你的屏幕" - llm.call 必须提示"会消耗你的 API 额度" - 所有能力的授予都记入本地审计日志

4.6 订阅机制（去中心化）

不建自有服务端的原则在插件分发上同样适用。用 GitHub 作为基础设施。

订阅源格式（一个静态 JSON 文件，托管在 GitHub Pages / raw / 任意静态托管）：

{
  "name": "某某的规则集",
  "author": "xxx",
  "updatedAt": "2026-09-21T10:00:00Z",
  "apiVersion": 1,
  "plugins": [
    {
      "id": "community.wechat.auto-reply",
      "name": "微信消息速回",
      "version": "1.0.3",
      "level": "L1",
      "capabilities": ["screen.read", "action.click"],
      "targetApps": ["com.tencent.mm"],
      "downloadUrl": "https://raw.githubusercontent.com/.../wechat.json",
      "sha256": "a1b2c3...",
      "signature": "MEUCIQ..."
    }
  ]
}

关键机制： 1. 哈希校验：下载后必须校验 SHA-256，不匹配则拒绝加载 2. 签名校验：插件作者用私钥签名，本体用作者公钥验签（防止中间人篡改） 3. 更新策略：手动检查 / 启动时检查 / 定时检查（用户可选） 4. 多源共存：支持多个订阅源，同 ID 插件按优先级取版本 5. 冲突解决：同一 App 有多个插件时，按优先级顺序执行，UI 上可视化冲突 6. 社区聚合：用 GitHub Topic（如 pocketagent-plugin）聚合第三方订阅源，本体内置一个"社区源列表"（可关闭）

订阅源的信任模型： - 订阅源本身不能获得任何权限，它只是插件清单的索引 - 每个插件的权限仍然逐个向用户申请 - 用户可以只看清单不安装，也可以只装其中某一个

5. 社区传播与发布策略

5.1 信任建立（第一优先级）

没有商店背书，信任必须靠工程手段建立，不能只靠"我们是好人"。

手段 具体做法 为什么有效
开源 采用 GPL-3.0（与 GKD 一致，防止闭源套壳）或 Apache-2.0（更宽松，利于生态） 代码可审计，社区可验证
固定签名 生成一次签名密钥，永不更换，公钥指纹公示在官网与仓库首页 用户可验证安装的包是官方版本
哈希公示 每个 Release 附 SHA-256，官网页可核对 防篡改
VirusTotal 报告 每次发布附扫描链接 应对"是不是病毒"的质疑
误报说明 专门一页说明"为什么安全软件会报毒"，附申诉进度 主动处理，不等用户来问
权限透明 App 内"权限使用说明"页 + 审计日志 用户可自查
隐私承诺 明确"无账号、无云端、数据不出设备"，并在代码中可验证 可信度最高的承诺是"我没能力作恶"
使用边界 README 明确禁止的用法（抢红包/刷单/游戏辅助） 主动切割灰产

5.2 分发渠道矩阵

渠道 用途 优点 风险
GitHub Releases 主发布渠道 稳定、可追溯、自带哈希 国内访问不稳定，需备镜像
GitHub Pages 官网 + 更新源 JSON 免费、无需服务器 同上
网盘（蓝奏云等） 国内备选下载 国内速度快 可能被清理，需多备份
私域群文件 直接触达 转化率高 群可能被封
论坛/社区帖 引流 长尾流量 可能被删帖
应用内分享 用户带用户 传播成本最低 需设计好分享内容

分发原则： 1. 不依赖单一渠道，任何渠道失效都不影响其他渠道 2. 所有渠道的包哈希一致，用户可交叉验证 3. 每个渠道独立渠道号，用于统计转化

5.3 渠道号与统计（隐私友好）

// 构建时注入，不联网上报，仅本地记录
buildConfigField("String", "CHANNEL", "\"github\"")

统计原则（避免触碰隐私红线）： - ❌ 不做设备指纹 - ❌ 不上报用户行为到自有服务器 - ✅ 渠道号随 APK 打包，本地记录 - ✅ 用户主动选择是否分享匿名统计（默认关闭） - ✅ 可选：使用开源的自托管统计（如 Umami），但默认不启用

说句实话：社区分发 + 不收集数据，意味着你很难做数据驱动的运营。 这是代价，要接受。用社区反馈（issue、群讨论）替代数据看板。

6. 红米 K60 适配与优化要点

6.1 设备规格与影响

项 规格 对开发的影响
处理器 骁龙 8+ Gen 1 ✅ 性能充足，端侧小模型推理可行（NPU 可用）

6.2 HyperOS / MIUI 权限配置清单 ★必做

这是本机型（以及所有小米系设备）能不能用的关键。 必须做进引导流程：

3 无障碍服务 设置 → 更多设置 → 无障碍 → 已下载的应用 → 本应用 → 开启 核心能力 关
4 悬浮窗权限 设置 → 应用 → 应用管理 → 本应用 → 权限管理 → 显示悬浮窗 悬浮球 关
5 后台弹出界面 设置 → 应用 → 应用管理 → 本应用 → 权限管理 → 后台弹出界面 MIUI 特有，不开则悬浮窗/Activity 无法从后台弹出 关
6 自启动 设置 → 应用 → 应用管理 → 本应用 → 自启动 开机后服务能起来 关
7 省电策略 设置 → 应用 → 应用管理 → 本应用 → 省电策略 → 无限制 防止后台被杀 智能省电
8 锁屏显示 设置 → 应用 → 应用管理 → 本应用 → 权限管理 → 锁屏显示 锁屏时悬浮球可见 关
9 通知权限 设置 → 应用 → 应用管理 → 本应用 → 通知管理 → 允许通知 前台服务常驻通知 开
10 电池优化白名单 设置 → 应用 → 特殊应用权限 → 电池优化 → 本应用 → 不优化 辅助保活 优化
11 最近任务锁定 最近任务界面 → 下拉应用卡片 → 加锁 防止一键清理杀掉 未锁

│   ├── 为什么要这个（大白话）
│   ├── 截图级步骤（真实截图，不是文字描述）
│   ├── [一键跳转] 按钮（能直达就直达）
│   └── 状态检测（自动判断是否已生效）
└── 完成后 → 权限自检页，可随时复查

技术实现要点：

// 部分设置可以用 Intent 直达
// 无障碍设置

6.3 2K 屏的截图成本优化 ★关键

问题：K60 的屏幕是 3200×1440。原生截图直接送多模态模型，token 消耗会非常可观。

计算示例（以常见的视觉 token 计算方式估算）：

处理方式 分辨率 估算 token 相对成本
原图直送 3200×1440 ~2800 100%
缩放到 1920×864 1920×864 ~1100 39%
缩放到 1280×576 1280×576 ~520 19%
1280 + WebP q75 1280×576 ~520（+体积更小） 19%
只截变化区域（半屏） ~1280×288 ~280 10%

推荐策略（写入 CaptureOptions 默认值）：

// 针对 2K 屏的默认参数
CaptureOptions(
    maxScreenshotEdge = 1280,      // 长边缩放到 1280
    screenshotQuality = 75,        // WebP 质量
    enableOcr = false,             // 按需开启
)

但要注意：缩放到 1280 后，小字和密集控件的识别准确率会下降。所以：

  1. 优先用无障碍树（K60 的树信息质量好，这是最省钱的路径）
  2. 只在树不可用时截图
  3. 截图时优先"区域裁剪"：只截当前操作相关的区域，而非全屏
  4. 建立准确率-成本曲线：EX-06 实验必须在 K60 上跑，找到准确率下降 < 5% 的最小分辨率

6.4 HyperOS 特有行为适配

行为 说明 应对
应用行为记录 HyperOS 会记录并展示应用的敏感行为（读屏、后台唤起等） ① 这是好事，说明行为透明 ② 在引导中主动解释"你会看到我的读屏记录，这是正常的" ③ 不要试图隐藏行为
权限使用提醒 长期后台运行会弹"应用正在后台运行"提醒 引导用户选择"不再提醒"
内存清理 一键清理会杀掉后台服务 引导用户锁定最近任务卡片
无障碍服务被系统关闭 系统更新或长时间不用可能自动关闭 ① 前台服务常驻 + 通知栏提示 ② 启动时自检 ③ 提供"服务已断开"的明显提示
多用户/分身 MIUI 的应用双开可能与无障碍服务冲突 明确不支持双开环境，检测到则提示

6.5 性能优化要点（针对骁龙 8+ Gen 1）

项 优化手段
无障碍事件处理 节流到 100ms，避免高频回调耗电
节点树遍历 300ms 超时 + 只遍历可见节点 + 结果缓存
截图 复用 ImageReader 的 Buffer，避免频繁分配
端侧模型 利用 Hexagon NPU（通过 QNN delegate），而非纯 CPU
内存 截图 Bitmap 用 RGB_565 或及时 recycle，避免 OOM
手势执行 与 120Hz 刷新率配合，滑动用贝塞尔曲线而非直线

7.3 关键依赖约束（新增）

  • :plugin:* 不得直接依赖 :perception / :action，只能依赖 :plugin:api 暴露的能力接口
  • :plugin:runtime 是唯一能触达平台层的插件模块，且必须经过能力代理与 SafetyGuard
  • :plugin:api 零 Android 依赖，保证插件作者可在纯 JVM 环境开发与测试
  • 插件永远无法依赖 :core:crypto 或 :keymgmt

8.3 M0 新增验证实验

EX-13 侧载应用的受限设置解除流程验证 ★关键

项 内容
假设 在红米 K60（HyperOS）上，能通过清晰的引导让用户成功解除受限设置并开启无障碍
方法 ① 侧载安装 APK ② 尝试直接开无障碍，记录系统提示 ③ 走"允许受限设置"流程，记录每一步的实际路径 ④ 记录截图 ⑤ 覆盖安装后再次检测，确认权限是否被重置 ⑥ 统计整个流程的步骤数与耗时
通过标准 找到完整可行的解除路径；覆盖安装后的权限重置行为有明确结论；整个流程 ≤ 6 步
失败预案 若无法解除，则整个产品形态在 Android 13+ 侧载场景下不成立，必须重新评估（可能只能靠 Shizuku 通道）
产出 《小米/HyperOS 权限配置指南》（含截图）+ 引导流程设计

⚠️ 这是 v2.0 新增的最高优先级实验。 v1.0 假定无障碍权限能正常获取， 但那是基于商店安装的假设。侧载场景下这一步完全可能走不通。

EX-14 K60 2K 屏截图成本与准确率基线 ★关键

项 内容
假设 在 3200×1440 屏幕上，缩放到 1280 长边后元素定位准确率下降不超过 5%
方法 在 K60 上采集 20 个典型界面，分别用 5 种分辨率/压缩组合送模型，对比 token 数与定位准确率
通过标准 找到「token 降至 25% 以下且准确率下降 ≤ 5%」的参数组合
失败预案 若缩放到 1280 准确率掉太多，则改为"区域裁剪 + 高分辨率"，或强制走无障碍树路径
产出 K60 专用的截图参数标准（写入默认 CaptureOptions）

EX-15 HyperOS 后台保活验证

项 内容
假设 完成 11 项权限配置后，悬浮窗与前台服务能稳定存活
方法 按 6.2 清单逐项配置后，测试：① 切后台 1 小时 ② 锁屏 4 小时 ③ 一键清理内存 ④ 重启手机 ⑤ 系统更新后
通过标准 悬浮窗存活率 ≥ 95%（除用户主动清理）
产出 《HyperOS 保活配置清单》+ 自检工具
