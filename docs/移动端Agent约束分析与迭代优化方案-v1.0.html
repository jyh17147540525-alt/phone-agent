移动端 Agent 约束分析与迭代优化方案

版本 v1.0 ｜ 2026-09-21 ｜ 状态：方案稿（待评审）

前置文档： - docs/豆包手机智能体考察与dsh移植可行性研讨-v1.0.md（下称"研讨文档"） - docs/BYOK模型接入与dsh代理设计-v1.0.md（下称"BYOK 文档"） - docs/M0技术验证与工程落地手册-v1.0.md（下称"M0 手册"）

本文的立场：把 PocketAgent 从「桌面 agent 的手机移植版」重新定义为「移动端原生 agent」。 这个转向不是修辞，它改变了架构取舍的优先级。

0. 结论速览

三条必须最先接受的结论：

① 现有方案缺的不是细节，是一个视角 —— 它默认"手机是小一号的电脑"。

通读四份既有文档，约束被当成待处理的麻烦（11 项权限配置、保活策略、 耗电 ≤3%/天），而不是设计的出发点。这导致几个关键取舍被做反了： 比如感知层被设计成"能截图就截图"，而移动端的第一原则应该是"能不感知就不感知"。

② 移动端 agent 的真正瓶颈不是算力，是「轮次」。

手机 SoC 已经很强（K60 是骁龙 8+ Gen 1），单次截图/推理都不慢。 但 agent 循环的每一步都要截图 + 上传 + 推理，能耗与流量随轮次线性增长。 一次 8 轮的任务约耗 0.07% 电量；失控到 30 轮就是 0.27%。 所以省电的第一手段不是"优化单步"，而是"减少轮次"—— 这需要 AgentBudget（轮次预算）成为一等公民，而不是事后优化项。

③ 最大的实现缺口是感知层与执行层，而它们恰好是移动端最难的部分。

实测模块盘点（附录 A）：perception 与 action 各只有 1 个文件， agent 也只有 1 个。而 17 个模块完全空壳，包括 keymgmt（BYOK 闭环） 与 plugin/runtime（插件体系运行时）。 "方案完备度"与"实现完备度"之间存在巨大落差 —— 这本身就是最大的风险。

第一部分 · 现有方案的不足（量化）

📌 这不是"进度慢"的问题，而是风险结构的问题： 有测试的模块（插件 API、Provider、安全）都是纯逻辑、易验证的部分； 没有测试的模块（感知、执行、agent 循环）都是强依赖真机、难验证的部分。 风险最高的地方验证最薄。

1.2 七个结构性不足

N1 · 移动端约束没有系统性建模

现有文档里关于移动端的约束散落在四处：v2.0 的 11 项权限配置、 M0 手册的保活实验、v3.0 的虚拟屏实验、项目方案的"耗电 ≤3%/天"。 没有一处把它们当作设计输入统一建模。

后果：约束是事后补救的（"跑起来发现耗电高再优化"），而不是前置约束的 （"给定耗电预算，反推感知频率上限"）。

N2 · "移植思维"压倒"移动端原生思维"

研讨文档的路线 C（dsh 为脑 + Android 为能力端）本质是移植方案： 把一个桌面 agent 框架搬过来，再给它接上手机的手脚。

移植方案的系统性偏差：它会保留桌面框架的隐含假设 —— 长会话、充裕内存、稳定后台、不计能耗、任务可以慢慢做。 这些假设在手机上全部不成立。

N3 · 感知层被设计成"能感知就感知"，方向反了

研讨文档 §3.3 的能力映射表里，screen_read 和 screen_capture 是并列的两个核心能力。 但移动端的第一原则应该是：能不感知就不感知。

理由： - 每次感知 = 一次截图/树遍历 = 能耗 + 时间 + 隐私暴露面 - 很多步骤不需要看屏幕就能完成（如"打开设置"→ 直接 am start，不用看） - 树可用时优先用树是对的，但"这一步是否需要感知"这个决策本身缺失了

N4 · 没有任何能耗、稳定性、长时运行的验证设计

M0 手册的实验清单（EX-01~EX-12）覆盖了功能可用性，但能耗测试是空白。 EX-12 测"保活"、EX-15 测"后台存活"，都是能不能活，不是活得多贵。

缺失的验证维度： - 单次任务的能耗（mAh 或 %） - 常驻时的静态功耗 - 连续 7 天的内存增长趋势（泄漏） - 弱网/断网下的行为 - 长时间运行的稳定性

N5 · 18 个实验全部未执行，而其中 3 个是决定性的

EX-01 ~ EX-18 全部停留在文档阶段。其中三个是决定产品形态的：

实验 决定什么
EX-16 虚拟屏能否实现 → "不影响用户使用"是否成立
EX-13 侧载能否拿到无障碍 → 整个产品形态是否成立
P0（Node 20+） 路线 C 是否成立

在三个决定性实验都没做的情况下继续深化方案，是在给一个可能不存在的地基画装修图。

N6 · 缺少"随时被打断"的设计

手机场景下，任务被打断是常态而非异常：来电、切应用、锁屏、系统杀进程、 用户主动放弃。现有方案没有任何任务状态持久化与恢复的设计。

对比：桌面 agent 被打断的代价是"重跑一次"，移动端被打断的代价是 "App 被杀了，任务做到一半，用户不知道现在是什么状态" —— 更糟的是， agent 可能已经执行了部分写操作（发了一条消息、下了一个订单）。

N7 · 没有"任务幂等性"设计

接 N6：如果任务在中途恢复，如何避免重复执行已完成的步骤？ 现有方案没有 checkpoint / 幂等键 / 回滚机制的概念。

第二部分 · 移动端 Agent 的六类硬约束

本章是全文的设计依据。每类约束给出：与桌面的差异 → 具体量化 → 对架构的强制要求。

2.1 权限约束

桌面 agent 移动端 agent
文件系统 完整读写 沙箱 + Scoped Storage
进程控制 任意 仅自己
输入注入 合成事件 API 需无障碍或 Shizuku
屏幕读取 任意截图 需 MediaProjection 或无障碍
授权方式 安装时一次 逐项、运行时、可随时撤销
政策风险 低 高且持续收紧（Android 17 APM）

硬数字：需要 5–7 项运行时权限 + 3 项特殊权限（无障碍、悬浮窗、通知监听）， 外加 HyperOS 的 11 项系统配置。任一项缺失，功能就残缺。

不可得性（研讨文档已论证）：READ_FRAME_BUFFER / INJECT_EVENTS / headless 虚拟屏三者依赖系统签名预装，第三方侧载应用物理上拿不到。

对架构的强制要求 1. 权限必须可降级 —— 不能假设"用户会全部授权"，每一档权限组合都要有可用形态 2. 权限状态要可自检 —— 启动时检测，缺失时给出可操作的修复指引 3. 不得依赖任何不可得权限 —— 这条已经写进架构原则，但要持续审计

2.2 资源约束

资源 桌面 移动端 PocketAgent 预算
内存 32GB 随便用 12GB 与系统+其他 App 分 App 常驻 ≤ 150MB，任务期峰值 ≤ 400MB（建议值）
存储 充裕 128–512GB 且用户敏感 APK ≤ 130MB + 数据 ≤ 200MB
CPU 不关心 强但跑满会烫 单核占用避免长时间 >50%
内存回收 手动 LMK 随时杀 必须能承受随时被回收

参考量级：豆包手机助手的 aikernel 进程常驻约 160MB （研讨文档 §1.6，第三方逆向分析）。

PocketAgent 的内存账（路线 C，估算）：

组件 估算
Android App 本体（Compose UI + 服务） 80–120 MB
Node 运行时（单 ABI） 30–40 MB
dsh 裁剪后 profile（JS 堆） 40–70 MB
合计常驻 150–230 MB

⚠️ 这个数字值得警惕。 如果 Node 与 dsh 常驻， 内存占用会超过豆包的 aikernel，且是在用户手机上常驻。 这直接支持 D-J 的结论：Node 进程应当"任务期间才启动"，而非常驻。 但"按需启动"又会带来启动延迟（Node 冷启动 + dsh 加载 profile 可能要 1–3 秒）， 这是体验与资源的直接冲突，需要一个折中（见 §4.2 P2-1）。

2.3 后台运行约束

机制 影响
Doze / App Standby 息屏后网络与唤醒被延迟
后台执行限制 后台服务被限制，需前台服务
前台服务类型限制（Android 14+） 必须声明类型并符合用途，否则启动失败
国产 ROM 额外管控 HyperOS 需 11 项配置；且系统更新可能重置
LMK 低内存杀进程 任何时候可能被杀

关键结构性问题：Node 进程是 App 的子进程。 App 被系统杀掉，Node 必然一起死 —— 无法通过"让 Node 独立保活"绕过。

且：无障碍服务被系统关闭（长时间不用/系统更新）时， agent 会静默失效 —— 用户不知道它已经不能工作了。

对架构的强制要求 1. 状态必须落盘 —— 假设进程随时会死，所有关键状态持久化 2. 启动时全量自检 —— 权限、服务、Node 可用性逐项检测并可视化 3. 失效要显性 —— 不能静默降级，必须让用户看见 4. 保活策略分级 —— 常驻（任务期）/ 按需（空闲）两档，不要一味追求"永不被杀"

2.4 能耗约束

现有指标：项目方案 M3 验收写"后台耗电 ≤ 3%/天"。这个指标不足以约束 agent 行为 —— 它只管"待机"，不管"干活"。

单次任务的能耗构成（估算，方法见附录 A）

假设一次 8 轮的任务，K60（5500mAh / 3.87V ≈ 21.3Wh ≈ 76,700J）：

环节 单轮耗时 估算功耗 单轮能耗
截图 + 编码（2K） ~150 ms 1–2 W ~0.3 J
图片上传（~200KB） ~0.5 s ~1.5 W ~0.75 J
等待云端推理（屏幕亮 + 网络保持） ~3 s ~2 W ~6 J
单轮合计 ~7 J

推论：

轮次 单次任务能耗 占电池 每天 20 次
5 轮 ~35 J 0.05% 0.9%
8 轮 ~56 J 0.07% 1.5%
15 轮 ~105 J 0.14% 2.7%
30 轮（失控） ~210 J 0.27% 5.5%

⚠️ 这是估算不是实测，但量级足以支撑一个关键判断： 能耗几乎完全由"轮次"决定，而非单步优化。 把单步截图优化 20% 只省 0.06J/轮；而把 30 轮压到 8 轮，省 154J —— 差三个数量级。

另一个大头：常驻功耗。 前台服务 + 无障碍监听 + （若常驻的）Node 进程， 会持续拉高待机功耗。这比单次任务更容易失控，因为它是 24 小时持续的。

对架构的强制要求 1. AgentBudget 是一等公民 —— 轮次上限、时长上限、能耗上限，超限主动中止 2. 减少轮次优先于优化单步 —— 合并步骤、批量操作、避免无谓感知 3. 任务期与空闲期分离 —— 空闲时 Node 不运行，无障碍事件降到最低 4. 能耗必须可测 —— 没有度量就没有优化（见 §5.2）

2.5 隐私约束

数据类型 敏感度 现有措施 缺口
API Key 极高 Keystore + AES-GCM，永不落明文 路线 C 的跨进程问题（BYOK 文档已解）
屏幕内容 极高 支付页面停止、不落盘 无数据最小化设计
短信/通讯录/相册 高 未涉及 —
剪贴板 高 导入 Key 后清空 其他场景未处理
通知内容 中 未涉及 —
使用记录/任务历史 中 本地存储 未定义保留策略

核心洞察：屏幕内容是移动端 agent 独有的、也是最大的隐私暴露面。

它同时包含：用户当时在做什么、和谁聊天、余额多少、住址、健康信息…… 而 agent 的设计要求是"频繁读取它"。 这两者天然冲突。

现有方案的不足： - 只做了"不做什么"（支付页面停止），没做"少做什么"（数据最小化） - 截图上传给云端模型时没有裁剪/降质/脱敏 —— 全屏原图直接发出去 - 没有"上传内容告知"机制 —— 用户不知道到底传了什么

对架构的强制要求 1. 数据最小化：上传前裁剪到相关区域、降质、必要时 OCR 后只传文本 2. 敏感区域本地遮蔽：状态栏（含通知）、输入框（可能含密码）本地涂黑 3. 可审计：用户能查看"最近上传了什么"（本地保留，不上报） 4. 默认不上传：能本地判断的不上云

2.6 网络与交互约束

桌面 移动端
网络 稳定宽带有线 4G/5G/WiFi 切换、弱网、地铁隧道
流量 不限 用户敏感（尤其非 WiFi）
交互 键鼠、大屏、可长时间专注 触屏、小屏、碎片时间、随时离开
任务节奏 一次做完 被打断后要能接着做

流量账：每轮上传 ~200KB，8 轮 ≈ 1.6MB/任务。 每天 20 次 ≈ 32MB/天 ≈ 1GB/月（仅上传，不含返回）。 在非 WiFi 环境下这是用户可感知的消耗，应提供"仅 WiFi 下执行重任务"的选项。

对架构的强制要求 1. 网络感知的任务调度 —— 弱网时降级（少截图、只传文本） 2. 流量预算与提示 —— 非 WiFi 下提示或限制 3. 输出适配小屏 —— 长文本要折叠、摘要优先 4. 中断友好 —— 见 N6 / N7

2.7 约束汇总：与桌面的本质差异

维度 桌面 agent 移动端专属 agent 架构含义
任务时长 分钟–小时 秒–分钟 不需要长会话优化，需要快速收敛
中断频率 低 极高 必须可恢复
内存 充裕 紧张 Node/dsh 不能常驻
能耗 不关心 核心指标 轮次预算制
网络 稳定 不稳定 分级降质
交互 键鼠大屏 触屏小屏 语音优先、输出精简
隐私面 文件 全部数字生活 数据最小化
失败代价 重试即可 可能误操作真实账号 幂等 + 确认
权限 一次授权 逐项、可撤销、政策收紧 全链路可降级

第三部分 · 什么是「移动端专属 Agent」

3.1 七条设计原则

从 §2 的约束反推出来的，不是从桌面 agent 抄来的。

原则 1 · 轮次预算制（最重要）

每个任务有明确的轮次上限（默认 8，可配），到达上限时： 不是"继续硬跑"，而是主动停下、报告进度、交还用户。

理由：能耗 ≈ 轮次 × 单轮成本（§2.4），轮次是唯一的一阶杠杆。

原则 2 · 可中断可恢复

任务状态在每一步之后持久化（checkpoint）。任何时刻被杀， 重启后能报告"做到哪了"并选择继续或放弃。

理由：手机上被打断是常态（§2.3 / §2.6）。

原则 3 · 感知降级阶梯

按代价从低到高排列，能用低档就不用高档：

第 0 档  不感知      —— 直接执行（如"打开设置"用 am start）
第 1 档  无障碍树    —— 结构化、便宜、无隐私图像
第 2 档  树 + 局部截图 —— 只截相关区域
第 3 档  全屏截图（降质）—— 树不可用时
第 4 档  全屏截图（原质）—— 兜底

关键：第 0 档的存在。 现有方案默认"总是要看屏幕"， 但很多步骤根本不需要 —— 这是最大的优化空间。

原则 4 · 本地优先判断

能用规则/小模型在本地判断的，不上云。 例：判断"当前页面是否是支付页面"应该是本地规则，不是问模型。

理由：省钱、省电、省流量、少隐私暴露。

原则 5 · 权限最小化 + 运行时降级

从"能不用就不用"出发，而非"能拿到就都拿"。 每一档权限组合都要有可用形态（见 §2.1）。

原则 6 · 数据最小化

上传给模型的内容应当是完成任务所必需的最小子集： 裁剪、降质、遮蔽敏感区域、必要时先本地 OCR 转文本。

原则 7 · 写操作幂等 + 确认

任何改变真实世界的操作（发消息、下单、转账）必须： - 有幂等键，避免恢复时重复执行 - 高风险的强制用户确认 - 支付环节永久放弃（既有原则，保持不变）

3.2 架构调整（相对路线 C）

在研讨文档的 L0–L4 之上，新增五个横切组件：

├─────────────────────────────────────────────────────────────┤

│     PerceptionLadder（感知降级阶梯）★新增                     │

新组件 职责 为什么必须是独立组件

A.2 能耗估算方法（§2.4 的依据）

方法：自下而上估算，非实测。

  1. 电池能量：K60 5500mAh × 3.87V（标称）≈ 21.3 Wh ≈ 76,700 J
  2. 单轮各环节耗时：取保守估计（截图 150ms / 上传 0.5s / 等待推理 3s）
  3. 功耗取值：截图与编码按 1–2W，网络按 1.5W，屏幕亮 + 待机按 2W
  4. 单轮能耗 = Σ(耗时 × 功耗) ≈ 7 J
  5. 总能耗 = 轮次 × 7 J

⚠️ 这是数量级估算，不是实测。 误差可能达 2–3 倍。 但结论（能耗与轮次线性相关、轮次是唯一一阶杠杆）不受误差影响。 实测验证列为 P0-5。

A.3 内存估算方法（§2.2 的依据）

  • Android App（Compose + 服务）：按同类应用经验值 80–120MB
  • Node 运行时（单 ABI）：参照 Termux 的 node 二进制体积（30–40MB）
  • dsh 裁剪后 profile：研讨文档 §2.3 的 JS 部分估算（40–70MB）
  • 参考对照：豆包 aikernel 约 160MB（第三方逆向分析）

⚠️ 同为估算，实测列为 P0-4。
