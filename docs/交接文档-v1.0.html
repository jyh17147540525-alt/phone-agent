PocketAgent 交接文档 v1.0

受众：下一个接手继续开发的人。

这份文档刻意不重复另外两份 —— README.md 面向使用者、CONTRIBUTING.md 面向贡献者。 它只回答三个问题： ① 这个项目为什么长成现在这样 ② 哪里埋着雷 ③ 按什么顺序读

对应状态：2026-09-26 · 提交 35a8be8 · 分支 main

§0 三十秒上手

项 值
是什么 BYOK 的 Android 手机 AI 智能体；正从「agent 工具」转向「AI 手机助理」
协议 GPL-3.0 · 发布主体「代码乌托邦」· 全开源、不盈利、不设捐款渠道
规模 44 个 Gradle 模块（24 个有源码 / 20 个空壳）· 201 个 Kotlin 文件 · 约 6.1 万行
测试 1339 个离线单测全绿（不需要 Android SDK）
阶段 S1–S4 ✅ · S5–S9 ❌ 未开始 · v4.0 方向设计稿待评审
目标机型 红米 K60（mondrian / Android 15 / API 35 / HyperOS）
★ 最高优先级 尽量少影响用户正常使用手机

三条不可协商的红线（详见 CONTRIBUTING.md）：不得涉及支付金融 · 不得薅羊毛作弊 · 不得申请被禁能力。

接手第一件事：跑 §1 的三条命令。 不要先读代码 —— 先确认你手上这份是活的。本仓库有过"文档比代码旧好几轮"的历史（§4.4）。

§1 先跑起来

1.1 环境要求

项 要求 说明
JDK 17 ⚠️ 不要 21+ —— AGP 8.x 对高版本 JDK 支持不稳
Android SDK 36 android/local.properties 里写 sdk.dir=...（已 gitignore，每台机器各自一份）
项目路径 必须纯 ASCII ⚠️ 含中文路径时 AGP 在 Windows 上直接拒绝构建

绕过路径检查的权宜之计：./gradlew assembleDebug -Pandroid.overridePathCheck=true （不要写进 gradle.properties —— 不该让所有协作者继承这个绕过）。

1.2 三条命令（按顺序跑）

python tools/verify/run_logic_tests.py                     # ① 离线单测，不需要 Android SDK
python android/gen_module_build_files.py android --check   # ② 模块构建文件是否落后于生成器
python tools/verify/check_module_deps.py android           # ③ 跨模块依赖是否漏声明

期望输出：

命令 通过的样子
① 末行 OK (1339 tests)
② 全部 43 个模块的 build 文件与生成器预期一致。
③ [OK] 所有跨模块引用都有对应的 project 依赖声明。

⚠️ ①的判据是 OK (N tests) 那一行，不是退出码。 清理被中断时退出码会是 1，而测试其实全绿。

1.3 完整构建

cd android
./gradlew test            # 单元测试
./gradlew assembleDebug   # 打 APK → app/build/outputs/apk/debug/app-debug.apk

⚠️ 诚实提示：本仓库最近几次改动没有在 JDK 17 上验证过。 维护者机器上只有 JDK 25（与 AGP 8.x 不兼容），所以 assembleDebug 这条路 处于"文档写了、但没人真跑过"的状态。如果你在 JDK 17 上构建失败， 那是新信息，不是你的环境有问题。

1.4 已知环境坑

  • ./gradlew 首次要下 Gradle 发行版。仓库里的 wrapper 指向腾讯云镜像 （services.gradle.org 在中国大陆实测不可达）。换回官方地址的写法在 gradle/wrapper/gradle-wrapper.properties 的注释里。
  • ⚠️ 不要给守护进程设 -Dfile.encoding=UTF-8 —— 会引发一个报错信息完全指不到 真实原因的编码错配（现象：每个测试类都 ClassNotFoundException，而 .class 明明在磁盘上）。 完整推导见 README.md 的「别给守护进程设 -Dfile.encoding=UTF-8」一节。

§3 为什么长成这样

3.1 十条架构原则（改动需评审）

# 原则 违反的后果
1 不建自有后端 —— 模型请求直连用户指定的 Provider；订阅源与更新源用 GitHub Pages / Releases 一旦有后端，"零推理成本 + 合规护身符"两个前提同时失效
2 执行层多通道抽象 —— ActionExecutor，无障碍 / Shizuku / IME / 悬浮窗引导四通道可插拔、可运行时降级 禁止任何模块直接依赖 AccessibilityService —— 否则换通道要改所有调用点
3 感知层不依赖无障碍树 —— 统一走 ScreenSnapshot，树可用优先用树，不可用截图兜底 树在某些 App 上根本读不到，硬依赖它等于功能直接消失
4 主动放弃支付环节 —— 命中敏感页面规则立即停止、丢弃截图、交还用户 规则只许加严，不许放宽
5 手动引导模式是正式产品形态，不是残废版 把它当降级方案会导致它永远做不好
6 domain 层零 Android 依赖 这是所有 *logic 模块存在的理由（见 §3.2）
7 Key 永不落明文 —— Keystore + AES-GCM + SQLCipher；不进日志、崩溃上报、备份、SharedPreferences 见 §4.1
8 插件边界：本体提供「能力」，插件提供「意图」 调用必须经 PluginHost 代理；插件拿不到 Key 明文 / 原始节点对象，绕不过 SafetyGuard。永不开放 payment.* / key.* / crypto.* / system.*
9 凭据一律运行时注入、绝不硬编码 GitHub token 用 OAuth Device Flow；不接触用户的 Key
10 ModelRouteCoordinator 刻意不缓存 否则"改了档位、正在跑的任务还按旧配置走"，且没有任何线索

3.2 三个最容易被质疑的取舍

① 为什么拆出这么多 *logic 模块？

:agentlogic / :overlaylogic / :filelogic / :capabilitylogic / :provider:gateway 以及 v4.0 的 :personalogic / :memorylogic / :voicelogic —— 它们的共同点是 零 Android 依赖，因此能进离线验证器。

判据不是"代码量"，而是：这一层判错的后果是不是静默的。 如果是（不抛异常、只在真机上"看起来不对劲"），那它必须能被离线确定性测试覆盖。 真机验证覆盖不了这类 bug —— 你根本看不到它发生。

配套的 Android 壳（:agent / :overlay / :capability / :voice…）只做一件事： 把纯逻辑层定下的端口接到系统 API 上，一行判定逻辑都不许有。

② 为什么网关必须先于 agent 循环做完？

因为网关是假的时，mock 测不出「流式 token 乱序」「[DONE] 发两次」。 这两类 bug 只在真流式下出现，而它们导致的后果是"回答看起来对、其实拼错了"。 先把 :provider:gateway 做成真的并真机验证，再往它上面接循环。

③ 为什么不直接用 dsh 当大脑？

已经做了（路线 C：dsh 为脑 + Android 为 MCP 能力端），但 dsh 是 RC 版本， 所以锁版本 + 隔离层，且护栏留在 L4。

§4 ★ 埋着的雷

这一节是本文档最值钱的部分。 下面每一条都是已经真实发生过的。

4.1 头号 bug 形态：「安静地少做一件事」

这个项目最高频的 bug 不是崩溃，是静默少做。已发生的例子：

现象 后果
encodeDefaults=false 序列化时字段静默消失
空 defaultModels 静默地没有默认模型可选
价格回落成 0.0 静默算成免费（最后一级回落必须是 null）
TTS 能力未知 静默丢掉 emotion / 语速参数

纪律：任何"回落/兜底值"都必须显式且可观测。 价格类回落必须是 null，不是 0.0 —— 0.0 是一个合法的价格，null 才表示"不知道"。

4.2 静默失败清单（不抛异常、真机上"一眼看不出来"）

这些正是 §3.2 里那些 *logic 模块要守的东西：

层 判错的表现
Agent 预算 只是多跑几轮（用户完全看不到）
卡死检测 漏排 WAIT/SCROLL → 任务在正常时莫名中止
感知档位 选错只是多花一份截图成本
文件路径归一化 漏掉一种 .. 变体 → 授权一个目录等于授权整块存储
文件包含判定 写成字符串前缀 → /Documents-evil 被当成在 /Documents 之下
第 0 档硬拒绝清单 漏一条设置键 → agent 能给自己授予无障碍权限，整个安全模型归零
确认标志 被提前消费 → "用户点过确认"变成绕过一切的后门
人格白名单（v4.0） 漏一个字段 → 安全边界被击穿且不抛异常
语音打断（v4.0） 漏掉"取消在途请求" → 助理停了，但 token 还在烧

没有一条抛异常，没有一条在真机上"一眼看出来"。唯一可靠的抓手是确定性离线测试。

4.3 已踩过的坑（工具与平台）

文件操作

  • renameDocument 是消耗性的，且会静默改名 —— 不报错，把文件改成 name (1)， 源 Uri 立刻失效。⇒ 覆盖必须「挪开旧文件 → 新建 → 删备份」， 且判据是改完之后它叫什么（displayName），不是"有没有报错"。
  • move 跨目录的 createDocument 也会静默改名（不丢数据，表现为"移动到 b (1).txt"）。
  • ⚠️ git rm 在本机环境会清空整个父目录（稳定复现两次）。 不要用 git rm —— 改用 mv <file> .build-trash/ + git add -A。 抢救方法见 skill windows-git-delete-safety。

Android 平台

  • 锁屏下 uiautomator dump 成功但零 text 节点、screencap 全黑。 ⇒ 判据：先看截图是否全黑。但别一看到 keyguard 就宣布硬边界 —— KEYCODE_WAKEUP 后等 2 秒再上滑有时真能解开。
  • uiautomator dump 没有 --display 参数 —— 永远只读 display 0。 用它测虚拟屏 = 测了个寂寞。判"无障碍能不能读"的唯一有效判据是 dumpsys accessibility 的 valid display 列表。
  • 别用 md5 判断界面状态 —— 息屏 / 时钟 / 温度刷新都会让它变。要看具体字段或看图。
  • 写系统设置是两类授权，绝不能合并：GLOBAL/SECURE 走 WRITE_SECURE_SETTINGS （pm grant 能授）；SYSTEM 走 WRITE_SETTINGS（appop 型，只能 appops set）。
  • 权限被拒类实验禁用 adb shell 复现 —— shell 持 INTERNAL_SYSTEM_WINDOW / ACTIVITY_EMBEDDING / ADD_TRUSTED_DISPLAY，会假阳性放行。

工程纪律

  • 改文件一律按字节读写 —— Path.write_text() 在 Windows 上会把 LF 翻成 CRLF。 tools/verify/check_line_endings.py 可查。
  • 同一文件的多个修改不能并行 —— 并发写回时后写的会静默覆盖先写的，而工具报"成功"。 要么串行，要么用一次性脚本原子完成（skill bulk-edit-with-script）。
  • 确认门是两道，必须分开（confirmedByUser + operationConfirmedByUser）—— 合成一个的后果是第二句话永远说不出来。

4.4 检查器的「假绿」陷阱 ★★

一个漏掉模块的检查，同样是假的 —— 只是它不报红，所以比"总是报红"更难发现。

真实事故：gen_module_build_files.py 的 PURE_KOTLIN 表里漏了 filelogic， 于是 --check 长期打印"全部 34 个模块一致"—— 而那个数字从没把 filelogic 算进去。 同一时期，CapabilityCall.kt 少了一个收尾 }，从写完到注册进验证器之前从没被编译过， 注册后第一次跑就报出来。

纪律：

  1. 往生成器加模块后，必须确认 --check 打印的「总数」在涨。 只看到"一致"两个字不算通过 —— 必须看到数字变大。
  2. 判据看具体行，不看退出码（OK (N tests)）。
  3. 检查器必须能"造违规输入证明它会红" —— 这就是 test_release_check.py 存在的理由。

  4. --check 零容忍。它曾经长期报 4 条"已确认的本地定制"，而检查器输出里 标注不了哪条是已知的 —— 于是真实漂移（比如少了 room-compiler， 会让 Room 直到运行时才崩）会被一起划掉。 ⇒ 现在那些"已知差异"被描述进生成器的配置表，红条归零，剩下的红条就是真问题。

    一个总有几条红条的检查等于没有检查。

  5. 模块数的权威口径 = settings.gradle.kts 的 include() 条数（现 44）。 ⚠️ find -name build.gradle.kts 得 45 —— 多出来的是根构建文件 android/build.gradle.kts，不是模块。而 check_module_deps.py 用 rglob("build.gradle.kts") 枚举，所以它报的「45 个模块」偏大 1。 （这条是 2026-09-26 订正 README 时发现的 —— 当时四份文档分别写着 36/30/37/45，全错。）

发版前还需清零的（当前是有意留着的）：

  • signingConfig 未声明 → 会产出未签名 APK
  • versionName = "0.1.0-m0" 含开发期标记

§7 改代码前的约定

7.1 新增模块 = 四个注册点（缺一个就"看不见"）

# 位置 缺了会怎样
1 android/settings.gradle.kts 的 include(":模块名") Gradle 根本不认这个模块
2 android/gen_module_build_files.py 的 PURE_KOTLIN 或 ANDROID_LIB 生成 build 文件时漏掉它；--check 也遍历不到
3 tools/verify/run_logic_tests.py 的 MODULES（仅纯 Kotlin 模块） 永远不会被编译、永远不进离线单测
4 android/<模块>/build.gradle.kts 由生成器产出，不要手写

详见 skill pocketagent-new-module。加完必须确认 --check 总数在涨。

7.2 依赖只加「今天磁盘上真的有它」的

PROJECT_DEPS / NEEDS_HILT / NEEDS_SERIALIZATION / EXTRA_TEST_DEPS 的判据是现在就有这个需求，不是"将来可能需要"。

7.3 提交前必跑

python tools/verify/run_logic_tests.py                     # 离线单测
python android/gen_module_build_files.py android --check   # 生成器一致性
python tools/verify/check_module_deps.py android           # 依赖声明
python tools/verify/check_no_secrets.py                    # 密钥泄露
python tools/verify/check_line_endings.py                  # 行尾
python tools/verify/check_kt_quotes.py android             # 中文文案里的 ASCII 引号误用
python tools/verify/check_xml_comments.py android          # XML 注释里的 `--` 非法序列

推送到公开仓库前，check_no_secrets.py 是硬门槛。

7.4 验证的哲学（贯穿全项目）

能离线确定性验证的，绝不放到真机上碰运气。

原因：本项目的 bug 大多不抛异常。真机验证只能证明"这次没出事"， 而离线测试能证明"这个分支不可能错"。

附录 C：⚠️ 不在仓库里的东西

这一节很重要。仓库里存的是「结论」，不是「推理过程」。

不在仓库里 后果
开发过程的长期记忆（决策理由、踩坑记录） 你只能看到"为什么这么写"的代码注释，看不到"我们试过哪三条路、为什么否掉两条"
任务板 / 路线图 有 docs/剩余待办实施方案… 作为快照，但不是活的
开发者的本机环境细节（JDK 25、Android SDK 路径、adb 位置） §1.1 写了要求，但"这台机器上发生过什么"没有

接手建议：把本文档 §3、§4 当作"推理过程"的浓缩版来读。 它们是从那些不在仓库里的记录里提炼出来的唯一还活着的部分。

附录 D：一句话总结

这是一个极其重视"不静默失败"的项目。 如果你只从本文档记一件事，请记 §4.4： 一个漏掉模块的检查同样是假的 —— 只是它不报红。
