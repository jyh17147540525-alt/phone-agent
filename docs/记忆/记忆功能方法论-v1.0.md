## §0 一页纸

记忆系统不是"存起来 + 拿出来"。它是**五个独立的闸门**，每个闸门都有独立的失败模式，
而且**修好一个会恶化另一个**：

| # | 闸门 | 核心问题 | 失败长什么样 | 主要来源 |
|---|---|---|---|---|
| 1 | **写入** | 什么该变成记忆 | 把逐字对话当记忆存（本项目真实发生过） | ProMem、Mem0 |
| 2 | **收敛** | 新旧冲突怎么办 | 已作废的规矩和最新状态并存，角色照旧规矩说话 | STALE、Zep、FadeMem |
| 3 | **检索** | 这一轮该想起哪几条 | 不相关的话被塞进回答，用户以为它没在听 | Generative Agents、LongMemEval |
| 4 | **遗忘** | 什么时候该淡出 | 全留（撑爆）/ 全丢（失忆）两种极端 | MemoryBank、FadeMem |
| 5 | **成本** | 花的是用户自己的钱 | 每轮都重算全表 | sleep-time compute、Anthropic 语境工程 |

本项目已经有的东西（`AtomExtractor` / `MemoryGate` / `MemoryRecall` / `Salience` / `MemoryDecay`）
在方法论上是**对的**，问题集中在三处：
**① 闸门 2（收敛）缺失；② 三个衰减常数互相矛盾；③ 没有任何可离线跑的评测。**

## §1 把整个领域压成一个骨架

两篇 2025–2026 的综述给了统一坐标，值得作为所有讨论的公共语言。

### 1.1 `forms × functions × dynamics`（arXiv 2512.13564，Hu et al.，47 作者）

> *Memory in the Age of AI Agents*

| 维度 | 取值 | 对本项目的意义 |
|---|---|---|
| **forms**（载体） | token-level / parametric / latent | 我们只能是 **token-level**（不训练模型，BYOK 且无自有服务端） |
| **functions**（用途） | **factual** / **experiential** / **working** | 见下 |
| **dynamics**（动态） | 怎么形成、怎么演化、怎么检索 | 即本文五个闸门 |

**functions 三分**是我们最该借的一条，因为现有 `AtomKind` 只有四类，缺"经验"这一维：

- **factual**（事实性）：「他住在杭州」「用 Android」
- **experiential**（经验性）：「上次用这个网站上传文件失败了，要改 MIME」——这是**做过的事的抽象**，
  和"事实"不同：它带**因果与教训**，能改变下一次的行为
- **working**（工作记忆）：当前任务的状态，任务结束就丢

> ⚠️ 现有四类 `FACT / PREFERENCE / CONSTRAINT / STAGE_CONCLUSION` 里，
> `STAGE_CONCLUSION` 名义上是 experiential，但 `docs/记忆/重写记录-2026-11-03.md`
> 记录了它的真实内容：**逐字对话记录**（`U>…A<…`，400 字截断）。
> ⇒ 这不是"经验"，是"对话副本"。**名字对、语义错**——这是最危险的一种命名。

### 1.2 `Storage → Reflection → Experience`（arXiv 2605.06716，Luo et al.，ACL 2026 Findings）

> *From Storage to Experience*

三阶段演化，且**每阶段的价值递增、成本也递增**：

```
Storage（轨迹保存）  →  Reflection（轨迹提炼）  →  Experience（轨迹抽象）
   "存下来"                "想明白"                   "变成方法"
   L0 turn                 L1 atom                   应该有的 L2/L3
```

论文指出的两个前沿机制：

- **proactive exploration**：不等用户问，主动去补全记忆（对应"主动抽取"，见 §2）
- **cross-trajectory abstraction**：跨多个轨迹抽象出可复用的经验（对应本项目 `L2 scene` 的正确形态）

> ★ 这条给了本项目一个**判据**：
> 如果 L2 只是"把若干原子归并成一句摘要"，那它停在 Reflection，
> **没有产出 Experience**。真正的 Experience 必须回答"下次遇到同类情况该怎么做"。
> 设计稿 §4.4 的 L2 写的是「把这些原子归纳成若干场景，每个场景给标题 + 一句 ≤80 字摘要」
> —— **这是 Reflection，不是 Experience。** 建议 L2 的 summary 模板改成两段式：
> 前半句"发生了什么"，后半句"所以下次……"。

## §2 写入闸门：抽取不是摘要

### 2.1 ProMem（arXiv 2601.04463，EMNLP 2026 Findings）

> *Beyond Static Summarization: Proactive Memory Extraction*

它点名了现有做法的两个缺陷，**两条都正中本项目**：

| 论文指出的缺陷 | 原文意思 | 本项目的对应 |
|---|---|---|
| **extraction is "ahead-of-time"** | 单条 summary prompt 把 details / events / relations 混在一起，有用信息被压掉 | `AtomExtractor` 一次调用批量出四类原子 —— 有分类但**共享一个 prompt**，容易串味 |
| **extraction is usually one-off** | 抽完不校验，错误与幻觉会长期留在记忆里 | **本项目零校验**：`AtomExtractor` 抽出什么就落什么，只有 `MemoryGate` 做**排除**（敏感/不适当），不做**事实核对** |

ProMem 的三条对策，逐条评估可移植性：

| 对策 | 内容 | 本项目能不能做 |
|---|---|---|
| **分离 details / events / relations** | 每类用不同的抽取策略 | ✅ 能做，零额外成本：**改 prompt 结构**，让一次调用内分三段输出。但要小心 token 预算（一次调用变长） |
| **完整性检查** | 抽完回头看"有没有漏掉整件事" | ✅ 能做，但**要多一次 LLM 调用**。建议只在"会话结束"那次跑（见 §5 的 L1 触发点），不在每 12 轮的中途跑 |
| **原子级事实校验** | 逐条核验是否忠于原文 | ⚠️ 成本高。折中：**只对 `confidence` 落在 0.4–0.7 灰区**的原子校验，高置信度直接过、低置信度直接丢。这条折中没有论文背书，是工程取舍 |

### 2.2 Mem0 的四动作（arXiv 2504.19413）

Mem0 的写入不是"append"，是**对每条新提取的信息做一次决策**：

```
ADD     库里没有 → 新增
UPDATE  库里有但这次更完整/更新 → 改
DELETE  库里有但这次被否定 → 删
NOOP    库里有且一致 → 什么都不做
```

> ⚠️ 这是 Mem0 能"token 成本省 90%+"的**真正原因**（不是模型便宜，是**不重复存**）。
> 报告里那个「vs full-context p95 延迟 −91%」是结果，四动作是机制。

**本项目现状**：`Atom.merge` 已经是一个合并语义（在 `MemoryRecall.kt:253` 附近作为 `AtomStore.mergeIn` 的默认实现），
但它只有 **ADD 与 UPDATE**，**没有 DELETE，也没有 NOOP 的显式判定**。
⇒ 这是 §3「收敛闸门缺失」的根。

### 2.3 本项目自己最贵的教训（`重写记录-2026-11-03.md`）

这是**外部论文没有、只有踩过才知道**的一条，必须写进方法论：

| 教训 | 机制 |
|---|---|
| **从记忆文本反推人格是错的** | 记忆是人格的**下游数据**，不是上游。人格设定在 `custom_persona`。从记忆反推 → 造出设定里不存在的"求婚/戒指刻字/备孕" |
| **`Atom.init` 有 `require(sourceTurnIds.isNotEmpty())`** | 重写时 src 为空 → `FileAtomStore.parse` 逐行抛 → **整库被判坏行 → 记忆被清空**。这是"数据迁移工具的失败模式比数据本身更危险"的实例 |
| **「阶段结论」= 逐字对话** | 852 条里 354 条是对话副本，88,592 字符 → 收敛后全库 1,657 字符。**压缩率 98%**，说明 98% 的"记忆"是噪音 |

★ 方法论结论：**记忆的写入质量比检索质量重要一个数量级。**
检索再聪明，也捞不出没被正确写入的东西；而写入一堆垃圾，检索越准反而越糟。

## §3 收敛闸门：本项目的最大缺口

### 3.1 STALE（arXiv 2605.06527，2026-05）—— 直击现有设计的软肋

> *STALE: Can LLM Agents Know When Their Memories Are No Longer Valid?*

核心概念 **Implicit Conflict（隐式冲突）**：

> 后来的观察**作废**了早先的记忆，**但没有任何显式否定**。
> 需要上下文推理 + 常识才能发现。

例：先说"我下周三去北京出差"，后来说"会议改线上了"——
**第二句没说"不去北京"**，但第一句已经作废。

三维探测框架（这三条可以直接当本项目的测试用例设计）：

| 维度 | 测什么 | 失败表现 |
|---|---|---|
| **State Resolution** | 能不能发现"旧信念过期了" | 仍然按旧状态回答 |
| **Premise Resistance** | 用户问句里**嵌着旧前提**时，敢不敢拒绝 | 「你上次说要带娃去，几点出发？」——**接受了错误前提** |
| **Implicit Policy Adaptation** | 后续行为有没有真的按新状态走 | 说对了但做错了 |

数据规模：400 个专家验证冲突场景 / 1,200 条探测查询 / 100+ 日常主题 / 上下文长至 150K token。

**结果（关键）**：前沿模型 + 专用记忆框架，**最好成绩只有 55.2%**。

> ★ 这条要放在最前面讲给决策者：**这不是"再调调 prompt 就好"的问题，
> 是整个领域都没解决的能力。** 本项目不该指望"顺手做对"，必须**分层兜底**。

论文给的雏形 **CUPMem** 两个机制：

| 机制 | 做什么 | 本项目怎么落 |
|---|---|---|
| **structured state consolidation** | 写入时就把"状态"结构化成可裁决的形式 | `profile` 表天然是 KV（`pref.reply_length` / `constraint.no_call_before_9`）→ **它就是 state**。冲突裁决应该发生在 `profile` 层，不在 `atom` 层 |
| **propagation-aware search** | 一个状态变了，要顺带检索受影响的关联记忆 | 现在完全没有。最小实现：`profile` 一项变更时，把它 `evidenceAtomIds` 指向的原子标 `stale`，下次 L2 触发时重算 |

### 3.2 设计稿现有做法的问题（必须改）

设计稿 §4.4 写：

> 新值与旧值矛盾 → 写新值但**降置信度**……冲突连续出现 N 次（默认 3）→ 采纳新值

**问题**：它把"用户明确改主意"和"模型猜错了"当成同一种冲突。

- 用户说「**以后别叫我老板**」——这是**显式否定**，应当**立刻生效**
- 模型自己归纳出两条互相矛盾的偏好——这是**噪声**，才该"连续 3 次"

⇒ 建议改成**两级判据**：

```
显式否定（原文含"不/别/以后不要/改成/算了"等否定词 + 指向已有记忆）
    → 立即 UPDATE，旧值进 superseded，置信度不降
隐式冲突（新观察与旧值语义不相容，但原文无否定）
    → 写新值 + 旧值降置信度；同向冲突累计 ≥3 次才采纳（保留现有规则）
```

这一改的**依据**：STALE 的 Implicit Conflict 定义本身就把"显式否定"排除在外
（"without explicit negation"）。设计稿把两者合并，是**比论文更保守、但更错**的处理。

### 3.3 另外三条收敛机制

| 机制 | 来源 | 内容 | 对本项目 |
|---|---|---|---|
| **bi-temporal** | Zep/Graphiti（2501.13956） | 每条边记两根时间轴：**事实有效时间** vs **系统记录时间** | ⚠️ 我们的 `Atom.at` 只有一根。但 `scene` 有 `firstAt`/`lastAt` 两根——方向对。建议 `atom` 加 `validFrom`/`validTo`（可空），成本极低 |
| **adaptive decay + fusion** | FadeMem（2601.18642） | 保留率 = 自适应指数衰减（受语义相关性/访问频率/时间模式调制）；LLM 引导冲突消解 + 记忆融合；**存储降 45%** | 我们的 `MemoryDecay` 已经用 `emotionalCharge` 调制衰减率——**同向且更早**。FadeMem 多的是"访问频率"与"融合" |
| **merge-certified + retrospective attribution** | MEMOIR（2611.07631） | ①合并前**筛查证据是否保留**（judge-gated merge）②用后归因：这次回答用了哪几条 → 更新它们的检索优先级 ③UCB 探索奖励，防止高频记忆挤掉有用的冷门记忆 | ⭐ **这套最值得抄**，而且**不需要额外 LLM 调用**（论文明确说"no additional LLM call on the online write path"） |

MEMOIR 的实测数字（LoCoMo 1,905 条去重 QA）：

- 完整检索栈比裸 cosine 的 **evidence recall@5 提升 11.92 个百分点**
- 置信门控反馈（不需参考答案、不训 reranker）**再 +1.50**
- 有参考答案的 oracle **再 +1.84**（多跳上 +8.05）
- judge-gated merge：文本证据召回 58.82% → 59.08%，活跃库**缩小 1.42%**，
  100 次人工审计合并 **0 次损失**（单侧 95% 上界 2.95%）

> ★ 为什么"用后归因"对我们特别合适：我们的"用"是**每一轮都发生的**（`MemoryRecall.rank`
> 每次都会挑出 N 条进 prompt），归因信号免费。
> 而"读数 × 用数"正好是 FadeMem 说的"访问频率"，两条文献在这里合流。

## §4 检索闸门

### 4.1 三因子加权（Generative Agents，Park et al.）

```
score = α·recency + β·importance + γ·relevance
```

这是这个领域的"标准答案"，后续几乎所有工作都是在调这三项的算法。

**本项目 `MemoryRecall.score`（`MemoryRecall.kt:160`）**：

```kotlin
coverage * 0.45 + kindBase(atom.kind) + freshness * 0.10 + atom.confidence * 0.20
```

对照：

| 因子 | 本项目 | 评价 |
|---|---|---|
| relevance | `coverage`（**bigram**，×0.45） | ✅ 中文不引分词库的务实选择。但**只用字面重合**，同义改述完全失配（"住哪" vs "杭州" 有重合？没有） |
| importance | `kindBase`（闭集，0.35/0.22/0.12/0） | ✅ **比论文更好**：把"重要性"从模型自评换成**类型先验**，可离线测、不漂移 |
| recency | `freshness`（线性，45 天，×0.10） | ⚠️ 见 §4.3 |
| confidence | `atom.confidence`（×0.20） | 论文没有，这是对的——我们每条记忆自带可信度 |

两条**已经被自己测试逼出来的**硬规则，方法论上很关键，别改：

1. **加权和而不是连乘**（`MemoryRecall.kt:158` 注释）：连乘会让"不相关"清零，
   于是 `CONSTRAINT` 也一起消失——**约束必须能靠基础分活下来**。
2. **`requiresCoverage`**（`MemoryRecall.kt:92`）：除约束外，**没有字面重合就不出现**。
   起因是一条 `confidence=0.8` 的「他住在杭州」在问股市时拿到 0.26 > 0.25 阈值。

> ★ 这两条是"检索闸门"最该守的纪律，比任何公式都重要：
> **宁可这一次没想起，也不要这一次想起不该想的。**

### 4.2 LongMemEval 的三项优化（arXiv 2410.10813）—— 对 LIKE 检索最实用

论文的三阶段框架 **indexing → retrieval → reading**，以及三项具体优化：

| 优化 | 原文含义 | 本项目怎么用 |
|---|---|---|
| **session decomposition for value granularity** | 按"信息价值"切分会话，不是按长度 | 我们的 `SessionBoundary` 已有（空闲 30 分钟 / 主动开新），方向对；但没有"价值"维度 |
| **fact-augmented key expansion** | 索引时把事实**展开成多个 key** | ⭐ **最便宜的一次改进**：`atom.text` 现在只被整存；建索引时额外存 `keywords`（原子已有 `squashName`），让 `LIKE` 能命中更多写法 |
| **time-aware query expansion** | 把「上次」「昨天」「之前」这类词**换成时间窗**，收窄搜索 | ⭐ **现在完全没做**。这是中文对话里的高频词，也是"时间推理"这一项能力的主要失分点 |

论文还给了基准事实：**五项核心能力** = information extraction / multi-session reasoning /
temporal reasoning / **knowledge updates** / **abstention**；500 题；
商用助手与长上下文 LLM 在持续交互中**准确率掉 30%**。

> ★ `knowledge updates` 与 `abstention` 这两项，正好对应 §3（收敛）与 §4.1 的 `requiresCoverage`
> （该不答就不答）。**我们的架构在这两项上先天有优势**——只要把收敛补上。

### 4.3 ⚠️ 本项目内部三个衰减常数互相矛盾（本轮新发现）

这是我读代码时发现的**真实冲突**，不是论文的观点：

| 常数 | 位置 | 值 | 折算半衰期 |
|---|---|---|---|
| `MemoryDecay.BASE_RATE` | `Salience.kt:104` | `0.010` **每小时** | **≈ 69 小时 ≈ 2.9 天** |
| `MemoryRecall.FRESHNESS_DAYS` | `MemoryRecall.kt:223` | 45 天（**线性**） | 45 天（线性归零，非线性衰减） |
| 设计稿 L2 `HALF_LIFE` | 设计稿 §4.4 | 30 天 | 30 天 |

三者差**一个数量级以上**。它们服务不同目的，但**没有一处写明这一点**：

- `Salience` 管 **"以什么保真度说出来"**（`Fidelity`：EXACT / 模糊 / FORGOTTEN）——模拟人类记忆淡化
- `MemoryRecall.freshness` 管 **"排序里新近度占多少"**（只占 0.10 权重）
- L2 `weight` 管 **"这段经历整体还活不活跃"**

**方法论建议**（不是改代码，是先把口径钉住）：

1. **不同层允许不同衰减率，但必须同层唯一**。现在 `atom` 这一层同时有
   `Salience`（2.9 天）和 `freshness`（45 天）两套，调参时无从下手。
2. 建议口径：**`Salience` 决定"怎么说"，`freshness` 决定"排多前"，两者不互相引用。**
   现在 `Salience.fidelityOf(atom, nowMs)`（`Salience.kt:199`）从 `Atom` 现算，
   而 `MemoryRecall.score` 用 `atom.at` 另算一遍——**同一条原子在同一轮里被两套衰减算了两次**。
3. 把三个常数**集中到一个文件**并写明各自的量纲与用途。现在它们散在两处 + 一份文档。

> ⚠️ 这条属于"实现细节"，但它是**方法论级别的缺陷**：记忆系统里最容易被忽视、
> 也最容易被用来解释一切异常的就是"衰减率"。三个都不知道该相信哪个时，
> 任何"我觉得它忘得太快"的反馈都无法被证伪。

## §5 遗忘闸门：这里本项目做得比多数论文细

### 5.1 MemoryBank（arXiv 2305.10250）—— 艾宾浩斯

按 **"经过时间 × 相对重要性"** 遗忘与强化。配套 chatbot SiliconFriend，闭源开源模型都能接。
这是"遗忘曲线"进入 LLM 记忆的开山工作。

### 5.2 FadeMem（arXiv 2601.18642）对现状的批评

> 现状是 **binary retention**（全留或全丢）。

两条对策：**双层不同衰减率** + **LLM 引导的冲突消解与记忆融合**。
结果：多跳推理与检索更优，**存储降 45%**。

### 5.3 本项目的 `Salience` / `MemoryDecay` 其实更细

`Salience.kt` 已经有三档保真度（`Fidelity`），而且**会改变措辞**：

| 档 | 触发 | 输出 |
|---|---|---|
| EXACT | `strength ≥ 0.72` | 原话直说 |
| 模糊 | `0.30 ≤ strength < 0.72` | 前缀随机取一：「好像」「隐约记得」「我记得你提过」「之前是不是说过」（`Salience.kt:174`） |
| FORGOTTEN | `strength < 0.30` | 不说 |

衰减公式（`Salience.kt:116-128`）：

```
factor = 1 - emotionalCharge × (1 - MIN_EMOTION_FACTOR)    // MIN_EMOTION_FACTOR = 0.06
rate   = BASE_RATE × factor                                // BASE_RATE = 0.010/小时
next   = strength × exp(-rate × hours)
```

即：**情绪越强，衰减越慢**（`emotionalCharge=1` 时速率降到 6%）。
强化（`:138`）：`gain = (1 - strength) × 0.35`，带 `emotionalCharge` 上限夹紧。

> ★ 这套设计在方法论上对应一个论文**没有明说但很重要**的概念：
> **fidelity-aware recall（保真度感知召回）**。
> 大多数系统只有"记得/不记得"两态，而人类记忆是"**记得但不太确定**"。
> 用模糊措辞表达低保真记忆，是**唯一能让"记错了"显得自然**的方式——
> 而这恰好解决了 §3 的 implicit conflict：低置信度的旧记忆被说得模模糊糊，
> 用户会主动纠正，而不是被一个理直气壮的错答案误导。
>
> ⚠️ 但这条**只能在真机上验证观感**，归 WorkBuddy。

## §6 成本闸门：花的是用户自己的钱

### 6.1 Sleep-time compute（arXiv 2504.13171）

> 离线（用户不提问时）预想用户会问什么并**提前计算**。

- 相同准确率下，测试时算力降约 **5×**（Stateful GSM-Symbolic / Stateful AIME）
- 扩大 sleep-time 算力还能再提 **13% / 18%**
- Multi-Query 场景每 query 成本再降 **2.5×**
- ⚠️ **效果与"用户 query 的可预测性"强相关**——个人助理的记忆整理**恰好**高度可预测
  （下周要问的还是这周那些人、那些事），所以这条对本项目**适用性很高**

### 6.2 Anthropic 语境工程（已全文读）

三条长程手段，本项目全都用得上：

| 手段 | 内容 | 本项目对应 |
|---|---|---|
| **compaction** | 接近窗口上限时总结后重启，保留架构决策/未解 bug/实现细节，丢掉冗余工具输出 | `ContextCompressor` / `ContextOffloader` 已有，且 `OffloadPayload` 构造函数私有 = **编译期钉死"不过 PrivacyFilter 编译不过"** |
| **structured note-taking** | 定期把笔记写到窗口外的持久存储，之后再拉回来 | 就是 L1/L2/L3 |
| **sub-agent** | 子 agent 烧几万 token，只回 1000–2000 token 摘要 | 项目的 `dsh` 侧已有 |

核心原则：**找"最小的、高信号的 token 集合"，而不是最短的**。
背景事实 **context rot**：token 越多，模型从上下文中**准确召回**的能力越差；
"attention budget" 有限，n token 有 n² 对注意力关系。

> ★ 这直接支持设计稿"不上向量、不上大而全上下文、只取前 3 条 scene"的选择。
> 但**理由要换**：不是"没服务器"，而是"**塞多了反而更差**"。这个理由更硬，也更该写进文档。

### 6.3 本项目的省钱三件套 + 一个缺口

设计稿已有：**游标**（`memory_cursor`）、**批量**（一次调用出 N 条）、**总开关**（关掉不删已有）。

⚠️ **缺口**：没有**单轮成本上限**。L1 触发条件是"会话空闲 30 分钟**或**累计 ≥12 轮"，
但一个长会话里"12 轮"会反复触发（12、24、36…），**每次都是全量未提取 turn 喂进去**。
虽然游标保证了"只处理新增"，但**单次调用的输入长度没有上限**——
用户连续聊 200 轮才空闲，那次提取就是 200 轮全塞。
⇒ 建议加**分片**：单次提取输入的 turn 上限（如 40 轮），超了分多次，游标逐片推进。

## §7 隐私闸门：MemPrivacy 给的方案本项目现在没有

### 7.1 MemPrivacy（arXiv 2605.09530，2026-05）

> *Privacy-Preserving Personalized Memory Management for Edge-Cloud Agents*

动机说得很准：

> 云端辅助的记忆管理会暴露敏感信息，而现有隐私手段通常是**激进掩码**，
> 把任务相关语义一起去掉，于是**记忆效用与个性化质量下降**。

三条机制：

1. **边缘侧识别隐私 span**（轻量 on-device 模型），给每个 span 分配**隐私类型**与**保护级别**
2. **替换为语义结构化的 type-aware placeholder** 再送去云端做记忆处理
3. **需要时在本地还原**原始值

结果：隐私信息抽取大幅超过 GPT-5.2 / Gemini-3.1-Pro 等通用模型，还降低推理延迟；
在多个主流记忆系统上，**效用损失限制在 1.6% 以内**；并构造了 MemPrivacy-Bench
（200 用户 / **155k+ 隐私实例**）与**四级隐私分类**。

### 7.2 本项目的现状与差距

现在有 `MemoryGate`（落盘前必须过）+ `PrivacyFilter`（卸载前必须过，**编译期强制**）。
但两者都是**排除式**：命中就删/就不落。

> ⚠️ 这与 MemPrivacy 批评的"aggressive masking"是**同一类问题**：
> 「他妈妈住在杭州市西湖区XX路XX号」→ 整条被门挡掉，
> 于是"记得用户的家人情况"这件**能力本身**消失了。

**BYOK 架构让这条格外重要**：用户的记忆要送进**第三方模型商**的 API 才能抽取。
现在是"要么全发，要么不发"。placeholder 方案给了第三条路：

```
本地：他妈妈住在 [ADDRESS_1]
云端：抽取 → 「用户的母亲居住地 = [ADDRESS_1]」（模型商看到的是占位符）
本地：落盘时还原 → 「用户的母亲居住地 = 杭州市西湖区XX路XX号」
```

> ★ 这是**本轮调研里唯一一条"新增能力"级别的建议**，其余都是修正。
> 它同时解决了"隐私"与"个性化质量"这对看似对立的矛盾。
> 但**识别隐私 span 需要一个模型**（论文是轻量 on-device 模型），
> 本项目不能自带模型（无自有服务端 + 包体积）。
> ⇒ 折中：**规则 + 正则 + 已有的 Gate 判据**做初版，把 `PrivacySpanRecognizer`
> 做成端口（Port），将来可换成模型。这一条**必须先跟决策者确认**再动手。

## §8 评测闸门：本项目最该补的一块

### 8.1 业界标准基准

| 基准 | 提出方 | 测什么 | 规模 |
|---|---|---|---|
| **LOCOMO** | snap-research | 超长期对话：QA / 事件摘要 / 多模态 | 长对话 |
| **LongMemEval** | Wu et al., ICLR 2025 | 五项能力（extraction / multi-session / temporal / **updates** / **abstention**） | 500 题 |
| **DMR** | MemGPT 团队 | Deep Memory Retrieval；MemGPT 93.4% → Zep 94.8% | — |
| **STALE** | 2605.06527 | 隐式冲突三维探测；**SOTA 仅 55.2%** | 400 场景 / 1,200 查询 |
| **LTI-Bench** | FadeMem 使用 | 长期推理 | — |
| **BEAM** | — | 与 LoCoMo / LongMemEval 并列的三大标准之一 | — |

### 8.2 ⚠️ 但这些基准对本项目的**适配性有限**

`LongMemEval-V2` 与 cost-aware 变体明确指出：**对话召回基准测不到工具使用型 agent 的记忆**。
而本项目是**手机操作 agent**——大量记忆是"上一次点哪里失败了"这种**经验性、程序性**记忆，
恰好是 LOCOMO/LongMemEval 覆盖不到的（它们几乎全是陈述性对话）。

⇒ **不能直接拿现成基准当验收标准**。但可以借它们的**方法**。

### 8.3 建议：自己造一个离线可跑的记忆基准

这是本文最该被采纳的工程建议，因为它**完全符合本项目的分工纪律**（我只能在离线做验证）：

```
tools/verify/memory_bench/
  cases/
    l1_extraction/     合成对话 → 期望抽出的原子（含"不该抽出"的负例）
    l1_dedup/          同一事实说 3 遍 → 库里只能有 1 条
    l1_conflict/       显式否定 vs 隐式冲突 → 断言两级判据
    l2_scene/          20 条原子 → 期望的场景摘要（含"下次该怎么做"）
    l3_profile/        只吃 PREFERENCE + CONSTRAINT，不许吃 FACT
    recall_rank/       给定 query + 原子表 → 期望的 top-N 顺序（确定性，可断言）
    recall_abstain/    不相关 query → 期望空串（对应 requiresCoverage）
    decay/             给定 Salience + 时间 → 期望 fidelity 档位与措辞前缀
  run_memory_bench.py  → 走 run_logic_tests.py 的同一套入口
```

**为什么这个能起作用**（依据在 `docs/工程/未接线清单.md` 的教训"审计工具本身也需要被审计"）：
现有测试（`MemoryRecallTest` / `MemoryDecayTest` / `AtomExtractorTest` 等 7 个）
测的是**单个函数的行为**，没有一条测**"整条记忆链路在真实对话上是否更好"**。
⇒ 我们知道每个零件是对的，但不知道装起来对不对。

> ★ 其中 `recall_rank` 与 `recall_abstain` 两组**最有价值**且**最便宜**：
> 它们纯逻辑、零 LLM、可以断言精确顺序（`rank` 已是确定性的：同分按 `at` 再按 `id`，
> 见 `MemoryRecall.kt:117-122`）。这正是"可离线验证"的甜点区。

### 8.4 借 STALE 的三维探测做用例模板

不用它的数据，用它的**提问方式**——这三类问题能写出很好的负例：

| 维度 | 用例模板 |
|---|---|
| State Resolution | 先说「我下周三去北京」，再说「会议改线上了」→ 问「我下周去哪」→ **期望：不去北京** |
| Premise Resistance | 同一前提 → 问「你去北京的高铁订几点的？」→ **期望：指出前提已失效，不是顺着编** |
| Implicit Policy Adaptation | 同一前提 → 请求「帮我订周四的酒店」→ **期望：不订** |

## §10 一句话结论

> **本项目的记忆架构在方法论上是站得住的**——分层、游标、加权而非过滤、
> 保真度感知召回，每一条都能在两篇综述里找到坐标。
> **缺的不是架构，是三样东西：收敛闸门（§3）、统一口径（§4.3）、可离线跑的全链路评测（§8）。**
> 前两样是修，第三样是地基——没有它，前两样改完之后我们**没有依据说"变好了"**。
