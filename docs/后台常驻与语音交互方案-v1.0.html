后台常驻、语音交互与插件安全检测方案 v1.0

English | 简体中文

本文回答六个问题：① agent 能否在后台持续运行而不干扰用户 ② 打开 App 即自动就绪， 不再需要 Termux ③ 各方案所需权限与系统限制 ④ 如何保证用户操作不受干扰 ⑤ 语音唤醒 + 用户自带 TTS Key 的交互设计 ⑥ 插件市场的病毒检测与隐私隔离

前置事实：P0 五项真机验证（2026-09-22）已确认 —— 虚拟屏已否决， dsh 通过 proot-distro Debian 容器跑通（容器 1.6 GB / node_modules 307 MB）。

0. 先说结论

问题 结论 性质
后台持续运行 可行，但有硬天花板 —— 前台服务 + 悬浮窗 + 无障碍三件套，Android 15 下 dataSync 类每天累计 6 小时 ⚠️ 需产品决策
打开 App 即就绪 可行 —— 首次引导装配 proot 环境，之后常驻 ✅ 无阻断
无需手动启动 Termux 可行 —— 我们自己跑 proot，Termux 只是开发期验证工具 ✅ 无阻断
不干扰用户 部分可行 —— 悬浮小窗可用；"完全不影响"在 P0-3 后已丢失，见 §4 ⚠️ 需重新定义
语音唤醒 可行但门槛高 —— 麦克风前台服务不能在后台凭空启动；需常驻通知 + 隐私指示器 ⚠️ 有系统性代价
TTS/对话弹窗 可行 —— 悬浮窗 + 独立配置页，Key 走既有加密链路 ✅ 无阻断
插件病毒检测 要改设计 —— VirusTotal 公开 API 禁止商业产品使用，且上传样本会分享给厂商 ❌ 原设想不可用

最需要你先拍板的一件事：dataSync 前台服务每天 6 小时上限。这直接决定 "agent 能不能全天候待命"，或者退一步做"任务期才激活"。详见 §3.3。

1. 总体架构：进程与生命周期

1.1 三层进程模型

┌─────────────────────────────────────────────────────────────┐
│  L0  主进程 (com.pocketagent)                                │
│      ├── UiActivity（Compose UI）                            │
│      ├── AgentForegroundService  ← 常驻通知，唯一保活锚点     │
│      ├── AgentAccessibilityService ← 系统绑定，独立生命周期    │
│      └── OverlayService（悬浮球/悬浮窗）                       │
├─────────────────────────────────────────────────────────────┤
│  L1  :agent 进程（Android 独立进程，android:process=":agent"） │
│      └── 任务编排、预算熔断、checkpoint                       │
│      ⚠️ 不常驻，任务期启停                                     │
├─────────────────────────────────────────────────────────────┤
│  L2  proot 容器内的 Node + dsh（Linux 进程，非 Android 进程）  │
│      └── 由 L1 通过 runInContainer 拉起，任务结束即回收        │
└─────────────────────────────────────────────────────────────┘

关键设计：只有一个常驻锚点。

所有保活压力集中在 AgentForegroundService 一个服务上。其余全部按需启停：

组件 生命周期 理由
AgentForegroundService 常驻（用户可关） 唯一保活锚点；被杀则全盘失效
AgentAccessibilityService 系统管，我们只能引导 系统绑定，不受我们的服务存亡影响
OverlayService 随主服务 悬浮球是用户可见的"正在待命"信号
:agent 进程 任务期 隔离崩溃；空闲时零开销
Node + dsh 任务期 P0-1 证明能跑，但 1.6 GB 常驻无意义

⚠️ 不要试图让 Node 独立保活。 《移动端约束分析》已写明：App 被系统杀掉， Node 必然一起死。proot 容器在这个 App 的 uid 下跑，没有独立的存活资格。

1.2 首次启动装配（"打开 App 即就绪"的核心）

用户永远不需要碰 Termux。Termux 只是我们在开发期用来验证 dsh 能否跑通的工具， 产品里不出现。

首次启动引导
├── 1. 权限引导（11 项，见 v2.0 §6.2）
├── 2. 【新增】运行时装配
│      ├── 解压 Debian rootfs 到 app 私有目录
│      │   （/data/data/com.pocketagent/files/proot/）
│      ├── 解压 Node arm64 二进制（122 MB）
│      ├── 解压裁剪后的 dsh profile（见 §1.3）
│      └── 进度条 + 可中断可续传
└── 3. 自检：起一个 hello 任务验证容器可用

⚠️ 必须做成可中断可续传。 1.6 GB 的解压 + 首次启动，用户可能中途切走。 断点续传的状态要持久化，否则重来一遍是灾难。

1.3 体积必须重做（与 P0 报告呼应）

P0-1 实测容器 1.6 GB 是未裁剪的全量部署。产品化必须砍：

项 全量 目标 手段
Debian rootfs ~1.4 GB 待实测 用 docker 导出精简 rootfs，删文档/man/apt 缓存
Node 122 MB 122 MB 已是最小官方 tarball，保留
node_modules 307 MB 待实测 裁掉 pnpm(39) / @opentelemetry(31) / @img/sharp(28) / node-pty(27) / @mistralai(25)
合计 1.6 GB 目标 ≤ 400 MB 需要一轮实测

⚠️ 关键问题：node-pty 能不能裁？ dsh 的终端工具依赖它，但我们安卓上没有 bash， 终端类工具本来就要剔除。若 node-pty 只是终端工具的依赖 → 可裁。这要实测验证 —— 如果它是 dsh 核心启动链路的一部分，裁不掉，体积下限就被卡住。

另一个选项：proot 是否必要？ 纯 Node 部分（无 native 模块）本来可以不用 proot。但 P0-1 已证明 dsh 需要 node-pty / @img/sharp 的 glibc 版本 —— 除非我们确认这两个能裁掉， 否则 proot 是硬需求。这同样是待实测项。

2. 打开 App 即自动启动：可行的实现路径

2.1 四种"自启动"触发源的现实评估

触发源 可行性 限制
用户点击图标 ✅ 最可靠 但需要用户主动点
BOOT_COMPLETED ⚠️ 受限 不得用它启动 dataSync / mediaPlayback / mediaProjection / camera / phoneCall 类型的前台服务（Android 15）；microphone 从 Android 14 起也不行
无障碍服务自启 ✅ 最佳路径 系统会在满足条件时自动绑定，不受 BOOT_COMPLETED 限制
快捷方式 / 桌面小组件 ✅ 可用 用户显式操作，豁免后台启动限制

结论：主路径走无障碍服务自绑定，而非 BOOT_COMPLETED。

开机
 └─ 系统扫描已启用的无障碍服务 → 自动绑定 AgentAccessibilityService
     └─ onServiceConnected() 里启动 AgentForegroundService
         └─ 此时"应用处于前台"吗？→ 见 §3.2 的豁免分析

⚠️ 这里的坑：onServiceConnected 回调时应用算不算"前台"？如果不算， 启动 microphone 或 dataSync 前台服务会被拒。这是必须真机验证的新实验（EX-17）。

2.2 建议新增 EX-17 实验

项 内容
假设 无障碍服务 onServiceConnected 回调期间，应用满足后台启动前台服务的豁免条件
方法 ① 冷启动后等服务自绑定，看 startForeground 是否抛 ForegroundServiceStartNotAllowedException ② 对比用户点击图标后的同操作 ③ 分别测各 foregroundServiceType
通过标准 至少 specialUse 类型能在绑定回调里启动成功
失败预案 退化为"必须用户点一次图标"，引导流程里明确要求

2.3 specialUse 类型是更优选择

Android 14+ 强制声明前台服务类型。对本项目，specialUse 比 dataSync 更合适：

类型 6 小时限制 适用性
dataSync ⚠️ 受限（Android 15 起每天 6 小时） 语义是"数据同步"，与我们不符
specialUse ✅ 不受 6 小时限制 语义是"其他用途"，需在 manifest 里写 PROPERTY_SPECIAL_USE_FGS_SUBTYPE 说明 
<service
    android:name=".service.AgentForegroundService"
    android:foregroundServiceType="specialUse">
    <property
        android:name="android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE"
        android:value="用户主动开启的屏幕辅助任务执行，任务期间需要保持与本地AI运行时的连接" />
</service>

⚠️ 别把 specialUse 当免死金牌。 Google Play 会审核该说明的合理性； 我们不上架，但滥用该类型会加速系统/厂商把我们列入管控名单。 声明必须诚实 —— 我们确实不是"数据同步"。

3. 系统限制全景（这是最需要你知道的部分）

3.1 各版本硬限制（已核实官方文档）

版本 限制 对我们的影响
Android 12 (API 31) 后台不得启动前台服务（少数例外） 必须在前台或豁免场景启动
Android 14 (API 34) 必须声明所有 FGS 类型 + 对应权限，否则 SecurityException 漏一个就崩
Android 14 microphone 不得从 BOOT_COMPLETED 启动 语音唤醒不能靠开机广播拉起
Android 15 (API 35) dataSync / mediaProcessing 24 小时内累计 6 小时 ⚠️ 本方案最大约束
Android 15 SYSTEM_ALERT_WINDOW 应用从后台启动 FGS 的豁免收窄 —— 必须当前有可见悬浮窗 悬浮窗策略要重新设计
Android 16 (API 36) 前台服务启动的后台作业须遵守 JobScheduler 配额 未来风险，先记录

Android 15 的悬浮窗豁免收窄，这条特别要注意 —— 它直接打在"悬浮小窗"这个方案上：

只有在应用当前具有可见的叠加层窗口时，持 SYSTEM_ALERT_WINDOW 的应用 才能从后台启动前台服务。之前豁免范围更广。

含义：悬浮球必须在"常显"状态，不能是"需要时才画"。这反而简化了设计 —— 悬浮球常驻既满足豁免条件，又是给用户的可见信号。

3.2 权限清单（在 v2.0 的 11 项之上新增）

# 权限 用途 何时申请
12 FOREGROUND_SERVICE 前台服务基础 安装即声明
13 FOREGROUND_SERVICE_SPECIAL_USE 我们的服务类型 安装即声明
14 POST_NOTIFICATIONS 前台服务通知（Android 13+ 需运行时申请） 引导流程
15 RECORD_AUDIO 语音唤醒 用户主动开启时，见 §5
16 SYSTEM_ALERT_WINDOW 悬浮窗 v2.0 已有（#4）
17 REQUEST_IGNORE_BATTERY_OPTIMIZATIONS 保活 v2.0 已有（#10）
18 INTERNET TTS / 模型调用 安装即声明

⚠️ RECORD_AUDIO 必须与"语音唤醒"功能开关绑定。不能因为"以后可能用"就提前要。 这是社区分发最容易被质疑的点，也是最容易被用户反感的权限。

3.3 ⚠️ 需要你决策：6 小时上限怎么处理

这是本方案唯一的产品级分叉：

方案 做法 优点 缺点
A. 常驻 用 specialUse 类型，不受 6 小时限制 全天候待命 常驻通知 + 悬浮球永远在；耗电；被厂商管控风险高
B. 任务期 空闲时停 FGS，用户召唤才启动 省电、干扰小 不能用语音唤醒（麦克风 FGS 不能在后台凭空起）
C. 混合 悬浮球常驻（低开销），重资源任务期才起 FGS 平衡 实现复杂，要考虑状态机

我的建议是 C，理由是它对应《移动端约束分析》里的资源分级： 悬浮球常驻成本极低（一个 overlay view），真正的开销在 Node/dsh/截图。 而"打开 App 即自动启动"这个需求，其实只需要悬浮球 + 无障碍服务 + 一个轻量服务， 不需要让整个 agent 运行时全天候空转。

4. 如何保证用户操作不受干扰（需要修订的期望）

4.1 一个必须承认的事实

P0-3 已否决虚拟屏，所以"完全不影响用户用手机"这个目标已经丢失。 这是我必须说清楚的，不能含糊过去。

原设计想的是：agent 在虚拟副屏上干活，用户在主屏照常用手机，两者互不干扰。 实测证明第三方侧载应用做不到（uid=2000 连 adb 都被拒）。

4.2 现实中的四档干扰程度

档位 形态 用户感受 何时可用
0 后台静默 不占屏，只处理数据类任务 🟢 无感 任务不需要看屏幕时
1 悬浮小窗 freeform 小窗浮在角落 🟡 占一小块屏 主形态
2 全屏接管 agent 全屏操作 🔴 用户完全无法用手机 用户主动交出控制权
3 手动引导 系统教用户自己点 🟢 用户完全掌控 政策收紧时的保命方案

4.3 干扰最小化的具体手段

  1. 进程优先级隔离：agent 任务跑在 :agent 进程，UI 线程永不被占
  2. 感知降级阶梯（《移动端约束分析》核心设计）： 优先第 0 档（不感知，直接 am start）→ 树 → 局部截图 → 全屏 每降低一档截图需求，就少一次屏幕占用
  3. 任务预算熔断：AgentBudget 限制轮次/时长/能耗，避免"跑飞了停不下来"
  4. 随时可中断：悬浮球长按 = 立即停止；这是给用户的"急停开关"
  5. 不抢焦点：悬浮窗用 FLAG_NOT_FOCUSABLE，不抢输入焦点
  6. 音频让路：语音唤醒检测到其他应用占用麦克风时主动退让（见 §5.3）

4.4 悬浮球：不仅仅是个 UI

在 Android 15 的豁免收窄规则下，常显的悬浮窗是"能否从后台启动服务"的钥匙。 所以悬浮球承担三个职责：

  • 用户可见的"agent 在待命"信号
  • 后台启动前台服务的豁免凭据（有可见 overlay 窗口）
  • 急停按钮

设计上要克制：一个小的半透明圆点，可在引导里让用户选"贴边隐藏"。 但"完全隐藏"要慎用 —— 隐藏了可能就丢豁免。这需要 EX-17 一并验证。

5. 语音交互

5.1 语音唤醒：真实的门槛

核心限制（已核实）：

RECORD_AUDIO 受"使用期间"（while-in-use）限制。应用在后台运行时， 无法创建 microphone 前台服务；也不能从 BOOT_COMPLETED 启动。

含义：语音唤醒不可能"开机自动待命"。 用户必须：

打开 App → 打开"语音唤醒"开关 → 授予麦克风权限
  → 应用在前台启动 microphone FGS → 之后可退到后台持续监听

这是 Android 的设计意图（防止偷偷录音），不是可以绕过的技术问题。

5.2 唤醒引擎选择

方案 体积 离线 唤醒词 备注
Porcupine（Picovoice） 小 ✅ 自定义 免费额度限个人；商用需授权
Vosk / Kaldi 中 ✅ 需训练 开源，体积较大
自训练小型模型 ~100 KB 级 ✅ 自定义 见 Mamba 架构方案，需自己训
系统 VoiceInteractionService 0 ✅ 系统唤醒词 需要系统签名预装，我们拿不到

建议：Porcupine 起步（验证流程），长期切自训练模型（GPL-3.0 合规 + 零授权费）。 ⚠️ Porcupine 商用需付费授权，而我们不盈利但接收捐赠 —— 这个边界要法务确认， 保守做法是直接用开源方案。

5.3 ⚠️ 麦克风独占冲突（必须在引导里说清）

Android 的麦克风是独占资源。我们常驻监听 → 用户用语音输入法、打电话、 录视频时可能冲突。

行业惯例做法（讯飞 SDK 文档提到）：屏幕点亮时暂停唤醒。

锁屏 / 息屏  → 持续监听唤醒词（此时没人和我们抢麦克风）
屏幕点亮     → 暂停监听，释放麦克风（用户可能在用语音输入）
悬浮球长按   → 手动进入语音输入

这个策略要写进引导，否则用户会觉得"这 App 让我的语音输入法坏了"。

5.4 TTS 与文字对话

TTS Key 的存放（按你的要求，独立弹窗）：

设置页
├── 模型 Key（对话用）        ← 独立入口，独立弹窗
├── 【新增】语音合成 Key      ← 独立入口，独立弹窗
└── 其他配置

UI 要点： - 两个 Key 各自独立页面，顶部互相标注"这是给语音合成用的，不是对话模型" - 填入后立即校验（发一个短合成请求），失败要明确指出是 Key 问题还是网络问题 - 显示 Key 时默认打码，需要点击"眼睛"才展开

5.5 弹窗文字对话

两种形态：

形态 触发 实现
悬浮球点击展开 用户点悬浮球 悬浮窗内嵌输入框，不抢主屏焦点
主动询问弹窗 agent 需要用户决策时 ask-user 类交互，悬浮窗内展示

⚠️ 悬浮窗内的文本输入是个技术难点：FLAG_NOT_FOCUSABLE 的悬浮窗收不到键盘输入。 需要： - 输入时临时移除 FLAG_NOT_FOCUSABLE - 或者跳一个透明 Activity 承载输入（更可靠，但会短暂抢焦点）

建议用透明 Activity 方案 —— 悬浮窗的输入法弹出行为在各 ROM 上差异太大。

7. 插件病毒检测（原设想需要改设计）

7.1 ❌ 坏消息：VirusTotal 公开 API 不能用

我核实了官方文档，有三条硬伤：

问题 原文
禁止商用 "The API must not be used in commercial products or services, it can not be used as a substitute for antivirus products... Noncompliance of these terms will result in immediate permanent ban"
上传即分享 上传的样本会进入 VirusTotal 的样本库，分享给安全厂商
速率极低 免费版 每分钟 4 次请求

第二条是致命的：插件的 .pagent 包可能包含作者未公开的内容，上传即等于公开。 而且"上传"这个动作本身就违背了我们"数据不出设备"的原则。

7.2 ✅ 改后的分层检测设计

核心原则：本地能判的绝不上传；必须联网的，只发哈希不发文件。

L0  本地静态分析（零网络，默认开启）★主力
├── AndroidManifest 解析
│   ├── 危险权限越权检测（插件声明了 keymgmt 不该有的权限？）
│   ├── exported 组件检测（是否导出了不该导出的组件）
│   └── 前台服务类型与实际行为是否匹配
├── DEX 字节码扫描
│   ├── 敏感 API 调用检测（反射 / Runtime.exec / 动态加载 dex）
│   ├── 已知恶意特征匹配（本地特征库）
│   └── 混淆强度评估
├── 资源与配置审计
│   ├── 硬编码 URL / IP（偷偷外传数据）
│   └── 内嵌可执行文件
└── 与声明能力做交叉验证 ★最重要
    └── 插件声明"读剪贴板"，却调了网络 API → 高危

L1  哈希查询（联网，只发 SHA256，不发文件）
├── 查询公开威胁情报的哈希库
├── 命中 → 直接拒绝
└── 未命中 → 不等于安全（新样本查不到），继续 L2

L2  隔离沙箱行为分析（可选，需用户显式同意）
├── 在受限环境运行插件，监控行为
└── ⚠️ Android 上做沙箱隔离极难，优先级放到 M3 之后

L1 到底查谁？ —— 这里需要你决策：

选项 可行性 隐私
VirusTotal 哈希查询 API ⚠️ 免费版禁商用，可查但违反 ToS 只发哈希，但仍需同意 ToS
自建哈希库（GitHub Pages 静态 JSON） ✅ 与"不建后端"原则一致 完全可控
Google Safe Browsing ✅ 系统级，但只覆盖 URL 不覆盖 APK 隐私好
多引擎聚合服务（如 MetaDefender） ❌ 商用需付费 —

建议：自建哈希库（威胁情报由社区贡献）+ 可选接入 Safe Browsing。 不依赖任何禁止商用的 API，也守住"数据不出设备"。

7.3 隔离要求的具体落实（你强调的重点）

"坚决拒绝该病毒检测程序直接接触到用户的隐私信息和 apikey"

落实为四条硬规则：

规则 实现
① 无 Key 访问 检测模块作为独立进程 + 独立模块，无法 @Inject 到 keymgmt。用依赖方向强制：plugin:scan 不依赖 keymgmt
② 只读待检文件 只接受一个 File 或 ByteArray 入参，不透出任何应用上下文
③ 网络请求最小化 只允许发 SHA256；请求体用 check_kt_quotes 式的静态审计脚本钉住（进 CI）
④ 用户可见 每次联网检测前告知"将上传文件哈希值"，可关闭

⚠️ plugin:scan 模块要在 settings.gradle.kts 里显式声明"禁止依赖 keymgmt"， 并用 check_module_deps.py 之类的脚本做守卫 —— 让架构约束可被自动化检查。

7.4 但说实话：静态扫描的局限

必须诚实告知用户：

静态扫描能拦住"明显恶意"的插件，但拦不住"看起来正常"的。 一个 L2 脚本插件完全可以在运行时才拼接出恶意行为。

所以真正可靠的防线不是扫描，而是能力边界本身： 插件永远拿不到 Key、绕不过 SafetyGuard、调不了 payment.*。 扫描是"多一道提醒"，安全边界才是"真正的保险"。

这个表述要写进插件页 UI —— 不能让用户以为"扫过了就安全"。

10. 一句话总结

技术上是可行的，代价是必须承认三件事：

  1. "完全不影响用户"已经做不到了（虚拟屏被否决），现实目标是"干扰可控"
  2. "全天候待命"与"省电 + 低管控风险"是矛盾的，必须选边
  3. 语音唤醒必须由用户主动开启且不能开机自启，这是 Android 的设计意图，不是技术缺陷

而 VirusTotal 那条路，从隐私和合规两个角度都必须放弃 —— 这与"数据不出设备"的根本原则冲突。
