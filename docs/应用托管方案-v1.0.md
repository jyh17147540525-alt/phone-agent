# 应用托管（虚拟屏）方案 v1.0

> 目标：角色能操作**用户授权过的账号**（QQ / 微信 / 抖音 / 微博…），
> 而**不占用用户的屏幕**、不让用户觉得被打断。
>
> 这份文档记录的是**实测结论**，不是设想。每条结论后面都跟着系统原话。

---

## 1. 用户要什么

用户原话：

> 模拟的角色可以操作用户授予的相关账号，例如 QQ、微信、抖音等等。
> 角色操作这些软件时，默认手机已经在 root 模式了，所以这些软件的操作
> **都必须在虚拟屏里**，不能对用户使用手机造成干扰。
> 要让用户无感，不占用用户的屏幕，而且响应速度要快。

拆成四条硬指标：

| # | 指标 | 判据 |
|---|---|---|
| 1 | 目标 App 的窗口**不出现在用户屏幕上** | `dumpsys window` 里没有它的可见窗口；用户屏幕的 `mCurrentFocus` 不变 |
| 2 | 能**读**它的界面 | 拿到节点树或像素 |
| 3 | 能**点**它、**打字** | 点击落到正确坐标 |
| 4 | 快 | 一次操作的端到端延迟在秒级 |

## 2. 已经排除的路（全部有真机证据）

### 2.1 freeform 小窗 + `am task resize`

能跑起来，但 **App 的窗口真的画在用户屏幕上**。

- 负坐标被系统拒绝：`Error: bad left arg: -2000` —— 所以"挪到屏幕外"不可能；
- 只能挪到角落，最小也是可见的一小块；
- freeform 窗口仍然抢 `topResumedActivity`，用户按 HOME 也拿不回来；
- 结果：**违反指标 1**。已实现的 `:hosting`（`AppHostingRunner`）保留，
  但它只是"体面地占一个小角"，不是用户要的东西。

### 2.2 自建 `VirtualDisplay`（只带 `PUBLIC` 标志）

系统直接拒绝：

```
SecurityException: Requires CAPTURE_VIDEO_OUTPUT or CAPTURE_SECURE_VIDEO_OUTPUT
permission, or an appropriate MediaProjection token in order to create a screen
sharing virtual display. In order to create a virtual display that does not
perform screen sharing (mirroring), please use the flag
VIRTUAL_DISPLAY_FLAG_OWN_CONTENT_ONLY.
```

★ 系统自己给出了正确答案：加 `OWN_CONTENT_ONLY`。见 2.3。

### 2.3 自建 `VirtualDisplay`（`PUBLIC | OWN_CONTENT_ONLY`）+ `setLaunchDisplayId`

**虚拟屏建成了**（这是好消息：不需要 root，也不需要录屏权限）：

```
B: createVirtualDisplay 成功 id=2 尺寸=720x1280
验证: Display = 0(内置屏幕), 2(pocketagent-host-probe)
```

**但把第三方 App 拉进去被拒**：

```
SecurityException: Permission Denial: starting Intent { act=android.intent.action.MAIN
cat=[android.intent.category.LAUNCHER] flg=0x10000000 pkg=com.tencent.mobileqq
cmp=com.tencent.mobileqq/.activity.SplashActivity }
from ProcessRecord{... com.pocketagent.debug/u0a499} (pid=4138, uid=10499)
with launchDisplayId=2
```

⇒ 结论：**"建虚拟屏"和"往虚拟屏里拉起别人的 Activity"是两件独立的事**，
前者的门槛低（一个标志位），后者只有 system / shell / root 能过。

### 2.4 `ActivityView`

`android.app.ActivityView` 本来是最省事的答案（自带虚拟屏 + `dispatchTouchEvent`
直投输入 + 不需要任何权限），但它**不是公开 API**（`@SystemApi`）。
compileSdk 36 下直接：

```
e: Unresolved reference 'ActivityView'
```

⇒ 过不了编译器，不用谈上架。

### 2.5 root 执行 `am start --display N`

```
SecurityException: SafeActivityOptions.checkPermissions
```

即使 `su -c` 是 uid 0 也一样。原因见 2.6。

## 3. 剩下的路

### 3.1 关键发现：`shell` 被允许，`root` 的 `am` 反而不行

系统里"能不能往非默认屏幕拉起 Activity"的判据是
**调用者是不是 system / shell / root**，而 `am` 这条 shell 脚本是以
**它自己的进程身份**去的 —— 经 `su -c am ...` 时它没有走那条判据认可的路径。
用 `adb shell am start --display N`（uid 2000）是另一条独立的调用链。

⇒ 两个可行方向：

| 方向 | 做法 | 依赖 |
|---|---|---|
| **A. root 助手进程** | `su -c app_process ...` 起一个 uid=0 的 Java 小程序：建 VirtualDisplay → 拉起目标 Activity → ImageReader 取帧 → `input -d N tap x y` 注入 | 需要 App 拿到 root |
| **B. Shizuku（uid 2000）** | 同上，但进程以 shell 身份跑；Shizuku 已装在用户手机上 | 需要 Shizuku 在跑 + 用户授权 |

两条路的产物是一样的：**一个常驻的"屏主"进程**，App 通过一个本地 socket
把"打开微信 / 点第 3 条消息 / 打这几个字 / 截图给我"发过去。

### 3.2 为什么现在还没跑通

**App 拿不到 root。** 真机状态：

```
$ adb shell su -c id
uid=0(root) ... context=u:r:ksu:s0          # adb 侧可以

$ adb shell run-as com.pocketagent.debug su -c id
run-as: exec failed for su: Permission denied   # App 侧不行
```

原因不是 SELinux，是 **KernelSU 的 allowlist 里没有这个 App**：

- 管理器包名：`com.resukisu.resukisu`（ReSukiSU，`ksud 4.2.0-rc3`，kernel 35187）
- **但管理器没装**（`pm list packages` 里没有它）
- `/data/adb/ksu/.allowlist` 是二进制格式（魔数 `USK\x7f`），内容只有
  `com.dsh.lochelper` 与 `com.icbc`
- `ksud debug set-manager` 走不通：`Error: CONFIG_KSU_DEBUG is not enabled`

⇒ 解锁动作只有一个：**装回 ReSukiSU 管理器，在它的界面里给本应用授权 root**。
装好之后 3.1 的方向 A 立刻可做。

## 5. 一条不能省的话

**不要**把 2.3 那个"虚拟屏建成了"当成"功能快好了"。
建屏只是第一环，而且是最容易的一环。真正的三座山是：

1. 把**别人的 Activity** 拉进这块屏（要 shell/root）；
2. 从这块屏**取帧**并让模型读懂（ImageReader 拿的是原始 RGBA，
   要么自己编码，要么接无障碍树）；
3. 把**触摸事件**打进这块屏（`input -d N` 或 `injectInputEvent`）。

第 3 条还有个隐患：注入的触摸事件在目标 App 看来是"真实用户"，
所以**安全闸门必须在注入之前**，不能指望目标 App 自己拦。
这与 `:mcp` 现有的六步安全关卡是同一条纪律，只是换了个注入通道。
