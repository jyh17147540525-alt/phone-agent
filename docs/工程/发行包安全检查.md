## 四项检查与它们对应的风险

| 检查 | 风险 |
|---|---|
| `debuggable` 不为 true | 为 true 时任何人 `adb` 接上就能读应用私有数据 —— 包括 API Key 密文，以及内存里的明文 |
| `allowBackup = false` | 为 true 时 `adb backup` 能把整个数据目录拖走 |
| 包名不带 `.debug` | 否则会在用户手机上装成"另一个应用"——两个图标、两份数据 |
| 签名状态 | 用 debug keystore 签的包不能上架；未签名的包不能直接装 |
| 体积 ≤ 45 MB | 涨回来说明 `abiFilters` 被撤掉，或引入了新的重量级原生依赖 |
| 无 x86 原生库 | x86 是模拟器架构，真机用不上，纯占体积 |

⚠️ `debuggable` 与 `allowBackup` 的"默认值陷阱"相反：
· `debuggable` 在 release 下**默认 false** ⇒ 没声明是**正确**的
· `allowBackup` **默认 true** ⇒ 没声明是**危险**的

脚本对这两者的判定逻辑不同，原因就在这里。

## 尚未解决：签名

`:app/build.gradle.kts` 里**没有 `signingConfig`**，所以
`assembleRelease` 的产物叫 `app-release-unsigned.apk` —— **装不上**。

这不是缺陷，是**有意留白**：
- 签名密钥属于维护者，不该进开源仓库
- 用 debug keystore 签名更糟（不能上架，且看起来像正式包）

要真正发行，需要：
1. 生成发布密钥库
2. 在 `local.properties` 或环境变量里给出路径与口令
3. `build.gradle.kts` 里接上 `signingConfigs.release`

⚠️ 这三步都涉及密钥，**应当由人来决定**，不该由自动化流程代劳。

## 已知未做

### ✅ 体积已解决（2026-11-01）

审计发现 `lib/` 占 57.7 MB（89%），其中 **32.3 MB 是 x86 模拟器架构**。

```
ML Kit OCR     39.2 MB（四个 ABI 各一份）
SQLCipher      18.5 MB（四个 ABI 各一份）
x86 + x86_64   32.3 MB  ← 模拟器架构，真机用不上
```

⇒ release 收紧 `abiFilters` 到 `arm64-v8a` + `armeabi-v7a`：

**65.0 MB → 32.7 MB（约 −50%）**

⚠️ 只对 release 收紧：debug 包要能在模拟器上跑，开发和 CI 都依赖它。
- **多维分析**：未检查 `extractNativeLibs`、`useLegacyPackaging`、
  以及 `baselineProfiles` 是否真的生效。
