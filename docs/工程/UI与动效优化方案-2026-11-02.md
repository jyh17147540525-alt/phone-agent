# UI 与动效优化方案

> 2026-11-02。**这是一份方案，不含任何代码改动。**
>
> 全部结论来自读代码与统计，不是印象。每条都标了证据。

---

## 一、先说底座：它比自己想的扎实，不要重做

动手之前必须承认：这个项目的动效**不缺体系**。

| 已有 | 位置 | 说明 |
|---|---|---|
| 时长令牌 5 档 | `Motion.kt` `PaDuration` | 100 / 180 / 280 / 380 / 520 ms |
| 缓动令牌 | `PaEasing` | `Standard` / `Emphasized` |
| spec 工厂 | `PaMotion` | `enter` / `exit` / `page` |
| **系统设置尊重** | `MotionPreference` | 读 `ANIMATOR_DURATION_SCALE` + `TRANSITION_ANIMATION_SCALE` + 省电模式 |
| 触觉反馈层 | `Haptics.kt` (119 行) | —— |
| 玻璃/渐变遮罩 | `Glass.kt` (283 行) | —— |
| 滚动边缘渐隐 | `ScrollingEdge.kt` (137 行) | —— |
| 图标尺寸档位 | `IconGeometry` | 16/20/24/32/48 |
| 卡片入场节奏 | `MotionRules` | 260ms 基础 + 40ms 阶梯（上限 240ms）|

⇒ **方案的目标不是"补一套动效"，是把已经有的令牌真正用上。**

⚠️ 特别提醒：`MotionPreference` 已经在读系统的动画缩放与省电模式了。
这个项目在这一项上比多数应用做得好，别把它当"待办"重做。

## 二、六个真问题（都有数字）

### 问题 1：51 处列表只有 11 处带 key ⚠️ 最该修

```
LazyColumn / LazyRow / items()   51 处
其中带 key =                      11 处
```

**后果不是"不好看"，是三种具体的错**：
· 增删一项时 Compose 靠位置复用 → **相邻项被当成同一项重新组合**
· 带入场动画的列表 → 新项出现时**旧项跟着闪一下**
· 滚动位置在数据刷新后**跳回**

⚠️ 这类 bug 在静态截图里完全看不出来，只有真机滚动时才"感觉怪"。

**方案**：给所有 `items()` 补 `key = { it.id }`。
代价极低（一行），收益是"列表不再莫名其妙地闪"。

---

### 问题 2：9 处无限循环动画，无人管

```
AgentCard.kt        3 处
CallMotion.kt       5 处
ThinkingSlider.kt   1 处
```

`rememberInfiniteTransition` 是**永远在跑**的：只要那个 Composable 在组合里，
它每一帧都在推进，哪怕不可见。

⚠️ 三个具体的耗电场景：
· 任务卡片的呼吸光晕 → **列表里同时有 20 张卡片就 20 个循环**
· 通话界面 3 个循环 → 后台时仍在跑（如果界面没被拆除）
· 思考拉条的闪烁 → 用户离开对话框后

**方案**（分两步，先做低风险的）：
1. **不可见即停**：用 `Lifecycle` / `isVisible` 门控，屏幕不可见时不启动
2. **列表内降级**：滚动中暂停光晕（`LazyListState.isScrollInProgress`）

⚠️ 不建议直接删——那几处光晕是产品气质的一部分。

### 问题 3：8 处可点区域小于 48dp

```
CallScreen        .size(12.dp)
Components        .size(40.dp)
Interactive       .size(24.dp) / .size(16.dp)
List              .size(32.dp)
KeysScreen        .size(28.dp)
SourcesScreen     .size(20.dp)
ComposerActions   .size(40.dp)
```

Android 的最小触控目标是 **48dp**。小于它的按钮：
· 手指点不准（尤其单手、走路时）
· 无障碍服务会判为"目标过小"

⚠️ 要区分两种：**视觉尺寸**小、但**点击区**够大（正确做法），
和两者都小（真问题）。这 8 处需要逐个看，不能一律放大 ——
放大会破坏视觉比例。

**方案**：视觉不变，用 `Modifier.minimumInteractiveComponentSize()`
或给 `clickable` 外面包一层透明 padding。

---

### 问题 4：4 处动画绕过了时长令牌

```
AgentCard.kt      tween(900ms)
CallMotion.kt     tween(2_400ms) / tween(3_600ms) / tween(1_200ms)
```

这些是**刻意的慢呼吸/长循环**，用 `PaDuration` 的 280ms 显然不对。

⚠️ 但它们直接写数字，所以：
· 以后调"全站节奏"时，这几处不会跟着变
· 看起来像遗漏，下一个人不知道是"刻意"还是"忘了"

**方案**：在 `PaDuration` 里加一组**明确命名**的长周期令牌：
```kotlin
/** 呼吸光晕的一轮。刻意慢于 Normal —— 它表达"活着"，不是"响应" */
const val Breathe = 2400
const val BreatheSlow = 3600
const val Shimmer = 900
```
数字不变，但**意图被写下来了**。

### 问题 5：`TasksScreen` 2580 行

一个文件 = 两个屏幕的量。里面 14 个 `@Composable`。

**后果**：Compose 的重组范围由"读到的 state"决定，文件大本身不直接导致卡顿；
但它的实际后果是：
· 任何一处小改动都可能碰到共享的局部状态
· 无法单独预览/测试某个片段
· 改动的 diff 永远很大

⚠️ 这一条**收益最低、风险最高**（纯重构，用户感知不到）。
放在最后，或者干脆不做。

---

### 问题 6：转场几乎没用 `AnimatedContent`

```
AnimatedContent    3 处
Crossfade          0 处
```

`AppShell` 里 14 个 `composable(route)` —— 页面切换大概率是**瞬间替换**。

⚠️ 需要真机确认：如果 Navigation 已配了默认转场，那就不算问题。
**这一条我无法从代码确认**（`NavHost` 的 `enterTransition` 参数没查）。

## 三、方案：按「用户感知 ÷ 成本」排序

| 序 | 做什么 | 用户感知 | 成本 | 风险 |
|---|---|---|---|---|
| **1** | 补 40 处 `items(key=)` | 高（列表不闪、滚动不跳）| 低 | 极低 |
| **2** | 8 处触控区补到 48dp | 中（点得准了）| 低 | 低 |
| **3** | 长周期动画令牌化 | 无（但不留坑）| 极低 | 无 |
| **4** | 无限动画"不可见即停" | 中（省电、发热）| 中 | 中 |
| **5** | 页面转场（若确实没有）| 高（"顺滑感"主要来自这里）| 中 | 中 |
| **6** | 拆 `TasksScreen` | 无 | 高 | 高 |

### 建议的做法

**第一批（1+2+3）**：纯增益、可离线验、几乎不可能出错。
一次做完，一次装机。

**第二批（4+5）**：需要真机看效果，尤其第 5 条要先确认导航现状。

**第 6 条**：**建议不做**，除非有明确的重构需求。

## 四、我建议**不要**做的

### ❌ 不要重写动效系统
`PaMotion` / `PaDuration` / `MotionPreference` 已经够用。重写一遍的收益是零，
代价是所有已调好的手感全部丢失。

### ❌ 不要给所有东西加动画
"每个元素都在动"是廉价感的来源。这个项目现在的克制是对的 ——
`MotionRules` 的阶梯上限 240ms、`MotionPreference` 尊重省电模式，
这些都说明作者知道分寸。

### ❌ 不要引入第三方动画库
Compose 自带的够用。外部库在低端机上是额外的 dex 与兼容风险。

### ❌ 不要在没有真机的情况下改转场
转场的手感只能看，不能推。改完必须装机。

## 五、可验证性：哪些我能离线验，哪些必须真机

| 项 | 离线可验 | 需真机 |
|---|---|---|
| 补 `items(key=)` | ✅ 编译 + 静态检查（脚本数 key 覆盖率）| 滚动是否真的不闪 |
| 触控区 48dp | ✅ 脚本扫 `.size(<48.dp)` + `clickable` | 实际点击手感 |
| 长周期令牌化 | ✅ 编译 + 数值不变 | —— |
| 无限动画停跑 | ⚠️ 只能验逻辑 | **必须**（看电量/发热）|
| 页面转场 | ❌ | **必须** |

⚠️ 前三项我有把握；后两项只能出方案、由真机判定。

## 六、如果只做一件事

**补 `items(key=)`。**

40 处，一处一行。它修的是"列表莫名其妙地闪一下"——
而这种问题用户说不出哪里不对，只会觉得"这个 app 有点毛躁"。
