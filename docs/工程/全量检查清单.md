## 一个必须记下来的教训

**建了 16 个检查，只跑 1 个，等于只有 1 个检查。**

这和"写了检查但没有检查"是同一类失败 —— 而且更隐蔽：
文档里列着一堆脚本，看起来覆盖很全面，实际上从没被执行过。

⇒ 建议：把这 11 个不需要参数的检查**串成一个入口**，
每次交付前跑一次。那才是"检查"而不是"检查的清单"。
（本轮没做那一步，先把问题修完。）

## 统一入口（2026-11-01 之后）

前面那张表列了 16 个脚本 —— **清单本身不是检查**。
把需要人工参数之外的 12 条串成了一个入口：

```powershell
cd D:\手机agent开发
python tools/verify/verify_all.py            # 全部（约 56 秒）
python tools/verify/verify_all.py --fast     # 跳过最慢的逻辑测试（约 30 秒）
python tools/verify/verify_all.py --list     # 只列出会跑什么
```

### 实测

```
跑了 12 条 / 共 12 条｜失败 0｜跳过 0｜耗时 56s
✓ 全部通过
```

### 设计取舍

**① 全部跑完再汇总，不快速失败**
一次就知道有几处坏了，比修一处重跑一次快得多。

**② 每个脚本只打印最后一行的要点**
完整输出太吵；需要细看时单独跑那一条。

**③ 前置条件不满足时"跳过"，不报失败，并说清怎么补**
· `check_release_apk.py` 需要先 `assembleRelease`
· `check_line_endings.py` 需要一个早于本轮的基线

**④ 失败时的摘要**优先取"有数字的结论"而不是"建议"
⚠️ 第一版取到了「改法：把 **粗体** 换成「直角引号」」——
那是**建议**不是**发现**。已改成按 `✗` → `发现` → `!!` 的顺序取。
