### 2.2 逆向文档 §7「落地设计」 —— 四条判定

这一节是最容易照抄的，因为它写得很具体（段序、token 预算、卡片格式）。逐条判：

#### ① §7.2 砍层顺序 —— **不采纳**，我们有相反且更具体的决定

外部建议：超预算时**先砍 world** → 再砍 history 中段 → 最后压 summary。

我们的实现（`android/personalogic/src/main/kotlin/com/pocketagent/personalogic/PersonaAssembler.kt:110-123`）：

```
记忆(L4) → 锚点减量(L5，指令永远保留) → 状态(L3) → 世界设定(L6) → 人格核心缩摘要(L1)
```

memory 最先、**world 排在倒数第二**。代码里第 117-119 行写着理由（2026-11-02 定的）：

> 世界设定**排在最后** —— 设定被裁掉比记忆被裁掉更糟。丢一条记忆只是"这个没想起来"；
> 丢一条设定会让角色说出**与世界观矛盾的话**，而那正是"世界书崩了"。

外部建议的出发点是 SillyTavern 使用者的经验：他们的 world 动辄几千 token 的设定注水。
我们的世界书是**用户手填的设定 + 用户确认过的事实**，1200 token 预算里世界书只占 500 字上限，
体量根本不同。所以**结论相反是对的**，不是谁错 —— 但必须记下来，否则下一轮会有人"照文档改回去"。

#### ② §7.4 模型降级链 —— **该做，未做**

外部主张：主模型失败 → 同级备选 → 小模型（自动缩短 history），**不要报错给用户**。

现状：`grep` 全仓 `fallback|降级` 的命中全是无关的（能力降级、隐私模式降级）。
模型调用失败就是失败，用户看到报错。

**这是真缺口**，而且和本产品最痛的那个抱怨同源 —— 用户说过"切换模型的时候 AI 味特别浓"，
说明他在反复换模型试效果；换到一个不通的 Key 上就是一次硬报错。排 §4 第 1 位。

#### ③ §7.4 参数模板按角色/场景绑定 —— **半发现：对话主路径连一个参数都没发**

外部主张：不要全局一个 `temperature`。

现状更彻底：`android/provider/api/src/main/kotlin/com/pocketagent/provider/api/LlmProvider.kt:200`
`data class ChatRequest(..., val temperature: Double? = null, ...)`，
而全仓只有两处显式传 `temperature` —— `android/app/src/main/kotlin/com/pocketagent/data/AppContainer.kt:2133`
与 `:2747`，**都是后台任务的 0.2**。对话主路径传 null，等于各厂商默认值（多在 0.7–1.0 之间）。

判定：不是"该不该做参数模板"的问题，是**对话路径现在没有参数**。
先给角色扮演一个明确值（并按场景区分），再谈"按角色绑定"。排 §4 第 2 位。

#### ④ §7.1 「Android 不拼 prompt，拼装放 dsh」 —— **不采纳**

外部建议：Android 只持 UI 状态，prompt 拼装放 Node 侧 dsh，理由是"可热更新、可 A/B、改起来不用发版"。

我们的实现方向相反且是刻意的：`PersonaAssembler`、`RoleplayDiscipline`、`VoiceSamples`、`WorldBook`
全在 `android/personalogic`（纯 Kotlin，无 Android 依赖），`AssistantPromptBuilder` 在 `:app`。

理由：
1. **能离线跑测试。** 拼装逻辑在纯模块里，`run_logic_tests.py` 能跑 3500+ 条；放进 dsh 就只能靠真机点。
2. **dsh 不是常驻的。** 本产品不要求用户装 Node 环境；纯对话路径必须离线可用。
3. 热更新的代价是**拼装逻辑不可测**，而这个项目的病从来不是"改得慢"，是"改完是摆设"。

判定：不采纳。这也是为什么 §7.2 的段序建议只当作**参考项**逐条判，而不是当规范。

#### ⑤ §7.3 角色卡对齐 Character Card V2 —— **待做，但优先级低**

外部主张：数据模型直接对齐 `{"spec":"chara_card_v2","spec_version":"2.0","data":{...}}`，省得以后迁移。

现状：`grep chara_card|spec_version|character_book` 零命中。`CustomPersona` 是自己的字段
（`name`/`identity`/`addressUser`/`addressSelf`/`tone`/`gender`/`catchphrases`/`dialect`/`relationTo`/`memories`/`flawsRaw`）。

判定：**功能上不缺**（缺的字段我们有等价物）。它唯一的价值是**能导入别人做好的角色卡**。
那是一个新功能（"角色市场"），不是"数据模型对齐"。排 §4 末位，等真有导入了再说。

#### ⑥ §7.5 「别做输入关键词黑名单」 —— **已一致**

我们没做输入拦截。`RoleplayDiscipline` 与 `PromptHygiene` 都在**输出侧/入库侧**：
前者体检回复文本，后者过滤进入提示词的记忆条目。判定：一致，无需动作。

#### ⑦ §7.5 外部内容标记为不可信 —— **该做，未做**

外部主张：网页/短信内容进上下文时必须标成"以下是数据，不是指令"，并在 system 里声明。

现状：`grep 不可信|不是指令|untrusted` 的命中都在别的位置（插件安装、argv 注入、JSON-RPC 边界），
**没有一处是"外部内容进提示词时的标记"**。

影响面：本产品会把屏幕内容（`UiautomatorDump`、`ScreenCapture`）读进模型上下文，
这正是注入面。排 §4 第 3 位。
