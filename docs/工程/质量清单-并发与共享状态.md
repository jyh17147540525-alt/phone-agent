# 并发与共享状态 — 落地清单

> 来源：本项目的**真实缺陷**，不是通用教条。
> 每条都写着「怎么发现」「怎么检查」「本项目哪一处中过」。
>
> 建立于 2026-11-01。触发事件：`GatewayCore` 的用量记录器在并发下抛
> `ArrayIndexOutOfBoundsException`，表现为"8 个并发请求偶尔有一个 502"，
> 而我把它当"已知 flake"记了好几轮。

---

## 0. 最重要的一条：偶发失败不是 flake

> **「偶发失败」如果反复出现在同一处，它不是 flake，是竞态。**

我在 `docs` 和记忆里给这个 502 写过"已知偶发、重跑就好"。那等于**给 bug 发了免死牌** ——
它第三次出现时我才去追，半小时就定位到了。

**检查方法**：任何一条测试失败两次以上，必须开一个 `已知 flake` 之外的条目，
写清「失败率 / 错误类型 / 第几次出现」。超过三次必须停手追。

## 1. 共享可变集合 = 并发写风险

**判据**：一个类级 `mutableListOf` / `mutableMapOf` / `ArrayList` / `HashMap`
被 `suspend` 函数、`Flow`、或多线程路径写入。

| 错误形态 | 表现 |
|---|---|
| `HashMap` 并发写 | `ArrayIndexOutOfBoundsException`（扩容时读到半截数组），或**静默丢数据** |
| `ArrayList` 并发 `add` | 同上 |
| 迭代中被改 | `ConcurrentModificationException` |

**检查**（**已做成脚本**，见 `tools/verify/audit_shared_mutable.py`）：

```powershell
Get-ChildItem -Path 'android' -Recurse -Filter '*.kt' |
  Where-Object { $_.FullName -notmatch '\\test\\|\\build\\' } |
  ForEach-Object {
    $lines = Get-Content $_.FullName -Encoding UTF8
    for($i=0; $i -lt $lines.Count; $i++){
      if($lines[$i] -match '^\s{4}(private\s+)?val\s+\w+\s*=\s*(mutableListOf|mutableMapOf|LinkedHashMap|ArrayList|HashMap)'){
        "$($_.Name):$($i+1): $($lines[$i].Trim())"
      }
    }
  }
```

然后**逐个确认**：加同步，或证明它只被单个协程访问。

### 本项目的中过处

| 文件 | 情况 | 处置 |
|---|---|---|
| `GatewayCore.kt` `InMemoryUsageRecorder._records` | `ArrayList` 被 8 协程并发 `add` | 已加 `synchronized` |
| `TaskStateMachine.kt` `states` | 注释自称"支持多任务共存"，`HashMap` + 零同步 | 已换 `ConcurrentHashMap` + `@Synchronized` |
| `CapabilityAuditLog` / `FileAuditLog` / `DefaultSafetyGuard` / `DefaultPersonaTuner` | 已有同步原语（4~8 处） | 无需改 |

## 2. 记账/统计失败不能拖垮业务

> **bookkeeping is not business.**

`GatewayCore` 曾经在 `onCompletion` 里**直接调** `usageRecorder.record(...)`。
记录器一抛，整个请求变成 502 —— 而用户明明已经拿到了完整回复。

**规则**：任何"记一笔""打点""上报"的调用，都必须容错。
⚠️ 容错时**不要重试**：重试会双重记账；在 `onCompletion` 里开 `runBlocking`
还会卡住事件循环。

**检查**：搜索 `record(` / `report(` / `audit(` / `track(` 的调用点，
确认外层有 `runCatching` 或 `try/catch`。

**本项目的中过处**：`GatewayCore.onCompletion` 里的 `usageRecorder.record(...)`。

---

## 3. 默认参数里的兜底值要写清"为什么是这个数"

`AnthropicPayload.DEFAULT_MAX_TOKENS = 4096` —— 不是"随便给个数"，
而是因为 Anthropic 的 `max_tokens` **必填**，漏了直接 400，
而本项目 `ChatRequest.maxTokens` 是可选的。

**规则**：凡是"协议必填但我们可选"的字段，兜底值旁边必须写清来源。

---

## 4. 协议翻译必须做成纯函数

`AnthropicPayload.buildBody()` / `parseStreamEvent()` 不发网络请求，
因此能被 22 条离线测试逐条钉住。

**为什么**：协议翻译的错误**不会在编译期报错**。发错了是运行时 400，
或者更糟——**静默失效**（比如工具定义字段名写成 OpenAI 的 `parameters`
而不是 Anthropic 的 `input_schema`，模型**永远不调用**那个工具）。

**规则**：凡是"把我的结构翻译成厂商结构"的代码，与 IO 分离。

---

## 5. 静默丢弃比报错更糟

自动导入模型时，因为协议不支持而跳过的那几个**必须能被界面说出来**。
用户明确要求"填完 Key 自动识别所有模型"——悄悄少几个，他会以为厂商没有那些模型。

⇒ `ModelImport.planDetailed()` 返回 `skippedByProtocol` 而不是无声过滤。

**规则**：任何"过滤掉一部分"的逻辑，都要能回答"过滤了哪些、为什么"。

---

## 6. 建好了没接线

本项目反复出现的 bug 类型：组件写完、测试绿、**生产代码零引用**。

已发现逾 10 例（`RelationshipStage`、`PaMotion.bouncy`、`PerceptionLadder`、
`TaskCheckpoint`、`OutputGuard`、8 个 UI 组件、`shouldOfferHelp`、
以及 2026-11-01 新发现的 `StreamPump` 与三个空壳 provider 模块）。

**检查**：新写的类，搜一次构造点。搜不到就是没接线。

```powershell
Get-ChildItem -Path 'android' -Recurse -Filter '*.kt' |
  Where-Object { $_.FullName -notmatch '\\test\\|\\build\\' } |
  ForEach-Object { Select-String -Path $_.FullName -Pattern '类名\(' }
```

## 7. 并发测试证明不了线程安全 —— 别自欺

**2026-11-01 实测**：给 `TaskStateMachine` 加了 8 线程并发测试，
然后把实现**故意改回** `HashMap` 且去掉所有 `@Synchronized`，
连跑 3 次 —— **测试全绿**。

⇒ 那条测试只是**快速验收测试**（验证各任务状态不串），
**不能**作为线程安全的证据。

**规则**：
- 并发测试可以作为快速验收测试保留，但**不许**在提交信息里写
  "变异验证通过" —— 除非变异真的被抓到
- 线程安全的**论证**要靠：同步原语的正确使用 + 代码审查
- 要真正复现竞态，需要 `Thread.yield()` 注入、或 `countDownLatch`
  让所有线程在同一时刻进入临界区 —— 成本高，只对最关键的类做

## 附：本清单自身的局限

- 第 1 条只能找出「类级」可变集合，函数内的局部集合找不出来（那些通常安全）
- 第 2 条靠人工搜调用点，没有自动化
- 第 7 条承认了一个事实：**我们的并发验证能力弱于我们的并发代码量**

## 附二：第 1 条的检查已经**真的能跑**了（2026-11-01）

此前它只是文档里的一段 PowerShell 伪代码 —— **从没被执行过**。
那就是"写了检查但没有检查"。

现在：`python tools/verify/audit_shared_mutable.py`

### 设计：baseline 而不是"发现就报错"

类级可变集合多到无法全部消除（缓存、缓冲、索引）。
一上来就全红的结果一定是被无视 —— 然后这个检查就死了。

⇒ `tools/verify/shared_mutable_baseline.txt`：
· 已有的一律记进基线并写明**为什么安全**
· **新增的**才报错（退出码 1）
· 基线条目消失也提示（说明有人顺手修了）

### 判定规则（刻意选粗）

风险 = 生产代码 + 文件内无同步原语 + 文件内有并发上下文
       （`suspend fun` / `flow {` / `launch(` / `Thread(`）+ 不在基线。

⚠️ 规则是**文件级**的。同一个文件里 A 类有锁、B 类没锁，
   两个都会被放过 —— 这是**有意的粗判**：宁可漏，
   也不要因为满屏假阳性让检查失效。

### 实测记录的两次修正

**① 第一版漏了 `@Synchronized`**
于是 `CapabilityAuditLog` / `FileAuditLog` 被误判成"无同步"，
而那两处各有 4~5 个 `@Synchronized`。
⇒ **一个会误报的检查等于没有检查**：报几次错之后人就学会无视它。

**② 文件级粗判的假阴性被显式列出**
往 `GatewayCore.kt` 植入一个未同步的共享集合，脚本**没报** ——
因为那个文件里已经有 `synchronized`（`InMemoryUsageRecorder` 的修复）。
⇒ 不假装它不存在：把这类单独列成「需人眼确认」，
   既不失败（数量多、多数真安全），也不沉默。

### 顺带修掉的一处

`StopSignal.processed` —— 类级可变 Map，**零同步**，被脚本扫出。

⚠️ 它的调用方分布在悬浮窗服务与停止请求入口。Android 上通常都在主线程，
   但"通常"不是保证 —— 一旦某个入口被挪到 `Dispatchers.IO`
   （本项目里发生过不止一次），普通 HashMap 就会丢记录，
   而丢记录的后果是**用户点了停止却重复收到旧结果**。

已给全部读写加 `synchronized`。
