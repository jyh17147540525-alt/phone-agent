# 作息与在场：从 real-life 借了什么，为什么大半没借

> 对象：`:personalogic` 新增的 `Presence.kt`（她此刻在吃饭 / 在洗澡 / 已睡下）
> + 两处调度接线（主动消息的门）。
>
> ⚠️ 本文只借**机制**，不抄代码。上游 real-life 是 MIT，`lib/engine.mjs` 与
> `lib/clock.mjs` 全文读过；下面凡引用到函数名的地方都是真读过的，没引用的
> 部分（面板、i18n、命令）一律没细看。
>
> 一句话结论：**拿的是"她的作息能拦住一条消息"这个结构，不是它那套身体状态机。**
> 它 1800 行里有 1400 行在维护"她此刻是否真的在洗澡"；我们只要一个能被
> 时刻表推出来、且**说不出来就不说**的处境。

---

## 0. 结论先放这

| 项 | real-life | 本项目 | 为什么不一样 |
|---|---|---|---|
| 作息怎么来 | 状态机 + 30 秒心跳推 `elapsedHours`，落盘 `away`/`asleep` | **时刻表推算**，纯函数无状态 | Android 上没有那个心跳（常驻定时器要付电量与保活代价）；且我们要能离线钉住"21:40 她在干嘛" |
| 三餐是事件还是作息 | 真实事件（`ensureTodayMeals`），所以敢说"我刚吃完" | **只是作息**，永远说"这个点你一般在吃饭" | 我们没有"她吃过"的记录。这正是 `Physiology.kt` 类注释那条纪律：编一个"我刚吃完"就是撒谎 |
| 热聊保护 | 15 分钟内有对话 → 绝不进入吃饭/洗澡/睡觉 | **原样保留**（`HOT_CHAT_MINUTES = 15`） | 这条是对的，且它防的坏最刺眼：聊到一半她说去洗澡 |
| 抖动幅度 | 每项 ±20 分钟 | 饭点 **±10**、洗澡 **±25** | 她的作息比上游那个"宠物"更规律；洗澡本来就散，给更大浮动 |
| 抖动怎么取 | FNV-1a 按 `(ymd, salt)` | 同（`jitter(dayIndex, salt, amplitude)`） | 必须**当天固定**。每 tick 随机会让"她几点洗澡"在一天里漂三次 |
| 可见性分级 | 三档：群聊 / 非主人私聊 / 主人私聊 | **两档**：能不能发（`gate`）/ 怎么说（`promptLine`） | 单用户产品，前两档没有对应场景 |
| 请示与求饶 | 「主人，我能去洗澡吗」「憋不住了」+ 保底 confession | **全部不要** | 那是支配关系设定。本项目纪律是"断言她自己，不断言用户"（`LifeformDay` 类注释），搬过来会变成另一种人 |
| 饥饿 / 膀胱 / PMS 彩蛋 | 有，且带"三段式保底救济，永不饿死" | **不做** | `Physiology.kt` 已明确不做饥饿与生病，理由同上：编不出可信的由头 |

## 1. 上游的机制里，真正值得抄的是两条

### 1.1 热聊保护（`chatIdleMinutes = 15`）

`tick()` 里第 ⑦ 步：十五分钟内有过对话，就**不进入**任何"离开"状态。

它的位置很说明问题 —— 排在一堆身体曲线之后、所有"她要离开"的判断之前。
换句话说：**"她在不在"这件事，用户的话语权高于作息表。**

我们没有那堆曲线，但这条纪律完整拿过来了，而且放在 `at()` 的最前面：

```kotlin
// Presence.kt
if (lastUserSpokeAtMs > 0L) {
    val quiet = nowMs - lastUserSpokeAtMs
    if (quiet >= 0L && quiet < hotChatMinutes * 60_000L) return Presence()  // AT_HAND
}
```

### 1.2 「做不到就别说」—— 出口分两级

上游 `buildContext` 的三档可见性，本质是"**能说的话**"与"**可用的状态**"分开。
我们把这个结构留下，砍掉档位：

| 出口 | 回答什么 | 谁用 |
|---|---|---|
| `gate(presence)` | 她**能不能**在此时主动开口 | `AppContainer` 的两个 tick |
| `promptLine(presence)` | 这一句**该怎么**说话 | `PersonaAssembler.renderState` |

`gate` 只有两种结果（`Allow` / `Mute(reason)`），`Mute` 的理由会原样进日志 ——
以后翻日志不用猜"为什么那晚她没发消息"。

---

## 2. 为什么只留两个状态（而不是上游的七个）

`Where` 只有四个值：`AT_HAND` / `MEAL` / `SHOWER` / `SLEEPING`。
而 `promptLine` **只对 MEAL 与 SHOWER 返回内容**，另外两个返回 `null`。

这是刻意的，理由分别不同：

| 状态 | 为什么不写进提示词 |
|---|---|
| `AT_HAND` | 在的时候什么都不用说，这是默认值 |
| `SLEEPING` | 睡着时**根本不该在对话里** —— 那种情况由 `gate` 拦在门外，不该混进"该怎么说话" |
| 困 / 刚醒 | 已经由 `PhysiologyEngine.promptLine` 写过（凌晨、6–8.5 点刚醒）。再写一遍会在同一段提示词里出现两句意思相近的话，模型的反应是变僵 |

⚠️ 所以 `Presence` **不是**第二个生理系统，它是"手上有没有事"这一维。
两者分工：

```
凌晨 3:00  →  累（Physiology）/ 睡着（Presence）
21:40      →  不累（Physiology）/ 在洗澡（Presence）
```

## 3. 三条自制（上游没有，或方向相反）

### 3.1 提示词里不许出现分钟数

上游会给"饥饿 78/100、配额吃完了"这种精确数字。我们不给 ——
数字会被模型复述出来（"我还有 6 分钟就洗完了"），那就成了播报，不是说话。
`PresenceEngineTest.提示词里不许出现分钟数` 钉着这一条。

### 3.2 文案是「这个点你一般…」而不是「我正在…」

因为她**可能正在聊天**（热聊保护把她按在 `AT_HAND`，但时刻上她确实在饭点）。
写"我正在吃饭"会在下一句自相矛盾；写"这个点你一般在吃饭"则两层都成立。
`提示词说的是作息不是断言` 钉着这一条。

### 3.3 对话里要**关掉**热聊保护

这是最反直觉的一处，写在这里免得以后被"修"回去：

`PersonaAssembler.renderState` 调 `PresenceEngine.at(..., hotChatMinutes = 0)`。

- 保护的语义是「别把她从对话里拉走」（主动消息要用）；
- 而 `renderState` 就是**对话本身** —— 她当然可以边吃边回。
  洗澡那条文案（"是听见提示音才腾出手看的"）正是照这个场景写的。
- 若在这里也开保护：渲染时 `lastActiveAtMs` 恒等于"现在"，
  于是永远命中保护、这一段永远不出现 —— 接了个寂寞。

## 4. 改动清单

| 文件 | 内容 |
|---|---|
| `android/personalogic/src/main/kotlin/com/pocketagent/personalogic/Presence.kt` | **新增**。时刻表 + `Presence` + `Where` + `gate` + `promptLine` + `minuteOfDay` |
| `android/personalogic/src/test/kotlin/com/pocketagent/personalogic/PresenceEngineTest.kt` | **新增** 19 条 |
| `android/personalogic/src/main/kotlin/com/pocketagent/personalogic/PersonaAssembler.kt` | `renderState` 增 `presenceLine`；两处早退各加 `&& presenceLine == null`；新增 `localOffsetMinutesOf` |
| `android/app/src/main/kotlin/com/pocketagent/data/AppContainer.kt` | 新增 `presenceBusyReasonOf`；`proactiveTick` 与 `lifeformProactiveTick` 各插一处提前 return |

### 4.1 两处早退条件必须一起改

`renderState` 里原本有两条「无由头就不渲染」的早退：

```kotlin
if (state.isNeutral() && guide == null) return ""
if (parts.isBlank() && guide == null) return ""
```

如果只加 `presenceLine` 不改这两行，**状态中立时她吃饭就白接了** ——
最坏情况下这一段永远进不去，而测试也不会红（测试测的是 `Presence` 本身）。
两行都加了 `&& presenceLine == null`。

### 4.2 为什么放在 `AppContainer` 而不是塞进 `ProactivePlanner.Facts`

`:legacy` 是纯 Kotlin JVM 模块、**零 project 依赖**，引不到 `PresenceEngine` 的类型。
一度试着给 `Facts` 加 `busyReason: String?` 字段，改了又撤回，理由：

1. `Facts` 装的是**可观测事实**（轮次、时间戳），而 `busyReason` 是**结论**（gate 造出来的）；
2. 真正的收益不在"拦得住"，而在**提前拦** —— `lifeformProactiveTick` 里
   `refreshLifeformWeb` 是一次网络请求，她洗澡时不该还去抓网页。

所以结论是：门禁留在调度层，`legacy` 一个字没动。

---

### 4.3 为什么只在「在场」模式（2026-11-17 收窄作用域）

用户口径：「这个功能是要加入到一个模式里的，就是（角色）的窗，深度参与用户生活的一个模式，
后续会根据需求，部分加入其他模式」。

**这不是"先做一半"的临时妥协，是这套机制本身的边界**：

| | 角色扮演 / 工作 | 在场 |
|---|---|---|
| 用户不说话时 | **她不存在** | 她还在过日子（`LifeformDay`） |
| "我先去吃饭" | 戏里的一句台词，说完全程在线 | 真的腾不出手，主动消息会被拦 |
| 给她按时刻表 | 给一个不存在的人编此刻 → 模型照着编场景 | 时刻表就是她的此刻 |

⇒ 在角色扮演里替她写"这个点你一般正在吃饭"，用户从没经历过那顿饭，
模型会照着把"我正在吃饭"讲出来 —— 那是幻觉的素材，不是设定。

**落地方式：一个开关，不是 `mode == LIFEFORM`。**

`ChatMode.Switches.presence`（`:personalogic`，`ChatMode.kt`），三个模式显式各填一次：
`ROLEPLAY=false` / `WORK=false` / `LIFEFORM=true`。选 `Switches` 而不是 `when (mode)` 的
理由是既有设计（`Switches` 类注释）：**将来新增模式漏填这个格子，编译不过**；
写成 `when` 加个 `else ->` 就又是一个静默的错。

它管三处，都在一处判定、没有第二份真相：

1. `PersonaAssembler.renderState(..., presence)` —— L3 状态层是否写「你手上正有事」；
2. `AppContainer.proactiveTick` 主体与 `lifeformProactiveTick` 两处门禁 ——
   主动消息是否被作息拦（判 `switches.presence` 而不是 `isAlive`：
   前者是"她有没有作息"，后者是"她有没有自己的今天"，现在两者同真但语义不同）；
3. `AssistantPromptBuilder.build(..., presence)` —— 一路透传到 `AssemblyInput.presence`，
   **默认 false**，所以自定义角色那支、`diagnose()`、`assistantCapabilitySection()`
   等老调用点行为一字不变。

关掉它，用户看到什么：什么都没有。她永远随叫随到，不会说"这会儿腾不出手"，
提示词里也不会多那一段 —— 就是加这个功能之前的样子。

- 热聊期间无论几点都 `AT_HAND`（含对睡觉生效）；

- 200 天 × 三餐+洗澡，浮动不超幅度；
- 60 天 × 三餐窗口两两不重叠；
- 一天 1440 分钟全走一遍：`minutesIn` / `minutesLeft` 不为负，`AT_HAND` 无终点；
- 只有 MEAL / SHOWER 会产出提示词，且提示词中**不含任何数字**、必须含"这个点"。
- 只有 `LIFEFORM` 的 `switches.presence` 为 true，另外两个模式为 false
  （`ChatModeTest.只有在场模式让她有作息`）。
- 同一个 12:30 的状态，`presence=true` 的 L3 含「## 你手上正有事」，
  `presence=false` 的 L3 不含 —— 且后者**非空**（否则测试是假的绿色：
  L3 本来就空也能"不含"）。见 `PersonaAssemblerTest.没开 presence 的模式不替她编作息`。

**未验证（需真机）**

1. 语气是否真的变短：需要在真机 12:20 / 21:35 各聊几句，看回复长度与"边吃边回"的感觉。
2. 主动消息是否真的被拦（**只在在场模式**）：23:40 之后不打开会话，等一个 tick 周期，看日志有没有

   若两个模式也被拦了，说明有调用点没跟上 `switches.presence`。

## 6. 下一步（按性价比，也是已知缺口）

1. **睡着时被消息吵醒，现在没有语气** ← 最实在的一个洞。
   `gate` 只拦主动消息；用户深夜发消息时 `promptLine(SLEEPING)` 返回 `null`，
   于是她**回得跟白天一样利索**。这是最容易察觉的假。
   做法：给 `SLEEPING` 一条提示词（"是被提示音吵醒的，先看清是谁再说"），
   但**不能**跟 `PhysiologyEngine` 的"凌晨困"打架 —— 需要先定谁先说话。
2. **`LifeformDay` 的 beat 与饭点可能撞**：beat 若写了"在厨房"，而 `Presence`
   同时说"在吃饭"，两段提示词会重复。目前没有去重。
3. **久坐与饭后同时命中**：14:00 刚吃完 + 坐了 3 小时，`Physiology` 会给"久坐"，
   `Presence` 已经回到 `AT_HAND`，暂时不冲突；但晚饭 18:30 之后如果坐满 3 小时，
   两段会一起出现，需要真机看会不会变成"她一直在抱怨"。
