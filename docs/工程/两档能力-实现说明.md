## 二、两档的真实差别：不是"能不能"，是"要不要占屏"

| 能力 | 普通模式 | root 模式 | 差别 |
|---|---|---|---|
| `screen.read` 读屏 | 无障碍树，**占住屏幕** | `SurfaceControl` 抓帧，不占屏 | 后台可读 |
| `screen.tap` 点按 | `dispatchGesture`，**占住屏幕** | `injectInputEvent`，不占屏 | 后台可点，游戏/Canvas 也能点 |
| `file.saf` 授权目录 | SAF | SAF（同一条路） | 无差别 |
| `file.any` 任意路径 | 做不到（沙箱） | root 直读 | 解锁 |
| `settings.write` 改设置 | 需一次 `adb pm grant`，改不了受保护项 | `settings put` 全可改 | 解锁 + 免 adb |
| `prop.set` 系统属性 | 做不到（SELinux） | 可写 | 解锁 |
| `pm.disable` 停用预装 | 做不到 | 可停 | 解锁 |
| `shell.root` root 命令 | 做不到 | 白名单 argv | 解锁 |

**产品承诺（已用测试钉住）**：`root.occupancy.weight <= plain.occupancy.weight`
—— 升级 root 之后，屏幕占用只能变少，不会更多。

## 三、三条设计决定及理由

### 1. 降级必须显式，不能静默

root 用户会突然用不了 root：Magisk 更新后授权重置、常驻进程被系统杀、
SELinux 换策略。这时直接判"不可用"是错的 —— 任务该继续跑，只是代价变大。

⇒ `Verdict.Ready.degraded = true` + `note = "退到普通模式（常驻通道 未就绪）：这一趟要占住屏幕"`。
悄悄降级比直接失败更坏：用户会以为 root 生效了，下次就不看提示了。

### 2. 被挡的工具不删，挂原因

工具从 `tools/list` 里消失时，模型不会认为"这条路被封了"，它会瞎猜参数、
或者拿别的工具硬凑。所以：留在清单里，描述尾部追加
`⚠️ 当前不可用：<原因>`，真被调用时在**执行前**回 `isError`（保证零字节执行）。

描述前缀保持稳定（动态内容只在尾部）—— 否则每次开关权限都会让提示词前缀整体变化，缓存全灭。

### 3. 用户的手永远优先（屏幕租约）

普通模式占屏期间，屏幕是共用的。规矩：

- 检测到触摸 → **立刻让开**（`YieldReason.USER_TOUCH`）
- 松手 `graceMillis`（默认 1.5s）→ 自动回来，不用点确认
- 用户明确按停（`USER_STOP`）→ **不再自动回来**
- **让开不延长租约**：总时长上限（默认 90s）对"让开"同样生效，否则
  "用户碰一下 → 重新计时"就成了无限续期
- 来电/切走（`APP_LEFT`）→ 用"让开的时刻"当锚点，否则一次来电就把任务永久卡死

## 七、已知缺口（不修会误导用户）

> 2026-11-04 已收口：本节当时写的「启动常驻通道开关不存在」已经不影响用户 ——
> `screen.read` / `screen.tap` / `shell.root` / `pm.disable` / `prop.set` / `file.any`
> 的 root 前置条件全部改成了 `ROOT_SU`（走 `su -c`，当天可用）。`Permission.ROOT_DAEMON`
> 只留给常驻守护进程上线后使用，枚举保留、表里已无使用者。下面保留原始判断作为记录。

**「启动常驻通道」这个开关还不存在。** `screen.read` / `screen.tap` 的 root 路径
前置条件原本写的是 `Permission.ROOT_DAEMON`，而设置页里没有这个入口。
后果有限但不该留着：root 用户如果把无障碍关掉，网关会回
"缺「常驻通道」→ 打开 PocketAgent → 设置 → 高级 → 启动常驻通道" —— 用户去找会找不到。

两条收口路线，二选一：

- **A（小）**：先去设置页做那个开关（哪怕只是个探活 + 状态显示），文案立刻成立；
- **B（大）**：把 `ROOT_INJECT` / `ROOT_CAPTURE` 用 `su -c input tap` / `su -c screencap`
  落地，前置条件从 `ROOT_DAEMON` 改成 `ROOT_SU` —— 当天就能用，不占屏。

> `shell.root` / `pm.disable` / `prop.set` / `file.any` 已经是路线 B 的形态（`su -c`），
> 所以它们的前置条件已经是 `ROOT_SU`，**root 档现在真的能用**。

## 八、2026-11-04 补充：root 档真的能动手了（路线 B 已落地）

### 8.1 root 侧的四个动作（`android/rootlogic/.../RootActions.kt`）

| 动作 | 落地命令 | 归属能力 |
|---|---|---|
| 点按 / 滑动 / 按键 / 输入 | `su -c input tap\|swipe\|keyevent\|text` | `screen.tap` |
| 截图 | `su -c screencap -p` | `screen.read` |
| 读界面树 | `su -c uiautomator dump` + `cat` | `screen.read` |
| 改设置 / 属性 / 停用应用 / 读任意文件 | `settings put` / `setprop` / `pm disable-user` / `cat` | 各自一条 |

**统一入口只有 `RootCommands.argv(action)`**，且：

- 参数先过 `safeToken`（空、超 256、含 `;` `$` 引号 `|` `&` 一律拒），**本地拒绝时一个字节都不发**；
- 键码走白名单（`KEY_CODES`），查询走白名单（`QUERY_HEADS`），坐标限 ±100000；
- 文字参数允许中文/空格/`;`，但拒单引号、反斜杠、换行 —— 因为它们会破坏 `input text '…'` 的引号语义。

### 8.2 两档汇合点

| 汇合点 | 规则 | 为什么不统一成一条规则 |
|---|---|---|
| `TieredDispatchPort`（点按） | root 档**只用 root**，失败不退回无障碍 | 退回＝占住用户屏幕，而用户选 root 就是为了不占屏 |
| `TieredScreenReader`（读屏） | root 档且 su 就绪走 root，否则走无障碍 | 读屏退回不碰用户界面，只是多一次 `rootInActiveWindow`；su 被撤时"读屏不可用"是纯退化 |

`SuShellPort` 的两个细节：`ProcessBuilder` 用**数组**形态（不拼字符串）；
**先读 stdout/stderr 再 `waitFor`** —— 否则 `screencap`/`dumpsys` 超过 64KB 会把管道堵死。

### 8.3 界面（`ui/settings/PrivilegeModeScreen.kt`）

- 能力列表从 `CapabilityMatrix` 的**静态**结论改成 `TierReport`（`TierReports.build(...)`）——
  后者来自 `TierRouter` 对着真实授权状态算出来的结论。这是一次**bug 修复**：
  原来无障碍没开也显示"可用"。
- 每行显示：状态图标 + 名称 + 路径徽章（占屏时写"占屏 · 无障碍手势"）+ 缺什么 + 怎么开。
- 「下一步」按钮组只列用户此刻能做的（打开无障碍设置 / 允许悬浮窗 / 去 root 管理器放行 / 重新检测）。
- `TierReport` 把「能力层就绪但没绑工具」和「两条路都没实现」分成两句话 ——
  前者说"还没有工具入口"，因为让人以为要重写能力层是误导。

### 8.4 还没做的

1. `ScreenLease` 仍无事件源（见第六节）。
2. `file.saf` **还没有独立的 MCP 工具入口** —— 它在普通档走的是 `office_tools` 的
   SAF 通道（用户授过的那棵树），不是一个独立的"任意目录读写"工具。
   其余四条（`file.any` / `settings.write` / `prop.set` / `pm.disable`）已见第九节。
3. `:overlay` 悬浮窗档仍未启用（普通档现在靠无障碍，不靠悬浮窗）。

## 九、2026-11-04 第二轮：系统级能力有了工具入口

### 9.1 四个新工具（`android/mcp/.../SystemOps.kt`）

| 工具 | 归属能力 | 参数 | 走安全判定 |
|---|---|---|---|
| `file_read` | `file.any` | `path` | ✗（只读；但硬拒 `/dev/block`、`/dev/mem`、`/proc/self/mem`、`/sys/kernel/debug`） |
| `setting_write` | `settings.write` | `namespace` + `key` + `value` + `purpose` | ✓ |
| `prop_write` | `prop.set` | `name` + `value` + `purpose` | ✓ |
| `app_disable` | `pm.disable` | `package` + `purpose` | ✓ |

### 9.2 两道闸，理由不同

1. **`tierGate`（按工具名查档位）** —— 普通档调用 `file_read` 会被**执行前**拦下，
   文案是「缺「root 授权」…」而不是"执行失败"。它回答的是"**这一档有没有这条路**"。
2. **工具内部 `rootAvailable()`** —— 就算网关因为漏配名字放行，工具自己也会回绝。
   它回答的是"**此刻 root 还在不在**"（用户可能刚在 Magisk 里撤回授权）。

只留一道都不行：只有网关，漏配一个名字就静默放行；只有工具内部，模型会拿到
"执行失败"而不是"你这一档没有这条路"。

### 9.3 三个刻意做反了会出事的地方

- **`app_disable` 的保护名单必须在包名格式校验之前**。`android` 不满足"至少两段"
  的包名格式，先校验格式会让它落到"package 不合法"的 Failed —— 模型会以为
  改个写法就能停用系统框架。现在先查保护名单，回 `Refused`。
- **`Rejected` 与 `Failed` 必须分开**（`SystemOpOutcome`）。前者是**参数**问题
  （模型该改参数重试），后者是**执行**问题（SELinux / 权限 / 目标不存在）。
  混成一档，模型会去换命令反复撞墙。
- **`file_read` 不弹确认**。给读文件加审批会让用户养成"看也不看就点同意"的习惯，
  而真正需要审批的写操作就藏在这个习惯后面。

### 9.4 验证

- `run_logic_tests.py` → **OK (3729 tests)**（+24：`SystemOpsToolsTest` 21 条 + 档位页 3 条改写）
- `verify_all.py` → **13/13**
- `:app:assembleDebug` → BUILD SUCCESSFUL
- `TierReportTest` 里两条断言按新真相改写并说明理由：
  `file.any`/`prop.set`/`pm.disable` 普通档现在是「需要 root」而不是「缺工具入口」；
  `settings.write` 在 `WRITE_SECURE_SETTINGS` 已授予时**仍是 READY**（普通档真有这条
  路，断言成"需要 root"会掩盖它）。

## 10. 批量动作（`android_batch`，2026-11-04 晚）

### 10.1 它省的是"往返模型"，不是"手机侧时间"

延迟账本（`docs/工程/agent能力扩张-方案.md` §9.5）里最大的一项从来不是手机：

| 项目 | 量级 | 说明 |
|---|---|---|
| **一次模型往返** | 800–3000ms | 每做一步就回一次模型，这一段就是全部成本 |
| 一次 `su -c input tap` | 80–300ms | 真正动手的时间只有它的零头 |
| 无障碍树读取 | 30–200ms | 一次批量只读一次 |
| 截图 | 150–400ms | 批量里不用 |

⇒ `android_batch` 让模型**一次声明一串动作**（最多 12 步），中间不重新读屏。

### 10.2 但它不替模型看屏幕（这是能力边界，不是缺陷）

整批只采一次屏（用于解析 `nodeId`/`text` 与做页面级安全判定），中间不重读。
所以：

- **适合**：已经知道点击顺序的确定性流程（展开 → 选一项 → 确认）；
- **不适合**：每一步的结果决定下一步点哪儿。那种情况请一步步来 ——
  本工具只保证"停下来"，不保证"停在你想的位置"。

### 10.3 安全关卡一步都不省

| 关卡 | 批里的处理 |
|---|---|
| 安全判定（`:safety`） | **每一步单独过**，不是整批过一遍 |
| 频率闸 | 整批**一次性占 N 份额度**（`ActionRateLimiter.tryAcquireBurst`） |
| 失败语义 | 任一步被拒/失败 → 立即停；**已做过的不回滚**，文案如实说明 |

⚠️ **为什么必须有 `tryAcquireBurst`**：`tryAcquire` 的防连点下限是 250ms，
它是给**人手节奏**定的（防同一按钮连点两下）。逐次申请会让批的第 2 步必然
撞上"间隔过短"—— 于是"一次调用做 12 步"在真机上根本跑不起来。
语义改成：批之间仍受 250ms 约束，每分钟**总**动作数仍受 20 次约束，
额度**先扣后做**（中途失败不退 —— 宁可少放行，不可多放行）。

### 10.4 `Refused` 与 `Failed` 在批里怎么分

| 情况 | 结论 | 为什么 |
|---|---|---|
| 安全策略拦下 / 需用户确认 | `Refused` | 换写法也没用，是最终结论 |
| 频率闸拒绝 | `Refused` | 同上，等一下可以再来，但不是"坏" |
| 目标解析失败 / 通道失败 | `Failed` | 可以换定位方式或重试 |
| 参数不合法 | `Failed` | 模型该改参数，一次字节都不发 |

### 10.5 验证

- `android/mcp/src/test/kotlin/com/pocketagent/mcp/BatchToolTest.kt` —— 14 条，钉住：
  整批**只采集一次**（`reader.count == 1`）、三步过**三次**判定、中途失败时文案含
  「第 2 步」「不会回滚」「screen_read」、参数错误 `reader.count == 0` 且零派发、
  超过 12 步要求拆分、未知 `op`/`key` 拒绝、`nodeId` 缺 `bounds` 拒绝、
  读屏不可用给出开权限的下一步、成功回执不回显屏幕文本。
- `run_logic_tests.py` → **OK (3750 tests)**
- `verify_all.py` → **13/13，64s**
- `:app:assembleDebug` → BUILD SUCCESSFUL

### 10.6 还没验证的（真机）

- 12 步的批在**真实设备**上实际耗时（预期 1–4s，取决于 root 通道）；
- 批中间界面变化时的真实表现（预期：点空 / 点到别处 —— 这正是"不适合"的含义）；
- 每分钟 20 次额度在高频任务里会不会碍事（如果会，改的是阈值，不是语义）。

## 11. 常驻守护进程：先落地可测的那一半

### 11.1 为什么只写了一半

守护进程要在 uid 0 的 `app_process` 里跑，用 `InputManager.injectInputEvent`、
`SurfaceControl`、`IPackageManager` —— 这些 API 的错误只能靠**真机**暴露
（权限被 SELinux 拦、隐藏 API 被反射封、SurfaceControl 的 Builder 字段随版本变）。
本项目不允许"我猜它应该能用"的代码进主路径，所以按可验证性切了一刀：

| 层 | 内容 | 状态 |
|---|---|---|
| 协议 | `PrivilegeWire` 帧编解码、请求/应答配对 | 已完成，16 条测试 |
| 客户端 | `PrivilegeClient` 六类结局、按 id 配对 | 已完成，含在同上 16 条 |
| **服务循环** | 读字节 → 解帧 → 按动词分发 → 写回 | **已完成，17 条测试（本轮）** |
| Android 薄壳 | 开 socket / `app_process` 入口 / `injectInputEvent` 等 | **未写**，需要真机 |
| 汇合点 | `RootShellPort` 换成"走守护进程"的实现 | 未写（接口已就绪） |

### 11.2 `DaemonLoop` 的三条硬纪律（都有测试钉住）

1. **一个请求一帧应答，id 原样回**。客户端靠 id 配对；错了表现成"点错地方"，
   不是报错 —— 最难查的一类故障。
2. **处理器抛异常 → ERROR 帧，绝不外抛**。守护进程因为一条坏请求退出，
   客户端看到的是"所有 root 能力突然消失"，而真因是某条命令。
3. **不认识的字 / 不认识的动词 → ERROR 帧并继续服务**。半开连接、
   版本不匹配都会走到这里；退出的代价是用户要重新 su 一次。

另有两条是写测试时才被逼出来的：

- `ERROR` 帧的 code 与 `PrivilegeClient` 的 `PrivilegeOutcome.Protocol` 对齐，
  客户端不需要猜"这是哪种错"；
- 处理器返回 `Ok(code = 2, stderr = "No such file")` 时**仍然走 REPLY 帧**，
  不是 ERROR —— 命令跑了但退出码非零，和"根本没跑"是两件事。

### 11.3 未写的薄壳长什么样（给出形状，不写假实现）

```kotlin
// 真机上大致是：su -c app_process /system/bin com.pocketagent.daemon.Main
val socket = LocalSocket().apply { connect(LocalSocketAddress(NAME, LocalSocketAddress.Namespace.ABSTRACT)) }
val channel = object : DaemonChannel {
    override fun read() = socket.inputStream.readNBytes(...)   // 0 → null
    override fun write(bytes: ByteArray) { socket.outputStream.write(bytes); flush() }
}
DaemonLoop(handlers = RootHandlers.build()).serve(channel)
```

`handlers` 每个动词一个函数：`PING` 回 `id` 的 stdout；`INJECT` 解析 argv 里的
坐标与时长后调 `injectInputEvent`；`CAPTURE` 走 `SurfaceControl`；
`SETTINGS` 校验 key 白名单；`PROBE` 先过 `ScopeGuard`。
**动词表里没有 `exec(String)`** —— 有它的话，能力层的白名单在 root 这层就被绕过了。

### 11.4 真机风险（已写在协议层注释里，重复一次）

Android 12+ 上 `untrusted_app` 域通常连不上 root 域的 abstract unix socket（SELinux）。
降级路径：loopback TCP + 一次性 token（照抄 `:mcp` 的 `McpServer` 加固：
绑 `127.0.0.1`、拒绝带 Origin 的请求、常量时间比较 token、日志不打 token）。

## 13. 2026-11-04 第四轮：急停终于有人听了（启用 `:overlay`）

### 13.1 这是一个「看着有、实际没有」的缺陷

`android/overlay/.../OverlayService.kt` 的 `sendStopBroadcast(request)` 原来只有一行
`Timber.d(...)`，注释写着「TODO(M1)：换成显式 Intent」。也就是说：

- 用户按下悬浮球上的「停」；
- 球缩回去、播一个动画、日志里出现一行「急停已受理」；
- **没有任何代码收到这个信号**，任务继续点屏幕。

这种缺陷比「没做急停」更坏：用户以为停住了，于是把手机放下。

### 13.2 现在这条链是通的

```
悬浮球按下
  → StopHandler 判定（Accepted / NothingToStop / Duplicate）
  → sendBroadcast(Intent(StopSignalReceiver.ACTION_STOP_REQUESTED).setPackage(packageName))
  → AppContainer.stopReceiver（Application.onCreate 里注册，RECEIVER_NOT_EXPORTED）
  → screenLease.onUserStop()
  → 下一次 TieredDispatchPort.dispatch（普通档）→ Refused(「你让任务停一下 —— 需要继续时再叫我」)
```

四个细节，都是刻意的：

| 决定 | 为什么 |
|---|---|
| 广播 `setPackage(packageName)` | 急停是应用内部信号，不该给外部应用伪造的机会 |
| 接收器在 `PocketAgentApp.onCreate` 注册 | 用户按停时界面可能根本没起来 —— 注册晚一步，那一下就是白按 |
| `RECEIVER_NOT_EXPORTED` | 同上；Android 14 起对隐式广播的放行也更严 |
| 拒绝文案直接来自 `lease.blockedReason()` | 另写一句必然和租约状态机漂移（三种让开原因各有各的说法） |

### 13.3 `ScreenLease` 现在真的会拦人

`TieredDispatchPort` 的普通档分支：

```kotlin
lease.acquire(SCREEN_REASON)   // 续租；Yielded 时恢复原期限，不重新计时
if (!lease.canAct()) return DispatchOutcome.Refused(lease.blockedReason() ?: "现在不能操作屏幕。")
plain.dispatch(action)
```

**闸门用 `canAct()`，不是 `blockedReason() != null`** —— 后者在 `Idle`（还没申请过）
时也返回一句话，拿它当闸门会把第一次点按直接拦死。

新增 5 条 `:app` 测试（`ScreenLeaseGateTest`）：

1. 第一次点按先申请租约再放行；
2. 按停之后点按被拒，且**无障碍通道一次都没被调用**（不是「执行了没看见」，是没执行）；
3. 摸屏后 0.4 秒内被让开、1.7 秒后放行（宽限 1.5 秒）；
4. root 档完全不受租约影响 —— 它不占屏，也就没有「让开」这回事（租约不是全局刹车）；
5. 没传租约时行为与从前一致（向后兼容）。

### 13.4 「按停」之后由谁解封：`beginAgentRun`

按停之后租约会一直停在 `Yielded(USER_STOP)`，`canResume()` 恒 false —— 这是刻意的
（用户没说继续，就不许继续）。但**总得有人把它解开**，否则 agent 从此再也动不了屏幕，
直到重启应用。

解封点是 `AppContainer.beginAgentRun()`，只在 `ContainerChatPort.send` 的**最开头**
调用一次（用户重新发一条消息）。两条约束写进了注释：

- 只有**用户自己开口**能解封 —— agent 不能自己解封自己，否则「停」退化成「暂停一秒」；
- 位置必须在 `send` 开头而不是「决定要动手之后」—— 用户按停后往往先聊两句再让它动手，
  卡在后半段会让中间那一轮看到「你让任务停一下」，而用户明明已经重新开口了。

### 13.5 三路事件源，现在都接上了

| 事件 | 谁发 | 落到租约 |
|---|---|---|
| 按「停」 | `OverlayService` → `ACTION_STOP_REQUESTED` | `onUserStop()`（**不自动回**） |
| 手指落到球上 | `OverlayService.onTouchEvent` 的 `ACTION_DOWN` → `ACTION_USER_TOUCH` | `onUserTouch()`（**1.5 秒后自己回来**） |
| 前台被切走 | `PocketAgentApp` 的 `ActivityLifecycleCallbacks` 计数器归零 | `onAppLeft()`（同样能自己回来） |

三条信号走同一个 `BroadcastReceiver`，但**落到租约上是三个不同方法**：
合并成「停一下」之后，用户就再也没法区分「让开」和「别动了」。

前台计数器（`PocketAgentApp.onCreate`）：

```kotlin
private var started = 0
override fun onActivityStarted(activity: Activity) { started += 1 }
override fun onActivityStopped(activity: Activity) {
    started -= 1
    if (started <= 0) { started = 0; container.onForegroundLost() }
}
```

用计数器而不是每个 Activity 自己上报：否则**应用内跳页**也会触发一次让开，
任务会被自己的页面切换打断。夹回 0 是因为 started/stopped 不保证严格配对
（进程被杀、配置变化都可能漏一个），漏一个之后必须能自愈。

## 14. 常驻通道的传输层：能跑、能测的一段（2026-11-04）

前面 §11 把守护进程拆成"可测的一半"与"等真机的薄壳"。这一节补的是那"一半"
里最后缺的两块：**字节怎么过去**、**动作怎么翻成通道请求**。现在这两块都有了
测试，薄壳剩下的只有 `app_process` 入口与 SELinux 那一层。

### 14.1 为什么先做 loopback TCP，而不是 unix domain socket

| | unix socket（`LocalSocket`） | loopback TCP |
|---|---|---|
| Android 12+ SELinux | `untrusted_app` → `root` 常被拦 | 多数机型不拦 |
| 离线可测 | 要真机才能验一句 | `ServerSocket` 两端都是纯 JVM，测试里能真跑往返 |
| 被同机应用连到 | 需要 `SOCK_SEQPACKET` + `SO_PEERCRED` 校验 | 靠 token + 只绑 loopback |

选了 TCP，并把 unix socket 列成后续项 —— 理由不是"TCP 更安全"（它更弱，
所以要 token），而是**现在能证明它真的通**。一条只有真机能验的传输层，
在离线验证器眼里等于不存在。

### 14.2 三个部件

| 文件 | 职责 | 测试 |
|---|---|---|
| `PrivilegeSocket.kt` | 客户端 `PrivilegeSocketPort` / 服务端 `DaemonSocketServer` / 握手 / 常量时间比较 / 只绑 loopback | `PrivilegeSocketTest`（13 条，**真起服务端**） |
| `DaemonCalls.kt` | `RootAction` → `DaemonCall(verb, argv)`：数组形态，不经 shell | `DaemonCallsTest`（18 条） |
| `DaemonHandlers.kt` | 服务端处理器表：`RootVerb` → 要不要真起一条命令 | `DaemonHandlersTest`（24 条，假 runner 精确断言命令） |
| `DaemonEndpoint.kt` | 发现文件（`端口 token` 一行）的解析与打开 | `DaemonEndpointTest`（10 条） |

握手是一行 ASCII：`PA1 <token>\n`，服务端回 `OK` 或 `DENY`。token 由启动时的
薄壳生成，写在 `/data/local/tmp/pocketagent-daemon.txt`，客户端读这个文件。
**端口用 `bind(0)` 让系统分配**再回写 —— 写死端口在手机上迟早撞上别的服务，
而"撞了之后连到别人的服务"是最坏的失败形态。

### 14.3 客户端怎么选路：优先通道，失败退 `su`

| 通道结局 | 动作 |
|---|---|
| `Ok` / `Exit(code≠0)` | 直接用，**不退 su**（"跑了但失败"是结论） |
| `DaemonError`（服务端明确拒绝） | 转成 `REJECTED`，**不退 su**（换条路试一遍改变不了参数错） |
| `PrivilegeClosed` / `DaemonDown` / `NoReply` / `Protocol` | 退回 `su -c` |

为什么不重试通道：重试会让"这条命令到底执行了没有"从确定变成未知，
而对 `input tap` 这种动作，"可能点了两次"比"没点"更糟。

### 14.4 服务端不信任客户端

客户端（`DaemonCalls`）已经校验过一遍；服务端（`DaemonHandlers`）**再校验一遍**。
理由直白：通道跑在 root 下，客户端被改写、被 hook、或 token 泄漏之后，
这一侧是最后一道闸。同一套规则（`RootCommands.safeToken` / keycode 白名单 /
坐标范围）被两处共用，规则只有一份。

`EXEC` 只认一种形状：`pm disable-user --user 0 <包名>`。**不做通用 exec** ——
通用 exec 等于把通道变成 root shell，前面所有白名单都成了装饰。要加新命令
就在那里加一条具名分支，加的时候必须想清楚它能不能被滥用。

### 14.5 顺手修掉的一个协议 bug

`PrivilegeWire.encodeArgv` 原本 `require(argv.isNotEmpty())`。而 `PING` 与
`PROBE` 本来就没有参数 ⇒ 这两个动词**在客户端根本发不出去**，探活失败会被
误读成"通道不可用"。现在空 list 编码成空正文，`decodeArgv` 还原成空 list。
这个 bug 只有"真的去发一次 PING"才会暴露 —— 又一个"有测试才有真相"的例子。

## 15. 薄壳（`app_process` 入口）已落地，只剩 dex 一次

`DaemonMain.kt` 就是那个入口。全部代码都在 `:rootlogic`（纯 JVM，无 Android 依赖），
所以它能被离线测试直接起一整套栈 —— 不需要模拟器，也不需要设备。

### 15.1 它只做三件事

1. `bind(127.0.0.1:0)` 拿一个系统分配的端口；
2. 把 `端口 token` 原子地写进发现文件（先写 `.tmp` 再 `renameTo`，
   避免客户端读到"端口对、token 截断"的半截内容）；
3. 服务循环（每个连接一次握手，之后交给 `DaemonLoop`）。

**故意不做**：`while(true)` 兜异常重启。服务循环内部已经吃掉单连接异常，
走到 `main` 退出只会是"端口绑不上"这类系统性故障 —— 重启一万次同结果。

token 由薄壳自己生成（16 字节 → 32 位十六进制，`SecureRandom`），
**不通过命令行传**：命令行走 `ps` 是全局可见的，token 出现在那儿等于没有 token。

### 15.2 离线已经证过的那条完整链路

`DaemonMainTest` 里有一条用例把整条链真的接起来：

```
DaemonMain.start(假 runner, 临时发现文件)
  → 发现文件里出现 端口 + token
  → DaemonEndpoint.read 读回来
  → PrivilegeSocketPort 连上去（真 socket）
  → RootActions.run(Tap(11,22))
  → 假 runner 收到 ["input","tap","11","22"]
```

这条用例把"真机上第一步会做的事"提前在离线跑通了。真机上如果这一步不通，
问题只可能在 SELinux 或文件权限 —— 协议、校验、选路、配对都已经排除。

同文件还钉了三条：token 每次不同且是 32 位十六进制；发现文件写不进去时
**如实报 `discoveryWritten=false` 而不是假装起来了**；`GetProp` 走
`QUERY` 动词并原样带回属性值。

### 15.3 真机上要做的（一次）

```bash
# 1. 把 :rootlogic 打成 dex，塞进设备
d8 --output /tmp/dex android/rootlogic/build/libs/rootlogic.jar
adb push /tmp/dex/classes.dex /data/local/tmp/pocketagent-daemon.jar

# 2. 起薄壳（发现文件路径可省略，默认 /data/local/tmp/pocketagent-daemon.txt）
adb shell su -c "CLASSPATH=/data/local/tmp/pocketagent-daemon.jar app_process /system/bin com.pocketagent.rootlogic.DaemonMain"

# 3. 确认发现文件
adb shell cat /data/local/tmp/pocketagent-daemon.txt   # 期望：<端口> <32 位 token>
```

起了之后，`:app` 侧什么都不用改 —— `AppContainer` 已经在构造 `RootActions`
时读发现文件（`DaemonEndpoint.open()`），读到就走通道，读不到就退回 `su`。

### 15.4 仍然如实标注的差距

| 目标里的写法 | 当前实现 | 差距 |
|---|---|---|
| `injectInputEvent` | 通道 `INJECT` → `input tap`（底层同为 `InputManager.injectInputEvent`，任意窗口含游戏） | 无 |
| `SurfaceControl` 抓帧 | `screencap -p`（SurfaceFlinger 合成后的整屏） | 不能只抓单层；延迟略高。要逐层抓得在守护进程里调 `SurfaceControl`，那部分只能真机验 |
| `IPackageManager` | `pm disable-user`（同一条 binder 调用） | 无 |
| 白名单 `EXEC` | 通道 `EXEC` 只认 `pm disable-user --user 0 <包名>` | 故意不做通用 exec |
| `PROBE` | 通道 `PROBE` 跑 `id`，非 `uid=0` 判不可用 | 无 |
