# 设备档案 v1.0 —— Redmi K60（mondrian）

> **这份文档的用途**：让开发**脱离手机**也能进行。
> 真机是稀缺资源（要插线、要供电、要人在旁边），而开发中反复要问的往往是同一批
> 问题 —— 屏幕多宽？无障碍有哪些能力？HyperOS 有没有拦？答案固化在这里。
>
> **数据来源**：`tools\device\collect-env.cmd` 实测采集（**2026-10-11 23:07**）。
> **重采方式**：跑那个脚本，把 `tools/device/reports/env-*.txt` 交给 Claude。
> **不要手抄** —— 手抄的副本必然与真机漂移（本文第一版就手抄错过一个字段，见 §5 的更正）。
>
> **证据标准**：标了实测时间的 = 真机读出来的；写「待确认」的 = 没读到，
> **不猜** —— 一个"看起来有值其实是默认值"的字段比空着更危险。

### ★★ 最关键的一条：侧载不会被拦

```
ACCESS_RESTRICTED_SETTINGS: default; rejectTime=+3m3s371ms ago
```
（来源：P0 报告 2026-09-22，命令 `cmd appops get com.pocketagent.debug ACCESS_RESTRICTED_SETTINGS`）

**含义**：Android 13+ 的「受限设置」机制**在这台机器上没有拦截侧载应用开启无障碍**。
它决定「社区分发（侧载）+ 无障碍读屏」这个产品形态**是否成立** —— 在这台机器上：**成立**。

⚠️ 两条限定：
1. `default` 只说明**权限层面放行**，不代表服务已启用（§6 当前就是**关着**的）；
2. 本次采集（2026-10-11）这一项读取失败 —— 采集脚本用错了命令（`dumpsys role`），
   **已修为 `cmd appops`**，下次采集会带上。此处沿用 P0 的结论。

### ★ 更正说明：`ro.debuggable=0` **不影响** `run-as com.termux`

第一版档案里我**推断**了 `ro.debuggable=1`，理由是"能 run-as 就说明系统可调试"。
**这个推断是错的**，实测是 `0`。而且真相更清楚：

- `ro.debuggable` 描述的是**系统构建**是否可调试（`0` = user 构建），
  它与"能不能 run-as 某个 App"**不是同一件事**；
- `run-as` 是否可用，取决于**目标 App 自己**是否 `android:debuggable="true"`；
- 实测：Termux 可以 `run-as`（§9），**而系统是 `ro.debuggable=0`**。

⇒ 结论按实测走：**`run-as com.termux` 可用**，与 `ro.debuggable` 的取值无关。
（这正是"别手抄、别推断"的活例子 —— 推断出来的字段与真值不一致，且**没人会发现**。）

## 6. 无障碍（⚠️ 当前是**关闭**状态）

| 项 | 实测值（2026-10-11） |
|---|---|
| 无障碍总开关 | **`0`（关）** |
| 已启用服务 | 空 |
| 我们期望的组件名 | `com.pocketagent.debug/com.pocketagent.assistant.AgentAccessibilityService` |
| 服务是否在启用列表里 | **否** |
| 能力位（capabilities） | 无从读取（服务关着）—— 历史上为 **`161`（含截图位 128）** |
| 有效显示器数 | `1` |

**为什么是关的**：**覆盖安装会重置无障碍**（项目既有结论）。装过新 APK 之后
需要重开：

```cmd
adb shell settings put secure enabled_accessibility_services com.pocketagent.debug/com.pocketagent.assistant.AgentAccessibilityService
adb shell settings put secure accessibility_enabled 1
```

⚠️ **组件名的两半是不同包**：`com.pocketagent.debug`（applicationId）
与 `com.pocketagent`（代码命名空间）。写错会拼出一个永不存在的组件，
**而且写入是静默成功的**（`tools/device/verify_fgs.py` 里为此专门留了注释）。

⚠️ **能力位只在服务启用时才有意义**。采集脚本原来在服务关着时也报「查询失败」，
会让人以为是查询姿势问题 —— **已改成明确区分**："服务未启用，无从读取"。

## 7. 后台与省电（★ 直接决定 FGS 保活成败）

| 项 | 实测值（2026-10-11） | 含义 |
|---|---|---|
| 电池优化白名单 | **不在白名单里** | 系统可以随时限制我们 |
| 待机策略（standby bucket） | **`40`（RARE）** | 属于**受限制档**：后台网络/任务会被压制 |
| deviceidle 白名单 | 不含我们的包 | 打瞌睡模式下会被冻结 |

**这三条合起来解释了一件事**：FGS 保活挡得住「冷冻」（已验证），
但**厂商强杀与备用电源压制**是另一条路径 —— 而当前这台机器上，我们正处在
**最容易被打压的档位**。

**用户侧可做的三件事**（adb 查不到，得在设置里手点）：
1. 「设置 → 应用 → PocketAgent → 省电策略」→ 设为**无限制**；
2. 「设置 → 应用 → 权限 → 自启动」→ 允许；
3. 最近任务里给 PocketAgent **加锁**。

> 注：`standby bucket` 由系统按使用习惯动态调整，`40` 不代表永久 ——
> 但它是**当时**的观测值，值得记下来作对照。

## 11. 已知边界与坑（**别重新踩**）

| 坑 | 表现 | 处置 |
|---|---|---|
| **锁屏** | `uiautomator dump` 成功但**零 text 节点**；`screencap` **全黑** | 判据：**先看截图是否全黑**。⚠️ 别一看到 keyguard 就宣布硬边界 —— `KEYCODE_WAKEUP` 后等 2 秒再上滑**有时真能解开** |
| **虚拟屏** | `flags=85003` 已解决大多数问题，但 `isVisible=false` **未解** | 疑因主屏安全锁，**需解锁复测** |
| **HyperOS 后台策略（EX-15）** | 未知 | **未测**。本次采集给了两个信号（RARE 档 + 不在白名单），见 §7 |
| **端口每次变** | 网关与能力桥端口每次启动都不同 | 这是**安全设计**；重投配置即可 |
| **遮蔽节点定位** | 可输入框在 `screen_read` 里显示 `[已遮蔽]`，但真实树是原文 | 必须用 `node_id` 定位（schema 里已写明） |
| **`adb shell cat` 拉二进制** | 会污染二进制 | 必须用 `exec-out` |
| **界面状态判据** | 用 md5 判断界面会误判（息屏/时钟/温度都会让它变） | **看具体字段或看图** |
| **覆盖安装** | 会**重置无障碍** | 装后重开（§6 的命令） |
| **多设备并存** | 有 offline 残留时 adb 会对**每条**命令报 "more than one device"，症状是**所有字段整齐失败** | 加 `-s <serial>`；或 `adb disconnect <地址>` |
