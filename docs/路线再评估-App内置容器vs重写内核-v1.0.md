# 路线再评估：把 dsh 搬进 App —— 「内置容器」还是「重写内核」

> 2026-10-03。起因：用户主张「把 dsh 桌面端的核心搬到我们的 App 里，包括他的循环这些」。
> 本文评估这个主张：**哪一半是对的，哪一半要修正，以及现成实例是怎么做的。**

---

## §0 结论速览

| 问题 | 结论 |
|---|---|
| "把核心搬到 App 里" 这个方向 | ✅ **对** —— 而且能解决我们两个老大难 |
| "包括他的循环" | ⚠️ **取决于你怎么理解"搬"** —— 见 §1，两种做法代价差一个数量级 |
| 应该选哪种 | ✅ **把 dsh 原样装进 App 自带的容器**（不重写） |
| 有现成的吗 | ✅ **有**：`Ajwyunsx/deepseek-harness-mobile`，**MIT**，上游 fork，改动隔离在 `dsh-mobile/` |
| 它重写循环了吗 | ❌ **没有** —— 直接跑原始 Node 版 `@deepseek-ai/dsh web` |
| 我们要抄的是它的什么 | ✅ **容器管理那一套**（proot / BootstrapInstaller / HarnessService / WebView / cookie 鉴权），**不是它的 UI** |

## §1 ★ 关键区分：「搬」有两种，代价差一个数量级

你的话里"**包括他的循环这些**"是关键。这句话有两种读法，**它们不是同一个项目**：

| 读法 | 做法 | 代价 | 文档里的原始评估 |
|---|---|---|---|
| **A. 把 dsh 原样搬进 App 的容器** | Node 版 dsh **一行不改**，App 负责起容器、守进程、连 UI | **低**（有现成的可抄） | 路线 C 的变体 |
| **B. 用 Kotlin 重写 dsh 的核心** | 自己实现 agent 循环 / 会话 / 压缩 / 工具集 | **极高** | 路线 B：「**等于重造 195 个包；生态归零**」，可行性 ⚠️ **低** |

★★ **A 里"循环"是自动包含的** —— 因为循环就是 dsh 的一部分，原样跑就带上了。
**不需要为了"要循环"而去重写。**

⇒ **建议明确选 A。** 下面全部按 A 展开。

### 为什么 B 不值得

- dsh 有 **240 个 `@deepseek-ai` 嵌套依赖**（我们真机实测过）
- 重写等于**自己重新实现一遍**：会话管理、上下文压缩、token 计量、计划模式、
  子代理编排、工作流、MCP、技能系统、沙箱……
- **而且生态归零** —— 上游每更新一次，我们都要追
- **收益是什么？** 体积小一点、启动快一点。**用数周换启动快两秒，不划算。**

## §2 ★ 现成实例：`Ajwyunsx/deepseek-harness-mobile` 怎么做的

| 项 | 事实 |
|---|---|
| **License** | **MIT** ✓（可借鉴，需保留版权声明） |
| **性质** | `deepseek-ai/deepseek-harness` 的 **fork**，上游原样，**改动全在 `dsh-mobile/`** |
| **Agent 循环** | **未重写**，容器内跑原始 `@deepseek-ai/dsh web` |
| **Node 打包** | ❌ **不打进 APK** —— 首启联网下载 **~200MB**（rootfs + Node + dsh），走中科大 / npmmirror |
| **容器** | proot 跑完整 Ubuntu 22.04 (aarch64) |
| **保活** | **前台服务（`HarnessService`）持有容器**，退出自动重启（上限 5 次） |
| **UI** | WebView 加载容器内 `127.0.0.1:3080`，注入 `mobile.css` / `inject.js` |
| **鉴权** | ★ 读容器内 `.credentials.yaml` 的签名密钥，**HMAC-SHA256 自签 cookie**（按 `host:port` 绑定，127.0.0.1 与 localhost 各一枚）；抓不到就回退"实时捕获带 token 的 URL" |
| **调试通道** | openssh-server 自启，**仅监听 `127.0.0.1:8022`** |
| **不需要 Root** | ✓ |

### ★ 它踩过、我们可以直接抄的两个细节

**① `dsh 0.1.5` 起 Web 入口带一次性 token** —— 根路径无 token / 无有效 cookie 直接 **401**。
它的解法是**自签 cookie**。⇒ **我们做 WebView 承载时会撞上同一个问题**，别从零踩。

**② 启动顺序有依赖**：加载前要**先等"带 cookie 的根路径"返回 HTTP 200（最多 120s）** 才加载 WebView。
⇒ 这是个**竞态**：服务没起来就加载 → 白屏。**它的处理是等 + 超时。**

## §3 ★ 这件事对我们解决什么（为什么你的方向是对的）

我们现在的形态：**dsh 装在用户自己的 Termux + proot 里**，App 只是"投递配置 + 起网关"。
⇒ 由此产生**三个老大难**，MEMORY 里全记着：

| 老大难 | 现在的表现 | App 内置容器后 |
|---|---|---|
| **跨 UID 写配置** | App **写不进 Termux 私有目录** ⇒ "生成配置"与"投递配置"必须分两层，靠用户手抄或 adb | ✅ **App 自己管容器，不需要投递** |
| **端口每次开启都变** | 每次都要重抄 `cordis.patch.yml` | ✅ App 内部协调，可以做成"自动重写" |
| **用户得先装 Termux** | 门槛 + 文档负担 | ✅ **不需要**，首启向导自动装容器 |

★ **而且我们刚做完的 FGS 正好复用** —— `deepseek-harness-mobile` 的做法
（前台服务持有容器 + 退出自动重启）**和我们 `AgentForegroundService` 是同一个模式**。
**不是重做，是扩一个持有对象。**

## §4 但要清醒：它和我们的**定位不同**，别把它的 UI 也搬来

| | `deepseek-harness-mobile` | 我们 |
|---|---|---|
| 用户看到什么 | **dsh 自己的 Web UI**（用户在浏览器里用 dsh） | **手机助理**（用我们的 Compose 界面，dsh 是后端） |
| 定位 | "把 dsh 装进口袋" | "**AI 手机助理**"（人格 + 记忆 + 语音 + 操作手机） |
| 能力端 | 无（它就是个 dsh 宿主） | ✅ **我们的 `:mcp` 能力桥**（无障碍 + 三道安全关卡） |

⇒ ★ **我们抄的是"容器管理那一套"，不是"它的产品形态"。**
**我们的 `:mcp` 是它没有的东西** —— 那是我们的护城河，不能因为"搬核心"而丢掉。

## §5 风险与代价

| 风险 | 说明 | 缓解 |
|---|---|---|
| **首启 200MB 下载** | 用户第一次打开要联网等 | 走国内镜像（它已验证）；向导里如实说明进度与体积 |
| **存储占用** | 容器 + Node + dsh ≈ 1GB | 向导里先报数字，让用户决定 |
| **APK 体积** | 它没把 Node 打进 APK ⇒ **APK 本身不大** ✓ | 照做（首启下载） |
| **MIT 合规** | fork 的代码要保留版权声明 | 抄代码时带上 LICENSE 与出处注释 |
| **上游漂移** | dsh 是 RC，接口会变 | 保持"容器内跑官方 npm 包"，不 fork dsh 本体 |
| **容器内 npm 装包** | 首启 `npm i -g @deepseek-ai/dsh` 依赖网络与源 | 镜像 + 失败重试（它有"安装保底重试"） |

## §6 建议路线（修正后的）

**不变的部分（已经对）**：
- `:mcp` 能力桥 = **手脚**（无障碍树 + 三道安全关卡）—— **这是我们的，不动**
- 架构位置 = **dsh 是脑，Android 是能力端**（路线 C）—— **不变**

**要变的**：**把"脑住在哪里"从"用户的 Termux"改成"App 自带的容器"**

| 步骤 | 内容 |
|---|---|
| **1** | 移植 / 借鉴 `dsh-mobile` 的容器层：`ProotRunner` + `BootstrapInstaller`（首启下载 + 镜像 + 重试） |
| **2** | `AgentForegroundService` 扩一个持有对象：**持有容器**（现在是持有网关/能力桥两个开关） |
| **3** | 容器就绪后，**App 自己把 MCP 配置写进容器**（`DshMcpConfigPatch` 已有幂等合并逻辑，直接复用）⇒ **跨 UID 投递问题消失** |
| **4** | UI：**先不做 WebView**。我们有自己的 Compose 界面，dsh 是后端 —— WebView 留到需要"轨迹视图"时再评估 |
| **5** | 保留 SSH 调试通道（`127.0.0.1:8022`）—— P3/P4 排查有用 |

**⚠️ 但别现在做。** 顺序应该是：

```
先 P3（android_tap，让 dsh 能动手）
  → 再搬容器（让交付形态干净）
```

理由：**搬容器不增加任何"能做什么"的能力，它只让"怎么交付"更干净。**
而 P3 是让 agent **第一次能动手** —— 那才是能力上的台阶。

---

## §7 一句话

**你的方向对：脑应该住在 App 里，而不是住在用户的 Termux 里。**
**但"搬"是把 dsh 原样装进去，不是把它重写一遍 ——
前者抄现成的（MIT），后者是重造 240 个包。**

**而且我们搬的是容器，不是它的 UI；我们的 `:mcp` 能力桥是它没有的东西，别丢。**
