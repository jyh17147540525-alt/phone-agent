# 会话侧边栏与全局记忆设计 v1.0

> 2026-10-12 · workbuddy · 状态：**设计稿，待评审**
> 需求来源：内测用户 ——「① 历史任务用可展开侧边栏查找与管理；② 记忆要覆盖**所有任务**的大概记忆，不只当前会话」
>
> ⚠️ **本稿不另起炉灶**：② 落在既有《AI 手机助理架构 v1.0》§4.3 的
> **L2 场景归纳 / L3 用户画像**上（那两节已设计、标 ⏳ P5、未实现）。本稿把它们
> 从"占位"补成"可实施的表结构与更新逻辑"，并补上①（原设计稿里没有 UI 侧的部分）。

---

## §0 一页纸结论

| # | 结论 | 理由 |
|---|---|---|
| 1 | **列表的单位是「会话」（session），不是「任务」** | 现在的 `AgentTaskUi` 是「一条消息 = 一张卡」。直接拿它做侧边栏，用户会看到几百张"hi"。而 `:memorylogic` 的 `Turn` **早就有 `sessionId`** —— 记忆层已经按会话分好了，UI 落后于数据层 |
| 2 | **侧边栏 = 记忆的可见面**（两条需求其实是一件事） | 记忆如果用户看不见、删不掉，它就只是"偷偷攒用户数据"。侧边栏让 L0/L1 变得可审计 |
| 3 | **全局记忆 = L2 场景 + L3 画像，输入是 L1 原子不是 L0 原文** | 原子已经过隐私卡且更短（省 token）。**跨会话聚合的泄漏面比单次对话大得多**，输入面必须收紧 |
| 4 | **检索用本地倒排 + 时间衰减，不上向量** | 无服务器（项目硬约束）；embedding 要额外花用户的钱；且 `Atom.sourceTurnIds` 让"为什么想起这条"可解释。**预留 `MemoryEmbedderPort` 将来可插** |
| 5 | **中文全文检索不用 Room FTS 默认分词器** | `simple` 分词器把整句中文当一个 token ⇒ 搜不到。v1 用 `LIKE` 子串（几千行 <10ms），量级到了再上 bigram 预切分 |
| 6 | **记忆更新是「游标推进 + 事件触发」，不是每次对话重算** | 重算 = 每次都花用户的钱。游标保证"只处理新增" |

## §1 现状（2026-10-12 实测，不是回忆）

### 1.1 两个必须先知道的事实

**① 任务根本不持久化。**

```kotlin
// TasksScreen.kt:516
val tasks = mutableStateListOf<AgentTaskUi>()
```

`TasksViewModel` 由 `AppShell` 用 `remember` 持有 —— 生命周期等于进程。
**进程一死，全部历史消失。** 所以侧边栏不是"给现有数据加个列表"，
而是**要从零建持久化**。

**② Room 里没有任务表，也没有记忆表。**

```
PocketAgentDatabase(version = 3)
  entities = [CredentialEntity, ModelConfigEntity, UsageRecordEntity]
```

`session` / `turn` / `atom` 三张表**都不存在**。`:memory` 模块**只有 build 文件、零源码**
（但已在 `ROOM_MODULES` 里 —— 这是当初刻意留的位）。

### 1.2 已经有的（别重复造）

| 层 | 落点 | 状态 |
|---|---|---|
| L0 原始对话 | `:memorylogic` `Turn(id, sessionId, role, text, at)` | ✅ 逻辑已落地 |
| L1 原子记忆 | `Atom(id, kind, text, sourceTurnIds, confidence, at)` · `AtomKind` = 事实/偏好/约束/阶段结论 · `AtomExtractor` | ✅ 逻辑已落地 |
| 上下文卸载 | `ContextOffloader` / `OffloadCodec` / `MemoryGate` | ✅ 已落地（含隐私顺序红线） |

## §2 ★ 先定建模：列表的单位是「会话」

这是**整个设计的地基**，定错了后面全白做。

### 2.1 现状的模型是错的

```
现在：  用户发一句话  →  生成一张 AgentTaskUi 卡片  →  卡片列表
        ↑ 「任务」= 「一次请求」
```

后果：侧边栏会变成"每条消息一行"。用户聊 50 句就有 50 行，其中 40 行是"hi""嗯""谢谢"。
ChatGPT / Claude 的侧边栏**从来不是这个粒度** —— 它们的单位是**会话**。

### 2.2 会话的定义（本稿拍板）

> **会话 = 一段连续交互，以"用户主动开新对话"或"空闲超时"为界。**

- 空闲超时：**30 分钟**（可配）。理由：手机上"想起来再说一句"很常见，
  超时太短会把一段连续思路切成好几段；太长会把两天的事并成一段。
- 边界判据是**时间 + 显式动作**，不是"话题变了" —— 话题检测要么花一次 LLM 调用，
  要么不准，**两个代价都不值得**。

### 2.3 与记忆层对齐

`:memorylogic` 的 `Turn.sessionId` **早就存在**，且注释写着
「跨会话的区分（以及「上次我们说到」）靠它」。也就是说：

> **记忆层一直在等一个会话概念，而 UI 层从来没给过它。**

本稿做的事，本质上是**让 UI 追上数据层**。副作用：`Atom` 将来可以带 `sessionId`，
L2 聚合才有"哪些原子来自同一段经历"这个信号。

### 2.4 `AgentTaskUi` 怎么办（不删）

它是"一次执行"的记录，仍有价值（进度、中止、失败原因）。
**新关系**：

```
session 1 ──┬── turn 1 (user: "hi")
            ├── turn 2 (assistant: "你好…")
            └── task 1 (执行记录：轮次/感知档位/中止原因)  ← 有执行才有，纯聊天没有
```

⇒ **`task` 表保留**，但它从"列表的主单位"降为"会话内的执行记录"。
侧边栏列 `session`；会话详情里才列 `task`。

## §3 侧边栏设计

### 3.0 参考了谁、**刻意不抄**什么

「参考成熟方案」不等于照抄 —— 这个项目的硬约束（**没有服务器、数据不出设备、
花的是用户自己的钱**）让三处必须分道扬镳：

| 成熟方案的做法 | 我们抄不抄 | 理由 |
|---|---|---|
| ChatGPT / Claude：左侧抽屉 + 分组列表 + 搜索 + 重命名/删除 | ✅ **抄** | 这是十年验证过的信息架构，没有理由标新立异 |
| 自动生成会话标题 | ✅ **抄**（但见 §3.3） | 抄形式，不抄成本：它们标题来自一次额外调用，我们**搭 L1 提取的便车** |
| 按 今天/昨天/前7天 分组 | ✅ **抄** | 符合人对时间的直觉 |
| **服务端全文检索 + 向量召回** | ❌ **不抄** | 我们**没有服务器**。检索必须纯本地（§3.4 / §4.4） |
| **云端记忆 + 跨设备同步** | ❌ **不抄** | 数据不出设备是合规护身符，也是这个项目存在的理由之一 |
| **自动把所有对话喂给记忆** | ❌ **不抄** | 那等于**持续花用户的钱**。我们靠**游标 + 事件触发**（§4.4） |
| **记忆对用户不透明**（攒了什么不告诉你） | ❌ **不抄，且反着做** | §4.5：L3 每一条都要可见、可否决、可溯源 —— 这是隐私红线 |
| **会话列表按「任务」粒度** | ❌ **不抄** | 见 §2：那会让列表里全是"hi" |

★ 一句话：**交互形态照抄（那是人类已经收敛的最优解），
数据架构全部自建（因为我们的约束和它们根本不同）。**


### 3.1 交互（对齐 ChatGPT / Claude 的手机版）

**入口**：左上角一个抽屉图标（现在是「任务」标题）。**不替换底部导航** ——
底部导航是**应用级**（任务 / 插件 / 设置），抽屉是**会话级**，层级不同，不冲突。

**抽屉布局**（宽屏 320dp，窄屏覆盖式 + 半透明遮罩）：

```
┌─────────────────────────────┐
│  [＋ 新对话]                │  ← 常驻顶部，最高频动作
│  ┌───────────────────────┐  │
│  │ 🔍 搜索对话…           │  │  ← 即时过滤（输入即筛，不走网络）
│  └───────────────────────┘  │
│  ─────────────────────────  │
│  今天                        │  ← 分组：今天 / 昨天 / 前 7 天 / 更早
│  ● 帮我查一下明天天气        │  ← 当前会话：左侧色条 + 高亮底
│    14:32 · 3 条              │
│    配好了 dsh 集成           │
│    11:05 · 12 条             │
│  昨天                        │
│    那份表格怎么导出          │
│    …                         │
│  ─────────────────────────  │
│  已归档（3）           ▸     │  ← 折叠，默认收起
└─────────────────────────────┘
```

**每项的操作**（长按或右滑）：

| 操作 | 说明 |
|---|---|
| 重命名 | 标题默认自动生成（见 §3.3），用户可改。**改过之后不再自动覆盖** |
| 置顶 | `pinned`，置顶项始终在最上（在分组之上，单独一组） |
| 删除 | **两步确认**。删的是 L0 + 该会话的原子（见 §4.6 的级联规则） |
| 归档 | 不进删除，只是从主列表移走（`archived`） |

**状态设计**（本项目纪律：不糊弄）：

| 状态 | 表现 |
|---|---|
| 空（从没用过） | 「还没有对话。说一句话开始。」+ 一个箭头指向输入框 |
| 搜索无结果 | 「没有匹配「xxx」的对话。」+ 一个"清除搜索"按钮 |
| 加载中 | 骨架屏（3 条灰条），**不要转圈** |
| 读取失败 | 「读不到对话历史（原因）」+ 重试。**不显示空列表** —— 空列表会被误读成"我的历史没了" |

### 3.2 存储结构（Room v3 → v4）

```sql
-- ── 会话（侧边栏的主单位）────────────────────────────
CREATE TABLE session (
  id           TEXT PRIMARY KEY,      -- UUID
  title        TEXT NOT NULL,         -- 展示标题（自动生成或用户改名）
  titleSource  TEXT NOT NULL,         -- AUTO | USER  ← 见 §3.3
  createdAt    INTEGER NOT NULL,
  updatedAt    INTEGER NOT NULL,      -- 排序键（最近活动优先）
  lastMessageAt INTEGER NOT NULL,     -- 与 updatedAt 分开：改名不该让它跳到最前
  turnCount    INTEGER NOT NULL DEFAULT 0,
  pinned       INTEGER NOT NULL DEFAULT 0,
  archived     INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_session_order ON session(archived, pinned DESC, lastMessageAt DESC);

-- ── L0 原始轮次（记忆层已有逻辑，这里只是落盘）─────────
CREATE TABLE turn (
  id         TEXT PRIMARY KEY,
  sessionId  TEXT NOT NULL REFERENCES session(id) ON DELETE CASCADE,
  role       TEXT NOT NULL,           -- USER | ASSISTANT | TOOL
  text       TEXT NOT NULL,
  at         INTEGER NOT NULL,
  tokenCount INTEGER                     -- 可空：算不出就是 null，不填 0
);
CREATE INDEX idx_turn_session ON turn(sessionId, at);

-- ── 执行记录（原 AgentTaskUi，降级为会话内的明细）──────
CREATE TABLE task (
  id           TEXT PRIMARY KEY,
  sessionId    TEXT NOT NULL REFERENCES session(id) ON DELETE CASCADE,
  prompt       TEXT NOT NULL,
  state        TEXT NOT NULL,         -- Running | Done | Aborted | Failed
  step         INTEGER NOT NULL DEFAULT 0,
  note         TEXT NOT NULL DEFAULT '',
  abortReason  TEXT,
  perceptionTier INTEGER NOT NULL DEFAULT 0,
  createdAt    INTEGER NOT NULL,
  finishedAt   INTEGER
);
CREATE INDEX idx_task_session ON task(sessionId, createdAt);
```

⚠️ **`ON DELETE CASCADE` 必须显式开**（Room 需要 `foreignKeys` 声明 + `PRAGMA foreign_keys=ON`）。
不然后果是**孤儿轮次**：会话删了，turn 还在库里躺着 —— 用户以为删干净了，
而磁盘上还留着他说过的每一句话。**这是隐私问题，不是整洁问题。**

### 3.3 标题从哪来（不许"取前 20 字"）

朴素做法是 `text.take(20)`，后果是列表里全是「你好，帮我查一下明天的天气…」这种半截话。

**本稿方案（两级，都不额外花钱）**：

1. **首轮启发式**（零成本，立刻可用）：
   取首条用户消息，按标点切成第一个**语义完整**的短句（≤ 16 字），去掉开头寒暄词
   （你好/帮我/请问/我想）。切不出来就退到前 16 字 + 「…」。
2. **L1 提取时顺带生成**（零额外调用）：
   会话空闲触发 L1 提取时，**同一次 LLM 调用**里多要一个字段 `title`。
   ⇒ 不额外花钱，且比启发式准。回来后**只在 `titleSource == AUTO` 时**覆盖。

⚠️ `titleSource == USER` 之后**永不自动覆盖**。用户改过的名字被自动改回去，
比不改更让人恼火 —— 而且他不会认为这是 bug，他会认为"这 App 记不住事"。

### 3.4 搜索：★ 中文全文检索的坑

**不要直接用 Room 的 FTS 默认配置。** 实测与原理：

| 方案 | 中文表现 | 结论 |
|---|---|---|
| `@Fts4` 默认（`simple` 分词器） | 按**非字母数字**切词 ⇒ 一整句中文变成**一个 token** | ❌ 搜"天气"搜不到「明天天气怎么样」 |
| `unicode61` 分词器 | 同上，unicode61 不做 CJK 切分 | ❌ |
| `LIKE '%kw%'` 子串 | 中文**天然可用**（子串即匹配） | ✅ **v1 用它** |
| FTS + 预切 bigram | 有效，但要自己维护辅助列 | ⏳ 量级到了再上 |

**v1 拍板：`LIKE` 子串 + 索引。**

```sql
SELECT id, title, lastMessageAt FROM session
WHERE archived = 0 AND (title LIKE '%' || :kw || '%'
   OR id IN (SELECT sessionId FROM turn WHERE text LIKE '%' || :kw || '%'))
ORDER BY lastMessageAt DESC LIMIT 50;
```

**为什么够用**：个人助理的会话量级是**千**，不是**百万**。
几千行的 `LIKE` 全表扫 < 10ms（SQLite 在本机内存里跑）。
**上 FTS 的触发条件写清楚**：会话 > 10,000 条 **或** 搜索耗时 > 50ms（真机实测）。
在此之前上 FTS 是**为不存在的问题付复杂度**。

⚠️ 搜 `turn.text` 时**必须**过 `MemoryGate` 的同一套规则吗？——**不用**。
搜索是本地行为、结果不离开设备、也不进 prompt。但**结果里的敏感片段要遮蔽**
（复用 `PrivacyFilter` 的文本遮蔽），否则"搜索"会变成一条**绕过遮蔽的读屏旁路**。

## §4 全局记忆设计

### 4.1 组织方式：四层 + 一条检索面

```
L0 turn      全量保留，不检索（只在"展开某次对话"时读）
   │  ← 提取（LLM，批量）
L1 atom      事实 / 偏好 / 约束 / 阶段结论，每条可回溯到源 turn
   │  ← 聚合（LLM，按主题）
L2 scene     一段"经历"（如「把 dsh 集成配通了」），带活跃度
   │  ← 蒸馏（LLM，低频）
L3 profile   稳定画像，单实例、持续收敛
   │
   ├─→ L1 原子  → PersonaAssembler.AssemblyInput.memories（省 token 的那条线）
   └─→ L3 画像  → PersonaDelta → PersonaTuner（调人格的那条线）
```

★ **两条出口，一个源**（承 §4.3.2-① 的既有判断）：
「省 token」和「调人格」**不能拆成两个模块**，否则会得到两套互相不知道的用户模型。

### 4.2 「全局」到底全局在哪

用户的原话是「汇总全局任务的关键信息，而非仅局限于当前会话」。具体化为三条：

| 维度 | 含义 | 落点 |
|---|---|---|
| **跨会话** | 不在单次对话里找，而在**全部**原子里找 | L2 的输入是 L1 全表，不是当前 session 的原子 |
| **跨时间** | 昨天的偏好和今天的一样有效 | 时间衰减是**加权**不是过滤（§4.4） |
| **跨类型** | 不只记"事实"，更记"偏好/约束" | `AtomKind` 已分四类，L3 **只吃 PREFERENCE + CONSTRAINT** |

⚠️ 第三条最容易做错：把 FACT 也喂进画像，画像会变成"用户说过的话的复述"，
而不是"用户是谁"。**画像要的是稳定倾向，不是流水账。**

### 4.3 存储结构（Room v3 → v4，续 §3.2）

```sql
-- ── L1 原子 ─────────────────────────────────────────
CREATE TABLE atom (
  id          TEXT PRIMARY KEY,       -- 由内容派生（确定性，见 §4.7）
  kind        TEXT NOT NULL,          -- FACT | PREFERENCE | CONSTRAINT | STAGE_CONCLUSION
  text        TEXT NOT NULL,
  confidence  REAL NOT NULL,          -- 0..1
  sessionId   TEXT,                   -- 可空：跨会话归纳出来的原子没有单一来源
  at          INTEGER NOT NULL,
  -- 溯源：JSON 数组。⚠️ 不用关联表 —— 它是"证据链"，只整体读、从不单条查
  sourceTurnIds TEXT NOT NULL
);
CREATE INDEX idx_atom_kind_at ON atom(kind, at DESC);
CREATE INDEX idx_atom_session ON atom(sessionId);

-- ── L2 场景 ─────────────────────────────────────────
CREATE TABLE scene (
  id         TEXT PRIMARY KEY,
  title      TEXT NOT NULL,
  summary    TEXT NOT NULL,           -- ★ 进 prompt 的就是这一句（≤ 80 字）
  atomIds    TEXT NOT NULL,           -- JSON 数组：这个场景由哪些原子归纳而来
  firstAt    INTEGER NOT NULL,
  lastAt     INTEGER NOT NULL,
  weight     REAL NOT NULL,           -- 活跃度（§4.4 的公式）
  -- ★ 聚合版本：同一批原子重复聚合时不重算（幂等键）
  aggregatedFrom TEXT NOT NULL
);
CREATE INDEX idx_scene_weight ON scene(weight DESC, lastAt DESC);

-- ── L3 画像（单表 KV，行数 = 画像维度数，个位数）──────
CREATE TABLE profile (
  key            TEXT PRIMARY KEY,    -- 如 "pref.reply_length" / "constraint.no_call_before_9"
  value          TEXT NOT NULL,
  confidence     REAL NOT NULL,
  updatedAt      INTEGER NOT NULL,
  evidenceAtomIds TEXT NOT NULL       -- JSON 数组：★ 没有证据的画像项不许存在
);

-- ── 蒸馏进度游标（★ 省 token 的关键）────────────────
CREATE TABLE memory_cursor (
  key   TEXT PRIMARY KEY,             -- "l1.lastTurnAt" / "l2.lastAtomAt" / "l3.lastRunAt"
  value TEXT NOT NULL
);
```

★ **`memory_cursor` 是这套设计里最不显眼、但最省钱的一张表**：
没有它，每次触发都要扫全表重算；有了它，每层只处理"上次之后新增的"。

### 4.4 更新逻辑（★ 用户特别问的）

#### 触发时机（三层各不同，刻意错开）

| 层 | 触发 | 频率 | 为什么是这个时机 |
|---|---|---|---|
| **L0** | 每轮对话结束**立即**落盘 | 每轮 | 它是**事实记录**，丢了就是丢了。零 LLM 成本 |
| **L1** | 会话**空闲 30 分钟**（= 会话结束）**或**累计 ≥ 12 轮 | 每会话 1 次 | 太频繁 = 烧钱；太晚 = 用户切走后丢失提取机会 |
| **L2** | L1 新增 ≥ 20 条原子 **或** 距上次 ≥ 1 天且 ≥ 5 条 | 约每天 1 次 | 场景要"攒够"才有归纳价值 |
| **L3** | **每 7 天** 或 原子总数翻倍 | 约每周 1 次 | 画像是**慢变量**。天天重算只会让它在噪声里抖 |

⚠️ **所有触发都必须是"有新增才跑"**（靠游标）。没新增还调 LLM = 纯烧钱。

#### 每层做什么

**L1 提取**（已有 `AtomExtractor`，此处只补接线）：
- 输入：该会话的**全部** turn（未提取过的）
- 一次 LLM 调用，**批量**返回 N 条原子 + 会话标题（§3.3）
- 过 `MemoryGate` → 落 `atom` 表 → 推进 `l1.lastTurnAt`

**L2 聚合**（本稿新增 `SceneAggregator`）：
- 输入：**游标之后新增的原子**（不是全部）
- 一次 LLM 调用：「把这些原子归纳成若干场景，每个场景给标题 + 一句 ≤80 字摘要」
- ★ **合并而非新增**：新场景与已有场景主题重合时**更新已有场景**（并 `lastAt`、`weight`），
  否则场景表会随天数线性增长 —— 而它是要进 prompt 的
- 落 `scene` 表

**L3 蒸馏**（本稿新增 `ProfileDistiller`）：
- 输入：**`PREFERENCE` + `CONSTRAINT` 两类原子**（§4.2 第三条）
- 一次 LLM 调用：「从这些偏好/约束里蒸馏出稳定画像项，每项给 key/value/置信度」
- ★ **冲突不覆盖，走 `PersonaContradictionPort`**（该端口已存在）：
  - 新值与旧值矛盾 → 写新值但**降置信度**，并把冲突上报
  - 冲突连续出现 N 次（默认 3）→ 提升新值置信度、**采纳新值**
  - 理由：用户改主意很正常（"以后别叫我老板"）。**一次冲突就覆盖**会把口误固化成画像
- 产出 → `PersonaDelta` → `PersonaTuner`（已有链路）→ **变更账本可见**（§4.5）

#### 活跃度公式（L2 的 `weight`）

```
weight = Σ(原子置信度 × 时间衰减)
时间衰减 = exp(-Δt_days / HALF_LIFE)     HALF_LIFE = 30 天
```

- 一个月前的场景权重减半 —— 但**永不为 0**（这是加权不是过滤）。
  「用户讨厌打电话」这种约束一年后仍然成立。
- 用途：L2 场景进 prompt 时**按 weight 排序取前 N 条**（N 默认 3）。

### 4.5 ★ L3 的产出必须可见（承既有红线）

既有设计里有一条硬判断：**「人格微调不是记忆问题，是感知问题 ——
用户看不见的调整等于没调整」**。

⇒ L3 蒸馏产出的每一条画像项，**必须**出现在「变更账本」里，且能：
- 看到**证据**（`evidenceAtomIds` → 反查到源 turn 的原文）
- **否决**（否决后该项进黑名单，不再被蒸馏出来）
- 看到**置信度**与**最近更新时间**

⚠️ 没有这一条，L3 就是一个**偷偷攒用户画像**的模块 —— 而这是隐私红线，
不是体验问题。

### 4.6 删除与级联（★ 用户能删才是真记忆）

| 用户动作 | 级联 |
|---|---|
| 删一个会话 | `turn` / `task` 级联删（§3.2）· 该会话**独有**的 `atom` 删 · 参与过该会话的 `scene` **重算**（不是删）|
| 删一条记忆（原子） | `atom` 删 · 引用它的 `scene` 重算 · 引用它的 `profile` 项**降置信度**，归零则删 |
| 一键清空全部记忆 | 全部 `atom`/`scene`/`profile` 删 · `turn` **保留**（那是对话记录，不是记忆）· 游标重置 |

⚠️ 场景的"重算"不能同步做（要调 LLM）。设计成**标记待重算** + 下次 L2 触发时处理。
在此之前该场景**标记为 `stale`**，进 prompt 时**跳过** ——
**宁可少给一条记忆，也不要给一条基于已删数据的记忆。**

### 4.7 确定性 id（承既有纪律）

`Atom.id` / `Scene.id` **由内容派生，不含时间**（`Hashing` 已有）。
理由见既有设计 §4.3.4-(4)：含时间会让重试落到两个 id，「幂等」当场失效。

`scene.aggregatedFrom` 同理 —— 它是**参与聚合的原子 id 集合的哈希**，
用来判断"这批原子是不是已经聚合过了"。

## §5 两条需求其实是一件事

```
                   ┌──────────────────────────────┐
   用户看到的是 →  │  侧边栏：会话列表 / 搜索 / 删除 │
                   └──────────────┬───────────────┘
                                  │ 读
                   ┌──────────────▼───────────────┐
   数据层是     →  │  session / turn / task  (L0)  │
                   └──────────────┬───────────────┘
                                  │ 提取
                   ┌──────────────▼───────────────┐
   助理"记住"的是→  │  atom (L1) → scene (L2) → profile (L3) │
                   └──────────────────────────────┘
```

**侧边栏不是"另一个功能"，它是记忆层的可审计面。** 具体：

1. 点开一个历史会话 = **从 L0 恢复上下文**（不是从记忆里猜）
2. 侧边栏里能搜到 = 记忆层确实存住了
3. 删掉一个会话 = 记忆层的对应原子跟着走（§4.6）
4. 会话标题 = L1 提取的副产品（§3.3）—— **同一份数据，两个用途**

⇒ **实施顺序必须是先 L0 持久化 + 侧边栏，再 L1 接线，最后 L2/L3。**
反过来做会得到"有记忆但看不到、删不掉"的东西 —— 那是隐私风险，不是功能。

## §6 红线与成本

### 6.1 红线（不可越，逐条有既有依据）

| # | 红线 | 依据 |
|---|---|---|
| 1 | **记忆落盘前必须过 `MemoryGate`** | 既有 §8.2-2，已用类型钉死 |
| 2 | **L2/L3 的 LLM 输入只送 L1 原子，不送 L0 原文** | 跨会话聚合的泄漏面更大；原子已过卡且更短 |
| 3 | **L3 的每一条产出必须可见、可否决** | §4.5；"看不见的调整等于没调整" |
| 4 | **搜索结果的敏感片段要遮蔽** | 否则搜索成了绕过遮蔽的旁路（§3.4） |
| 5 | **删除必须真删（含级联）** | §4.6；"用户以为删干净了"是隐私问题 |
| 6 | **数据不出设备** | 项目硬约束。记忆的 LLM 调用走**用户自己的 Provider** |

### 6.2 成本（花的是用户的钱，必须可控）

| 项 | 频率 | 量级 |
|---|---|---|
| L0 落盘 | 每轮 | 零 LLM |
| L1 提取 | 每会话 1 次 | 1 次调用（输入 = 该会话全部 turn）|
| L2 聚合 | 约每天 1 次 | 1 次调用（输入 = 新增原子）|
| L3 蒸馏 | 约每周 1 次 | 1 次调用（输入 = 偏好+约束原子）|

⇒ 一个每天聊 10 轮的活跃用户：**约 11 次调用/天**，且都是小输入。

**三个必须做的省钱措施**：
1. **游标**（§4.3）—— 只处理新增
2. **批量**（§4.4）—— 一个会话一次调用，不是一轮一次
3. **记忆总开关** —— 用户可以关。⚠️ 关掉时**不删已有记忆**（那是两件事），
   只是不再产生新的；界面上要写清楚这个区别

## §7 分阶段落地

| 阶段 | 内容 | 可验证的判据 |
|---|---|---|
| **S1** | `:memory` 落 `session`/`turn`/`task` 三表（Room v3→v4 + 迁移）· 侧边栏 UI · 会话分组/搜索/重命名/删除 | 杀掉进程重开，历史还在；搜索能搜到中文子串 |
| **S2** | 会话边界（空闲 30 分钟）+ 标题两级生成 + L1 提取接线（含 `memory_cursor`）| 新会话空闲后 `atom` 表出现行；标题不是"取前 20 字" |
| **S3** | `SceneAggregator`（L2）+ 场景进 prompt（按 weight 取前 3） | `AssemblyInput.memories` 里出现跨会话的条目 |
| **S4** | `ProfileDistiller`（L3）+ `PersonaContradictionPort` 接线 + 变更账本可见 | 改口癖两次后，账本里能看到冲突与置信度变化 |
| **S5** | 删除级联 + 记忆管理页（看/否决/清空） | 删会话后原子跟着走；删记忆后 prompt 里不再出现 |

⚠️ **S1 单独就有价值**（历史不再丢），且**不花用户一分钱**。建议先落 S1 收反馈。
