# 外部实例考察：后台虚拟屏 与 dsh 手机版

> 2026-10-03。起因：用户看到"有博主把 deepseek harness 部署到手机上，实现了后台虚拟屏运行"，
> 问对本项目的可行性与风险。**本文先纠正一个前提，再分别评估两个真实项目。**

---

## §0 结论速览

| 问题 | 结论 |
|---|---|
| "dsh 实现了后台虚拟屏" | ❌ **不成立** —— 那是**两个独立项目**，被当成一个了 |
| 后台虚拟屏能否用于本项目 | ⚠️ **技术上能，但代价是 Root + LSPosed 注入 `system_server`** |
| 这个代价本项目付不付得起 | ❌ **付不起**（见 §4） |
| 那这个实例对我们有没有价值 | ✅ **有，而且很大** —— 它替我们验证了两条我们只能推测的结论（见 §5） |
| dsh 手机版那部分值不值得学 | ✅ **值得** —— 它和我们的做法已经撞车（FGS 持有容器），但它多了两样我们没做的 |

---

## §1 先纠正前提：那是两个项目

| 项目 | 它做什么 | 关键技术 | 要 Root 吗 |
|---|---|---|---|
| **`deepseek-harness-mobile`**（dsh 手机版） | 把 **dsh 跑在手机里** | App 内置 proot + Ubuntu 22.04 + WebView | ❌ 不要 |
| **`agent-mobile-use`**（后台虚拟屏） | 在**后台开一块虚拟屏**，让 AI 在里面操作 | `VirtualDisplay` + LSPosed Hook + H.264 流 | ✅ **要** |

★ **两者之间唯一的联系**：`agent-mobile-use` 的网关是 `vd-server-go`（端口 3070），
**它的控制台就是 DSH（端口 3080）** —— 也就是说 **dsh 是它的"操作界面"，不是它的"虚拟屏实现"**。

⇒ 博主看到的很可能是**这两个拼在一起**的画面，于是被概括成"dsh 实现了后台虚拟屏"。
**这个概括是错的，而且错得很关键** —— 因为它会让人以为"我们只要把 dsh 装上去就有了虚拟屏"。

---

## §2 后台虚拟屏（`agent-mobile-use`）到底怎么做出来的

从它的 README 提取到的**明确事实**：

```
组件              技术
─────────────────────────────────────────────────────────────
DaemonMain        「通过特权 API 动态创建 VirtualDisplay，镜像主屏物理打孔，
                   管理全分辨率的高性能 JPEG 帧缓存」
HookEntry         「基于 LSPosed 的 system_server 特权补丁，解锁虚拟副屏
                   ★ 多任务承载能力、★ 主屏输入法隔离（IMMS），
                   以及 SystemUI 流体云过滤与硬拦截」
ToolMain          「UiAutomation 抓取结构化平铺 UI 控件树」+
                   「基于无障碍的纯确定性双轨文字注入」（可指定 UI 树节点 ID
                   或直接灌入聚焦输入框，0 键盘弹窗）
流                WebSocket H.264 低延迟裸流（1080P/60FPS/6Mbps，硬件编码）
权限              AppOps 精准抑制副屏音频流
环境              KernelSU / APatch / Magisk + LSPosed
                  实测 ColorOS 16 / Android 15-16 / 内核 6.12+
```

### ★★ 两条事实**证实了我们只能推测的结论**

本项目在虚拟屏上踩过并写进 MEMORY 的两条硬伤，**它用 Hook 解决，等于反证了这两条是真的**：

| 我们的结论（MEMORY） | 它的对策 |
|---|---|
| **「无感」在多任务交叉时崩塌**（虚拟屏上跨应用跳转 → 主屏被整个切走） | HookEntry **解锁"虚拟副屏多任务承载能力"** |
| **输入法/焦点冲突** | HookEntry **做"主屏输入法隔离（IMMS）"** |

⇒ **这两件事都不是"调参能解决"的，必须系统级介入。**
我们当时判断"这条路代价很大" —— **现在有人用代价证明了这个判断是对的。**

### ⚠️ 但它自己的成熟度存疑

它仓库的 commit 记录里有这样几条（README 自己列的）：

> - "eliminate **deceptive fallbacks**, report type/dump errors **honestly**"
> - "Return Success: false on type injection errors and daemon failures
>   **instead of faking success**"
> - "Propagate dump failures in action response **instead of silently returning empty screens**"

⇒ **早期版本存在"伪造成功"和"静默返回空屏"**。
这是**本项目最警惕的 bug 形态**（"安静地少做一件事"）。
**说明这类系统的默认失败模式就是静默** —— 它踩过，我们也踩过。

## §3 dsh 手机版（`deepseek-harness-mobile`）值不值得学

### 它和我们**已经撞车**的部分

| 它的做法 | 我们的现状 |
|---|---|
| **前台服务持有容器**（"后台保活：前台服务持有容器，附电池白名单与自启动引导"） | ✅ **今天刚做完**（`AgentForegroundService`，`specialUse`） |
| App 内置容器，不依赖用户装 Termux | ⚠️ 我们目前依赖用户自己装 Termux + proot |
| 首启联网下载 ~400MB 容器 | ⚠️ 我们的 dsh 装在用户 Termux 里 |

★ **注意**：它**不需要 root**，和我们的定位一致 ✓

### ★ 它有两样**我们没做但该考虑**的

**① 外置 SD 卡映射进容器**

> 「外置 SD 卡映射进容器工作区（`sd/`、`shared/` 两个入口），文件双向传递；
> 系统文件管理器直接上传附件」

⇒ **这正好接上我们 `:filelogic` 的"工作区"设计** ——
我们的工作区是 App 私有目录（用户打不开），它的做法是**给用户两个能看见的入口**。
**这解决的是"应用私有目录（非 root 设备打不开）"那个我们自己写在界面上的尴尬。**

**② 容器 SSH 自启**

> 「`ssh dsh@127.0.0.1 -p 8022`，本机终端直连」

⇒ 这是个**调试通道**。对我们做 P3/P4 时的排查会很有用。

**③ 移动端 Web UI 注入适配**（覆盖式抽屉、触控目标加大、弹窗不溢出）

⇒ 我们在 `docs/后台常驻与语音交互方案-v1.0.md` 里规划的 WebView 承载 dsh UI，
**它已经把适配细节趟过一遍了**，可以直接抄。

## §4 风险与限制（为什么"照抄虚拟屏"这条路我们走不通）

### ① 硬门槛：**Root + LSPosed**

- 它明确依赖 **KernelSU / APatch / Magisk + LSPosed**
- 且要**注入 `system_server`** —— 这是**系统进程**，不是普通 App
- ⇒ 与本项目「**尽量少影响用户正常使用手机**」的**最高优先级原则直接冲突**
- ⇒ 与本项目「**全开源、社区分发、不上架**」的定位也冲突 —— 要求用户 root 会把用户面砍到极小
- ⇒ 与「**Key 永不落明文**」同源的**信任模型**冲突：一个能注入 `system_server` 的模块，
  其攻击面远大于一个用无障碍的 App

### ② 隐私红线（我们自己记过，它没解决）

MEMORY 里记的：**虚拟屏的帧里是用户真实的私人聊天列表**。
`agent-mobile-use` 的应对是 **H.264 流 + 录屏** —— 它把画面**更多地**搬出来了，
而不是更少。⇒ **它的隐私姿态比我们更激进，不能照抄。**

### ③ 成熟度

见 §2 末尾：它自己承认过"伪造成功"。
**一个在"是否真的成功"上出过问题的系统，不适合作为我们唯一依赖的底座。**

### ④ 版本敏感

实测环境是 ColorOS 16 / Android 15-16 / 内核 6.12+。
我们是 **HyperOS / Android 15 / API 35** —— 不同 ROM 的 `system_server` 差异极大，
Hook 方案的移植成本不可预估。

## §5 ★ 那这个实例对我们的真正价值是什么

**不是"我们也可以去做虚拟屏"，而是三条：**

### 1. 它替我们**验证了两条推测**（§2）

"多任务承载"和"IME 隔离"必须系统级介入 —— 我们的判断是对的。
⇒ **可以正式把虚拟屏从"待探索"降级为"已确认代价过高"**，不再重复投入。

### 2. ★ 它揭示了一个我们**没意识到的架构位置**

看这张图：

```
agent-mobile-use 的形态：
   vd-server-go (3070)  ← 虚拟屏 + 输入注入 + UI 树
          ↑
        DSH (3080)      ← agent 大脑，把上面当工具用
```

**它的"虚拟屏"对 dsh 而言，就是一个工具/一个 MCP server。**

⇒ **而这正是我们 P2 已经建成的形态**：
我们的 `:mcp` 已经把 `screen_read` 暴露成 `mcp__phone__screen_read`。
**它用的是虚拟屏 + H.264 + Root，我们用的是无障碍树 + FGS —— 接口位置完全一样。**

⇒ **结论：我们和它在同一个架构位置上，只是实现手段不同。**
**我们的手段（无障碍）门槛低、隐私姿态好；它的手段（虚拟屏）无感但要求 root。**
**这两条路可以并存** —— 将来若要加"无感"档，加的是**一个新的 MCP 工具**
（如 `screen_read_stealth`），而不是推翻现有架构。

## §6 建议

| 建议 | 理由 |
|---|---|
| ❌ **不跟 Root/LSPosed 路线** | 与项目三条原则冲突，代价不可控 |
| ✅ **把虚拟屏正式记为"已确认代价过高"** | 避免重复投入；文档里已有结论，现在有外部佐证 |
| ✅ **借鉴 dsh 手机版的三个做法** | 外置 SD 映射 / 容器 SSH 调试通道 / 移动端 Web UI 适配 |
| ✅ **保持现有架构位置不变** | 我们的 `:mcp` 与它同级；将来加"无感档"是**加一个工具**，不是重构 |
| ⏳ **先做 P3（`android_tap`）** | 现在缺的是"能动手"，不是"更无感"。**能动手之后，"无感"才有意义** |

### 一句话

**它证明了"这条路能走通"，也顺便证明了"这条路要付什么代价" ——
而那个代价，我们明确不付。但它的架构位置告诉我们：我们已经在正确的位置上了。**
