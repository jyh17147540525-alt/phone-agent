# 多 Key、多模型与调度层设计 v1.0

[English](多Key与模型调度设计-v1.0.en.md) | **简体中文**

> 发布主体「代码乌托邦」。本文回答五个需求：
> ① 多 API Key 管理页面 ② 多模型配置（价格有高有低）
> ③ 可选的底层调度模型（按任务难度派发） ④ 单模型模式（可选项）
> ⑤ 悬浮球替代虚拟屏的交互形态
>
> **最高优先级约束：尽可能减少对用户正常使用手机的影响。**
> 本文每个设计决策都以这条为准绳，§6 给出量化目标。

## 0. 现状盘点（先看清有什么，避免重复造轮子）

| 能力 | 现状 | 结论 |
|---|---|---|
| 多 Key 存储 | ✅ `CredentialEntity` 有 `id`/`label`/`isDefault`，**已支持多条** | 复用，只需扩 UI |
| Key 加密 | ✅ Keystore + AES-GCM + SQLCipher，明文只在两个受控作用域出现 | **不动** |
| Key 校验 | ✅ 六态状态机（含 `UNREACHABLE` 与 `INVALID` 严格分开） | **不动** |
| Provider 抽象 | ✅ `ModelInfo` 已带 `inputPricePerMillion` / `Capability` | **正是调度所需** |
| 模型配置 | ❌ **无实体、无表** —— 当前只有"Key 能列出哪些模型" | **本次新增** |
| 调度层 | ❌ **完全没有** | **本次新增** |
| 虚拟屏 | ❌ P0-3 已否决 | 改悬浮球 |
| 悬浮球 | ❌ **无任何代码** | **本次新增** |

**关键发现：`ModelInfo` 里已经有价格字段和 `Capability` 枚举。**
调度层不需要新造模型元信息体系 —— 直接消费 Provider 返回的这个结构即可。

## 1. 需求一：多 API Key 管理

### 1.1 已有基础上的扩展

`CredentialsScreen`（现 `KeysScreen`）已支持增删改查、校验、设为默认。
本次只补三个点：

| 补充 | 理由 |
|---|---|
| **按 Provider 分组** | 用户有 5 个 Key 时，平铺列表看不出哪个是哪个厂商 |
| **用途标签**（对话 / 语音合成 / 调度） | 见需求五的 TTS Key —— 必须能区分 |
| **使用统计**（可选） | "这个 Key 这个月花了多少" —— 帮用户判断该留哪个 |

### 1.2 用途标签的设计（解决 TTS Key 混淆）

⚠️ 用户明确要求过：**TTS Key 要单独弹窗，避免与其他配置混淆。**

落到数据层是给 `CredentialEntity` 加一个字段：

```kotlin
/** 这条 Key 的用途。默认 CHAT，语音合成必须显式指定 */
val purpose: CredentialPurpose = CredentialPurpose.CHAT

enum class CredentialPurpose {
    CHAT,           // 对话模型
    SPEECH,         // 语音合成（TTS）
    SCHEDULER,      // 调度模型（见需求三）
}
```

**为什么用同一个表 + 字段，而不是开新表？**
- 加密链路完全复用（`CryptoManager`、`withDecryptedKey`），不用重写
- 校验逻辑复用（`validate` 一套代码）
- 只需要**界面层分开展示** —— 用户看到的是两个独立页面，实现上是同一张表

> **用户看到"分离"，实现保持"统一"。** 这是减少重复代码的关键。

⚠️ **迁移**：数据库 `version` 1 → 2，加一条 `Migration`。已有数据默认 `CHAT`。

### 1.3 界面结构

```
设置
├── 联网 API Key          ← CredentialsScreen(purpose=CHAT)
├── 语音合成 Key          ← CredentialsScreen(purpose=SPEECH)   ★独立页面
├── 模型配置              ← ModelsScreen（本次新增）
└── ...
```

## 2. 需求二：多模型配置

### 2.1 为什么需要独立于 Key 的"模型配置"

用户的 Key 和模型是**多对多**关系：

```
Key A (OpenRouter) ──┐
                     ├── 可用模型：gpt-4o / claude-3.5 / llama-3.1-8b ...
Key B (DeepSeek) ────┼── 可用模型：deepseek-chat / deepseek-reasoner
                     │
Key C (本地 Ollama) ──┴── 可用模型：qwen2.5:7b ...
```

**同一个模型可能通过不同 Key 访问**（且价格可能不同）。
所以需要一张"模型配置"表，指向某条 Key + 某个模型 id。

### 2.2 数据模型

```kotlin
@Entity(tableName = "model_config")
data class ModelConfigEntity(
    @PrimaryKey val id: String,               // UUID

    /** 用户起的名字，如"便宜的快速模型"。空则用模型名 */
    val label: String,

    /** 指向 credential.id —— 决定用哪个 Key */
    val credentialId: String,

    /** 模型 id，如 "deepseek-chat" / "gpt-4o-mini" */
    val modelId: String,

    /** 展示名，来自 ModelInfo.displayName */
    val modelDisplayName: String,

    /**
     * 能力档位 —— **这是调度层的核心输入**
     * 从 ModelInfo.capabilities + 价格推导，用户可覆盖
     */
    val tier: ModelTier,

    /** 价格（每百万 token，美元）。缓存下来避免每次调度都要查 */
    val inputPricePerMillion: Double?,
    val outputPricePerMillion: Double?,

    /** 用户手动指定的角色偏好 —— 见 §3.4 */
    val roles: Set<ModelRole>,

    val enabled: Boolean,
    val createdAtMillis: Long,
)

/**
 * 能力档位。
 *
 * ⚠️ 刻意用**三档**而不是连续分数：用户能理解"高中低"，
 *    理解不了"这个模型能力值 0.73"。档位也让调度决策可解释。
 */
enum class ModelTier {
    /** 便宜/快/能力弱。适合：简单问答、格式转换、提取字段 */
    LIGHT,
    /** 均衡。默认档 */
    STANDARD,
    /** 贵/慢/能力强。适合：复杂推理、多步规划、长上下文 */
    HEAVY,
}

enum class ModelRole {
    /** 可被选为调度者 */
    SCHEDULER,
    /** 可被调度执行任务 */
    WORKER,
    /** 用户手动指定用于简单对话 */
    CHAT_LIGHT,
    /** 用户手动指定用于复杂任务 */
    CHAT_HEAVY,
}
```

### 2.3 档位如何自动推导（减少用户配置负担）

用户不该手工为每个模型打档位 —— 那是我们的活。推导规则：

```
从 ModelInfo 推导 tier：
├── 有价格信息？
│   ├── outputPrice < $1/M   → LIGHT
│   ├── $1/M ≤ price < $8/M  → STANDARD
│   └── price ≥ $8/M         → HEAVY
└── 无价格（本地/自建）？
    └── 按能力推断：
        ├── 有 VISION + LONG_CTX  → HEAVY
        ├── 有 TOOL_CALL          → STANDARD
        └── 其余                  → LIGHT
```

⚠️ **必须允许用户覆盖**。价格是估算，能力是主观判断 ——
用户可能知道"这个模型便宜但很聪明"。自动推导只是**默认值**，不是定论。

### 2.4 界面（列表 + 编辑）

```
模型配置
┌────────────────────────────────────────┐
│  ⓘ 配置多个模型后，可以让 agent 按任务难度   │
│    自动选择。只配一个也能用。               │
├────────────────────────────────────────┤
│  便宜快速        deepseek-chat          │
│  [轻量] $0.14/M  ●可用         [调度者] │
├────────────────────────────────────────┤
│  主力            claude-sonnet-4        │
│  [均衡] $3.00/M  ●可用                  │
├────────────────────────────────────────┤
│  复杂任务        o3                     │
│  [重型] $15.00/M ●可用                  │
├────────────────────────────────────────┤
│  + 添加模型                              │
└────────────────────────────────────────┘
```

**每行右侧的 `[调度者]` 标签**直接关联需求三 —— 用户在这里就能看出
哪个模型会被用来做派发决策。

## 3. 需求三：可选的底层调度模型

### 3.1 这是"可选"的 —— 架构必须支持两种模式

```
模式 A：单模型（默认，零配置）
  所有任务 → 同一个模型
  ✅ 用户零额外配置
  ✅ 无调度开销（省一次 API 调用）
  ✅ 行为可预测
  ⚠️ 要么浪费（简单任务用贵模型）要么吃力（复杂任务用便宜模型）

模式 B：调度模式（可选，用户显式开启）
  任务 → 调度模型评估难度 → 路由到对应档位模型
  ✅ 省钱（简单任务不烧贵模型的 token）
  ✅ 复杂任务有更好的结果
  ⚠️ 多一次 API 调用（调度本身的成本）
  ⚠️ 调度可能判断错
```

> **默认是模式 A。** 用户不配置任何东西也能用 —— 这符合"尽可能简化配置"。

### 3.2 调度的本质是一次分类，不是一次对话

⚠️ **这是本设计最关键的判断：调度模型不应该"思考"，只应该"分类"。**

| 做法 | 成本 | 延迟 | 可解释性 |
|---|---|---|---|
| ❌ 让调度模型输出推理过程再决定 | 高 | 慢 | 差 |
| ✅ **让调度模型只输出一个档位标签** | 极低 | ~200ms | **好（可记录可审计）** |

**做法**：要求 JSON 输出 + `max_tokens` 极小 + 低 temperature。

```
System: 你是任务路由器。只看任务描述，输出难度档位。
        不要解释，不要多余文字。
        LIGHT = 简单问答/查询/格式转换/单位换算
        STANDARD = 需要多步操作/需要判断/涉及2-5个App
        HEAVY = 复杂规划/长上下文/需要推理/涉及5个以上App
        只输出 JSON：{"tier":"LIGHT|STANDARD|HEAVY","reason":"不超过10字"}

User: <任务描述>

→ max_tokens: 64, temperature: 0, jsonMode: true
```

**成本核算**：假设 prompt 200 token + 输出 30 token，
用最便宜的模型（$0.14/M 输入）→ **单次调度约 $0.00004**。
相比让贵模型处理整个任务（可能 $0.01+），**省下的远大于调度成本**。

### 3.3 ⚠️ 调度会失败，必须有兜底

| 失败情形 | 兜底策略 |
|---|---|
| 调度模型不可用（Key 失效/网络） | **静默降级到单模型模式**，用默认模型 |
| 返回的不是合法 JSON | 按关键词启发式判断；再失败则用 STANDARD |
| 调度模型把任务判成 HEAVY 但用户没配 HEAVY | 用已配置的最高档 |
| 调度花了太长时间（>2s） | 超时 → 直接按 STANDARD 走 |

> **核心原则：调度是优化，不是依赖。调度挂了必须还能干活。**

### 3.4 调度者可以是任何档位

⚠️ 有个反直觉但重要的点：**调度者本身应该用便宜模型。**

调度只需要"分类"能力，不需要"推理"能力。用一个昂贵的推理模型做调度，
是纯粹的浪费。所以：

- `roles` 里带 `SCHEDULER` 的模型**通常是 LIGHT 档**
- 界面上的提示语要说清这点，否则用户会直觉地选最强的模型当调度者

```
选择调度模型
ⓘ 调度模型只负责"判断任务难易"，不做实际工作。
  所以便宜、快的模型最合适 —— 不需要给它配最强的。
```

### 3.5 手动干预的入口（用户不信任自动时的出路）

调度可能判断错。给用户两个手动开关：

| 入口 | 位置 | 作用 |
|---|---|---|
| **临时指定** | 悬浮球长按 → "这次用 XX 模型" | 只影响当前任务 |
| **永久覆盖** | 模型配置页 → 设为默认 | 影响所有任务 |

⚠️ 手动指定后**必须显示出来**（悬浮球上换个颜色/角标），
否则用户会忘记自己覆盖过，然后困惑"为什么它一直用这个模型"。

## 4. 需求四：单模型模式（默认，可选项）

### 4.1 实现的极简性

单模型模式**不需要任何额外代码** —— 它就是"调度层不启用"：

```kotlin
sealed interface RoutingMode {
    /** 单模型：所有任务走 defaultModelId */
    data class Single(val modelConfigId: String) : RoutingMode

    /** 调度：按难度派发 */
    data class Scheduled(
        val schedulerModelConfigId: String,
        val light: String,      // 各档位对应的 modelConfig.id
        val standard: String,
        val heavy: String,
    ) : RoutingMode
}
```

**用户视角的配置流程**：

```
模型配置页
├── 只配了一个模型 → 界面**完全不显示**调度相关选项
└── 配了两个以上 → 出现一个开关：
    [ ] 按任务难度自动选择模型（可选）
        开启后可指定一个"调度模型"
```

> **零配置路径必须真的零配置。** 只配一个模型的用户，
> 永远不该看到"调度"这个词 —— 那是给他们增加认知负担。

### 4.2 缺档位的处理

用户配了 2 个模型但都不是 LIGHT 档 → 调度时怎么处理？

**不要静默用别的**，而要**在界面上提前说明**：

```
[!] 你没有配置「轻量」档模型。
    简单任务将使用「均衡」档的 claude-sonnet-4。
    想省钱的话，去添加一个便宜的模型。
```

## 5. 需求五：悬浮球交互（减少影响的核心）

### 5.1 为什么悬浮球是对的方向

P0-3 已否决虚拟屏 —— **"后台隔离、互不干扰"这条路走不通了**。
但悬浮球在"减少影响"这个目标上，反而有几个真实优势：

| 优势 | 说明 |
|---|---|
| **不抢焦点** | 用 `FLAG_NOT_FOCUSABLE`，用户能照常用下面的 App |
| **占用极小** | 一个半透明圆点，几十 px |
| **可随时收起** | 贴边隐藏，完全让出屏幕 |
| **是豁免凭据** | Android 15 收窄豁免后，可见 overlay 是后台启动服务的条件 |

### 5.2 悬浮球的三种状态（占用递增）

```
状态 0：极简圆点（默认）
  ▫ 直径 40dp 半透明
  ▫ 贴边可自动隐藏为一条细线
  ▫ 占用：几乎为零

状态 1：展开面板（用户点击时）
  ▫ 圆点上滑出一小块卡片
  ▫ 显示：当前任务 / 输入框 / 停止按钮
  ▫ 占用：约 1/4 屏，且**只在用户主动打开时**

状态 2：任务进行中
  ▫ 圆点变成进度环
  ▫ 不需要看屏幕的任务：仍只是圆点
  ▫ ⚠️ 刻意不做"展开显示 agent 在干什么" —— 那是干扰源
```

### 5.3 ⚠️ 一个反直觉的设计决策

**不要默认展示 agent 的执行过程。**

大多数"AI 助手"类产品喜欢把每一步都显示出来（"正在打开微信..."
"正在点击..."），看起来透明，实际是**持续吸引用户注意力**。

本项目的选择：

```
任务执行中 → 圆点显示进度环（一个不动的视觉元素）
           → 不显示具体步骤
           → 用户可以点开看（主动行为）
           → 用户不点，就不知道细节，也不需要知道
```

**理由**：用户交办任务后应该能去干自己的事。
不断刷新的步骤日志会让用户忍不住盯着看 —— 这本身就是干扰。

### 5.4 权限与限制

| 项 | 说明 |
|---|---|
| `SYSTEM_ALERT_WINDOW` | 必需，已在 v2.0 权限清单第 4 项 |
| Android 15 豁免 | **悬浮窗必须可见**才能从后台启动前台服务（见前份方案 §3.1） |
| 贴边隐藏的风险 | ⚠️ 隐藏后是否仍算"可见 overlay" → **需 EX-20 验证** |

**结论**：贴边隐藏可以让圆点变成极细的一条线（视觉上近乎消失），
但**不能完全移出屏幕** —— 那可能丢掉后台启动服务的资格。

### 5.5 与"任务执行"的关系

⚠️ 关键：**悬浮球本身不执行任务。**

```
悬浮球（OverlayService）—— 只负责显示与交互
    ↓ 用户下达任务
:agent 进程 —— 执行任务（独立进程，崩溃不影响 UI）
    ↓ 需要模型
LlmGateway —— 按 RoutingMode 选择模型
```

悬浮球**永远不做重活**。它是 UI，不是执行器。
这样即使 agent 跑飞了，圆点仍然响应"停止" —— 因为它和执行器不在一个进程。

> **这是"急停开关必须在另一个进程"的具体落地。**

## 6. 量化目标：减少影响的硬指标

既然"减少影响"是最高优先级，就必须有可测的数字，否则是空话。

| 指标 | 目标 | 怎么测 |
|---|---|---|
| **空闲时 CPU** | ≤ 0.5% | `dumpsys cpuinfo` |
| **空闲时内存增量** | ≤ 15 MB（悬浮球 + 服务） | P0-4 的 PSS 差值 |
| **空闲时电量** | ≤ 0.3% / 小时 | 电池统计 |
| **任务中屏幕占用** | 状态 0/1 时 ≈ 0 | 人为评估 |
| **急停响应** | ≤ 500ms | 人为评估 |
| **调度额外延迟** | ≤ 800ms | 计时 |
| **单次调度成本** | ≤ $0.0001 | 按 token 计算 |

⚠️ **注意 P0-5 的教训**：能耗读数的 ±1% 量化误差意味着
**测不了"单次任务"的耗电**，只能测长时间基线。上表的电量指标要按小时测。


**实现中发现并修正的两个真实缺陷**（都已由测试钉住）：

1. **推理词权重过低** —— 初版权重 1，"帮我分析一下这几个数据"只得 1 分被判 LIGHT。
   而"分析"恰恰最需要强模型。权重提到 2。
2. **单个连接词不足以升档** —— "先打开微信，然后发消息"这种明确两步任务被judged轻量。
   连接词权重从 1 提到 2。

> 两处都是**"判低"**方向的缺陷 —— 正是文档里说要避免的：
> 判低导致任务失败重试，比多花钱严重。

### 8.2 `RoutingOutcome` 而不是 Kotlin 的 `Result<T>`

⚠️ 这是个刻意的设计选择，值得记下：

Kotlin 的 `Result<T>` 要求失败侧是 `Throwable`。而"用户还没配 Key"、
"模型被禁用了"**不是异常，是正常业务状态**。

如果硬塞进 `Result`，就得到处写 `RuntimeException("no models")`，
然后调用方被迫用 `try/catch` 处理本来就该用 `when` 处理的流程 ——
**类型系统在诱导写错的代码**。所以自定义了 `RoutingOutcome`。

### 8.3 离线验证的关键价值

`modelrouter` 加进了 `run_logic_tests.py` 的 `MODULES`，
**在没有手机的机器上 0.4 秒跑完 344 个测试**。

路由选错模型的表现是：
- 不会崩
- 不会抛异常
- 只会"静默地走了贵的那个"或"任务办砸"

**这类 bug 读代码发现不了。** 已用"故意注入故障"验证过测试效力：
把降级方向从"优先升档"改成"优先降档"，测试立刻报
`expected:<strong> but was:<cheap>` —— 精确指出本该用强模型却用了便宜的。

### 8.4 `modelrouter` 必须零 Android 依赖

这是本项目最贵的一课（`:agent` 缺依赖藏了很久）：

> **离线单测跑绿 ≠ 代码能编译。**

**能放进这个模块的**：难度评估、档位选择、降级链、预算计算、失败兜底
**不能放的**：任何网络调用、任何 Context 依赖、任何 Key 访问

## 10. 一句话总结

三件事：

1. **基础设施已有一半** —— 多 Key 存储、加密、校验都现成，主要工作在新增模型配置与调度层
2. **调度是可选优化，不是依赖** —— 默认单模型零配置，调度挂了必须还能干活
3. **减少影响靠"克制"而非"技术"** —— 不展示执行过程、悬浮球不做重活、
   圆点贴边不抢焦点。**最好的交互是用户不需要看它**
