1.3 关键提醒：UAC 提权

本机账号虽在 Administrators 组，但 shell 拿到的是 UAC 降权令牌。Android Studio 安装程序属于 GUI 提权安装，必须由用户手动放行 UAC 弹窗，脚本直接拉起会静默退出。所以第 2 章的安装步骤是给用户执行的清单，不是自动化脚本。

2. 环境准备清单

2.1 第 1 步：安装 Android Studio（用户手动，约 20 分钟）

  1. 下载 Android Studio 最新稳定版（约 1.5 GB）
  2. 安装时放行 UAC 弹窗
  3. 安装类型选 Custom，组件勾选： - Android SDK - Android SDK Platform（API 36，满足 Google Play 的 targetSdk 要求） - Android SDK Build-Tools - Android SDK Platform-Tools（含 adb） - Android Emulator - Android SDK Command-line Tools
  4. SDK 路径建议改为非 C 盘（C 盘空间紧张）： D:\Android\Sdk 或 E:\Android\Sdk
  5. 安装完成后，在 Settings → Languages & Frameworks → Android SDK 中确认： - SDK Platforms 勾选 Android 12 (API 31) 与 Android 16/17 (API 36+) - SDK Tools 勾选 Android SDK Command-line Tools、Platform-Tools

JDK 说明：不要用系统的 JDK 25。Studio 自带 JetBrains Runtime（JBR 21），构建时会自动使用。 如需命令行构建，配置 JAVA_HOME 指向 Studio 的 jbr 目录。

2.4 第 4 步：本地模型联调环境（可选，但强烈建议）

本机已有 Ollama 与 qwen3.8:27b，这是零成本的联调环境，M0 阶段所有 Provider 测试都先用它：

# 验证 OpenAI 兼容端点（Ollama 原生支持）

⚠️ 注意：Ollama 默认只监听 127.0.0.1，手机访问不到。需设置环境变量 OLLAMA_HOST=0.0.0.0 后重启。另外 Android 9+ 默认禁止明文 HTTP， 需在 network_security_config.xml 中为局域网 IP 段放行（工程骨架已预留该文件）。

⚠️ qwen3.8:27b 是纯文本模型，不支持视觉。M0 的截图理解实验需要另装多模态模型 （如 qwen3-vl 或 gemma4 系列），或直接用云端多模态 Provider。

3.2 已定义的核心接口（可直接开工实现）

文件 内容 为什么先定这个
LlmProvider.kt Provider 抽象、ProviderCredential（ByteArray 承载）、Capability 枚举、统一异常 上层业务不得感知厂商差异；Key 的载体形式决定了整个安全模型

ActionExecutor.kt 四通道抽象、UiAction、ElementRef、HumanizePolicy 最重要的抗风险设计，禁止任何模块直接依赖 AccessibilityService
SafetyGuard.kt 敏感页面规则库、AutomationPolicyRegistry（SAEP 兼容）、拦截审计 合规底线，规则只允许加严
AgentOrchestrator.kt 双脑架构、AgentEvent 事件流、Grounder/Verifier、TaskStateMachine 执行过程必须对用户可见
CryptoManager.kt Keystore + AES-GCM、withDecryptedKey 强制清零作用域 安全红线，接口设计错了后期改不动
LogSanitizer.kt Key/PII 正则脱敏、base64 图片过滤、请求头脱敏 日志是最容易泄漏 Key 的地方

4. M0 验证实验

12 个实验，每个都回答一个会影响架构决策的问题。 不是"跑个 demo 看看"，而是"验证假设，否则改设计"。

EX-01 无障碍树读取覆盖率

项 内容
假设 无障碍树能覆盖主流 App 80% 以上的可交互元素
方法 在 10 个 App 的典型页面（首页/列表页/详情页/设置页）采集节点树，统计：可交互元素数、有文本或 desc 的比例、有 viewIdResourceName 的比例
样本 微信、支付宝、美团、淘宝、高德地图、B站、小红书、抖音、系统设置、Chrome
通过标准 平均可交互元素识别率 ≥ 80%；有 viewIdResourceName 的比例 ≥ 60%
失败预案 若覆盖率 < 60%，说明必须把截图兜底作为主路径而非备选，感知层成本模型要重算
产出 《无障碍覆盖率报告》（按 App × 页面类型矩阵）

关键代码要点：

// 采集时必须设置超时，复杂界面遍历可能耗时数百毫秒
val root = rootInActiveWindow ?: return null
val collected = withTimeoutOrNull(300) {
    traverse(root, depth = 0)
}
// 原生节点必须 recycle，否则会阻塞 GC
root.recycle()

EX-02 无障碍手势执行可靠性

项 内容
假设 dispatchGesture 的点击成功率 ≥ 95%
方法 在 5 个 App 上各执行 100 次点击（元素中心点击），统计成功率与耗时分布
通过标准 成功率 ≥ 95%，单次耗时 P95 ≤ 300ms
失败预案 若成功率偏低，需引入「点击后校验 + 自动重试」机制，或改用 ACTION_CLICK（节点直接点击，比手势更可靠但兼容性差）
产出 成功率与延迟分布数据

EX-03 Android 17 高级保护模式限制实测 ★关键

项 内容
假设 APM 模式下非无障碍类应用确实无法获取/保留无障碍权限
方法 在 Android 17 设备/模拟器上：① 开启 APM ② 尝试授权本 App 的无障碍权限 ③ 观察入口是否可用 ④ 已授权状态下开启 APM，观察权限是否被撤销 ⑤ 尝试用 ADB 绕过
通过标准 明确得出「APM 下可行/不可行」的确定结论，并记录系统版本号与复现步骤
失败预案 这不是"失败"，是情报收集。无论结果如何都要输出结论，因为结论直接决定 Shizuku 通道的优先级
产出 《Android 17 APM 限制实测报告》

⚠️ 这个实验的信息价值最高。如果 APM 下确实完全不可用，Shizuku 通道必须从 M1 提到 M0。

EX-04 MediaProjection 截图链路

项 内容
假设 截图链路可用，且 Android 14+ 的每次会话确认流程可接受
方法 实现前台服务 + MediaProjection 会话，验证：① 首次授权流程 ② 会话建立耗时 ③ 连续截图的稳定性 ④ 会话被系统终止后的恢复 ⑤ 能否实现"仅截当前 App"模式
通过标准 会话建立 ≤ 1s；连续截图 100 次无崩溃；会话终止后能自动恢复
失败预案 若授权流程过于割裂，需设计"一次授权、长期复用"的引导话术，并优先依赖无障碍树避免频繁截图
产出 截图模块可复用代码 + 授权流程 UX 记录

EX-05 Shizuku 通道可用性 ★关键

项 内容
假设 Shizuku 可提供 input tap、am start、screencap 等能力，且授权流程对用户可接受
方法 ① 引导用户安装 Shizuku App ② 通过无线调试激活 ③ 验证 shell 命令执行 ④ 测量重启后重新授权的流程成本 ⑤ 验证 am start 直达目标 Activity 的能力
通过标准 核心命令全部可执行；重启后重新授权步骤 ≤ 3 步；input tap 成功率 ≥ 95%
失败预案 若 Shizuku 门槛过高，产品需提供分级的权限方案：普通用户用无障碍，高级用户用 Shizuku
产出 Shizuku 通道可复用代码 + 用户授权引导流程

EX-06 截图成本基线

项 内容
假设 经过裁剪与压缩，单次截图理解的 token 成本可控制在可接受范围
方法 对同一张 1440p 截图做 5 种处理（原图 / 缩放到 1280 / 缩放到 960 / WebP q75 / 只截变化区域），分别送多模态模型，记录 token 数与识别准确率
通过标准 找到「成本 ≤ 原始 40% 且元素定位准确率不下降超过 5%」的参数组合
失败预案 若压缩后准确率掉太多，说明必须优先用无障碍树，截图仅作兜底
产出 截图处理参数标准（写入 CaptureOptions 默认值）

EX-07 端侧小模型推理性能

项 内容
假设 2B 级多模态模型可在目标机型上做到 ≤ 1.5s/次 的元素定位
方法 用 MediaPipe LLM Inference 或 LiteRT-LM 加载模型，测量：冷启动加载时间、单次推理延迟、内存占用、连续推理的发热与掉帧
通过标准 单次定位 ≤ 1.5s；峰值内存 ≤ 1.5 GB；连续 20 次推理不触发降频
失败预案 若端侧跑不动，则 Grounder 降级为「用便宜的云端小模型」，端侧仅保留"本地模式"作为隐私选项（性能打折但可用）
产出 端侧推理可行性结论 + 推荐模型与参数

EX-08 Provider 流式对话打通

项 内容
假设 OpenAI 兼容协议可覆盖 8 家以上厂商，SSE 解析无坑
方法 用本机 Ollama（零成本）先打通链路，再依次接入 DeepSeek / 通义 / 火山方舟 / OpenRouter；重点验证 SSE 的多行 data、[DONE]、中途断流、429 重试
通过标准 5 家 Provider 全部流式可用；断流能正确抛出异常；429 能指数退避重试
失败预案 若某家协议差异过大，说明自定义 Provider 逃生舱的必要性，需优先实现
产出 provider-openai-compat 可用实现

EX-09 Key 加密与日志脱敏审计 ★关键

项 内容
假设 全链路无明文 Key 落盘
方法 ① 导入一个 Key ② 触发各种操作（对话、失败、崩溃） ③ 用 adb shell 导出应用数据目录 ④ 全盘 grep Key 明文 ⑤ 检查 logcat 全量输出 ⑥ 检查 SharedPreferences / Room 数据库文件 ⑦ 检查崩溃上报内容
通过标准 任何位置都搜不到 Key 明文（含前缀后 8 位）
失败预案 有泄漏则立即修复并重测；这是不可妥协的项，不通过则 M0 不通过
产出 《Key 安全审计报告》

审计脚本思路：

# 导出应用数据（需 root 或 debuggable 包）
adb shell run-as com.pocketagent.debug tar -c -f - . | tar -x -C ./dump
# 全盘搜索 Key 明文片段
grep -r "<key 的后 8 位>" ./dump
# 搜索 logcat 历史
adb logcat -d | grep -i "sk-\|api.key\|bearer"

EX-10 敏感页面识别准确率 ★关键

项 内容
假设 关键词 + 包名 + 控件特征的三重规则能 100% 拦住支付类页面
方法 构造 30 个测试页面（含 15 个真实敏感页：支付宝付款码、微信转账、银行 App 首页、验证码页等，以及 15 个非敏感页作为对照），统计误报率与漏报率
通过标准 漏报率 = 0（宁可误报不可漏报）；误报率 ≤ 10%
失败预案 若漏报，立即扩充关键词库与包名黑名单，并考虑加入页面结构特征识别
产出 敏感页面规则库 v1 + 测试用例集

⚠️ 这是唯一一个"漏报率必须为 0"的指标。 误报用户只是烦，漏报用户可能损失钱。

EX-11 UI 图谱缓存命中率验证

项 内容
假设 同一 App 的常用页面重复出现时，页面特征哈希能稳定命中缓存，命中率 ≥ 40%
方法 用 EX-01 采集的节点树，计算页面特征哈希（可用元素数 + 关键元素文本 + 层级结构的组合哈希），统计同页面多次访问的哈希稳定性
通过标准 同页面哈希一致率 ≥ 90%；预估缓存命中率 ≥ 40%
失败预案 若哈希不稳定（动态内容多），改用「部分特征匹配」或降低哈希粒度（只看顶部区域）
产出 页面指纹算法 + 缓存策略设计

这个实验决定 M2 的降本目标（缓存命中 40% → 成本降 50%）是否成立。M0 就要探。

EX-12 悬浮窗与前台服务保活（国产 ROM 差异）

项 内容
假设 悬浮窗在主流 ROM 上可常驻，前台服务不会被激进杀后台
方法 在小米/华为/OPPO/vivo/三星/Pixel 上测试：① 悬浮窗权限申请流程 ② 应用切后台后悬浮窗是否存活 ③ 锁屏 30 分钟后是否被杀 ④ 需要哪些额外的"自启动/后台运行"白名单设置
通过标准 形成各 ROM 的权限配置矩阵；悬浮窗存活率 ≥ 90%
失败预案 若保活困难，需在引导流程中加入「按机型定制的设置向导」，并提供诊断页帮用户自查
产出 《机型适配矩阵》（方案 R8 风险的应对）

5. 权限引导 UX 详设

这个产品的转化率完全取决于权限引导。用户面对的是"读屏 + 操作屏幕 + 截图"三连，任何一屏讲不清楚都会流失。

5.1 设计原则

  1. 一次只要一个权限，不要在首屏堆一堆申请按钮
  2. 每屏都回答"为什么"，并且用具体场景而非技术术语（不说"无障碍服务"，说"让我能看见屏幕上的按钮"）
  3. 允许跳过，但明确告知跳过后的能力损失（进入"降级模式"）
  4. 可随时回来，设置页有常驻的权限状态面板与诊断工具
  5. 诚实，不隐瞒数据流向

5.2 逐屏流程

S1 欢迎页
   标题：让我帮你操作手机
   正文：我会看见你屏幕上的内容，替你完成跨应用的操作。
        你可以随时叫停我，也随时能看我在做什么。
   [开始设置]  [先看看再说]
       ↓
S2 选择模式
   ○ 完整体验（需要 3 项权限）
   ● 精简模式（只需 1 项权限，我能看屏幕但不能替你操作）
   —— 用一句话说明差异，让用户有"低门槛入口"
       ↓
S3 悬浮窗权限
   为什么需要：让我在你打开任何 App 时都能被叫出来
   [去授权]  [跳过]
       ↓
S4 无障碍权限  ★最关键的一屏
   为什么需要：让我能看见屏幕上的按钮和文字，并替你点击
   我需要能做什么：
     · 读取屏幕上的文字和按钮位置
     · 点击、滑动、输入
   我不会做什么：
     · 不读取你的输入密码（技术上已排除）
     · 不在支付页面做任何操作
     · 不上传截图，除非你同意
   [去授权]  [改用 Shizuku（进阶）]  [跳过]
       ↓
S5 截图权限
   为什么需要：当无障碍信息不够时，我需要看一眼屏幕
   说明：每次截图都会在通知栏显示，你随时能停
   [去授权]
       ↓
S6 导入 API Key
   标题：接入你的 AI 大脑
   正文：本应用不提供 AI 模型，你用自己的 API Key 调用任意模型。
        好处：数据不经我们服务器，模型随时可换，费用你自己掌控。
   [推荐：OpenRouter（一个 Key 通吃）]
   [手动粘贴 Key]
       ↓
S7 首次任务引导
   建议开启「每步都问我」模式
   文案：第一次用，我会每做一步都问过你。熟悉之后可以关掉。
       ↓
S8 诊断页（设置页常驻）
   ┌ 悬浮窗        ✅ 已授权
   ├ 无障碍服务    ✅ 运行中
   ├ 截图能力      ⚠️ 会话已过期，点击重新授权
   ├ Shizuku       ❌ 未安装（可选，装了之后即使无障碍被系统禁用我仍能工作）
   ├ API Key       ✅ DeepSeek · 有效 · 今日 $0.12
   └ [运行自检]

5.3 关键文案约束

禁止的写法 应该的写法
"请开启无障碍服务以启用核心功能" "让我能看见屏幕上的按钮，这样我才能替你点击"
"本应用需要 SYSTEM_ALERT_WINDOW 权限" "让我能随时被你叫出来"
"请求失败" "Key 已过期，请到 DeepSeek 控制台重新生成"
"操作失败" "我没找到'搜索框'，可能页面还没加载完。要我再试一次吗？"
"该应用不支持自动化" "美团声明了不希望被自动操作。我可以把步骤列出来，你手动点会更快。"

6. 性能预算分解

预算是设计约束，不是事后测量。任何模块超标都要在评审中说明。

6.1 延迟预算（单步操作端到端）

环节 预算 说明
屏幕采集（无障碍树） ≤ 150 ms 含遍历与归一化，超时上限 300ms
屏幕采集（截图） ≤ 400 ms 含 MediaProjection 取帧 + 缩放 + 压缩
Grounder 定位（缓存命中） ≤ 10 ms 纯本地查表，这是缓存的价值所在
Grounder 定位（端侧模型） ≤ 1500 ms
Grounder 定位（云端模型） ≤ 2500 ms 含网络往返
Orchestrator 规划（每步） ≤ 3000 ms 强模型，可接受较慢
动作执行 ≤ 300 ms P95
Verifier 校验（规则层） ≤ 50 ms 必须优先走规则层
Verifier 校验（模型层） ≤ 1500 ms 仅在规则层无法判断时
单步端到端（缓存命中） ≤ 800 ms 目标
单步端到端（无缓存） ≤ 4000 ms 目标

关键：用户感知的是"整个任务要多久"。5 步任务在缓存命中情况下应 ≤ 8s，无缓存 ≤ 25s。

6.2 内存预算

项 预算 说明
应用常驻（无任务） ≤ 120 MB 悬浮窗 + 前台服务
任务执行峰值 ≤ 400 MB 含截图 Bitmap
单张截图 Bitmap ≤ 12 MB 1440p ARGB_8888 ≈ 14.7MB，必须用 RGB_565 或缩放
端侧模型加载 ≤ 1.5 GB 仅在启用本地模式时
数据库 ≤ 50 MB 不含对话附件

红线：截图 Bitmap 必须在 ScreenSnapshot.dispose() 中 recycle，任务结束前不得同时持有超过 2 张。

6.3 耗电预算

场景 预算 说明
后台待机（悬浮窗常驻） ≤ 3% / 天 无障碍事件节流到 100ms 是关键
连续执行任务 ≤ 8% / 小时
屏幕采集空闲时 0 不采集时不得有任何轮询，必须由事件驱动

6.4 成本预算（用户 token 支出）

以 DeepSeek + 一个多模态模型为例，单次 5 步任务：

环节 调用次数 单次 token 小计
Orchestrator 规划 1 + 重规划 ~2000 in / 300 out ~2300
Grounder（缓存命中） 0 0 0
Grounder（云端） 3 ~1500 in / 50 out ~4650
截图理解 2 ~1200 in（压缩后） ~2400
Verifier（规则层） 0 0 0
合计 ~9350 token

成本优化目标（M2）：通过 UI 图谱缓存 + 规则层校验 + 截图裁剪，把单任务 token 从 ~9350 降到 ≤ 4500（降幅 ≥ 50%）。

熔断规则：用户可设每日预算。达到 80% 时提示，100% 时停止调用云端模型并提示切换本地模型。

7.2 快照回放机制（强烈建议）

把真实设备的 ScreenSnapshot 序列化保存为 fixture，测试时回放：

// 生产环境：录制
if (BuildConfig.RECORD_SNAPSHOTS) {
    SnapshotRecorder.save(taskId, snapshot)
}

// 测试环境：回放
val snapshots = SnapshotFixtures.load("wechat_search_flow")
val orchestrator = AgentOrchestrator(perception = ReplayPerceptionManager(snapshots))

价值：无真机也能回归决策逻辑；模型换版本后能对比行为差异；新成员能快速理解真实数据长什么样。

⚠️ Fixture 中含真实屏幕内容，不得提交到代码仓库。用 .gitignore 排除，或做文本脱敏后提交。

8. 开发规范与协作流程

8.1 分支模型

main            ← 可发布状态，受保护，禁止直接推送
 └── develop    ← 集成分支
      ├── feature/<模块>-<简述>     如 feature/action-shizuku-executor
      ├── fix/<简述>               如 fix/log-sanitizer-uuid-false-positive
      └── refactor/<简述>
 └── release/<版本>                发布准备
 └── hotfix/<简述>                 紧急修复

8.2 提交信息（Conventional Commits）

<type>(<scope>): <描述>

type:  feat | fix | refactor | perf | test | docs | build | ci | chore | security
scope: 模块名，如 action / perception / provider-openai / crypto

示例：

feat(action): 实现 Shizuku 通道的 input tap 与 am start
security(crypto): Key 使用后强制清零，修复异常路径泄漏
perf(perception): 无障碍树遍历加 300ms 超时，避免复杂界面卡顿

security 类型的提交必须由技术负责人 review。

8.3 代码风格

  • ktlint + detekt，提交前自动执行
  • 命名：类用 PascalCase，函数/属性用 camelCase，常量用 SCREAMING_SNAKE_CASE
  • 禁止 !!（除非有明确注释说明为何不可能为 null）
  • 禁止 在协程中吞异常（catch (e: Exception) {}）
  • 公开 API 必须有 KDoc，说明为什么而不只是是什么
  • 单个文件不超过 500 行，超出则拆分

8.4 PR 检查项（Reviewer 必查）

检查项 说明
是否有明文 Key 落盘/落日志 最高优先级，见即打回
是否绕过 LogSanitizer 直接打日志 打回
是否直接依赖 AccessibilityService 而非 ActionExecutor 抽象 打回
是否新增了未被 SafetyGuard 覆盖的动作路径 打回
截图 Bitmap 是否有明确的 recycle 路径 打回
是否引入了新的敏感权限 需技术负责人批准
单元测试覆盖 核心逻辑覆盖率 ≥ 70%

10.2 出现以下情况则 No-Go（需重新设计）

信号 含义 应对
无障碍与 Shizuku 都不可用 无法代操作，产品形态不成立 转为「屏幕分析 + 步骤引导」形态，重新评估产品定位

Key 无法做到无泄漏 安全底线失守 停止开发，重做安全设计
