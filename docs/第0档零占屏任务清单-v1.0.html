第 0 档零占屏任务清单 v1.0

2026-09-23 · 全部命令均在真机 K60（mondrian / Android 15 / API 35 / HyperOS OS3.0.8.0.VMNCNXM） 上实测取得，标注 ✅ 的表示现场验证过，标注 ⚠️ 的表示仅推断、待实测。

0. 为什么要有这份清单

前面几轮已经依次否掉三条路：

方向 结论 死因
虚拟屏 ❌ 已否决 P0-3：isCallerAllowedToLaunchOnDisplay() 架构封死，第三方无法把别人的 App 启到非默认屏
freeform 小窗 ❌ 本机不可用 无 freeform_window_management feature + setprop 被 SELinux 拒 + --windowingMode 5 静默降级
系统分身 ❌ 已否决 全机只有一块 INTERNAL display，分身与主空间是切换式关系

⇒ 「不占屏地操作别人的 App」这条路，第三方应用走不通。

第 0 档换一个问法：不操作界面，能不能把事办了？

答案是可以，而且能办的事比预想的多 —— 前提是目标 App 提供了无界面的入口。

1. 定义与判据

第 0 档 = 任务执行全程，屏幕上不出现任何「因 agent 而起」的界面变化。

三条判据（必须全满足）：

  1. 不调用 startActivity
  2. 不读无障碍节点树、不截图
  3. 不注入触摸/按键事件（媒体键除外 —— 它不改变画面）

1.1 一个必要的细分

档位 含义 例子
第 0 档（严格） 全程零界面变化 「把 Wi-Fi 关了」「给张三发条短信」
第 0 档+（终点跳转） 全程零界面变化，只在最后跳一次到结果页 「打开淘宝的订单页」

⚠️ 关键区分：

  • 「agent 为了自己操作而把界面拉起来」→ 占屏
  • 「任务的结果本身就是给用户看的页面」→ 不算占屏

这条区分决定了 startActivity 不是绝对禁止 —— 但它只能出现在终点，且只能出现一次。 一旦出现第二次（翻页、返回、重进），任务就掉出第 0 档。

2.1 T0-A 的实测细节（重要）

WRITE_SECURE_SETTINGS 是本清单里唯一能让 App 直接写系统设置的路径。实测结论：

# ① 该权限本身是可变更的 —— 对照组能反证
$ pm grant <pkg> android.permission.WRITE_SECURE_SETTINGS        # → 无异常
$ pm grant <pkg> android.permission.BIND_NOTIFICATION_LISTENER_SERVICE
  SecurityException: ... is not a changeable permission type      # ← 纯 signature 的报这个

# ② 但「没在 manifest 里声明」时，pm grant 是【静默无效】的
$ pm grant <pkg> android.permission.WRITE_SECURE_SETTINGS        # → 不报错
$ dumpsys package <pkg> | grep WRITE_SECURE_SETTINGS             # → 空，没生效

⇒ 正确流程：先在 AndroidManifest.xml 里声明，再由用户 adb shell pm grant 授予。 跳过声明那一步不会报错，只会安静地不生效 —— 属于本项目反复踩的那类 bug。

✅ 已实测通过（2026-09-23，K60 / Android 15）：声明放进 :capability 的 manifest、 构建安装后：

$ dumpsys package com.pocketagent.debug | sed -n '/requested permissions:/,/install permissions:/p'
      android.permission.WRITE_SETTINGS
      android.permission.WRITE_SECURE_SETTINGS                    # ← 声明进了 APK
$ pm grant com.pocketagent.debug android.permission.WRITE_SECURE_SETTINGS   # → 退出码 0
$ dumpsys package com.pocketagent.debug | grep "WRITE_SECURE_SETTINGS:"
      android.permission.WRITE_SECURE_SETTINGS: granted=true      # ← 真的生效了

⚠️ 但声明要进 APK，:app 必须真的依赖 :capability —— manifest 合并只在 有人依赖那个模块时才生效。少那一行的话模块代码照样编译通过、权限却不在 APK 里， pm grant 静默无效。又一次"不报错、只是安静地少做一件事"。

★★ 三个命名空间用的是两类权限（真机 dumpsys package android 实测）

命名空间 权限 保护级别（原样） pm grant
GLOBAL / SECURE WRITE_SECURE_SETTINGS signature\|privileged\|development\|installer\|role ✅ 能授
SYSTEM WRITE_SETTINGS signature\|appop\|pre23\|preinstalled\|role ❌ 报错

差别就在那一位上：development 位让 pm grant 生效；appop 型的不走包管理器。

WRITE_SETTINGS 的三条实测（声明进 manifest 之后）：

  • pm grant … WRITE_SETTINGS → SecurityException: Permission … is managed by role，退出码 255
  • cmd appops get <pkg> WRITE_SETTINGS → 声明前 No operations / Default mode: default，声明后 ignore
  • cmd appops set <pkg> WRITE_SETTINGS allow → 复查为 allow ✅ 可行

⚠️ 把两者混成一个"没有写设置权限"，用户拿到的指引会有一半是错的 —— 而错的指引比没有指引更坏：他会照着 pm grant 做一遍、撞上一个 is managed by role 的报错（那句话里没有一个字提到"你该改用 appops"）， 然后认定"这个功能坏了"。

⇒ 两条指引已固化在 SettingsPermissionPolicy.guidanceFor()，逐字命令有测试钉住。

2.2 T0-B 的边界

Shizuku 给的是 uid 2000（shell），不是 root。它能做 cmd/pm/settings/svc/am， 不能改 SELinux 策略、不能 setprop 受限属性（P0-3 里 enable_freeform_support 就是被这条挡住的）。

⚠️⚠️ Shizuku#newProcess 已经不存在了（2026-09-23 核实）

对 dev.rikka.shizuku:api:13.1.5 的 classes.jar 直接 javap：

  • rikka.shizuku.Shizuku 里没有 newProcess。它只有 pingBinder / checkSelfPermission / requestPermission / getBinder / bindUserService / unbindUserService / transactRemote 等
  • rikka.shizuku.ShizukuRemoteProcess 还在，但构造器收的是 moe.shizuku.server.IRemoteProcess，而且是包内可见的 —— 外部构造不了
  • 官方 Changelog 13.1.1：「Prepare to remove Shizuku#newProcess, developers should have to use UserService instead」

⇒ T0-B 的实现路径是 UserService：应用自带一个 .aidl 接口 + 一个 service 类， 由 Shizuku 在 shell/root 身份的进程里拉起，应用再通过 bindUserService 拿它的 binder。 代价是要开 AIDL 代码生成（buildFeatures { aidl = true }）。

⚠️ 为什么要把这段写下来：社区里仍在流传 Shizuku.newProcess 的写法，而它们 看起来能跑。实测过的一个开源终端 App 就是用反射去调它 —— 反射失败后回落到无权限的 Runtime.exec，界面上照常显示「Shizuku 模式」， 命令却一点特权都没有；而它的 README 还写着"可访问 /data、pm grant、dumpsys"。 ⇒ 那正是本项目最忌讳的形态：不报错、不崩溃，只是安静地少做一件事。

⚠️ 因此 :capability 刻意不依赖 shizuku —— 设置通道走 Settings.* 的 API， 不需要 shell 身份。这是第 0 档能在 Shizuku 服务没跑起来时仍然可用的原因。

7. 与既有架构的衔接

  • 感知阶梯的第 0 档就是本清单：不感知 → 直接走能力通道，跳过树/截图
  • ✅ 纯逻辑层已实现：:capabilitylogic（纯 Kotlin、零 Android 依赖，见 §9.1）
  • Capability 声明 + CapabilityCatalog（15 条内置能力）+ CapabilityParams 参数校验
  • CapabilityGuard 七步裁决：目录 → 硬拒绝 → 来源 → 参数 → 规划 → 规划后硬校验 → 放行 → 确认
  • CommandPlanner 展开成 PlannedExecution；ShellArgv 用数组，注入在结构上不可能
  • CapabilityAuditLog 审计：只记包名与设置键，绝不记参数原值
  • ✅ 通道层也已就位（纯模块内）：SettingsAccess / ShellRunner 两个端口 + ChannelResult 结果模型 + CapabilityRunner 派发器 + CapabilityRuntime 编排
  • ⚠️ 端口声明在纯模块、实现在 Android 侧，与 filelogic 的 FileChannel 同构 —— 好处是派发逻辑能离线钉死（argv 过边界、先读后写、端口缺失走哪个分支）
  • ⚠️ 编排层（CapabilityRuntime）也在纯模块里，而不是 Android 侧：它一行 Android 代码都没有，三个依赖全是本模块定义的纯对象。而「裁决 → 执行 → 记账」 的顺序恰恰最该被钉住 —— 单看每个组件都对，连错顺序也不会让任何一条 "正向测试"变红（记账提前 = 日志说执行了而实际没执行）
  • ⚠️ ShellRunner.run 收的是 List<String>。把它改成 String（或实现方自己 joinToString(" ") 再交给 shell）会让「注入在结构上不可能」这条论证整个作废 —— 而后果不会立刻显现，要等某条能力的某个参数恰好含 ; 才发作
  • ⚠️ 两种「不可用」必须分开：Unavailable（去配置：权限没给 / Shizuku 没跑 / 端口没接）与 Failed（试过了，没成）。混成一个 Boolean 之后界面上就只剩 「操作失败」一句 —— 而那句话对这两种情况都是错的指引
  • ⚠️ 设置写入先读原值再写。顺序反了不报错，只会让撤销把设置「恢复」成 它刚变成的那个样子（SAFE 的判据之一是「可逆」）
  • ⚠️ 连续同因的通道失败只记第一条（不同能力不合并 —— 它们的 targetDigest 不同）。 不合并的后果是 500 格环形缓冲被同一句话填满，而那份日志是用户判断 「这个插件想干什么」的唯一线索
  • ✅ Android 侧薄适配器已落地：:capability（2026-09-23，compileDebugKotlin 通过）
  • AndroidSettingsAccess：Settings.Global / System / Secure 的读写
    • ⚠️ 走 API 而不是 settings put 命令 —— 两者权限要求相同，但只有 API 路径 有返回值，能区分「权限被拒」与「写成功了」
    • ⚠️ 权限判据与界面必须同源（isGranted() 就是 write() 用的那一个）， 否则会出现"页面显示已授权、点下去却报没权限"，而用户无从判断该信哪一个
  • ⚠️ 权限声明放在 :capability 自己的 manifest 里（遵循「随功能落地逐项启用」）， 但 :app 必须真的依赖 :capability —— 见 §2.1
  • ⏳ shell 通道（T0-B）尚未实现：上游已移除 Shizuku#newProcess，正解是 UserService（要开 AIDL 代码生成）。不要照旧文档写 newProcess —— 见 §2.2
  • ⏳ 还差一个用户入口：PermissionsScreen 里还没有「写系统设置」这一项， 也没有任何界面能真的触发一条能力。⇒ 现在用户还用不了，只是底层通了
  • ⏳ ActionExecutor 需要新增一条 T0 通道：无手势、无节点树，只有 PlannedExecution
  • SafetyGuard 必须覆盖 T0 —— settings put / pm disable / cmd * 的破坏力不比点击小
  • ✅ 已按「能力白名单」落地（不是命令白名单）：能力必须先在目录里声明才能被调用
  • ✅ 危险项由 CapabilityDenyRules 固定拒绝，不参与任何覆盖逻辑： 10 类能力 id 前缀（setting.write.* / locksettings.* / credential.* / role.* / package.install / package.uninstall / package.grant / package.revoke / process.kill / debug.*）+ 28 条设置键 + 13 个系统包
  • ⚠️ 最重要的一条是 secure/enabled_accessibility_services：它可写 = agent 能 给自己授予无障碍权限（读全屏、点全屏、看得到支付页）， 而整个安全模型建立在"特殊权限只能由用户亲手授予"这个前提上
  • AgentBudget：T0 任务几乎不耗 token（多数是本地命令）→ 预算压力最小
  • ⚠️ T0 是唯一能「息屏 + 后台」执行的档位 → 与 PowerGovernor 天然契合， 也让「悬浮球只作待命信号」这个设计更有意义

  5. 拍照在 FGS(camera) 下无 UI 是否可行
  6. 省电模式 / 输入法切换的可写性 - 亮度（SYSTEM/screen_brightness）已由权限侧覆盖 —— 走的是 WRITE_SETTINGS appop 那条路，通路已通，剩下的只是值域与副作用
  7. Shizuku#newProcess 移除后，UserService 方案的实际代价 —— 要开 AIDL 代码生成 + 一个 service 类，且必须在 Shizuku 服务运行中才能验。 当前设备上 Shizuku 服务没在跑，所以 T0-B 暂时无法验证（见 §2.2）

9. 建议的落地顺序

  1. ✅ 纯逻辑层已完成 —— android/capabilitylogic：11 个源文件 + 7 个测试类、 离线测试 1250 条（全仓基线从 1116 起，每步都有变异验证兜底） ✅ 通道层 + 编排层也已就位（两者都在纯模块内）：SettingsAccess / ShellRunner 两个端口 + ChannelResult 结果模型 + CapabilityRunner（派发）+ CapabilityRuntime（裁决→执行→记账）+ SettingsPermissionPolicy（权限映射与指引）。 13 处故障注入全部命中（argv 被拼成字符串 / 先写后读 / 吞掉取消异常 / 端口缺失抛异常 / toString 泄露原值 / 顺手碰另一个端口 …） ✅ Android 侧薄适配器已落地 —— android/capability：AndroidSettingsAccess （Settings.Global / System / Secure 的读写，走 API 不走 settings put） + WRITE_SECURE_SETTINGS / WRITE_SETTINGS 两个声明。 :app 已依赖它（manifest 合并需要），compileDebugKotlin 与 assembleDebug 均通过， WRITE_SECURE_SETTINGS 在真机上 pm grant 实测 granted=true（见 §2.1） ⏳ 还剩两件事： - ① PermissionsScreen 里加「写系统设置」一项 + 一个能真的触发能力的入口。 没有它用户还用不了 —— 现在只是底层通了 - ② T0-B 的 shell 通道。上游已移除 Shizuku#newProcess，正解是 UserService （要开 AIDL 代码生成）；且当前设备 Shizuku 服务没在跑，暂时验不了（见 §2.2）

①做完即可解锁 §4.1 里走设置的那几条：深色模式 / 亮度 / 熄屏超时 / 自动旋转 / 充电保持亮屏。②做完才能解锁 cmd 那批（Wi-Fi / 飞行模式 / 勿扰 / 音量 / 停用 App / 媒体控制） 2. T0-E 的 TTS 播报 —— 解锁「语音回结果」，配合第 1 步形成「说一句 → 做完 → 说一句」的闭环 3. T0-C 的读通知 —— 解锁通知类任务 4. T0-D 的网络 + SAF —— 需 :gateway / :agent 先接线 5. T0-C 的 RemoteInput 回复 —— 收益最大但最不确定，放最后当实验做

第 1 步做完，「不占屏」这件事就从「不可能」变成「有一批任务真的能做到」—— 这是整个产品唯一一条不靠占屏也能立住的路。

9.1 落地时确立的硬约束（改动需评审）

约束 为什么
一条能力 = 一个具体动作；禁止 shell.exec(argv…) / setting.write(ns,key,val) 这类通用能力 通用能力一旦存在，风险分级 / 参数校验 / 确认流程都只是在给一个后门镶边
ShellArgv 必须是数组，实现方不得拼成字符串再交给 shell Shizuku.newProcess(String[]) → Runtime.exec(String[]) 不经过 shell，分号 / 竖线 / 反引号 / $() 全是普通字符
配方里不支持拼接（不许出现 --set={index} 这种半拼接 token） 拼接是注入的温床。代价是少数能力暂时进不来，这个取舍划算
设置键是配方字面量，不能由参数决定 否则一条能力就能写任意设置键，CapabilityDenyRules 的键白名单立刻失效
confirmedByUser 只在最后一步被消费 提前消费 = 把"用户点过确认"变成绕过一切的后门
规划后的产物要再校验一次 防"安全的能力 + 危险的参数"：app.set_enabled 本身正当，而 com.android.systemui 是格式合法的包名，参数校验拦不住
审计只记包名与设置键，绝不记参数原值 通知正文是用户内容；而"昨晚停用了哪个 App"是必须能回答的 —— 单条规则（只有像包名的值才记）让这个取舍不随能力数量漂移
CapabilityRisk 只有 SAFE / GUARDED 两级，不设 FORBIDDEN "永不放行"的东西要做成能力不存在，而不是"出现在目录里但标着禁止" —— 后者迟早会有人写一行 if (risk != FORBIDDEN) 放它过去
通道层必须区分 Unavailable 与 Failed 前者是「去配置」，后者是「试过了，没成」。而「用户放行这条能力」与「系统给了这个权限」是两套独立授权（前者在本体数据库、后者在系统包管理）—— 混起来用户就不知道该去点授权还是去跑 adb
端口签名 ShellRunner.run(List<String>) 不得改成 String 这是 argv 过边界的最后一道。后果不会立刻显现，要等某条能力的某个参数恰好含 ; 才发作
设置写入必须先读原值、再写 顺序反了不报错，只会让撤销把设置「恢复」成它刚变成的那个样子。SAFE 的判据之一是「可逆」，而不知道原值就改不回去
Succeeded.previousValue 不进审计日志，且 toString() 必须覆写隐去它 data class 自动生成的 toString() 会原样打出来 —— 一句 Log.d(TAG, result.toString()) 就把它写进日志。自动生成的东西没人会去审，所以它是最安全的泄漏路径
不要用 internal 构造器去「加固」PlannedExecution 试过，白费力气：data class 的 copy() 绕得过任何非公开构造器（编译器会警告 non-public primary constructor is exposed via the generated copy()）。更根本的是，可见性挡不住真正危险的那件事 ——「跳过裁决器直接调 runner」。⇒ 真正的边界是接口形状：runner 要的那个对象只能来自 Allowed.execution。可见性挡不住「绕过去」，只有「没有别的入口」才挡得住
GLOBAL/SECURE 与 SYSTEM 是两类授权，指引绝不能合并 WRITE_SECURE_SETTINGS 有 development 位（pm grant 能授）；WRITE_SETTINGS 是 appop 型（pm grant 报 is managed by role，只能 appops set … allow）。合并成一个"没有写设置权限"= 一半指引是错的，而错的指引比没有指引更坏：用户照做一遍、撞上一个看不懂的报错，然后认定功能坏了
权限声明所在模块必须被 :app 真正依赖 manifest 合并只在有人依赖时生效。少那一行的话模块代码照样编译通过、权限却不在 APK 里，pm grant 静默无效。声明写在哪不重要，"有没有人依赖它"才决定它进不进 APK
CapabilityRuntime（编排）留在纯模块，不下沉到 Android 侧 它一行 Android 代码都没有。而「裁决 → 执行 → 记账」的顺序必须能离线钉住 —— 记账提前的后果是"日志说执行了、实际没执行"，而它不会让任何正向测试变红
连续同因的通道失败只记第一条（不同能力不合并） 权限没配时每一次调用都产生一条 Unavailable，500 格环形缓冲会被同一句话填满。而那份日志是用户判断「这个插件想干什么」的唯一线索 —— 被填满的日志看起来和"什么都没发生"一样。不同能力即使原因相同也不合并：它们的 targetDigest 不同，而"想动哪个目标"正是那份日志的主要用途
界面的权限判据必须与执行判据同源 AndroidSettingsAccess.isGranted() 就是 write() 用的那一个。界面自己写一套会出现"页面显示已授权、点下去却报没权限"，而用户完全无从判断该信哪一个
T0-B 的实现路径是 Shizuku UserService，不是 newProcess Shizuku#newProcess 在 13.1.1 起已被移除（javap 核实 13.1.5 的 Shizuku 类里没有它）。照旧文档写 newProcess 会静默降级成无特权的 Runtime.exec —— 有开源项目就是这么做的，界面显示"Shizuku 模式"而命令一点特权都没有。不要照旧文档写实现
