沙箱优先架构与离线优先交付方案 v1.0

English | 简体中文

发布主体：「代码乌托邦」（GitHub jyh17147540525-alt） 立场：该账号下发布的一切内容永久免费，不设任何捐款渠道。 我们只负责开发，其余环节由用户自行配置 —— 目标是把配置流程尽可能简化。 约束：我们没有服务器，也不打算有。所有数据与功能只能跑在用户自己的机器上。

本文取代 后台常驻与语音交互方案-v1.0.md §7（插件病毒检测）的联网检测部分。

0. 架构转向：从"我们检测"到"我们隔离"

前一份方案试图给插件市场接入病毒检测，核实后发现 VirusTotal 这类服务 禁止商用 + 上传即分享样本，与"数据不出设备"根本冲突。那个方向已经放弃。

转向后的原则只有一条：

默认不信任任何插件与 agent，全部关在沙箱里。 想出来，用户必须读过免责声明并逐个签字放行。

这个转向带来三个好处：

  1. 不需要服务器 —— 检测能力不再依赖云端情报库
  2. 不需要为插件行为负责 —— 责任通过"知情同意"转移给用户（免责声明效力分析见 §5）
  3. 默认安全姿态是"拒绝" —— 不依赖"我们判断得够不够准"

1. 沙箱的四层模型

1.1 分层总览

┌────────────────────────────────────────────────────────────────┐
│  第 0 层：进程隔离（内核级，最硬）                                │
│    L3 原生插件 → 独立 APK 独立 UID，Android 内核强制隔离          │
│    L2 脚本     → 独立进程 + 解释器级沙箱                         │
│    L1 规则包   → 无代码执行，纯数据                             │
├────────────────────────────────────────────────────────────────┤
│  第 1 层：能力代理（PluginHost，架构级）                          │
│    所有插件调用必须经此处；不提供"原始对象"出口                    │
├────────────────────────────────────────────────────────────────┤
│  第 2 层：资源配额（运行时级）                                    │
│    CPU 时间 / 内存 / 调用次数 / 网络字节 / 存储                   │
├────────────────────────────────────────────────────────────────┤
│  第 3 层：数据边界（隐私级，唯一出口）                             │
│    PrivacyFilter 是所有上传路径的唯一出口                        │
└────────────────────────────────────────────────────────────────┘

关键认识：第 0 层是唯一"硬"的。 其余三层都是我们自己代码里的约定 —— 约定被绕过的代价是零。所以设计重心必须放在把能交给内核管的都交给内核。

1.2 三级插件各自的沙箱强度

级别 形态 沙箱机制 强度 能否绕过
L1 规则包 JSON 数据 无代码执行 ⭐⭐⭐⭐⭐ 结构上不可能（没有代码）
L2 JS 脚本 脚本 解释器沙箱 + 独立进程 ⭐⭐⭐⭐ 需解释器漏洞
L3 原生 APK 独立 APK 内核 UID 隔离 ⭐⭐⭐⭐⭐ 需攻破 Linux 内核

L1 的强度最高，因为它没有可执行的东西。 这提示了一个产品策略：能把插件做成规则包的，就不要做成脚本。

1.3 L1 规则包：为什么它天然安全

L1 是纯 JSON —— 选择器 + 动作声明。没有表达式求值、没有脚本、没有变量。 沙箱在这里不是"限制"，而是语言设计本身就不提供出口。

⚠️ 唯一要防的是解析器：JSON 解析必须用流式 + 深度限制，防止 "深度嵌套 JSON 导致栈溢出"。这是解析器的事，不是插件的事。

1.4 L2 脚本：沙箱的三条逃逸路径（必须逐条堵）

JS 沙箱逃逸在历史上几乎都来自这三个方向：

逃逸路径 堵法
原型链污染 → 拿到宿主对象 用 QuickJS 这类无宿主原型共享的引擎；每个插件一个独立 JSRuntime
eval / Function 构造器 直接禁用，不是"限制"
宿主函数泄漏（回调里带出宿主引用） 所有跨边界传参只走 JSON 序列化，不传对象引用

引擎选择：plugin:script 模块原定 QuickJS（见 D13）。

引擎 沙箱强度 体积 备注
QuickJS 高 —— 独立 runtime、可设内存/时间上限、无宿主原型 小 推荐
Rhino（GKD 生态） 中 —— JVM 上跑，原型链逃逸面大 中 兼容性好但更危险

建议维持 QuickJS。 若为复用 GKD 生态选 Rhino，则必须接受沙箱强度下降 —— 这是一次明确的安全-生态权衡，不能含糊过去。

配额实现（QuickJS 原生支持）：

val runtime = QuickJS.createRuntimeWithFlags(...)
runtime.setMemoryLimit(16 * 1024 * 1024)        // 16 MB
runtime.setMaxStackSize(512 * 1024)              // 512 KB
runtime.setInterruptHandler { deadlineExceeded } // 超时中断

⚠️ setInterruptHandler 是唯一的超时手段 —— QuickJS 没有"强制杀线程"能力。 如果中断回调不被调用（死循环在 C 层），整个宿主进程会卡住。 → 必须把脚本执行放在独立进程，这样卡死了能杀进程。这是"独立进程"存在的真正理由， 不是"为了隔离"这么笼统。

1.5 L3 原生插件：唯一真正的沙箱，也是最大的责任

L3 是独立 APK → Android 内核给它独立 UID，默认情况下什么都读不到。 这是四层里唯一"不靠我们自觉"的保护。

但危险也在这里：独立 APK 意味着它有完整 Android 能力。它能： - 自己声明权限（用户装它时看到的是一份新的权限清单） - 自己联网 - 自己申请无障碍

所以 L3 的沙箱不是"我们要不要放它出来"，而是"它自己本来就在外面"。

⚠️ 这是 L3 与 L1/L2 的根本区别：L1/L2 的沙箱由我们实施， L3 的沙箱由 Android 实施 —— 而 Android 的沙箱只保护它不伤害别的应用， 不阻止它做自己的事。

结论：L3 必须默认不提供。 在 plugin:runtime 层，L3 应处于 "用户必须显式开启"高级模式"才能安装"的状态。见 D12（原定 M1-M3 暂不做）。

2. 沙箱的默认策略与放行机制

2.1 默认拒绝清单

插件默认全部被拒绝，逐项申请。这不是"允许清单"，而是默认关闭的能力矩阵：

能力域 默认 说明
screen.read（读屏） ❌ 拒绝 最高敏感度
action.tap（点击） ❌ 拒绝 最高敏感度
storage.read/write ❌ 拒绝 沙箱内私有目录除外
network.* ❌ 拒绝 且必须由用户提供 Key 才能用
payment.* / key.* / crypto.* / system.* ⛔ 永不开放 原则 8，无讨论空间
clipboard.read ❌ 拒绝 —
notification.read ❌ 拒绝 —

⚠️ network.* 有一条特殊规则（见 §4）：即使放行，也需要用户自己填 Key。 我们没有服务器，所以插件也不该有"我们的服务器"可用。

2.2 放行流程（免责声明的落地）

用户在插件页看到某插件申请的能力
  ↓
点击「在沙箱外运行此插件」
  ↓
┌──────────────────────────────────────────────┐
│  ⚠️ 免责声明（必须完整滚到底部才能点同意）        │
│                                                │
│  插件作者：<url/署名>                            │
│  来源源：<订阅源地址>                            │
│  【本插件将获得以下能力】                         │
│    □ 读取你的屏幕内容                            │
│    □ 模拟点击                                    │
│    □ 访问网络（使用你配置的 Key）                 │
│                                                │
│  【重要】                                       │
│  1. 本插件由第三方提供，「代码乌托邦」不对其行为负责 │
│  2. 我们已做静态检查，但检查结果不代表绝对安全       │
│  3. 沙箱运行和放行运行的风险不同：                 │
│     - 沙箱内：功能受限，但风险低                   │

└──────────────────────────────────────────────┘

2.3 放行的三条设计纪律

① 放行必须可撤销，且撤销立即生效。 用户会犯错，出口必须比入口容易走。

② 放行记录必须可见、可审计。 新增「已放行插件」页，列出每个放行项：什么时候放的、放了哪些能力。 这是用户在几个月后回想"我为什么会信任这个插件"的唯一凭据。

③ 永不出现"全部放行"。 没有"信任该作者"这类批量按钮 —— 每个插件、每个能力单独确认。 批量按钮会让免责声明彻底失效（用户不再阅读）。

2.4 沙箱内 vs 沙箱外：功能差异必须诚实呈现

⚠️ 最忌讳的做法：让沙箱内插件"看起来能跑但实际不工作"。

正确做法：能力被拒绝时，插件调用该能力立即抛明确异常， UI 上显示"此功能需要放行"。绝不做静默降级 —— 静默降级会让用户以为插件坏了，去投诉作者，而真正原因是没放行。

这条与 UI 设计系统的第 6 条立场一致：不要把"未生效"伪装成"可用"。

3. 离线优先：没有服务器意味着什么

3.1 三条不可协商的推论

推论 含义
无云端检测 没有"我们的威胁情报库"，也没有实时更新的黑名单
无云端配置同步 用户的配置只在用户设备上，换机要自己导出导入
无云端 Key 托管 Key 只在设备本地加密存储；我们永远不接触任何 Key

这不是妥协，是架构优势：因为没有服务器，也没有可被攻击、可被传票、 可被泄露的集中式数据。用户数据泄露的风险面是零 —— 因为根本不存在那个面。

3.2 威胁情报方案的本地化改造

原来设想"自建哈希库放 GitHub Pages"。但按新约束，需要更彻底：

改造后：哈希库随应用打包 + 社区源可选订阅

威胁情报的三层（全部在本地）
├── L0 内置特征库（随 APK 打包）
│     └── 已知恶意插件的 SHA256 + 已知恶意代码特征
│     └── 更新方式：随应用版本更新（走 GitHub Releases）
├── L1 本地积累库（用户设备上）
│     └── 用户自己遇到的、标记为可疑的插件
│     └── 完全本地，不上传
└── L2 可选社区源（用户主动订阅）
      └── 用户自己添加的静态 JSON 地址
      └── ⚠️ 我们只是"列举"这些源，不为内容背书

⚠️ 关键区别：GitHub Pages 上放哈希库，任何人（包括我们）都能改。 所以不能把"内置库"理解成"可信库" —— 它只是一个起点，不是权威。

并且要写清楚：如果「代码乌托邦」的账号被盗，攻击者可以推一个 "所有插件都安全"的假哈希库。所以客户端必须校验哈希库本身的签名（见 §3.3）。

3.3 哈希库的签名与校验

发布侧（我们）
  hashes.json  →  用离线私钥签名  →  hashes.json.sig
  ⚠️ 私钥离线保管，不进 CI，不进仓库

客户端
  下载 hashes.json + hashes.json.sig
    ↓
  用内置公钥验签
    ↓
  失败 → 拒绝使用该库（不是"警告后继续"）

⚠️ 公钥内置在 APK 里，即使账号被盗也无法伪造签名 —— 攻击者只能 "不更新"，不能"推假库"。这是没有服务器时唯一可信的更新通道。

3.4 所有 Key 的存储（重申并强化）

用户的 TTS Key 与模型 Key 都遵循同一套链路（keymgmt 模块，已有 30 个测试）：

用户输入 Key
  ↓
Keystore（TEE/StrongBox，密钥不出硬件）
  ↓  AES-GCM
SQLCipher 加密库
  ↓
仅在构造 HTTP 请求头的那一行解密（withDecryptedKey 作用域）
  ↓  作用域结束立即 fill(0) 清零
发出请求 —— 直连用户指定的服务商

新增待办：Key 相关页面加 FLAG_SECURE（防截屏）。

4. 语音：只提供填入入口，不接入引擎

按你的要求，我们不自研、不内置语音引擎，只做两件事：

4.1 我们提供的（仅此而已）

提供 不提供
TTS 服务商 Key 的填入入口（独立弹窗） ❌ 任何 TTS 引擎
几个常见服务商的填法说明（极简，可跳过） ❌ 任何语音识别
请求转发（用用户的 Key 直连服务商） ❌ 任何语音唤醒
音色/语速等参数的可选配置 ❌ 任何音频处理

4.2 UI 设计（"尽可能简化配置"的落地）

设置 → 语音
┌────────────────────────────────────────────┐
│  语音合成（可选）                            │
│  ────────────────────────────────────────  │
│  想让 agent 用语音回答？填入你的语音服务 Key。 │
│  不填也能用，只是回答只有文字。               │
│                                            │
│  [ 服务商 ▼ ]  OpenAI / Azure / 火山 / 讯飞… │
│                                            │
│  [ API Key                    ] [👁]        │
│  [ 区域/Endpoint（部分服务商需要）]           │
│                                            │
│  [ 测试一下 ]  ← 填完点这里，会合成一句话     │
│                                            │
│  ⓘ Key 加密存储在本机，不会上传到任何服务器    │
│  ⓘ 我们只负责转发请求，语音由服务商生成        │
└────────────────────────────────────────────┘

三个简化设计：

  1. 默认折叠 —— 不用语音的用户永远看不到这一节
  2. 「测试一下」按钮 —— 填完立即验证，不用等真正用的时候才发现填错
  3. 不填也能用 —— 明确告知"只有文字也能用"，降低心理负担

4.3 独立弹窗的强要求（你特别强调的）

TTS Key 绝不能和模型 Key 放在同一个表单里。 实现上：

  • 两个独立的设置页（SettingsKeyModelScreen / SettingsKeyTtsScreen）
  • 顶部互相标注："这是给语音合成用的，不是对话模型"
  • 各自的独立存储键（数据库里是两个不同的记录，不是同一表的不同字段）

⚠️ 混在一起的风险很实在：用户看到"API Key"就填了 DeepSeek 的 Key， 然后语音一直报错，他以为是软件坏了。

5. 免责声明的效力（必须先说清楚）

免责声明不是万能的。 我不能让方案建立在一个虚假的法律安全感上。

5.1 声明能覆盖什么、不能覆盖什么

能覆盖 不能覆盖
✅ 插件行为造成的损失（用户已知情并放行） ❌ 我们自己的过错（如沙箱漏洞、我们分发的本体内含恶意代码）
✅ 用户配置错误导致的问题 ❌ 故意或重大过失
✅ 第三方服务商的问题（Key 被服务商封禁等） ❌ 违反强制性法规的部分

5.2 所以免责声明必须有"我们做了什么"的对价

法律上，免责声明的效力与"提供方是否尽到合理注意义务"强相关。 如果我们的沙箱形同虚设，声明就是空文。

因此声明里必须包含"我们做了什么"：

我们做了什么：
  1. 插件默认在沙箱内运行，不获得任何敏感能力
  2. 放行需要你逐个能力确认
  3. 我们提供本地静态检查（但不能覆盖所有情况）
  4. 插件的 Key 访问、支付能力在架构上被彻底禁止

我们不能保证什么：
  1. 静态检查无法发现所有恶意行为
  2. 放行后的插件行为由作者负责
  3. 我们无法审查所有订阅源的内容

这段话比"我们不承担任何责任"更有用 —— 它证明了我们尽到了注意义务。

5.3 一条必须写进声明的现实

我们没有服务器，所以也无法远程帮你下架一个恶意插件。 如果你放行了一个恶意插件，卸载它 + 撤销放行是你唯一的手段。 请只放行你愿意承担后果的插件。

诚实比漂亮有用。

6.1 涉及模块

模块 状态 本次改动

6.2 plugin:scan 的隔离硬规则（你明确要求）

规则 实施 守卫
不接触 Key 不依赖 keymgmt 模块 check_module_deps.py 加规则，CI 拦截

无 Android 依赖 纯 Kotlin，可离线单测 加进 run_logic_tests.py 的 MODULES

⚠️ 最后一条特别重要：plugin:scan 做成零 Android 依赖的纯逻辑模块， 就能被离线验证器覆盖。这符合项目"优先做源码零 Android 依赖的模块"的原则 —— "跑得过测试的代码"比"看起来对的代码"值钱得多。

6.3 静态检查该查什么（本地、无网络）

L0 本地静态分析（plugin:scan，零网络）
├── 清单审计
│   ├── 申请了禁止前缀（payment./key./crypto./system.）→ ERROR
│   ├── 申请能力与实际调用不匹配 → WARNING（最有价值的一条）
│   └── 未知能力 id → WARNING
├── 代码特征（L2 脚本）
│   ├── eval / Function 构造器 → ERROR（我们本来就禁）
│   ├── 超长字符串（混淆特征） → WARNING
│   └── 硬编码 URL / IP → WARNING
├── 完整性
│   ├── 包签名校验（PluginIntegrity 已有）
│   └── SHA256 与内置特征库比对 → 命中即 ERROR
└── 输出
    └── 风险等级（复用 Risk.kt 的四档）

最有价值的一条是"能力与调用不匹配"：一个只声明 screen.read 的插件 却在拼接 HTTP 请求 —— 静态就能看出来。这是没有云端情报时最有效的信号。

9. 一句话总结

无服务器不是缺陷，它让架构变得更简单也更诚实：

  • 没有云端检测 → 检测能力做成纯本地静态分析，反而跑得过离线测试
  • 没有云端存储 → 数据泄露风险面为零，因为不存在那个面
  • 没有云端托管 → Key 永远只在用户设备，我们从不接触
  • 没有云端下架能力 → 所以默认全部关进沙箱，出路是用户签字

「代码乌托邦」只做两件事：写代码，和把配置流程做到最简。 剩下的，交给用户和沙箱。
