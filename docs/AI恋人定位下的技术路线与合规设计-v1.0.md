## §0 一页纸结论

| # | 结论 |
|---|---|
| 1 | **本地模型不该做主体，该做兜底**。7B 在手机 SoC 上是 4GB 内存 + 发热 + 个位数 tok/s，而恋爱陪伴是**长时段**使用 —— 那是致命的（§1） |
| 2 | **端侧真正的位置**：① 断网兜底（对情感依赖用户，"突然联系不上"本身就是伤害）② 省钱的小任务（意图识别/摘要/标题）（§1.4） |
| 3 | ★★ **《人工智能拟人化互动服务管理暂行办法》已生效**，含「**严禁向未成年人提供虚拟伴侣**」。**这不是建议，是硬禁令**（§2） |
| 4 | ★ 但那份规章里**多条要求我们天然满足**（数据不出设备 / 可导出可删除 / 不阻碍退出）—— 这是差异化，不是负担（§2.3） |
| 5 | ★★ **「开箱即用」需要"我们提供模型服务"，那需要服务器 + 花钱 + 备案** —— 与三条硬约束同时冲突。**这是本项目最大的未决问题**（§3） |
| 6 | **差异化不该建在"能操作手机"上**（Operit/Aries/Open-AutoGLM 都在做），该建在「**情感记忆的连续性 + 合规可信**」上（§5） |

## §1 本地模型：你的判断对，但可以更细

### 1.1 你的判断是对的（先确认这一点）

> "他们很大概率是没有电脑的，我们如果要这样让 ai 跑在他们的手机上，他们手机会炸的"

**对。** 而且比"炸"更糟的是**体验**：恋爱陪伴是**长时间、连续**的使用场景
（用户可能一晚上聊几百轮）。本地推理在这种场景下是：

| 模型 | 内存 | 预期速度（K60 级 SoC）| 实际体验 |
|---|---|---|---|
| 1.5B Q4 | ~1 GB | 20–30 tok/s | 快，但**说话像傻子** —— 恋爱场景最不能接受的 |
| 3B Q4 | ~2 GB | 10–15 tok/s | 勉强，但长对话里**人格会崩** |
| 7B Q4 | **~4 GB** | **5–10 tok/s** | 一句 30 字的话等 10 秒 + **发热 + 掉电** |

**2026 年的真实数据**（来源见附录）：llama.cpp b4500 在 **M5 Max**（笔记本级芯片）上
7B Q4_K_M 才 **87 tok/s**。手机 SoC 的持续算力与散热**远低于**笔记本 ——
而且手机是**被动散热**，跑十分钟就开始降频。

⇒ **恋爱陪伴要的是"随时都在、随时能聊"，而本地大模型给不了这个。**

### 1.2 「专门训一个小体量非主流架构模型」这条路

你说的这个方向**技术上存在**（线性注意力 / SSM / 混合架构确实能大幅降 KV 缓存与算力），
但把它作为**主线**有三个问题：

1. **成本**：不是"预算超级多"能解决的 —— 是**要持续投入**（训练 + 迭代 + 评测）。
   一次性训完的模型，三个月后就落后了。
2. **质量**：恋爱场景要的是**人格稳定 + 情感细腻 + 长期记忆**。
   这三样恰好是**小模型最弱**的地方（7B 以下的复杂推理都不如 GPT-4o，
   而情感理解比推理更难评测、更难优化）。
3. **与项目定位冲突**：项目明写「不盈利、不设捐款、不建自有后端」。
   自训模型需要**自有算力** —— 那是比"建后端"更重的投入。

⇒ **可以作为远期探索，但不能作为近期路线。**

### 1.3 云端 API 是主路（同意你的判断）

★ 而且**它正好与项目的既有约束同向**：

- **不建自有后端** ⇒ 模型请求直连用户指定的 Provider（合规护身符 + 零推理成本）
- **BYOK** ⇒ 花的是用户自己的钱，**我们不承担推理成本**，也就不需要变现
- **数据不出设备** ⇒ 只有请求本身离开设备

### 1.4 ★ 端侧真正该做的两件事（不是"跑 LLM"）

**① 断网兜底 —— 这条对恋爱场景是刚需，不是锦上添花**

> 对一个把 AI 当恋人的人，**"突然联系不上"本身就是伤害**。

所以端侧该做的是：**一个 1.5–3B 的小模型，在没网时维持对话不断**。
它不需要聪明，只需要：
- 记得住当前会话最近几十轮
- 保持人格口吻（`PersonaAssembler` 的 L0 骨骼 + L2 语气层**恰好够小**，能塞进小模型）
- **明确告知"我现在是本机的小模型，可能答得不好"**（诚实，也是合规要求 —— 见 §2.2）

**② 省钱的小任务**（本项目的 `MemoryLlmPort` 正是为此预留的）

| 任务 | 为什么适合端侧 |
|---|---|
| 意图识别 / 难度判断 | 分类任务，小模型够用 |
| 会话标题生成（§3.3 of 侧边栏设计）| 一句话摘要 |
| L1 原子提取的**预筛**（哪些轮次值得送云端）| 省钱且不牺牲质量 |
| 敏感内容的**本地预判** | 数据不出设备 |

⇒ **这两件事都不需要"跑一个能聊天的 7B"。**

### 2.3 ★ 这份规章里，有几条我们**天然满足** —— 那是差异化，不是负担

| 要求 | 我们为什么天然满足 |
|---|---|
| 数据不出设备（#9）| 项目硬约束「没有服务器，永远不会有」 |
| 可导出、可删除（#8）| 侧边栏设计稿 §3.6 / §4.6（**今天刚写的**）|
| 不阻碍退出（#6）| 急停按钮是正式产品形态 |
| 显著标识（#3）| 「如实显示」是本项目的既有原则 |

⇒ **在一个"靠情感操控留人"是行业默认做法的赛道里，"合规可信"本身就是产品差异点。**
尤其对**成年人**用户：他们被"AI 恋人被下架/消失"伤过（服务停了、模型换了、人格变了），
**一个能导出、能本地保存、人格稳定的产品**是有说服力的。

### 2.4 ⚠️ 必须新增的五件事（按优先级）

1. **年龄识别 + 未成年人硬拦截 + 未成年人模式**（14-1 / 14-2 / 14-3）
   —— **法律红线，没有它不能上线**。⚠️ **不是免责声明，是"有效措施"**
2. **危机干预流程**（13-2）—— 最容易被忽略，但后果最严重
3. **2 小时提醒 + 沉迷倾向识别**（18-2）—— 我们已有 `PersonaStateEngine`，可复用
4. **人格设计要避开"讨好型"**（8-5 / 10-2）—— ★ 这条最容易被当成"产品特性"做反：
   「过度迎合用户、诱导情感依赖」**是明令禁止的**。
   恋爱陪伴产品最容易走的方向恰好就是它。**这是设计约束，不是道德劝告。**
5. **上线前的安全评估 + 算法备案**（22-1 / 26）—— ★ 需要**备案主体**，
   个人开发者能否备案要单独确认（可能是本项目最大的行政障碍）

## §3 「开箱即用」的真正含义（**已修正**）

> ⚠️ **2026-10-14 修正**：本节初版把用户的「一站式、开箱即用」读成了
> **「由我们提供模型服务」** —— **读错了**。
>
> 用户明确：「**我们不提供模型服务啊**……我们当然没有服务器，也不会有服务器。」
>
> ⇒ **不存在"与硬约束冲突"这回事**。真正要解决的是**配置体验**（§3.3 的 B 方案）。
> 下面 §3.1 / §3.2 的"冲突分析"保留，但**它描述的是一个不存在的方案**，
> 只作为"如果将来有人提议 C，要付什么代价"的备查。

### 3.1 冲突在哪（⚠️ 仅针对假想的 C 方案，不是本项目现状）

用户要的「一站式、开箱即用」，在这个品类里意味着：

> **下载 App → 直接开始和恋人聊天**（不需要注册 API、不需要充值、不需要理解"模型"是什么）

而项目现在有三条硬约束：

| 约束 | 与"开箱即用"的关系 |
|---|---|
| **不建自有后端** | ❌ 直接冲突 —— "开箱即用"需要**我们**提供模型服务 |
| **不盈利** | ❌ 冲突 —— 提供服务就有推理成本，而"不设捐款"意味着**我们自己掏钱** |
| **BYOK** | ⚠️ 与"开箱即用"冲突 —— 目标用户**不懂也不愿意**去注册 API Key |

★ **这是本项目目前最大的未决问题，比任何技术债都重要。**
因为它决定**目标用户到底能不能用上**。

### 3.2 三条路，各要付什么代价

| 路线 | 用户侧 | 我们要付 | 与既有约束 |
|---|---|---|---|
| **A. 纯 BYOK**（现状）| 用户自己去厂商注册 → 充值 → 拿 Key → 填进来 | 零 | ✅ 完全符合 |
| **B. 引导式 BYOK**（改良 A）| 首次启动**手把手**带着走，一键校验、一键测通 | 零（只做引导）| ✅ 符合 |
| **C. 我们提供**（真·开箱即用）| 下载即聊 | **服务器 + 推理成本 + 备案 + 安全评估** | ❌ **三条全冲突** |

### 3.3 我的建议：**B 为主，C 留作远期**

**为什么 B 可行**：AI 恋爱用户的痛点不是"不愿意花钱"，是**"不会配"**。
（他们本来就在别的产品上买会员、买卡。）
⇒ **把"配置"从"技术活"变成"照着做三步"**：

```
① 选一个厂商（我们推荐 + 说明各家的价格与特点）
② 打开链接 → 注册 → 复制 Key（有截图指引）
③ 粘回来 → 我们立刻校验并显示"通了 ✅，当前余额 ¥X"
```

★ 关键细节：**第 ③ 步的"校验"必须是真实的一次调用**（项目已有"校验 Key"能力），
而且**要在界面上显示余额**（很多厂商有余额接口）——
让用户**立刻看到"能用"**，而不是回去等第一次聊天才发现配错了。
（这正是上一轮「模型不存在」事故的教训：**用户在配置阶段得不到反馈，就会在聊天阶段被吓到**。）

**为什么 C 现在不能做**：它不只是钱的问题 —— 一旦我们提供模型服务，
我们就成了**生成式AI服务提供者**，§2.2 的全部义务（含**算法备案**）都落到我们头上。
**那是另一个量级的合规负担。**

### 3.4 「随仓模型」（用户提出的方案）—— 评估

> 用户原话：「除非我们的预算超级多，自训练一个**非 transformer 架构的极小体量模型**
> 发布到这个仓库里去，当作一个**随仓模型**」

**技术方向成立**：非 transformer（SSM / Mamba / RWKV 这一类）在推理时是 **O(n) 复杂度、
每 token 内存恒定**，端侧确实比 transformer 友好得多（§1.1 那张表的困境正来自 KV 缓存）。

**但有三件事要先想清楚**：

| # | 问题 | 说明 |
|---|---|---|
| 1 | **不必自训** | 已有开源的小体量非 transformer 模型可直接打包（RWKV 系列等）。**自训的性价比要单独论证** —— 见 §1.2 的三条理由 |
| 2 | **权重不该进 git** | GitHub 单文件 100 MB 上限、仓库建议 < 1 GB。走 **Releases** 或独立仓库分发 |
| 3 | ★ **权重的许可独立于代码的 GPL-3** | 打包别人训的模型要遵守**那个模型自己的许可**。"放进 GPL 仓库"**不会**让它的许可变成 GPL，也**不会**让它自动合规 |

★ **最关键的一点**（见 §2.5）：**自带模型不改变合规义务。**
你是"服务提供者"是因为**你的 App 向公众提供了拟人化互动服务**，
与你**是否提供推理**无关。⇒ **随仓模型不是一条合规捷径。**

### 3.5 ⚠️ 一条必须纠正的假设：「说明一下不允许未成年使用」不够

> 用户原话：「模型的使用用途不归我们管，我们最多就只会在这里面说明，
> 这是一个语言大模型……不允许未成年用其进行使用」

**这个思路不成立**，原因是法条原文（§2.2 已列，这里给准确的条号）：

| 条 | 原文要点 |
|---|---|
| **第十二条** | 服务提供者应当与用户签订服务协议，**要求用户……提供用户年龄**、监护人或者紧急联系人等必要信息 |
| **第十四条 第三款** | 服务提供者应当……**采取有效措施识别未成年人用户身份**；识别为未成年人用户的，应当将相关服务切换至未成年人模式或者按照国家有关规定采取其他措施，**并提供相应申诉渠道** |
| **第三十条** | 违反的：警告、通报批评、责令限期改正；拒不改正或情节严重的，**责令停止提供相关服务**，并处**1–10 万元罚款**；涉及危害公民生命健康安全且有危害后果的，并处 **10–20 万元罚款** |

⇒ **「采取有效措施识别未成年人身份」是明确的技术义务**，
   而**一句免责声明不是"有效措施"**。
   「使用用途不归我们管」在法律上也站不住 —— 义务落在**提供者**身上，
   **声明**不能把义务转移给用户。

⚠️ 而且要注意 §2 第二条的**适用范围**恰好命中我们：

> 「利用人工智能技术，向中华人民共和国境内公众提供**模拟自然人人格特征、
> 思维模式和沟通风格的持续性的情感互动服务**，适用本办法。」
>
> 「提供智能客服、知识问答、**工作助手**、学习教育、科学研究等服务，
> **不涉及持续性的情感互动的，不适用本办法**。」

★ **值得注意的取舍**：只做"办公助手"**不适用**本办法；
**加上"恋人"定位，就把本办法的全部义务引进来了**。
这不是"别做恋人"的理由 —— 而是**知道代价、并在设计里内置合规**（§2.3 已论证那是差异化）。

## §4 借鉴同行的技术设计（具体到"抄哪一条"）

| 来源 | 借鉴什么 | 我们的落点 |
|---|---|---|
| **Operit** | 按用途分配模型（chat/memory/summarization/UI control）| ✅ **今天已落地**（`ModelRole.CHAT` + 三级回落）|
| **Operit** | 每工具三态权限（允许/每次询问/拒绝）| ⏳ 被**确认通道**阻塞（见调研报告 §7）|
| **Operit** | 消息分支 / 导出备份 / 会话管理 | ✅ 已进设计稿（§3.5 / §3.6）|
| **Operit** | 本地模型（MNN / llama.cpp / Ollama）| ⏳ 按 §1.4 的定位做（兜底 + 小任务，不做主体）|
| **陪伴类产品**（星野/猫箱/Talkie 等）| **角色卡**（人设 + 开场白 + 语音）| ⚠️ 我们有 `PersonaField` + 语音设计，但**没有"角色卡"这个产品形态** |
| **陪伴类产品** | **长期记忆的可见化**（"TA 记得你说过…"）| ✅ 我们的 L1/L2/L3 + 侧边栏可审计面，**设计上更强** |
| **陪伴类产品** | 语音（这是陪伴类的**核心体验**，不是附加）| ⏳ 设计完未实现 —— ★ **优先级应上调** |

### 4.1 ★ 一条被我们低估的事：**语音**

对"把手机当恋人躯壳"的用户，**打字聊天和语音聊天是两种产品**。
项目的语音设计（级联 ASR→LLM→TTS + 检测到 Realtime 时升级）**已经设计好了但没实现**。

⇒ 在 AI 恋人定位下，**语音应该从 P4 提到 P1**。

## §5 差异化该建在哪

### 5.1 ❌ 不该建在"能操作手机"上

用户说："如果 ai 助理恋人不能操作手机、帮你办公，我们的竞争也就缺少了这个方面的市场。"

**前半句对，后半句要改。** "能操作手机"**已经不是差异点了**：

| 项目 | 能操作手机 | 状态 |
|---|---|---|
| Operit | ✅ 无障碍 + Shizuku + **Root** | 8,658★ |
| Aries-AI | ✅ **独创虚拟屏** | 活跃 |
| Open-AutoGLM（智谱）| ✅ | 24h 1.7k★ |
| rikkahub-agent-pure | ✅ | 活跃 |
| phone-pilot | ✅ MCP 路线 | 活跃 |

⇒ **它是"入场券"，不是"护城河"。** 不做，用户会觉得缺一块；
做了，也只是追平。**资源该按"入场券"配，不该按"护城河"配。**

### 5.2 ✅ 该建在「情感记忆的连续性 + 合规可信」

这两条恰好是**既有资产**能支撑、而**同行没做好的**：

| 差异化 | 我们的既有资产 | 同行现状 |
|---|---|---|
| **记忆的连续性**（"TA 真的记得我"）| L0–L3 分层 + 每条原子**可溯源到源对话** + 用户**可否决** | 陪伴类产品的记忆普遍是**黑盒**，用户看不到也删不掉 |
| **人格的稳定性**（"TA 还是 TA"）| `SafetyBones` 骨骼永不可微调 + `PersonaField` 白名单 + **变更账本** | 陪伴类产品换模型/更新后**人格漂移**是用户最大抱怨之一 |
| **合规可信**（"不会突然消失/被下架"）| 数据不出设备 + 可导出 + 可删除 + 开源 | 闭源产品停服即"失恋" |
| **可审计**（"我知道它记住了什么"）| 侧边栏 = 记忆的可见面（设计稿 §5）| 几乎没有 |

★ 一句话：**同行在比"谁更像人"，我们该比"谁更值得托付"。**
前者是技术军备竞赛（我们打不起），后者是设计选择（我们能赢）。

### 5.3 「能操作手机」在恋人场景下的**正确用法**

不是"帮你办公"，而是**"替你分担"**：

| 场景 | 为什么是恋人场景的刚需 |
|---|---|
| 提醒 / 日程 / 叫醒 | "TA 记得你明天要早起" |
| 点外卖、叫车 | "TA 帮你把饭点了" |
| **代读通知并摘要**（你不在时）| "TA 帮你看着手机" |
| 查东西（天气/路线/价格）| 日常关心 |

⚠️ **但这条线的隐私门槛比"办公助理"高得多**：
用户会允许一个**工具**读通知，但会警惕一个**"恋人"**读他的全部隐私。
⇒ 必须**逐项授权 + 每次可见 + 随时收回**（这正是 §4.1 那个"每工具三态权限"该解决的，
而它现在被"确认通道"阻塞）。

## §6 对既有定位报告的修订

《同类项目对比与借鉴 v1.0》的结论需要**部分修订**：

| 那份报告的结论 | 在 AI 恋人定位下 |
|---|---|
| 定位收紧成「可读、可测、可信的助理」 | ⚠️ **"可信"保留，"可读可测"降级** —— 目标用户**不读代码**，那是给贡献者的卖点，不是给用户的 |
| 不碰终端 / 工作区 / 3D 形象 / 市场 | ✅ **仍然成立**（恋人用户不需要 Ubuntu 终端）|
| 本地模型进路线图 | ⚠️ **修正**：进路线图，但定位是**兜底 + 小任务**（§1.4），不是"跑一个能聊天的模型" |
| 离线验证器开源出去 | ✅ 仍然成立，但它现在是**给贡献者的**，与目标用户无关 |
| 「不追功能数量」 | ✅ **仍然成立**，但要改成"追**情感体验的深度**，不追功能广度" |

★ **新增的最高优先级项**：**合规四件**（§2.4）+ **语音**（§4.1）+ **开箱即用的配置引导**（§3.3）。
